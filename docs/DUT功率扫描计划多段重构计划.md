# DUT 功率扫描计划多段重构计划

## 1. 文档目的

当前配置只支持一组 DUT 输入功率扫描参数：起始功率、结束功率和统一步长。
实际测试中，低功率区增益变化较小，可以使用较大步长；接近增益压缩区时需要使用较小步长。因此本次重构将单组扫描参数扩展为多个按顺序执行的功率扫描计划。

本计划基于现有代码调研结果编写，补充并细化 `docs/功放输入功率流程重构计划.md` 中关于 DUT 输入功率扫描的内容。

### 目标

- 用户可以在配置页添加、编辑和删除多个 DUT 功率扫描计划。
- 每个计划包含起始功率、步长和终止功率。
- 每个计划下显示实际生成的 DUT 输入功率点。
- 多个计划必须连续衔接，不能有空档或重叠。
- 驱动映射、无驱动测试和驱动模式正式测试使用同一套目标功率点。
- 旧的单计划配置可以安全读取，并在保存时转换为新格式。

### 不在本次范围内

- 不改变频率扫描规则。
- 不实现根据实时增益自动调整步长的自适应扫描。
- 不改变测试结果文件中 `sg_power`、`input_power_dut` 等字段的含义。
- 不运行真实硬件测试，除非另行获得硬件冒烟授权。

## 2. 调研结论与总体技术决定

### 2.1 当前实现位置

当前单计划逻辑分布在以下位置：

- Qt 配置页：`presentation/qt/test_configuration_page.py`
- 控件读写与回填：`presentation/qt/config_form_state.py`、`config_projection.py`、`config_form_adapter.py`
- 配置草稿与类型化快照：`application/configuration_draft.py`、`configuration_view_model.py`
- 正式配置编写：`application/configuration_authoring.py`
- 配置模型与校验：`domain/configuration/models.py`、`domain/configuration/rules.py`
- 正式运行输入：`application/dto/amplifier_inputs.py`
- 驱动映射和主功放测试：`application/measurements/services.py`、`application/measurements/driver_mapping.py`

目前 `PowerSweep` 表示一组扫描参数，`target_input_power_grid()` 负责生成目标 DUT 输入功率点。重构应扩展这条已有链路，而不是在 UI、驱动映射和主功放服务中分别实现点位算法。

### 2.2 新配置形状

新编辑文档和 1.2 正式 `test_plan` 统一使用以下形状：

```json
{
  "signal_source": {
    "power_scan_plans": [
      {"start_power": -38.0, "step": 1.0, "stop_power": -10.0},
      {"start_power": -10.0, "step": 0.25, "stop_power": -2.0}
    ],
    "unit": "dBm",
    "power_reference": "dut_input"
  }
}
```

`PowerSweep` 继续表示单个计划；多个计划由有序集合表示。列表顺序就是执行顺序，不自动排序。

### 2.3 功率点规则

1. 每段生成 `start + n × step`，不超过该段 `stop`。
2. `stop` 不在步长网格上时，仍补入 `stop` 作为该段最后一点。
3. 相邻计划必须满足：后一段起点等于前一段终点，使用现有浮点容差判断。
4. 大于前一段终点表示空档；小于前一段终点表示重叠；两者均不能通过校验。
5. 相邻计划的公共边界在总点列中只保留一次。
6. DUT 最大输入功率仍是最终硬上限；有效上限取最后计划终点和 DUT 最大输入功率的较小值。
7. 如果 DUT 上限不在步长网格上，补入 DUT 上限；如果首个目标点高于上限，配置无效。

### 2.4 版本与兼容策略

当前正式配置版本为 1.1，旧版本列表包含 1.0 和 1.1。由于扫描字段形状发生变化，正式写出版本升级到 1.2。

- 1.0：继续只能通过现有迁移器升级。
- 1.1 单计划配置：读取时转换成一个计划行；保存时写为 1.2 列表格式。
- 缺少 `power_reference` 的旧配置：只能提示用户确认，不能根据历史数值猜测其功率语义。
- 新版本不同时写旧的 `start_power`、`stop_power`、`step` 标量字段，避免出现两个来源。

## 3. 分阶段实施计划

每一步只处理一个局部契约，完成后先运行该步骤对应的测试，再进入下一步。

## 阶段一：冻结扫描规则并建立纯计算能力

### 步骤 1.1：定义单段与多段扫描对象

**执行策略**

- 保留现有 `PowerSweep`，继续表示一行扫描计划。
- 在 `application/dto/amplifier_inputs.py` 增加有序计划集合或等价的不可变值对象。
- 集合只保存计划，不直接连接 Qt、配置文件或仪器。
- 明确空集合、非有限数值、非正步长和起点大于终点的错误。

**技术决定**

- 计划使用不可变对象，避免测量过程中被 UI 状态改变。
- 计划顺序使用 tuple 保存，不使用 set 或按起点自动排序。
- 单段起止相等允许作为单点扫描。
- 多段至少需要一段有效计划。
- 非法输入按层归属，不把不同原因混成一种异常：非有限数值由 `PowerDbm` / `Decibels` 构造期以 `MeasurementValueError` 拒绝；非正步长与起点大于终点由 `PowerSweep` 以 `AmplifierInputError` 拒绝；空集合、非 `list`/`tuple` 容器与非法元素由计划集合以 `AmplifierInputError` 拒绝，元素错误带下标。
- 计划集合构造期不生成点位、不校验相邻段连续性；这两件事分别由步骤 1.2、1.3 的纯计算入口负责。

**完成标准**

- 可以从多个 `PowerSweep` 构造正式计划集合。
- 非法值在构造时给出明确异常。
- 不涉及配置读写和 Qt 代码。

### 步骤 1.2：实现分段点位生成

**执行策略**

- 把现有 `PowerSweep.points()` 和 `target_input_power_grid()` 中的端点容差逻辑整理成共享实现。
- 增加分段列表到最终目标点列表的纯计算入口。
- 生成每段预览点和合并后的总点列。

**技术决定**

- 每段终止点始终可见；非整步终止点作为额外最后点加入。
- 相邻计划公共边界只保留一次。
- 最终点列必须按升序排列且不能重复。
- DUT 最大输入限制在统一入口处理，不能由不同调用方自行截断。

**完成标准**

- 支持整步、非整步、不同步长、共享端点和 DUT 上限补点。
- 预览算法和测量算法调用同一入口。

### 步骤 1.3：实现连续性校验

**执行策略**

- 在纯计算层增加相邻计划连续性检查。
- 为每个问题保留计划索引，生成可映射到配置路径的错误信息。
- 分别覆盖空档、重叠和浮点容差内相等三种情况。

**技术决定**

- 计划顺序以用户填写顺序为准，不自动排序修复。
- 只允许相邻计划共享一个边界点；不允许其他形式的重叠。
- 错误信息明确指出“第 N 段终止功率”和“第 N+1 段起始功率”。

**完成标准**

- 连续计划通过。
- 有空档或重叠的计划不通过。
- 浮点计算造成的极小误差不会误报。

### 步骤 1.4：补充纯计算测试

**执行策略**

- 扩展 `tests/test_target_input_power_grid.py`，必要时新增 `tests/test_power_scan_schedule.py`。
- 先覆盖值对象和点位函数，再接入其他层。

**技术决定**

- 测试固定验证点列值、顺序、唯一性和上限，不只验证“不抛异常”。
- 测试浮点容差的边界和真正超出容差的情况。

**完成标准**

- 纯计算测试在不启动 Qt、不连接仪器的情况下全部通过。

## 阶段二：扩展配置模型与版本兼容

### 步骤 2.1：升级配置版本常量与版本门禁

**执行策略**

- 在 `domain/configuration/models.py` 将当前写入版本提升到 1.2。
- 更新可读取版本、当前版本校验、运行创建门禁和错误文案。
- 检查 `application/configuration_authoring.py` 的保存版本门禁。

**技术决定**

- 1.2 只写新列表结构。
- 1.0 迁移行为保持不变。
- 1.1 只能通过明确的读取、确认和重新编写进入 1.2，不隐式修改文件。

**完成标准**

- 版本检查不会把 1.2 误判为未知版本。
- 旧版读取、当前版保存和旧版运行门禁符合既有策略。

### 步骤 2.2：扩展 `TestPlan` 与配置值对象

**执行策略**

- 在 `domain/configuration/models.py` 增加多段计划字段及其 `from_dict()`、`to_dict()` 处理。
- 如为降低迁移风险保留 `start_power` 等兼容属性，只允许它们作为单段读取兼容，不允许正式运行继续依赖。
- 新增计划条目的基础类型和序列化规则。

**技术决定**

- 正式 TestPlan 以多段计划为唯一来源。
- 多段列表顺序必须在序列化和反序列化中保持不变。
- 新字段与旧标量同时存在且冲突时失败，而不是选择一个继续运行。

**完成标准**

- 1.2 多段配置可以完整 round-trip。
- 1.1 单段配置可以读取为一个计划。
- 非法列表元素能定位到具体索引。

### 步骤 2.3：扩展 `ConfigurationDraft` 读取与写出

**执行策略**

- 将 `ConfigurationDraft.sweep` 扩展为多段计划集合。
- 更新 `from_document()`、`to_document()`、`_read_sweep()` 和 `_sweep_document()`。
- 旧标量字段只在读取边界包装为单元素列表。

**技术决定**

- 草稿层负责结构转换和类型收敛，不复制连续性业务规则。
- 保存时始终写 `power_scan_plans`，并继续写 `power_reference`。
- 缺失计划保持“缺失”状态，不能自动伪造一组有效计划掩盖配置问题。

**完成标准**

- 草稿可以表示多段计划。
- 旧配置读取后保存为新列表。
- 结构错误能够通过现有 `ValidationIssue` 返回。

### 步骤 2.4：接入正式配置校验与 authoring

**执行策略**

- 更新 `domain/configuration/rules.py` 的编辑文档校验。
- 更新 `domain/configuration/models.py` 的 TestPlan 校验。
- 更新 `application/configuration_authoring.py` 的正式 `test_plan` 编写。
- 为驱动映射阶段和完整主功放阶段分别确认最小必需校验。

**技术决定**

- 页面校验和运行前校验使用同一连续性规则。
- 错误路径采用 `signal_source.power_scan_plans[N]...` 形式。
- 线损测量不应因为未配置完整功率计划而被无关阻塞；驱动映射和主功放运行必须阻止非法计划进入硬件。

**完成标准**

- 正式 TestPlan 保存后包含 1.2 多段计划。
- 断档、重叠、非法步长和越限在硬件动作前被拒绝。

## 阶段三：实现配置页动态计划编辑器

### 步骤 3.1：抽取单行计划控件

**执行策略**

- 新增小型 Qt 组件，例如 `presentation/qt/power_sweep_plan_row.py`。
- 组件只负责一行的三个输入框、删除按钮、计划编号和灰色预览标签。
- 不在组件内实现配置文件解析、运行逻辑或 DUT 上限业务。

**技术决定**

- 起始、步长、终止的显示顺序与用户需求一致。
- 功率输入范围沿用现有控件范围。
- 删除操作交给父编辑器决定，至少保留一行。

**完成标准**

- 单行组件可以独立创建、读取和销毁。
- 控件替身可以在无 QApplication 业务依赖的测试中使用。

### 步骤 3.2：实现动态计划列表

**执行策略**

- 在测试参数组中增加“DUT功率扫描计划”标题和带框加号按钮。
- 父编辑器维护行对象列表，处理新增、删除、编号刷新和布局更新。
- 新增行默认起点取上一行终点，步长沿用上一行步长，终点先等于起点，避免凭空生成业务范围。

**技术决定**

- 用户列表顺序就是执行顺序。
- 新建空配置默认创建一行；旧单计划配置回填为一行。
- 每行提供删除按钮，防止误点加号后无法撤销。

**完成标准**

- 可以连续添加多个计划。
- 删除中间行后编号、布局和状态正确。
- `apply_config({})` 会清除旧行并恢复默认一行。

### 步骤 3.3：接入点位预览和实时错误显示

**执行策略**

- 每行输入变化时调用共享点位生成器，更新灰色点位文本。
- 输入暂时非法时不保留旧预览，显示“待完善”或具体错误。
- 对点数很多的计划显示首尾点、总点数，并提供完整文本 tooltip，避免撑大页面。

**技术决定**

- 预览显示的是实际会进入目标序列的点，而不是简单的字符串拼接结果。
- 多行连续性问题显示在相邻行附近，同时汇总到现有 `validation_failed` 通道。
- UI 不自动修改用户输入来修复空档或重叠。

**完成标准**

- 修改起始、步长、终止后预览立即更新。
- 空档和重叠能指出具体行号和值。
- 计划无效时保存按钮和创建运行入口被阻止。

### 步骤 3.4：接入表单状态、投影和 dirty 管理

**执行策略**

- 更新 `config_form_state.py` 读取计划列表。
- 更新 `config_projection.py` 回填、重置和默认值。
- 更新 `config_form_adapter.py` 与 `configuration_view_model.py` 的测试参数快照。
- 确保页面控件读数和类型化快照来自同一次读取。

**技术决定**

- 动态行对象由页面持有，但计划语义由 adapter/draft 统一解释。
- 不在 Qt 层新增第二套连续性算法。
- 保存、回填、取消和 dirty 比较均以计划列表为整体，保留顺序。

**完成标准**

- 多段配置保存后重新打开，行数、顺序、数值和预览一致。
- 配置 A 回填后再回填空配置，不残留 A 的计划行。

## 阶段四：接入正式运行和测量链路

### 步骤 4.1：扩展正式测量输入 DTO

**执行策略**

- 更新 `application/dto/amplifier_inputs.py` 的 `AmplifierMeasurementInputs`，从单一 `input_power_sweep` 迁移到多段计划集合。
- 更新 `from_run_configuration()`，从 1.2 `TestPlan` 读取计划并构造值对象。
- 在 DTO 构造期生成或验证最终目标点，确保硬件动作前失败。

**技术决定**

- 正式测量服务不读取原始配置字典字段。
- 旧配置只有完成 1.2 编写后才能进入新的正式运行输入。
- 目标点顺序和配置列表顺序保持一致。

**完成标准**

- 多段正式输入可以构造。
- 缺失计划、断档、重叠、越限均在连接仪器前失败。

### 步骤 4.2：更新驱动映射目标网格

**执行策略**

- 更新 `DriverPowerMappingService._target_powers()` 和 `driver_mapping._service_config()`，传递多段计划。
- 每个频率使用相同目标点序列。
- 保留现有每个目标点独立命中、原始点保存和目标表插值逻辑。

**技术决定**

- 驱动映射的目标表主键仍是目标 DUT 输入功率。
- 不把计划编号写成目标功率键，也不改变现有映射结果 schema。
- 目标表必须覆盖共享点位生成器产生的全部目标点。

**完成标准**

- 驱动映射测量点顺序与配置页预览一致。
- 多段计划的粗段和细段都出现在目标映射中。

### 步骤 4.3：修正无驱动模式的 DUT 输入反算

**执行策略**

- 更新主功放 `perform_power_sweep()` 的无驱动分支。
- 循环输入使用目标 DUT 输入功率；根据信号路径线损反算信号源设定功率。
- 在 RF 输出开启前预检查整组目标点对应的信号源功率范围。

**技术决定**

- 无驱动模式采用 `signal_source_power = target_dut_input_power + cable1_loss` 的现有反算语义。
- `input_power_dut` 记录目标 DUT 输入功率，`sg_power` 记录实际信号源设定功率。
- 不允许在每个点执行到一半才发现源功率越界。

**完成标准**

- 无驱动测试实际使用的 DUT 输入目标点与预览一致。
- 线损不同的频点能得到各自正确的信号源设定。
- 源功率越界时没有 RF 输出或测量动作。

### 步骤 4.4：校验驱动模式目标点一致性

**执行策略**

- 主功放驱动模式从当前运行目录的 `target_points` 读取源功率和驱放输出功率。
- 将映射目标点与配置生成的目标 DUT 点做数量、顺序、频率和功率唯一性校验。
- 保留现有达到压缩目标后提前停止的行为。

**技术决定**

- 驱动映射不能缺点、重复点或使用旧的单计划目标表。
- 主功放正式测量不重新测量驱放，只消费已完成映射。
- 压缩点后的继续扫描策略本次不改变，后续如需完整扫到终止点另立需求。

**完成标准**

- 驱动模式不会因目标表不完整而进入硬件动作。
- `sg_power` 和 `input_power_dut` 的结果语义保持不变。

## 阶段五：测试、样例和文档收口

### 步骤 5.1：补充配置与模型测试

## 4. 推荐实施顺序与阶段门

1. 先完成阶段一，锁定点位和连续性规则；否则 UI、配置和测量会产生不同解释。
2. 再完成阶段二，确保新配置可以被读取、保存和冻结。
3. 阶段三只做面板和表单状态，不在页面中提前接入仪器逻辑。
4. 阶段四在配置契约稳定后接入驱动映射和正式测量。
5. 阶段五集中补回归测试、fixture 和说明。
6. 阶段六通过后再考虑真实设备冒烟。

每个阶段完成后应满足：上一阶段的测试通过、没有引入未定义的兼容行为、下一阶段可以直接消费上一阶段的稳定接口。每个步骤只修改一个局部职责，避免同时修改 UI、配置格式和硬件流程导致问题难以定位。

## 5. 主要风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| UI 预览与实际测量点不一致 | 统一使用共享目标点生成器，禁止在 Qt 和服务中各写一套算法 |
| 旧 1.1 配置无法打开或被错误换算 | 旧标量只包装为一行，不猜测功率含义；保存时显式升级到 1.2 |
| 计划边界浮点误差导致误报 | 复用统一相对容差，并测试容差内外两种情况 |
| 驱动映射仍使用旧单计划 | 在映射服务构造期验证目标点集合，并增加端到端目标序列测试 |
| 无驱动模式把 DUT 目标直接写给信号源 | 先生成目标 DUT 点，再统一执行线损反算和源功率范围预检 |
| 动态 Qt 控件残留造成测试变慢或不稳定 | 明确行销毁流程，并在 UI 测试中销毁顶层控件 |
| 改动覆盖用户当前配置 | 实施前后检查 `git status`，不覆盖现有未提交的 `config.json` 修改 |
