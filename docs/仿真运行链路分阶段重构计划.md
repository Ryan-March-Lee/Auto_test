# 仿真运行链路分阶段重构计划

> 状态：方案待实施（步骤 1～25）。
>
> 目标：把现有“Mock UI 回放”替换为“端口级仿真运行”，只替换仪器读数来源；
> 连接、通信、驱动、VISA 不模拟，端口之上的用例、服务、计算、事件、落盘、归档、
> 页面全部是正式代码。
>
> 维护约定：每完成一步，在本步骤下追加“实施记录”，并更新步骤状态；未记录实施
> 前，本文件是计划而不是实现说明。

## 1. 目标与不变量

### 1.1 目标

1. 只保留一条测量运行链路：正式链路。仿真运行不新增第二套 worker、第二套事件
   协议或第二套结果展示。
2. 仿真运行与正式运行的唯一差异是：`MeasurementInstrumentPort` 的读数由
   `readings.json` 提供，而不是由 VISA/驱动/仪器提供。
3. 现有 `mock_data` 数据包保留：`scenario.json` 继续作为数据来源，现有正式结果
   保留为“期望输出”，但运行时不再直接展示它们；结果由真实服务重新计算。
4. 旧 UI 回放（`MockReplayWorker`、`SimulationSession`、`simulation_completed`
   等）在方案最后删除，避免两套“模拟”概念并存。

### 1.2 不变量

- 不修改 `domain` 与 `application/measurements` 的测量算法、事件形状、结果契约。
- 不修改三个测量页面的正式交互与结果渲染；只删除旧回放分支。
- 不打开 VISA，不构造驱动/传输层对象，不执行 SCPI。
- 仿真运行必须创建真实 `PreparedRun`，走真实运行快照、阶段记录、manifest、
  归档与部分结果保存。
- 仿真运行不能在任何入口被当成真机运行重新连接。

### 1.3 非目标

- 不验证真实仪器、驱动、SCPI 命令或 VISA 连接；这些属于“其他系统”。
- 不新增历史运行/可视化页面对仿真结果的专门入口。
- 不改变 Mock 配置的命名规则、只读规则或数据包内容格式。
- 不修复现有页面呈现问题；本计划只改变数据来源与运行链路。

## 2. 调研基线

### 2.1 现有 Mock 链路

当前 GUI 的 Mock 链路是 **UI 事件回放**，不是测量链路：

```text
页面 → MeasurementStartFacade → MeasurementController
     → MockReplayWorker（读 scenario.json）
     → 直接 emit message / progress / data_update / result / simulation_completed
     → 同一页面
```

证据：

- `presentation/qt/mock_replay_worker.py` 文档头明确“不调用
  `create_*_measurement`、不创建正式运行、不打开 VISA、不写正式结果目录”。
- `presentation/qt/measurement_worker_factories.py::build_simulation_worker_factories`
  只按阶段创建 `MockReplayWorker`。
- `presentation/qt/measurement_controller.py` 按 `MeasurementExecutionMode.SIMULATION`
  切换工厂表，且模拟命令不调用端口 `begin_stage()`。

### 2.2 正式链路

```text
页面 → MeasurementStartFacade → MeasurementController
     → CableLossWorker / DriverMappingWorker / AmplifierWorker
     → app.gui_runtime.create_*_measurement
       （运行快照校验、校准输入预检、连接仪器、结果/阶段/归档仓库装配）
     → 用例 application/measurements/*
     → 服务 application/measurements/services.py（仪器动作 + 计算 + 事件）
     → test_results/<stage>/ 正式结果 + 运行 manifest + 自动归档
```

### 2.3 共用与差异

| 环节 | 现有 Mock 链路 | 正式链路 | 结论 |
| --- | --- | --- | --- |
| 页面按钮 / 忙碌检查 | 同一 Facade | 同一 Facade | 共用 |
| 运行契约 / 接线确认 | 跳过 | 校验 `PreparedRun` + 接线弹窗 | 不共用 |
| 测量 Worker | `MockReplayWorker` 读 JSON | 正式 Worker 装配用例 | 不共用 |
| 状态机 / 信号契约 | `MeasurementController` | `MeasurementController` | 共用 |
| 实时数据 → 页面 | `data_update` → `update_realtime` | 同左 | 共用 |
| 进度 / 日志 / 停止 / 路径2确认 | 场景值 + 0.5 秒/点 | 服务计算 + 3 秒/点级延时 | 部分共用 |
| 测量计算 | 预置正式结果 | 服务现场计算 | 不共用 |
| 校准输入 | 自动绑定、不校验摘要/目标网格 | 显式加载 + 摘要 + 目标网格 | 不共用 |
| 结果落盘 / manifest | 不写 | `test_results/<stage>/` | 不共用 |
| 归档 / CSV / 报告 | 仅模拟完成提示 | 归档服务生成 | 不共用 |
| 停止 / 部分结果 / 清理 | 只停回放 | 部分结果 + 安全清理 | 不共用 |
| 历史 / 可视化 / 导出 | 没有数据 | 读 `test_results` | 不共用 |

### 2.4 已核对的证据

1. 三套场景 `data.payload` 的键集合与真实服务发出的 `RealtimeDataEvent.data`
   完全一致（线损、驱动映射、主功放）。
2. 现有正式结果与用 `domain.measurement.calculations` 从回放数据重算的结果一致：
   线损 `cable1..4/total_path1,total_path2` 在 `1e-6 dB` 内一致；主功放的
   `compression_point`、`small_signal_gain`、`compression_achieved` 逐字段一致；
   驱动映射 `raw_points` 与最后回放事件逐点一致。
3. 主功放真实进度按每频点 31 点重置（`services.py` 的 `(index+1)/len(scan_points)`），
   而 Mock 场景契约禁止进度倒退，因此模拟进度是全局单调 0→100；这正是“模拟通过
   不代表真实一致”的典型例子。
4. 当前 `create_measurement_port(mode="simulation")` 不能直接使用：频谱仪默认恒定
   `-30 dBm`，电源电流默认 `0 A`（效率会全是 0%），且没有接入 GUI；`prepare_configuration`
   还会拒绝模拟绑定。它只是单元测试用的管道替身。

### 2.5 结论

现有 Mock 链路是 **UI 演示/验收工具**，只能证明“给定这组事件，页面渲染正常”；
它不执行“拿到仪器数据之后的程序”。要缩小差异，替换点必须下沉到
`MeasurementInstrumentPort` 的读数层，而不是事件层。

附注：调研中发现一个与本次重构无关的共享呈现行为——驱动映射完成时页面会把结果
`raw_points` 追加到实时曲线（同频点 2 点会变 4 点，并丢掉 `gain` 序列）。它在模拟
和正式链路完全一致，因为都是同一个 `show_result`。本计划不修复它，另行评估。

## 3. 已确认的技术决定

1. **替换边界**：只替换 `MeasurementInstrumentPort` 的读数方法
   （`measure_power_with_average`、`read_voltage`、`read_current`）；控制方法
   （`set_*`、`rf_output_on/off`、`setup_*`、`power_on/off_*`）由回放端口记录，
   不产生真实设备动作。
2. **不替换事件层**：不再用 `data_update` 直接回放界面数据；所有事件由真实服务产生。
3. **保留现有数据**：`mock_data/*/scenario.json` 和正式结果保留；新增由工具生成的
   `mock_data/*/readings.json`（原始读数）。正式结果只作为期望输出/对照。
4. **生成而非手写**：`readings.json` 由 `tools/build_simulation_readings.py` 从场景
   和现有正式结果反算生成，带 `--check`；换算必须正向调用真实补偿函数做往返断言。
5. **仿真运行 = 正式运行 + 注入端口**：创建真实 `PreparedRun`，worker、用例、服务、
   阶段记录、归档全部使用正式实现；不新增 worker 类型。
6. **数据根目录**：`temp/simulation_runs/`，内含 `configs/`、`runs/`、
   `test_results/`；真实 `runs/` 与 `test_results/` 不受影响，历史/可视化不会被污染。
7. **运行标记与守卫**：仿真运行目录写入 `inputs/simulation.json` 标记；
   `connect_instruments()` / `_hardware_config_path()` 见到标记直接拒绝，防止被当成
   真机运行恢复。
8. **入口与配置**：仍由显示名为 `Mock` 的快照触发；配置页保持只读；“连接仪器”进入
   仿真运行，而不是旧模拟会话。
9. **接线确认**：默认保留正式接线确认对话框；它是正式流程的一部分，页面不新增分支。
   如果后续觉得多余，在窗口层做仿真运行自动接受，不改页面。
10. **时序**：默认真实时序（线损 1 秒级、驱放/主功放 3 秒/点）；测试/CI 可注入快放
    `sleep_fn`，但“真实时序抽样”保留为验收项。
11. **对照策略**：阶段隔离（精确对照）与全链路（容差对照）并存。阶段隔离用于证明
    “拿到数据后的程序”逐点一致；全链路用于证明三段串接和真实输入流。
12. **旧回放最后删除**：新链路全绿后再删除旧文件、旧符号和旧测试，避免中间状态
    同时坏两套。

## 5. 数据契约：`readings.json`

### 5.1 顶层结构

```json
{
  "schema_version": 1,
  "kind": "simulation_readings",
  "measurement_type": "cable_loss | driver_power_mapping | amplifier",
  "source": {
    "scenario": "scenario.json",
    "scenario_sha256": "...",
    "cable_loss_result": "2026...json",
    "cable_loss_sha256": "..."
  },
  "frequencies": {
    "1.0": {}
  }
}
```

### 5.2 各阶段形状

线损：

```json
"1.0": {"path1_raw_dbm": -41.842, "path2_raw_dbm": -43.418}
```

驱动映射：

```json
"1.0": {
  "probes": [
    {"source_power_dbm": -70.0, "raw_output_dbm": -70.802}
  ]
}
```

主功放：

```json
"1.0": {
  "points": [
    {
      "sg_power_dbm": -60.0,
      "raw_output_dbm": -26.709,
      "voltages": {"DP8B0885_CH1": 1.001},
      "currents": {"DP8B0885_CH1": 0.12}
    }
  ]
}
```

### 5.3 换算规则

- 线损：`path1_raw = -path1_loss`，`path2_raw = -path2_loss`。
- 驱动映射：`raw = output_power_driver - (attenuator + cable2)`。
- 主功放：`raw = output_power_dut - (cable4 + attenuator + cable2)`；
  `voltages` / `currents` 原样复制。
- 生成后必须正向调用 `compensate_driver_output_power` /
  `compensate_amplifier_output_power`，断言回到记录的补偿后值，误差 `< 1e-9`。
- 主功放的 `input_power_dut` / `sg_power` 保持记录值；端口按点序回放，
  增益与效率仍由真实服务计算。

## 6. 分阶段步骤

### 阶段一：冻结边界与数据契约

#### 步骤 1：固化替换边界与术语

- **范围**：文档与命名约定；不改代码。
- **执行策略**：在本文件、`mock_data/README.md` 和 `docs/使用说明.md` 统一术语：
  “正式运行”“仿真运行”“数据包”“原始读数”；明确替换点是端口读数层。
- **技术决定**：不替换事件层；不模拟连接/通信；页面与用例不改；旧回放最终删除。
- **验收**：三处文档术语一致；不存在“仿真运行回放 UI 事件”的表述。
- **工作量控制**：只写文档，不引入代码或测试改动。

#### 步骤 2：定义 `simulation_readings` 契约

- **范围**：新增 `application/dto/simulation_readings.py` 与单测。
- **执行策略**：用不可变 dataclass 定义顶层、阶段形状与来源摘要；提供
  `from_document()` 严格解析；拒绝未知字段、非有限数、频率缺失和空点集。
- **技术决定**：`schema_version = 1`；`kind = simulation_readings`；
  频率键统一为 GHz 字符串；阶段形状按 `measurement_type` 分派；来源摘要记录
  `scenario` / `cable_loss_result` 的 SHA-256，供生成工具与运行时自检。
- **验收**：合法样例通过；缺字段、未知字段、非数值、空 `probes/points`、
  频率与 `source_config` 不一致都给出带字段名的错误。
- **工作量控制**：纯 DTO 与单测，不读文件、不接端口。

#### 步骤 3：实现读数生成器

- **范围**：新增 `tools/build_simulation_readings.py` 与工具测试。
- **执行策略**：读取 `scenario.json` 与对应阶段的现有正式结果，按第 5.3 节反算；
  原子写入 `mock_data/<stage>/readings.json`；`--check` 只生成到内存并比对。
- **技术决定**：换算只调用真实补偿函数做正向断言，不复制公式；线损用场景的
  `path1_loss/path2_loss`；驱动/主功放使用 `source_config` 的衰减器与线损结果；
  生成文件带来源摘要，数据变化可被 `--check` 发现。
- **验收**：三份文件可由一条命令重建；`--check` 在数据一致时退出 0，改动场景或
  正式结果时退出非 0；往返误差 `< 1e-9`。
- **工作量控制**：只做离线工具，不接运行时。

#### 步骤 4：生成读数并扩展 Mock 路径服务

- **范围**：提交三份 `readings.json`；修改 `MockDataPathService` 与路径测试。
- **执行策略**：运行步骤 3 的工具生成数据；增加 `MOCK_READINGS_FILENAME`、
  `require_readings_path_for(stage)`，沿用“阶段目录直接子文件 + 链接解析”的边界。
- **技术决定**：`readings.json` 放在 `mock_data/<stage>/`，与场景/正式结果同目录；
  缺文件、越界、指向目录、Windows 保留名都在读取前失败。
- **验收**：三份文件在仓库中；路径服务覆盖缺失、越界、链接、目录场景；
  `--check` 通过。
- **工作量控制**：数据 + 一个小路径服务改动，不改运行链路。

### 阶段二：实现回放端口

#### 步骤 5：端口骨架与生命周期

- **范围**：新增 `instrument/simulation_port.py` 的控制面与单测。
- **执行策略**：实现 `MeasurementInstrumentPort` 的控制方法、`activate(kind)`、
  `begin_stage` / `end_stage` / `close_all` / `safe_shutdown` / `signal_gen`；
  数据读取先返回明确“未激活”错误。
- **技术决定**：控制方法只记录状态，不动作；不导入 `pyvisa`、驱动或传输模块；
  `close_all` 返回空列表；`signal_gen` 提供非空值，保证 `SafetyCleanupAdapter`
  仍走 RF 清理分支；阶段激活重置游标。
- **验收**：`require_measurement_capabilities` 通过；关闭幂等；未激活读取报错；
  静态检查确认端口模块不依赖 VISA/驱动。
- **工作量控制**：只做骨架和生命周期测试，不实现具体读数。

#### 步骤 6：线损读数

- **范围**：端口线损分支与单测。
- **执行策略**：按当前频率与“每频点第 1/2 次测量”返回 `path1_raw_dbm` /
  `path2_raw_dbm`；`activate` 与重新开始都重置游标。
- **技术决定**：端口只返回原始 dBm，不计算线损；服务仍执行
  `abs(0 - value)` 与 `calculate_cable_losses`；路径 1 完成、等待路径 2、
  继续、停止后重测都使用同一游标规则。
- **验收**：11 频点 × 2 路径顺序正确；停止在路径 1 后重测从路径 1 重新开始；
  缺频点或多余读取给出明确错误。
- **工作量控制**：只做线损数据分支，不碰驱动/主功放。

#### 步骤 7：驱动映射读数

- **范围**：端口驱动分支与单测。
- **执行策略**：按当前频率与 `set_power` 的源功率查记录点；精确命中返回记录值，
  未命中做线性插值；超出记录范围报错。
- **技术决定**：端口只返回原始读数，不补偿；插值按源功率单调区间；
  提供严格模式：阶段隔离测试要求每个请求功率都落在记录点上，全链路模式允许插值；
  阶段切换重置。
- **验收**：精确点、插值点、越界、阶段重置、严格模式失败用例；插值结果单调。
- **工作量控制**：只做驱动分支，不改服务搜索逻辑。

#### 步骤 8：主功放读数

- **范围**：端口主功放分支与单测。
- **执行策略**：按频率与点序返回 `raw_output_dbm` 和该点的 `voltages/currents`；
  `read_voltage` / `read_current` 读取当前点，未找到 `supply_channel` 键时报错；
  校验目标网格点数与记录点数一致。
- **技术决定**：按点序而不是按源功率键控，避免驱动命中微小差异导致查表失败；
  原始输出取记录值，不用记录的 `gain` 反推；压缩提前结束时未消费的点允许保留；
  阶段切换重置游标。
- **验收**：11 频点、每频点 27–29 点；V/I 与记录一致；提前结束、通道缺失、
  点数不一致的用例。
- **工作量控制**：只做主功放分支，不改压缩/效率计算。

#### 步骤 9：端口契约与安全清理测试

- **范围**：端口能力、生命周期、安全清理与静态导入测试。
- **执行策略**：用最小假读数覆盖能力校验、`begin_stage/end_stage`、重复关闭、
  `SafetyCleanupAdapter` 的 RF 清理路径；用 AST/导入检查确认无 VISA/驱动依赖。
- **技术决定**：端口必须能被 `require_measurement_capabilities` 接受；
  `close_all` 返回空错误；`end_stage` 可重复调用；错误使用现有
  `ConfigurationError` / `ValueError`，不新增异常分类。
- **验收**：能力缺失、未激活、重复关闭、安全清理记录、导入边界全部通过。
- **工作量控制**：只补测试，不改端口行为（除测试暴露的必要修正）。

## 8. 风险与回退

1. **驱动搜索对代码改动敏感**：阶段隔离严格模式先于全链路；搜索请求记录外功率时
   明确失败并提示重新生成 `readings.json`；不要在测试里静默改成插值。
2. **主功放点序与目标网格绑定**：端口在阶段开始前校验频率/点数/源功率；配置或
   数据漂移时失败，而不是回放错位。
3. **仿真运行被当成真机运行**：独立数据根 + `inputs/simulation.json` 标记 +
   `connect_instruments` 守卫三重保证；必须有测试。
4. **旧回放删除面大**：放在最后一步；删除前新链路全绿；删除后跑全量。
5. **真实时序导致验证慢**：默认真实时序，测试注入快放；保留一次真实时序抽样。
6. **`temp/simulation_runs` 增长**：整目录可删；文档说明；后续可加清理命令。
7. **接线确认对话框**：默认保留；若觉得多余，只在窗口层对仿真运行自动接受，
   不新增页面分支。
8. **不修改测量算法**：如果新链路暴露真实算法问题，按独立缺陷处理，不混入本
   重构。

## 9. 完成判据

- 生产代码只剩一条测量运行链路；旧回放符号无引用。
- 三段测量都通过真实用例/服务/阶段记录/归档运行，只有端口读数来自
  `readings.json`；不构造 VISA/驱动/传输对象。
- 阶段隔离测试能逐点复现现有数据与正式结果；全链路测试在约定容差内完成。
- 仿真运行写入 `temp/simulation_runs`，真实 `runs/` 与 `test_results/` 不变。
- 仿真运行不能被 `connect_instruments` 当成真机运行连接。
- 新链路文档、旧文档清理、全量测试与启动检查全部通过。
