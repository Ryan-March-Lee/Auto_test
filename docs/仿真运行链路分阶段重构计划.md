## 1. 目标与不变量

### 1.1 目标

1. 只保留一条测量运行链路：正式链路。仿真运行不新增第二套 worker、第二套事件
   协议或第二套结果展示。
2. 仿真运行与正式运行的唯一差异是：`MeasurementInstrumentPort` 的读数由
   `readings.json` 提供，而不是由 VISA/驱动/仪器提供。
3. 现有 `mock_data` 数据包保留：`scenario.json` 继续作为数据来源，现有正式结果
   保留为“期望输出”，但运行时不再直接展示它们；结果由真实服务重新计算。
4. 读数包在“进入仿真运行”时一次性加载、校验并冻结为不可变对象；运行期间不再
   读取 `mock_data`，运行结束后也不重新扫描。
5. 旧 UI 回放（`MockReplayWorker`、`SimulationSession`、`simulation_completed`
   等）在方案最后删除，避免两套“模拟”概念并存。

### 1.2 不变量

- 不修改 `domain` 与 `application/measurements` 的测量算法、事件形状、结果契约。
- 不修改三个测量页面的正式交互与结果渲染；只删除旧回放分支。
- 不打开 VISA，不构造驱动/传输层对象，不执行 SCPI；`instrument/simulation_port.py`
  不导入 `pyvisa`、`instrument.drivers`、`instrument.transport`。
- 仿真运行必须创建真实 `PreparedRun`，走真实运行快照、阶段记录、manifest、
  归档与部分结果保存。
- 仿真运行只消费仿真数据根内的运行、阶段结果与产物；真实 `runs/`、
  `test_results/` 在进入、运行、退出前后保持不变。
- 仿真运行不能在任何入口被当成真机运行重新连接，也不能被“加载运行”入口恢复。
- 仿真运行是一次性运行：返回欢迎页或退出进程后不提供恢复入口；需要重跑就重新
  进入并创建新运行。

### 1.3 非目标

- 不验证真实仪器、驱动、SCPI 命令或 VISA 连接；这些属于“其他系统”。
- 不新增历史运行/可视化页面对仿真结果的专门入口。
- 不改变 Mock 配置的命名规则、只读规则或数据包内容格式。
- 不修复现有页面呈现问题；本计划只改变数据来源与运行链路。
- 不改变正式链路的进度语义。主功放进度按频点重置、驱动映射进度按探针推进，
  仿真运行与正式运行保持同一条服务路径，不为了“看起来单调”另做平滑。

## 2. 调研基线

### 2.1 现有 Mock 链路

当前 GUI 的 Mock 链路是 **UI 事件回放**，不是测量链路：

```text
页面 → MeasurementStartFacade → MeasurementController
     → MockReplayWorker（读 scenario.json）
     → 直接 emit message / progress / data_update / result / simulation_completed
     → 同一页面
```

证据：

- `presentation/qt/mock_replay_worker.py` 文档头明确“不调用
  `create_*_measurement`、不创建正式运行、不打开 VISA、不写正式结果目录”。
- `presentation/qt/measurement_worker_factories.py::build_simulation_worker_factories`
  只按阶段创建 `MockReplayWorker`。
- `presentation/qt/measurement_controller.py` 按 `MeasurementExecutionMode.SIMULATION`
  切换工厂表，且模拟命令不调用端口 `begin_stage()`。

### 2.2 正式链路

```text
页面 → MeasurementStartFacade → MeasurementController
     → CableLossWorker / DriverMappingWorker / AmplifierWorker
     → app.gui_runtime.create_*_measurement
       （运行快照校验、校准输入预检、连接仪器、结果/阶段/归档仓库装配）
     → 用例 application/measurements/*
     → 服务 application/measurements/services.py（仪器动作 + 计算 + 事件）
     → test_results/<stage>/ 正式结果 + 运行 manifest + 自动归档
```

端口由协调器持有并注入；worker 只负责构造用例、驱动与停止。控制器开始一次测量时
的真实顺序是：

```text
MeasurementController._start()
  → 状态进入 PREPARING
  → port.begin_stage()            # 复用前的就绪检查，无参数
  → factory(command, measurement_port=port)
  → 状态转为 RUNNING
  → worker.start()
```

阶段在 worker 创建前失败时，控制器发出 `stage_start_failed`，协调器按异常阶段关闭
端口（`release_port_after_measurement()` → `_close_port_after_stage()`）；阶段成功
完成时，协调器调用端口 `end_stage()` 结算并保留端口供下一阶段复用。仿真端口必须
遵守同一所有权与结算规则，见第 3 节第 14 条、步骤 18。

### 2.3 共用与差异

| 环节 | 现有 Mock 链路 | 正式链路 | 结论 |
| --- | --- | --- | --- |
| 页面按钮 / 忙碌检查 | 同一 Facade | 同一 Facade | 共用 |
| 运行契约 / 接线确认 | 跳过 | 校验 `PreparedRun` + 接线弹窗 | 不共用 |
| 测量 Worker | `MockReplayWorker` 读 JSON | 正式 Worker 装配用例 | 不共用 |
| 状态机 / 信号契约 | `MeasurementController` | `MeasurementController` | 共用 |
| 实时数据 → 页面 | `data_update` → `update_realtime` | 同左 | 共用 |
| 进度 / 日志 / 停止 / 路径2确认 | 场景值 + 0.5 秒/点 | 服务计算 + 1 秒/线损点、5 秒/驱放与主功放点 | 仿真运行改用后者 |
| 测量计算 | 预置正式结果 | 服务现场计算 | 仿真运行改用后者 |
| 校准输入 | 自动绑定、不校验摘要/目标网格 | 显式加载 + 摘要 + 目标网格 | 仿真运行改用后者 |
| 结果落盘 / manifest | 不写 | 阶段目录 + 运行 manifest | 仿真运行改用后者（写仿真根） |
| 归档 / CSV / 报告 | 仅模拟完成提示 | 归档服务生成 | 仿真运行改用后者（写仿真根） |
| 停止 / 部分结果 / 清理 | 只停回放 | 部分结果 + 安全清理 | 仿真运行改用后者 |
| 历史 / 可视化 / 导出 | 没有数据 | 读 `test_results` | 仿真运行不进入 |

### 2.4 已核对的代码事实

1. 控制器在创建 worker 之前调用 `port.begin_stage()`；`begin_stage()` 不接受测量
   类型。因此“按阶段激活端口”必须发生在其后的 worker 工厂里，不能假设控制器会
   传入阶段。
2. 线损服务先测**路径 1 的全部频点**，再等待路径 2 确认，然后测**路径 2 的全部
   频点**（`CableLossService.run()` 的两个循环）；不是“同一频点连续测两条路径”。
   读数包若按频点交错记录，会与服务请求顺序不一致。
3. 真实服务的稳定延时是：线损每点 1 秒；驱动映射每探针 5 秒；主功放每点 5 秒，
   阶段开始时另有一次 2 秒上电等待。计划旧稿的“3 秒/点”与代码不符。按现有 Mock
   数据量估算，主功放真实时序约 26 分钟，驱动映射约 30 分钟。
4. `RunRepository(paths=PathService(...))` 的默认运行根是
   `<结果根目录>/test_results/runs`，不是 `<结果根目录>/runs`；要让
   `runs/` 与 `test_results/` 平级，必须显式传入 `root=`。
5. `PathService` 是冻结数据类，所有路径从 `root` 派生；`temp/` 已被 `.gitignore`
   忽略，适合作为仿真数据根。
6. 三套场景 `data.payload` 的键集合与真实服务发出的 `RealtimeDataEvent.data`
   一致；现有正式结果与用 `domain.measurement.calculations` 从回放数据重算的结果
   一致（线损 `1e-6 dB` 内，主功放压缩点与增益逐字段一致，驱动映射 `raw_points`
   逐点一致）。
7. 当前 `create_measurement_port(mode="simulation")` 不能直接使用：频谱仪默认恒定
   `-30 dBm`，电源电流默认 `0 A`（效率会全是 0%），且没有接入 GUI；
   `prepare_configuration` 还会拒绝模拟绑定。它只是单元测试用的管道替身。
8. 计划旧稿引用的 `docs/使用说明.md` 不存在；面向用户的操作说明应写入
   `mock_data/README.md` 与 `docs/运行配置说明.md`（新增“仿真运行”一节）。
9. `tests/simulation/` 不在默认全量离线发现的范围内；新的关键测试必须放在
   `tests/` 根目录或 `tests/integration/`，不能只放在 `tests/simulation/`。
10. 前置计划已实施：`docs/配置快照与执行上下文分离重构计划.md` 把“保存配置”和
    “创建执行上下文”分开；本计划的仿真入口只在“连接仪器”时创建运行，不借用
    `background_run`，也不因保存配置创建仿真运行。`docs/测量结果独立管理与运行降级重构计划.md`
    的阶段结果目录、显式路径与摘要契约继续复用，仿真只替换这些仓库的根目录。

### 2.5 结论

现有 Mock 链路是 **UI 演示/验收工具**，只能证明“给定这组事件，页面渲染正常”；
它不执行“拿到仪器数据之后的程序”。要缩小差异，替换点必须下沉到
`MeasurementInstrumentPort` 的读数层，而不是事件层。

## 3. 已确认的技术决定

1. **替换边界**：只替换 `MeasurementInstrumentPort` 的读数方法
   （`measure_power_with_average`、`read_voltage`、`read_current`）；控制方法
   （`set_*`、`rf_output_on/off`、`setup_*`、`power_on/off_*`）由仿真端口记录，
   不产生真实设备动作。
2. **不替换事件层**：不再用 `data_update` 直接回放界面数据；所有事件由真实服务产生。
3. **保留现有数据**：`mock_data/*/scenario.json` 和正式结果保留；新增由工具生成的
   `mock_data/*/readings.json`（原始读数）。正式结果只作为期望输出/对照。
4. **生成而非手写**：`readings.json` 由 `tools/build_simulation_readings.py` 从场景
   和现有正式结果反算生成，带 `--check`；换算必须正向调用真实补偿函数做往返断言。
5. **仿真运行 = 正式运行 + 注入端口**：创建真实 `PreparedRun`，worker、用例、服务、
   阶段记录、归档全部使用正式实现；不新增 worker 类型。
6. **数据根目录**：`temp/simulation_runs/`，由 `PathService.simulation_root` 派生；
   其中 `test_results/` 用 `PathService(root=simulation_root)` 派生，`runs/` 用
   `RunRepository(root=simulation_root / "runs")` 显式指定（不能用 `paths=`，否则
   会落到 `test_results/runs`）。真实 `runs/` 与 `test_results/` 不受影响。
7. **运行标记与事务边界**：仿真运行通过运行仓储写入并登记
   `inputs/simulation.json`（不修改 manifest schema，只增加一条 input 记录）。
   标记的 DTO、路径常量与读取判据只在 `application/simulation_run.py` 定义一次，
   创建、连接守卫与加载守卫共用。运行创建、标记写入与登记、manifest 更新是一个
   事务：失败时用 `discard_unstarted_run()` 撤销本次新建且尚未开始的运行，不留下
   “看起来像真机”的孤儿目录。
8. **守卫**：`connect_instruments()` 在解析硬件快照、打开任何 VISA 资源之前调用
   `is_simulated_run()` 检查 manifest 中登记的仿真标记；标记存在但缺失/摘要不一致
   时按失败关闭处理，抛 `RunNotResumable`。为避免“创建后、登记前崩溃”的窗口，
   连接守卫同时对位于 `PathService.simulation_root` 下的运行目录按仿真运行拒绝；
   生产默认根之外的自定义注入根以标记为准（只用于测试）。`load_prepared_run()`
   同样拒绝这两类运行；仿真运行不提供“加载运行”恢复入口。
9. **入口与配置**：仍由显示名为 `Mock` 的快照触发；配置页保持只读；“连接仪器”进入
   仿真运行，而不是旧模拟会话。进入过程只写仿真数据根内的配置草稿，不改
   `config.json`，也不写命名配置快照。
10. **接线确认**：默认保留正式接线确认对话框；它是正式流程的一部分，页面不新增分支。
    如果后续觉得多余，在窗口层做仿真运行自动接受，不改页面。
11. **时序**：服务保留真实时序语义（线损 1 秒/点、驱放 5 秒/探针、主功放 5 秒/点），
    但仿真运行在进入时注入 `time_scale`（默认 50）的快放 `sleep_fn`，使完整三段在
    几分钟内完成；`time_scale=1` 保留为手动验收选项。测试注入假时钟，不依赖墙钟。
    快放只改休眠时长，不改事件顺序、进度分母或结果计算。`time_scale` 由
    `app/simulation_runtime.py` 的模块常量/调试开关控制，不新增用户配置项。
12. **对照策略**：阶段隔离（精确对照）与全链路（按“同一份 raw + 新校准”重算
    期望值）并存。阶段隔离使用打包校准结果和端口严格模式；全链路使用本次仿真
    产生的校准结果，端口允许区间内插值，但禁止外推，并记录插值次数。
13. **读数包的运行时完整性**：进入仿真运行前一次性校验 schema、测量类型、频率网格、
    场景摘要与打包校准结果摘要；加载后的不可变读数对象随运行上下文冻结。运行期间
    端口不再读文件，因此仓库中 `readings.json` 的后续变化不会影响已进入的运行；
    标记文件记录本次实际使用的摘要，供审计。
14. **端口激活、所有权与复用**：协调器是端口的唯一所有者；worker 以
    `owns_measurement_port=False` 使用端口。控制器先调用 `begin_stage()`，worker
    工厂随后调用 `port.activate(measurement_type)` 绑定阶段，worker 才能启动。阶段
    成功时协调器调用 `end_stage()` 结算并保留端口；失败、取消或阶段启动失败时协调器
    关闭端口，下一次进入阶段或重连必须重建端口。端口不自行关闭，也不在 worker 内被
    关闭。
15. **仿真输入的路径范围**：仿真页面的校准选择、自动回填、阶段结果读取全部使用
    仿真作用域的 `ResultQueryPort`（由本次装配派生的 `PathService`，默认
    `SIMULATION_PATHS`），不得复用全局 `GuiDataService` 的真实结果查询；全局
    历史/可视化继续只读真实 `test_results/`，不感知仿真根。仿真运行只允许消费
    仿真数据根内的阶段结果。
16. **旧回放最后删除**：新链路全绿后再删除旧文件、旧符号和旧测试，避免中间状态
    同时坏两套。

## 4. 目标结构与文件变更

### 4.1 目标结构

```text
真实：页面 → 用例 → 服务 → [MeasurementInstrumentPort 读数]
                              → 端口适配器 → 驱动 → SCPI/VISA → 仪器

仿真：页面 → 用例 → 服务 → [SimulationRunPort]
                              ← 冻结的 readings（进入运行时加载一次）
                              ✗ 适配器/驱动/SCPI/VISA/仪器 整段不执行
```

### 4.2 数据根目录

```text
temp/simulation_runs/
├─ configs/<timestamp>_<short>.json # 仿真输入草稿（规范化后的当前编辑文档）
├─ runs/<run_id>/                   # 真实运行目录（RunRepository(root=runs)）
│  ├─ config.json
│  ├─ manifest.json
│  ├─ inputs/hardware_config.json
│  ├─ inputs/simulation.json        # 仿真运行标记（manifest 登记）
│  └─ artifacts/
└─ test_results/
   ├─ cable_loss/<measurement_id>.json
   ├─ driver_mapping/<measurement_id>.json
   └─ amplifier/<measurement_id>.json + CSV + 报告
```

派生关系：

```text
SIMULATION_ROOT      = PathService.simulation_root
                       （= DEFAULT_PATHS.temp_dir / "simulation_runs"）
SIMULATION_PATHS     = PathService(root=SIMULATION_ROOT)
                       （test_results/<stage>、configurations 均从其派生）
SIMULATION_RUNS_ROOT = SIMULATION_ROOT / "runs"
                       （显式传给 RunRepository(root=...)）
SIMULATION_CONFIGS   = SIMULATION_ROOT / "configs"
```

真实运行与仿真运行由“运行目录根 + manifest 登记的仿真标记”共同区分；不靠进程内
布尔值，也不靠目录名猜测。

## 5. 数据契约：`readings.json`

### 5.1 顶层结构

```json
{
  "schema_version": 1,
  "kind": "simulation_readings",
  "measurement_type": "cable_loss | driver_power_mapping | amplifier",
  "source": {
    "scenario": "scenario.json",
    "scenario_sha256": "...",
    "cable_loss_result": "2026...json",
    "cable_loss_sha256": "...",
    "driver_mapping_result": null,
    "driver_mapping_sha256": null
  },
  "payload": {}
}
```

示例只展示字段形状：线损文件的 `cable_loss_result` 等上游字段为 `null`。

- `schema_version` 只支持 `1`；未知版本、未知字段、非有限数、空点集一律拒绝。
  schema 变更必须新增版本并在 DTO 中显式支持，同时升级生成工具与已提交数据，
  不允许对未知版本静默降级或按旧形状猜测。
- `measurement_type` 必须与该文件所在阶段一致，并与运行时激活的阶段一致。
- `source` 是生成事实：场景与打包校准结果的相对文件名和 SHA-256。线损没有上游
  校准结果，相关字段为 `null`；驱动映射引用线损；主功放在驱动模式下同时引用线损
  与驱动映射。文件名只用于审计，运行时按 `MockDataPathService` 解析同名文件并核对
  摘要：`cable_loss_result` 在线损阶段目录解析，`driver_mapping_result` 在驱动映射
  阶段目录解析；它不是“本次选中校准结果”的摘要。
- 顶层不写 `readings.json` 自身的摘要；自身摘要由读取入口返回，写进运行标记。

### 5.2 各阶段形状

线损使用**有序测量序列**，顺序与 `CableLossService.run()` 一致（路径 1 全频点 →
路径 2 全频点；下例只列 3 项示意，实际先列完路径 1 的全部频点）：

```json
"payload": {
  "measurements": [
    {"frequency_ghz": 1.0, "path": 1, "raw_dbm": -41.842},
    {"frequency_ghz": 2.0, "path": 1, "raw_dbm": -42.103},
    {"frequency_ghz": 1.0, "path": 2, "raw_dbm": -43.418}
  ]
}
```

驱动映射按频点保存探针，源功率严格递增、不得重复：

```json
"payload": {
  "frequencies": {
    "1.0": {
      "probes": [
        {"source_power_dbm": -70.0, "raw_output_dbm": -70.802}
      ]
    }
  }
}
```

主功放按频点保存扫描点，`sg_power_dbm` 严格递增、不得重复；同一频点内各点的
`voltages` / `currents` 通道集合必须完全一致：

```json
"payload": {
  "frequencies": {
    "1.0": {
      "points": [
        {
          "sg_power_dbm": -60.0,
          "raw_output_dbm": -26.709,
          "voltages": {"DP8B0885_CH1": 1.001, "DP8B0885_CH2": 2.002},
          "currents": {"DP8B0885_CH1": 0.12, "DP8B0885_CH2": 0.08}
        }
      ]
    }
  }
}
```

频率键统一用 `domain.measurement.Frequency` 的规范化键；端口按数值匹配，容差
`1e-9 GHz`，不按原始字符串匹配。

### 5.3 换算规则

- 线损：`raw_dbm = -loss_db`；服务仍执行 `abs(0 - value)`。
- 驱动映射：`raw = output_power_driver - (attenuator + cable2)`。
- 主功放：`raw = output_power_dut - (cable4 + attenuator + cable2)`；
  `voltages` / `currents` 原样复制。
- 生成后必须正向调用 `compensate_driver_output_power` /
  `compensate_amplifier_output_power`，断言回到记录的补偿后值，误差 `< 1e-9`。
- 主功放的 `sg_power` 保持记录值；增益、效率、压缩点仍由真实服务计算。
- 原始读数与校准无关：全链路换用新的线损/映射时，raw 保持不变，补偿后的结果
  按新校准重新计算。测试不能用“打包结果”直接当全链路期望值。

### 5.4 运行时加载与完整性

进入仿真运行时按以下顺序执行；前 3 步失败时尚未创建运行目录，创建后的失败由
`discard_unstarted_run()` 撤销，不保留半成品运行：

1. 读取 `mock_data/<stage>/readings.json` 原始字节，得到 SHA-256 与大小。
2. 严格解析 DTO：schema/kind/类型、未知字段、有限数、频率键、点集顺序与重复项。
3. 校验频率集合与冻结配置的测试频率逐点一致，多一个或少一个都失败。
4. 按 `source` 校验场景文件与打包校准结果的 SHA-256；缺失或不一致失败。驱动模式下
   的主功放还要求记录并校验打包驱动映射摘要；驱动关闭时该字段为 `null`。
5. 把 DTO、摘要与路径放进不可变运行上下文；端口只接收 DTO，不接收路径。

运行期间不再读取 `mock_data`；`readings.json` 在运行中被修改不会改变本次运行，
由标记中的摘要解释“本次实际使用了哪一份数据”。

### 5.5 端口读取语义

| 阶段 | 查找键 | 精确命中 | 未命中 | 严格模式 |
| --- | --- | --- | --- | --- |
| 线损 | 有序测量序列的下一项 | 校验当前频率与预期路径后返回，成功返回后才推进游标 | 无插值；顺序/频率不符立即失败 | 同左 |
| 驱动映射 | `(frequency, source_power)` | 返回记录 raw | 在相邻记录点之间线性插值；区间外失败 | 只接受记录点 |
| 主功放 | `(frequency, set_power)` | 返回记录 raw 与 V/I | 在相邻记录点之间对 raw 与 V/I 线性插值；区间外失败 | 只接受记录点 |

补充规则：

- 重复读取同一键返回同一结果，不推进任何游标；停止/重试不得造成读数错位。
- 主功放的 V/I 读取绑定“最近一次成功消费的测量点”（精确命中或插值点）；
  没有消费点时读取 V/I 失败。
- 线损阶段只在激活线损测量时重置游标；中途停止后重跑必须重建端口并重新激活，
  不能复用半途游标。
- 严格模式只用于阶段隔离测试，由端口构造参数开启；生产/GUI 默认允许插值。
- 功率查找键先按信号源驱动的命令量化（`f"{value:g}"`，6 位有效数字）收敛：真实仪器
  收到的就是量化后的设定值，`readings.json` 记录的也是它。量化不改变 `1e-9 dB`
  的记录点容差，也不允许外推；量化后仍不是记录点的请求照常失败。
- 插值按频点记录次数并写日志；出现外推或记录点缺失时错误消息必须提示重新生成
  `readings.json`，不得静默改用邻近值。

  重复 `end_stage` 不抛错；静态检查确认端口模块不依赖 VISA/驱动/传输。
- **工作量控制**：只做骨架和生命周期测试，不实现具体读数。

- **实施记录**（2026-11-18）：新增 `instrument/simulation_port.py` 的
  `SimulationRunPort` 与 `tests/test_simulation_port.py`。端口只接收冻结
  `SimulationReadings`（单个阶段或按阶段索引的本轮三份读数包），不接收路径；它是
  运行级 router，`activate(measurement_type)` 选择对应读数包，一个端口可以连续服务
  线损 → 驱动映射 → 主功放，缺失阶段或读数类型与阶段不符都在激活时失败。控制方法
  只记录状态与命令序列（`recorded_commands`），`signal_gen` 提供只镜像 `rf_enabled`
  的占位对象，保证 `SafetyCleanupAdapter` 仍走 RF 清理分支。`begin_stage()` 只做
  “未关闭、无活动阶段”的就绪检查；`activate` 清空游标、查找缓存与插值计数；
  `end_stage()` 释放阶段绑定、幂等且保留端口可复用；`close_all()` 幂等、返回空
  错误列表，关闭后所有读数与控制都要求重建端口。错误分两类：
  `SimulationPortError(ConfigurationError)` 表示冻结读数回答不了本次请求（提示重新
  生成 `readings.json`），`SimulationPortStateError` 表示生命周期误用
  （未激活、已关闭、阶段未结算）；`require_measurement_capabilities` 对三类测量的
  全部能力校验通过。未激活读取、重复关闭、重复 `end_stage`、阶段启动失败后关闭再
  读取、三阶段共用同一端口都有用例。控制面在 `activate()` 时清空上一阶段留下的
  频率/中心频率/跨度/功率设定：阶段切换后漏设 `set_frequency`/`set_power` 按生命周期
  错误失败，不会悄悄复用旧值；`activate()` 先判“已有未结算阶段”再查读数包，重复
  激活始终报告生命周期误用。`SimulationPortStateError` 继承 `ConfigurationError`
  与 `RuntimeError`：归入配置类异常门禁，同时保留分类之前就存在的
  `except RuntimeError` 语义。

#### 步骤 6：线损读数

- **范围**：端口线损分支与单测。
- **执行策略**：按冻结的有序序列逐项返回；每次读取校验“当前设置频率”与下一项
  频率一致、路径切换只发生在序列预期的位置；成功返回后才推进游标。
- **技术决定**：端口只返回原始 dBm，不计算线损；服务仍执行 `abs(0 - value)` 与
  `calculate_cable_losses`；顺序固定为路径 1 全频点 → 路径 2 全频点；停止后重跑
  由 `activate` 重置游标（协调器已关闭旧端口时需重建端口）。
- **验收**：11 频点 × 2 路径顺序正确；路径 1 → 路径 2 的切换位置正确；频率不符、
  提前/多余读取、停止后复用旧游标都给出明确错误。
- **工作量控制**：只做线损数据分支，不碰驱动/主功放。

- **实施记录**（2026-11-18）：线损分支按冻结的有序序列逐项消费，`set_frequency`
  与下一项频率按 `1e-9 GHz` 容差校验，路径 1 → 路径 2 的切换位置由序列长度决定；
  游标只在成功返回后推进，频率不符、提前读取、读完后多余读取、停止后不重新
  `activate` 就复用旧游标都会失败，并提示按 `readings.json` 的顺序重测或重建端口。
  `activate` 重置游标。已用真实 `mock_data/cable_loss/readings.json` 与真实
  `CableLossService.run()` 做离线联调：11 个频点 × 2 路径的补偿结果与打包正式结果
  最大偏差 `2.9e-15 dB`。

#### 步骤 7：驱动映射读数

- **范围**：端口驱动分支与单测。
- **执行策略**：按 `(frequency, source_power)` 查记录点；精确命中返回记录值，
  未命中在相邻点之间线性插值；超出记录范围报错；重复键返回同一值。
- **技术决定**：端口只返回原始读数，不补偿；插值按源功率单调区间；加载时拒绝
  重复或乱序的源功率；严格模式只接受记录点（阶段隔离测试用），生产默认插值；
  插值次数按频点记录日志；阶段激活清空查找缓存。
- **验收**：精确点、插值点、越界、重复读取、阶段重置、严格模式失败用例；插值
  结果单调且落在相邻记录值之间。
- **工作量控制**：只做驱动分支，不改服务搜索逻辑。

- **实施记录**（2026-11-18）：驱动分支按 `(set_frequency, set_power)` 查找记录点，
  记录点容差 `1e-9 dB`；精确命中走记录值，未命中在相邻记录点之间线性插值并把次数
  计入 `interpolation_counts`、写日志；区间外与非记录点（严格模式）都失败并提示
  重新生成 `readings.json`。同一键的重复读取命中查找缓存，返回同一结果且不再累计
  插值次数；`activate` 清空缓存与计数。真实打包数据联调发现两处偏差，根因不在
  端口查找规则：信号源驱动在写 SCPI 前把功率格式化成 6 位有效数字
  （`SignalGeneratorDriver._format_number`），仪器实际设定值是量化后的 `-69.753`，
  而搜索算出的请求是 `-69.752975`，`readings.json` 记录的也是量化值。端口现在用
  同一规则记录和查找功率（`SIMULATION_POWER_COMMAND_FORMAT = "g"`）；量化后仍不在
  记录点上的请求照常失败，容差保持 `1e-9 dB`，也不外推。用真实
  `DriverPowerMappingService` 对冻结读数重放：量化后 11 个频点都能覆盖 31 个目标，
  只剩 1.0 / 1.4 / 1.9 GHz 在上界外 `1e-4`～`1e-3 dB` 各多要一个点。原因是打包
  轨迹本身是等步进编造曲线（`-60.0, -58.988, …`），不是当前自适应搜索生成的，
  最后一点是整数截断而不是算法落点。严格模式因此仍会在这三个频点失败，这是步骤 12
  的决策点（按当前算法重放并补足记录边界），不得放宽容差或外推。

#### 步骤 8：主功放读数

- **范围**：端口主功放分支与单测。
- **执行策略**：按 `(frequency, 当前 set_power)` 查记录点，返回 raw 与 V/I；
  未命中在相邻点之间对 raw 与 V/I 线性插值；V/I 读取绑定最近一次成功消费的点；
  未找到通道键时报错。
- **技术决定**：以 `measure_power_with_average()` 为消费边界，而不是以 `set_power`
  为边界（初始化 `set_power` 不产生测量）；原始输出取记录值，不用记录的增益反推；
  压缩提前结束时未消费的点允许保留；输入保护提前停止不视为数据错误；阶段激活
  清空当前点与插值缓存。
- **验收**：11 频点、每频点 27–29 点；V/I 与记录一致；提前结束、通道缺失、
  插值点、越界、重复读取、V/I 无活动点的用例。
- **工作量控制**：只做主功放分支，不改压缩/效率计算。

- **实施记录**（2026-11-18）：主功放分支按 `(set_frequency, set_power)` 查找扫描点；
  精确命中直接绑定记录点的 raw 与 V/I，插值点对 raw、各通道电压与电流同时做线性
  插值（通道集合不一致直接失败）。`measure_power_with_average()` 是唯一消费边界：
  只有成功解析出测量点才更新 `read_voltage` / `read_current` 的绑定，失败请求不会
  改变绑定；没有消费点、跨阶段结算后读取、在其它阶段读取都给出生命周期错误。
  通道键沿用结果契约的 `<电源>_<通道>`，缺失时列出可用通道并提示重新生成
  `readings.json`。区间外与严格模式失败；同一键重复读取不推进任何游标。

## 8. 风险与回退

1. **驱动搜索对代码改动敏感**：阶段隔离严格模式先于全链路；搜索请求记录外功率时
   明确失败并提示重新生成 `readings.json`；不要在测试里静默改成插值。
2. **主功放点序与目标网格绑定**：端口按 `(频率, set_power)` 查找；校准变化导致新
   功率点时只允许在记录区间内插值，越界即失败，而不是回放错位。
3. **全链路校准漂移**：raw 与校准无关；期望值必须用“同一份 raw + 新校准”重算。
   不能把打包结果直接当全链路期望值，也不能用固定大容差掩盖耦合问题。
4. **仿真运行被当成真机运行**：独立数据根 + manifest 登记的仿真标记 +
   `connect_instruments` 守卫 + `load_prepared_run` 拒绝；失败关闭；必须有测试。
5. **创建/标记不是原子的**：先建运行、再写标记、再登记，任一步失败用
   `discard_unstarted_run()` 撤销；崩溃残留由文档说明并按未开始运行清理。
6. **真实时序导致验证慢**：默认 `time_scale=50`，测试用假时钟；保留一次单点真实
   时序抽样，不把 26 分钟全流程放进常规测试。
7. **旧回放删除面大**：放在最后一步；删除前新链路全绿；删除后跑全量；页面构造
   基线、静态门禁、测试支持文件同一提交更新。
8. **`temp/simulation_runs` 增长**：整目录可删；文档说明；后续可加清理命令。
9. **接线确认对话框**：默认保留；若觉得多余，只在窗口层对仿真运行自动接受，
   不新增页面分支。
10. **不修改测量算法**：如果新链路暴露真实算法问题，按独立缺陷处理，不混入本
    重构。

## 9. 完成判据

- 生产代码只剩一条测量运行链路；旧回放符号无引用。
- 三段测量都通过真实用例/服务/阶段记录/归档运行，只有端口读数来自
  `readings.json`；不构造 VISA/驱动/传输对象。
- 阶段隔离测试能逐点复现现有数据与正式结果；全链路测试用“同一份 raw + 新校准”
  重算期望值并通过，无外推。
- 仿真运行写入 `temp/simulation_runs`，真实 `runs/` 与 `test_results/` 不变；
  全局历史/可视化不显示仿真结果。
- 仿真运行不能被 `connect_instruments` 当成真机运行连接，也不能被
  `load_prepared_run` 恢复；标记缺失/损坏时失败关闭。
- 运行创建、标记写入与 manifest 登记失败时可撤销，不留下半成品运行。
- 默认快放时序下完整三段在几分钟内完成；真实时序可手动开启。
- 新链路文档、旧文档清理、全量测试与启动检查全部通过。

## 10. 审查修订记录（2026-11-18）

本轮审查以当前代码为准，修正了旧稿中会导致实现返工或错误结论的地方：

1. **线损扫描顺序**：旧稿写“每频点第 1/2 次测量”，与
   `CableLossService.run()` 的“路径 1 全频点 → 路径 2 全频点”不符。改为有序
   测量序列，端口按顺序消费并校验频率。
2. **端口激活时序**：控制器在创建 worker 前调用无参数 `begin_stage()`；旧稿把
   阶段绑定写在工厂里但未说明顺序。明确为 `begin_stage()` → `activate(measurement_type)` →
   `worker.start()`，并区分成功结算与失败关闭的所有权。
3. **读数查找语义**：旧稿按“点序/每频点第 n 次”驱动和主功放，重试与停止后容易
   错位。改为按 `(频率, set_power)` 键查找、重复读取幂等、区间内插值、禁止外推；
   严格模式只用于阶段隔离测试。
4. **读数运行时完整性**：补充进入时一次性加载、schema/网格/摘要校验、冻结对象、
   运行期不读文件、标记记录本次摘要；明确 `source` 摘要不是“本次选中校准”的摘要。
5. **创建与标记事务**：明确标记必须经运行仓储写入并登记 manifest，创建/标记/
   登记失败用 `discard_unstarted_run()` 撤销，守卫失败关闭，`load_prepared_run`
   拒绝仿真运行。
6. **仿真输入路径范围**：补充仿真作用域 `ResultQueryPort`；校准选择、自动回填、
   阶段读取都不得复用全局真实结果查询；历史/可视化保持隔离。
7. **路径根派生**：修正 `RunRepository(paths=...)` 会把 `runs/` 落到
   `test_results/runs` 的事实，明确用 `RunRepository(root=SIMULATION_RUNS_ROOT)`；
   数据根改由 `PathService` 派生。
8. **时序数值与默认策略**：修正“3 秒/点”为线损 1 秒、驱放/主功放 5 秒；默认
   注入 `time_scale=50` 快放，真实时序保留为手动验收，避免 GUI 验证等待 26 分钟。
9. **全链路对照口径**：明确 raw 与校准无关，期望值用“同一份 raw + 新校准”重算；
   不再用打包结果直接比较，也不靠大容差掩盖差异。
10. **状态机与重连**：移除 `SIMULATING`，使用 `CONNECTED + simulated`；重连只重建
    端口，绝不走 `InstrumentWorker`/`connect_instruments`；返回欢迎页统一收尾。
11. **文档与测试位置**：修正不存在的 `docs/使用说明.md`；明确用户说明落在
    `mock_data/README.md` 与 `docs/运行配置说明.md`；关键测试不放
    `tests/simulation/`，避免默认全量不运行。
12. **验证与门禁**：补充 `test_config_write_boundary.py`、页面构造函数基线、
    静态质量门禁旧回放登记等必须在同一步更新，避免“代码删了但门禁还指着旧符号”。
