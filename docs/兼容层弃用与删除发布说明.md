目标版本和回滚/查看方案。

| 项目 | 结论 |

全局删除前置条件：

1. **仓库内调用方清单已清空或只剩已批准的兼容调用**：
   `tests/test_compatibility_deletion_conditions.py` 固定各接口当前生产调用文件集合，新增
   调用方立即失败；删除前必须迁移正式运行调用，并明确处理清单中剩余的兼容调用。当前
   `save_compatibility_copy()` 在正式测量用例与旧入口中的调用已在步骤 2、3（2026-10-26）
   删除，生产代码为零引用；接口本身也已删除，记录见 3.3.1、3.3.2。
2. **外部调用方迁移确认**：建立并归档调用方清单，逐个取得脚本所有者的迁移确认，或
   确认该调用方已退役。`DeprecationWarning` 默认可能被 Python 过滤，不能用“一个周期
   没有看到告警”代替确认。**2026-10-24 已由任务授权人确认仓库不存在任何外部调用方/外部
   脚本**，来源与确认方式见 6.2。
3. **回滚/查看方案已验证**：历史结果仍可只读查看与导出（见各接口“回滚与查看”），且
   存在一份已实跑验证的回滚基线（见 6.3）。

删除按**影响面分级**（授权依据见 6.6）：

- **数据类删除**（v1.2 批次：停止写全局兼容副本、旧运行快照、旧兼容测量根入口）：在满足
  以上三条之外，**必须完成[重构指南步骤 F](测试运行目录与配置结果解耦重构指南.md) 现场验收并归档**。
  步骤 F 是唯一验收口径；[重构收尾与真实HardwareSmoke验收.md](重构收尾与真实HardwareSmoke验收.md)
  只承载现场证据与签字。F 归档只解除现场验收这一环，不自动完成 C 与 E2 至 E4；其中
  C1 至 C4 与 E2 至 E4 已由技术债步骤 2 至 4（2026-10-26）完成（见 3.3.3）。
- **纯代码路径删除**（v1.1 批次：`LegacyResultInputReader`、`latest_path()` / `latest_compatibility_path()` 等）：
  不删除或改写任何数据文件，在满足以上三条并具备已实跑验证的回滚基线后执行。**项目负责人
  于 2026-10-24 授权该分级例外（见 6.6）**，步骤 F 不作为其前置条件；F 归档前禁止继续执行
  任何数据类删除。

未同时满足对应级别条件的接口**继续保留**，并在第 4 节记录保留原因。当前调用方清单不是
“零生产调用方”证明，而是删除决策基线；删除时必须重新验证清单为空或残余调用已迁出。

## 3. 各接口删除条件

### 3.1 `latest_path()` / `latest_compatibility_path()`

拟定删除目标版本：**v1.1**。当前状态：**已删除（步骤 B3，2026-10-24）**。

- 原端口声明：`application/ports/result_repository.py` 的
  `MeasurementResultRepository.latest_path`（已删除）。

  `DeprecationWarning`）与 `latest_compatibility_path`（仅服务该弃用链），均已删除；
  `warnings` 依赖一并移除。
- 删除前调用方清单（仓库内生产代码，删除许可依据）：
  1. `application/inputs/legacy_result_input_reader.py`：
     `latest_legacy_driver_mapping_path() -> repository.latest_path("driver_power_mapping")`。
  2. 步骤 B3 随兼容读取器一并删除上述唯一调用方；删除后生产代码零引用，由门禁
     `tests/test_compatibility_deletion_conditions.py` 的 `StepB3RemovalTests` 固定。
  3. 仓库外：任务授权人确认无外部调用方（6.2）。
- 删除条件：
  1. 3.2 的无路径映射读取先删除（`latest_path()` 的唯一调用方就在其中）。→ 已完成（步骤 B3）。

     `tests/test_result_repository.py` 中依赖 `latest_path()` 的四个用例改为“接口已删除”

  3. 满足全局条件 2 至 4。→ 条件 2 已由任务授权人确认零外部调用方；条件 4 的回滚/查看

### 9.5 审查修复记录（2026-10-24）

步骤 D 初版实现经代码审查发现三处边界/行为缺陷，已修复并补测试，不改动任何数据文件：

1. **运行目录重解析点越界**：原实现只对结果文件做“位于运行目录内”校验，但校验基准是
   `run_directory.resolve()`；若运行目录本身是指向运行根目录之外的符号链接或 Windows 目录
   联接（junction），解析后基准随之越界，校验形同失效。修复为以“解析后的运行目录必须严格
   位于解析后的运行根目录内”为准（`_run_directory`），符号链接/联接一律判为 `INVALID` 并
   拒绝 `list_results` / `load` / `read_bytes`。测试用真实目录链接（必要时回退 junction）
   覆盖，Windows 上实际执行而非跳过。
2. **非阶段结果输入被当作历史结果**：原读取入口从 `inputs + outputs` 查引用，导致
   `inputs/hardware_config.json` 等已登记输入也能被导出。修复为统一“阶段结果白名单”
   （`_result_entries`：各阶段 `record.result` + 登记到已知阶段的 outputs 拆分结果），
   `list_results` 与 `load` / `read_bytes` 共用该集合，非阶段结果输入不可读。
3. **`latest_result()` 非确定性且不跳过损坏结果**：原实现按文件 mtime 取最大并只加载一次，
   最新文件被篡改会直接抛错且不继续尝试。修复为确定性顺序（运行创建时间新→旧，同运行内
   结果修改时间新→旧），逐个候选做完整性校验，损坏候选记录日志并继续尝试更旧候选；全部
   运行候选不可用时才回退最新兼容副本。
