# PA 自动测试系统后续重构路线图与实施指南

## 1. 文档目的

本文档是三期重构完成后的长期重构指南，用于约束后续代码整理、模块迁移和架构演进。

本文档解决的问题不是“再拆几个大文件”，而是让已经建立的新模块边界成为唯一的生产代码依赖方向，逐步退出历史根目录模块，降低新旧架构并存带来的理解成本和维护风险。

后续重构必须遵循以下原则：

1. 先明确依赖方向，再迁移实现。
2. 先建立新入口，再移除旧入口。
3. 每个阶段都必须有可执行的验收标准。
4. 兼容层只负责转发，不得继续承载业务实现。
5. 任何涉及真实仪器、电源或 RF 的变化，都必须经过离线验证和独立的 Hardware smoke 安全门禁。
6. 不为了追求目录形式而增加抽象；只有能够减少职责耦合、重复实现或测试成本的抽象才应保留。

当前状态应描述为：**第一期至第三期重构离线验收完成；新旧模块边界尚未完全收口；真实 Hardware smoke 仍以《重构收尾与真实HardwareSmoke验收》为准。**

## 2. 当前结构判断

### 2.1 已经完成的部分

- `enhanced_workers.py` 及其生产兼容入口已经退出生产路径。
- Qt 页面、测量 controller、worker factory 和主窗口已经完成主要职责拆分。
- 三类测量已经具备用例、服务、端口和页面等分层雏形。
- `presentation/qt/` 已经成为 GUI 的正式实现位置。
- 仿真、离线测试、架构静态门禁和安全清理测试已经形成基础保护网。
- 设备控制已经明确了应用、测量端口、安全会话、driver、transport 的基本边界。

### 2.2 仍然导致项目混乱的部分

当前主要问题是新旧结构并存，而不是单个模块的规模问题：

- 根目录仍然存在 `config_io.py`、`config_models.py`、`config_validation.py`、`result_storage.py`、`result_reading.py`、`measurement_services.py`、`measurement_calculations.py`、`instrument_control.py` 等历史模块。
- `application/`、`infrastructure/`、`instrument/` 和 `presentation/` 已存在，但部分新模块仍直接依赖根目录实现。
- `persistence/` 与 `infrastructure/persistence/` 存在职责重叠，需要确定唯一归属。
- `instrument/` 与根目录 `instrument_control.py` 同时承担设备相关入口，需要建立唯一正式 API。
- `enhanced_main_gui.py` 已经是兼容入口，但旧测试和历史脚本仍通过它访问新实现。
- 测试名称包含大量 `phase`、`refactor` 和 `acceptance` 语义，适合迁移期，不适合作为长期架构分类。
- 路径、日志、配置、结果存储和格式解析仍有部分基础设施逻辑散落在业务模块中。

### 2.3 当前阶段的判断

项目目前处于“职责已拆分、依赖未收口”的阶段。因此下一步不应继续进行大规模 GUI 拆分，也不应同时更换测试框架、配置格式或日志框架。当前最有价值的工作是建立唯一内部 API，迁移生产代码的依赖，然后逐步退出兼容模块。

## 3. 目标架构

### 3.1 目标依赖方向

目标依赖方向如下：

```text
launcher
    ↓
presentation
    ↓
application
    ↓
domain / application.ports
    ↓
infrastructure / instrument
    ↓
文件系统、JSON、VISA、SCPI 和具体设备
```

更具体地说：

```text
presentation.qt
    ↓
application.measurements
    ↓
application.ports
    ↓
infrastructure
    ↓
instrument
```

依赖规则：

- `presentation` 可以依赖 `application` 的 DTO、用例和公开协议，但不得直接依赖 VISA、SCPI、结果存储实现或具体设备 driver。
- `application` 负责用例编排，不得依赖 Qt。
- `domain` 只包含纯业务规则、计算、值对象和状态，不得依赖 Qt、VISA、文件系统或具体设备。
- `application.ports` 只定义应用所需的接口和协议，不实现 JSON、VISA 或 GUI 行为。
- `infrastructure` 实现持久化、配置、日志、外部服务和其他端口。
- `instrument` 负责设备会话、driver、transport、仿真和安全动作。
- `launcher` 负责参数解析、环境检查、配置校验和启动，不承担测量业务。
- 兼容模块可以依赖新模块；新模块不得反向依赖兼容模块。

### 3.2 建议的目标目录

不要求一次性完成目录迁移。目标结构可逐步形成如下布局：

```text
application/
    dto/
    measurements/
    ports/
    inputs/

domain/
    measurement/
    configuration/
    results/

infrastructure/
    config/
    logging/
    persistence/
    filesystem/

instrument/
    drivers/
    transport/
    session.py
    safety.py
    simulation.py

presentation/
    qt/

hardware/
analysis/
assistant/
tests/
```

`domain/` 是否单独建立，可以根据迁移过程中纯逻辑模块的数量决定。若当前纯逻辑较少，也可以暂时放在 `application` 内，但必须保持不依赖基础设施的规则。

## 4. 总体实施顺序

后续工作分为五个阶段。每个阶段完成后应运行完整离线测试、应用检查、配置校验和编译检查，再进入下一阶段。

| 阶段 | 名称 | 主要目标 |
| --- | --- | --- |
| 第四期 | 边界收口 | 建立唯一内部 API，停止新代码依赖根目录历史实现 |
| 第五期 | 运行时模型收敛 | 统一测量请求、状态、生命周期和资源所有权 |
| 第六期 | 配置与持久化收口 | 统一配置、结果模型、仓储和路径服务 |
| 第七期 | 兼容层退出 | 删除无调用方的历史实现，保留必要的有限兼容入口 |
| 第八期 | 运行方式与交付收敛 | 统一启动、打包、文档、诊断和现场交付流程 |

真实 Hardware smoke 不属于上述阶段的替代验收。涉及设备动作的改动仍必须单独遵循《重构收尾与真实HardwareSmoke验收》中的现场条件和安全顺序。

## 5. 第四期：边界收口

### 5.1 目标

让新目录成为生产代码的正式依赖方向，根目录历史模块只保留薄兼容层。

### 4.1.2 统一执行规则

1. 每个模块迁移前重新执行全仓 AST 导入扫描和文本扫描，结果必须分别记录静态导入、局部/动态导入、`patch("module.symbol")`、发布清单和脚本入口。
2. 每个模块必须单独有迁移状态：`未开始`、`迁移中`、`兼容层`、`待删除` 或 `保留正式入口`。本表的 `目标状态` 不是迁移完成状态，不能替代实施记录。
3. 兼容模块只能重导出正式实现，不得保留第二套业务逻辑、全局设备状态、文件读写、隐式初始化或旧 repository 对新 repository 的反向依赖。
4. `result_repository.py -> result_storage.py` 是第四期 P0 阻塞项；必须先把结果持久化实现收口到 `infrastructure/persistence`，再迁移调用方。
5. `persistence/config_repository.py` 的唯一归属必须在步骤 4.2 决定；`instrument_control.py` 和 `measurement_lifecycle.py` 的拆分必须在步骤 4.3 决定；未决策前不得删除旧模块。
6. 测试迁移分两类：正式行为测试改用新 API；仅验证兼容性的测试保留旧 API，并在测试名或注释中明确兼容目的。所有旧路径 patch 必须同步更新到实际实现位置。
7. 每个 P0/P1 批次完成后运行完整离线测试、应用检查、配置校验和编译检查；涉及设备控制、RF、电源或 VISA 资源时，另外执行独立 Hardware smoke 安全门禁。

### 4.1.3 第四期建议迁移顺序

1. 先完成 4.2 的唯一持久化边界和 4.3 的唯一设备控制边界决策。
2. 迁移 `project_paths.py`、`app_logging.py`、`config_io.py`、`config_models.py` 和 `config_validation.py`。
3. 迁移 `result_storage.py`、`result_reading.py` 和 `persistence/config_repository.py`，解除 repository 对旧模块的反向依赖。
4. 迁移 `instrument_control.py` 和 `measurement_lifecycle.py`，验证安全动作、资源所有权和异常清理。
5. 迁移 `measurement_calculations.py`、`measurement_services.py` 及三个历史测量入口。
6. 迁移可视化、连接图、GUI、助手和工具入口，最后按删除门槛退出兼容层。

#### 步骤 4.2：确定唯一持久化边界

目前存在 `persistence/` 与 `infrastructure/persistence/` 两个候选位置。应选择一个正式方案，推荐：

```text
application/ports/
    config_repository.py
    result_repository.py

infrastructure/persistence/
    json_config_repository.py
    json_result_repository.py
    json_encoder.py
```

应用层只依赖 `application.ports`。JSON 文件、目录创建、编码和兼容格式解析全部放到 `infrastructure/persistence`。

#### 步骤 4.3：确定唯一设备控制边界

将根目录 `instrument_control.py` 中仍有生产调用的能力迁移到 `instrument/`，建议最终形成：

```text
instrument/
    ports.py
    session.py
    safety.py
    power_control.py
    drivers/
    transport/
    simulation.py
```

`session.py` 或 `safety.py` 必须集中表达以下语义：

- RF 关闭。
- 电源按 `Drain -> Gate` 顺序关闭。
- 普通停止、紧急停止和异常清理的区别。
- VISA resource 和 ResourceManager 的释放。
- 外部注入资源的所有权边界。
- 重复连接和重新连接行为。

#### 步骤 4.4：迁移生产导入

按以下顺序迁移：

1. `application/` 内部导入。
2. `presentation/qt/` 内部导入。
3. `launcher.py` 和硬件 smoke 入口。
4. 测试导入。
5. 历史脚本和兼容入口。

每迁移一个模块，先运行对应测试，再继续下一个模块。新代码不得为了方便继续导入根目录实现模块。

实施状态：已完成（2026-10-10）。结果解析迁入 `domain/result_reading.py`，文件 JSON 读写留在 `infrastructure/persistence/json_result_repository.py`；应用装配和 Qt 展示导入正式模块，根目录 `result_reading.py` 保留旧 API 兼容转发。生产导入扫描、兼容 API 测试、架构测试、完整离线测试、启动器检查、配置校验及编译检查通过。测试仍有意保留对 `result_storage` 兼容层的覆盖。

#### 步骤 4.5：把根目录模块变成兼容层

兼容层只允许包含重新导出，例如：

```python
from infrastructure.persistence.json_result_repository import JsonResultRepository

__all__ = ["JsonResultRepository"]
```

兼容层不得包含第二套业务实现、全局设备状态或隐式初始化。

实施状态：已完成（2026-10-10）。配置模型、配置规则、JSON 配置读取、旧配置转换、路径服务和日志服务已迁入正式目录；根目录对应入口仅保留显式 API 转发。领域配置模块不依赖基础设施，文件读取和文件级校验由 `infrastructure/config` 与 `infrastructure/persistence` 负责。设备控制、结果解析和结果持久化兼容入口已沿用此前收口结果。测量服务、纯计算、历史测量入口、可视化和连接图仍按模块登记为后续迁移范围，不在本步骤宣称已完成。架构门禁、兼容 API 测试、完整离线测试、启动器检查、配置校验和编译检查通过。

### 5.3 第四期验收标准

- 新生产代码不再新增对根目录历史实现模块的导入。
- `application` 不导入 Qt、VISA、SCPI 或具体 driver。
- `presentation/qt` 不直接读写结果文件，不直接拼接业务输出路径。
- `infrastructure/persistence` 成为结果持久化的唯一实现位置。
- `instrument/` 成为设备控制的唯一正式实现位置。
- 根目录兼容模块只保留转发代码。
- 现有离线测试、架构测试、配置检查和编译检查全部通过。

## 6. 第五期：运行时模型收敛

### 6.1 目标

减少 `controller`、`worker`、`service` 和页面之间重复保存状态的问题，让三类测量使用统一的请求、状态和生命周期协议。

### 6.2 步骤

#### 步骤 5.1：统一测量请求和结果 DTO

建议将请求和结果集中到：

```text
application/dto/
    measurement_requests.py
    measurement_results.py
```

请求对象应明确包含测量类型、配置快照、频率范围、功率范围、运行标识和安全选项。结果对象应包含测量类型、状态、数据引用、摘要、错误信息和清理结果。

#### 步骤 5.2：统一生命周期状态

建议至少统一以下状态：

```text
Idle
Preparing
Running
Stopping
Completed
Failed
Cancelled
EmergencyStopped
```

状态转换应由 application 层负责，页面只展示状态，worker 只报告执行事件。

实施状态：已完成（2026-10-10）。统一生命周期状态和纯 Python 状态机已迁入
`application/dto` 与 `application/lifecycle`；Qt controller 仅协调 worker 事件并转发
状态快照，普通停止、取消和紧急停止保持独立语义。历史 service 的 `waiting`、`finished`
和 `stopped` 状态仅由 `application/dto/legacy_result_adapter.py` 转换，规范结果 DTO
不再接受旧状态字符串。紧急停止意图优先于 worker 的普通 stopped 或 finished 事件。
新增生命周期、终态优先级和兼容转换测试；完整离线测试、启动器检查、配置校验和编译检查通过。

#### 步骤 5.3：明确停止、取消和紧急停止

- 停止：允许当前安全边界内的动作完成，再清理资源。
- 取消：用户不再需要当前任务，应用应尽快结束并记录取消结果。
- 紧急停止：优先执行设备安全动作，不能等待普通测量流程完成。

三者必须在请求、事件、日志、结果和测试中保持一致命名。

#### 步骤 5.4：明确资源所有权

每个设备资源都应明确由谁创建、由谁关闭、异常时由谁兜底。外部注入的 `measurement_port` 不得由 controller 越权关闭；由应用创建的会话必须在完成、异常、取消和紧急停止后释放。

#### 步骤 5.5：压缩 controller 职责

`MeasurementController` 只负责：

- 接收页面请求。
- 启动对应 application 用例。
- 转发状态和结果。
- 协调 worker 生命周期。
- 防止同类任务重复启动。

它不应负责计算、配置文件读取、结果 JSON 写入、VISA 命令拼接或具体电源清理。

### 6.3 第五期验收标准

- 三类测量共享统一的请求、结果和生命周期协议。
- 正常完成、停止、取消、异常和紧急停止都有明确状态。
- 同一状态只有一个权威来源。
- 资源所有权和清理责任有测试覆盖。
- controller 不包含测量计算、文件读写或具体设备控制逻辑。

## 7. 第六期：配置与持久化收口

### 7.1 目标

让 GUI 和测量用例不再直接读取 JSON、拼接路径或调用底层存储函数，统一配置模型、校验、转换和结果归档。

### 7.2 步骤

#### 步骤 6.1：分离配置对象和配置文件

配置对象属于业务模型，JSON 属于外部格式。推荐形成以下边界：

```text
domain/configuration/
    models.py
    rules.py

application/ports/
    config_repository.py

infrastructure/config/
    json_config_repository.py
    legacy_conversion.py
```

旧配置格式转换只能存在一个实现位置，不得在 GUI、launcher 和测量服务中重复转换。

#### 步骤 6.2：统一结果模型

结果模型应统一表达：

- 测量类型。
- 配置快照。
- 设备身份摘要。
- 原始数据引用。
- 计算摘要。
- 测量状态。
- 错误和清理记录。
- 创建时间和运行标识。

原始现场敏感数据必须遵守现有本地保存规则，不进入版本库。

#### 步骤 6.3：统一路径服务

业务代码不应直接使用 `PROJECT_ROOT`、`TEST_RESULTS_DIR` 等全局路径常量。应通过文件系统端口或路径服务获取：

- 配置文件位置。
- 结果目录。
- 日志目录。
- 图片和资源目录。
- 临时目录。

这样测试可以注入临时目录，生产环境也可以更换数据根目录。

#### 步骤 6.4：让 GUI 只依赖接口

配置页、可视化页和导出页不应直接读取 JSON 或调用根目录存储函数。它们只使用 application 服务或 ports，并通过 DTO 接收数据。

### 7.3 第六期验收标准

- 配置模型、配置读取、配置校验和旧格式转换职责分离。
- 结果写入和读取使用统一模型契约。
- GUI 不直接访问 JSON、VISA 或结果存储实现。
- 测试可以注入临时路径和内存仓储。
- 现场敏感数据不会因测试或默认配置进入版本库。

## 8. 第七期：兼容层退出

### 8.1 目标

在确认内部调用方全部迁移后，删除无价值的历史实现和重复入口，保留有限、明确、可追踪的外部兼容接口。

### 8.2 步骤

1. 使用静态搜索统计每个兼容模块的调用方。
2. 将生产代码和测试全部迁移到正式包路径。
3. 为仍需保留的兼容模块增加弃用说明和迁移目标。
4. 兼容模块只保留公开符号转发。
5. 删除无调用方的旧实现。
6. 删除只用于阶段验收、且已被长期架构测试取代的重复测试。
7. 更新 README、启动帮助、开发文档和现场操作文档。

### 8.3 兼容层删除条件

只有同时满足以下条件，才允许删除一个历史模块：

- 生产代码没有导入。
- 测试没有导入。
- 已知外部脚本有替代入口，或明确接受破坏性变更。
- 目标模块的行为测试覆盖完整。
- 文档和启动入口已经更新。
- 删除后完整离线验收通过。

## 9. 第八期：运行方式与交付收敛

### 9.1 目标

统一开发、测试、诊断和现场交付方式，减少“不同入口实际执行不同路径”的风险。

### 9.2 步骤

- 统一 `launcher.py`、测试脚本和硬件 smoke 的解释器来源。
- 保持 `.env` 中 `AUTO_TEST_PYTHON` 为项目命令的唯一解释器配置。
- 统一 `--check`、`--validate-config` 和 Hardware smoke 的诊断输出。
- 明确离线仿真、最小动作 smoke 和真实现场测量的边界。
- 为每类测量保留可脱敏的结果、配置快照和清理证据格式。
- 将现场报告、设备身份和回滚决定纳入独立归档流程，不提交敏感资料。

### 9.3 第八期验收标准

- 开发、CI 和现场入口使用明确且可验证的解释器。
- 只读检查不会初始化真实设备或产生危险动作。
- Hardware smoke 具备独立安全门禁，不会在普通测试中误触发。
- 现场证据可以关联到配置版本、代码版本和运行标识。

## 10. 测试和架构门禁

### 10.1 测试目录调整方向

当前按重构阶段命名的测试可以保留作历史记录，但新测试应逐步按行为和边界组织：

```text

        application/
        instrument/
        infrastructure/
    integration/
        persistence/

### 10.2 必须长期保留的架构门禁

- `presentation` 不得导入 VISA、SCPI、具体 driver 或结果存储实现。
- `application` 不得导入 Qt。
- `domain` 不得导入基础设施、Qt 或设备模块。
- `infrastructure` 可以实现 ports，但不得让 domain 反向依赖它。
- 新生产代码不得导入根目录兼容模块。
- 兼容模块不得包含第二套业务实现。

- 正常、停止、紧急停止、异常和重新连接路径都必须验证清理结果。

### 10.3 每个阶段的固定验证命令

```

如果修改了导入、目录或发布入口，还应执行项目已有的编译检查和架构静态测试。真实 Hardware smoke 只能在现场前置条件满足时执行，不得用离线测试替代现场验收。

## 12. 当前推荐执行清单

建议下一次重构按以下三个小任务开始，每个任务独立验证：

### 任务 A：统一结果持久化

4. 迁移 application、GUI 和测试导入。

### 任务 B：统一配置边界

## 13. 暂不处理的事项

在上述边界收口完成前，暂不优先处理以下事项：

- 再次大规模拆分 `MainWindow`。
- 为每个小文件继续增加抽象层。
- 一次性引入 `src/` 布局并同时改变打包和测试方式。
- 在没有现场授权和安全窗口时重写设备控制流程。

## 14. 完成定义

当所有计划阶段完成时，项目应满足：

- 生产代码有唯一且可解释的依赖方向。
- 每项职责只有一个正式实现位置。
- 根目录历史模块已经删除或明确降级为兼容层。
- GUI、application、domain、infrastructure 和 instrument 的边界有自动化门禁。
- 配置、结果、日志、路径和设备会话都有明确的资源所有权。
- 三类测量共享统一的请求、状态、清理和结果契约。
- 离线测试和应用检查持续通过。
- 真实 Hardware smoke 按独立验收文档完成，并具备现场证据。
- 后续新增功能能够直接进入正式包路径，不再创建新的根目录历史模块。

本文档是后续重构的路线指南；具体现场设备动作、安全限制和真实验收标准，以《重构收尾与真实HardwareSmoke验收》为准。
