# 异常分类与静态质量门禁

本文是**异常分类与静态质量门禁**的说明文档。
异常分类的代码边界是 `application/errors.py`，静态门禁的可执行形式是
`tests/test_static_quality_gate.py`，异常归类与收窄的契约测试是 `tests/test_exception_taxonomy.py`。

## 1. 六类异常

| 类别 | 基类 | 判定标准 | 典型抛出点 |
| --- | --- | --- | --- |
| 配置 | `ConfigurationError` | 配置、校准输入或运行契约不满足正式结构 | `AmplifierCalibrationError`、`AmplifierInputError`（主功放正式输入模型）、`StageInputUnavailable`、`RunNotResumable`、`ConfigurationAuthoringError`、`ConfigBackfillError` |
| 连接 | `DeviceConnectionError` | 无法建立设备连接 | `instrument.measurement_factory` 打开 VISA 资源失败 |
| 协议 | `ProtocolError` | 命令/响应层失败，含超时 | `ScpiTransportError`、`ScpiTransportTimeoutError` |
| 设备能力 | `DeviceCapabilityError` | 注入的设备对象缺少测量所需能力，或设备不满足本次测量的前提（型号不符、初始状态不安全） | `InstrumentCapabilityError`、装配时的型号/初始输出校验 |
| 测量 | `MeasurementError` | 测量动作失败或结果不可解释 | `SpectrumAnalyzerMeasurementError`、`PowerOnFlowError` |
| 清理 | `CleanupError` | 安全清理失败，按动作聚合 | `SafetyCleanupError`、`SafetyShutdownError`、`InstrumentSafetyError`、`InstrumentSessionError`、`PowerControlError`、`PowerOffFlowError` |

`AutoTestError` 是根异常，本身不带具体类别。分类是**叠加**而不是替换：设备、测量和清理
失败仍然同时是 `RuntimeError`，配置失败仍然同时是 `ValueError`，所以既有的
`except RuntimeError` / `except ValueError` 处理器继续生效。

`StageInputUnavailable` 归类为配置失败，同时显式保留 `RuntimeError` 基类：分类之前它就是
`RuntimeError`，这两个内置基类都必须继续成立。聚合异常（`InstrumentSafetyError`、
`InstrumentSessionError`、`PowerOffFlowError`、`PowerOnFlowError`、`PowerControlError`）
在分类之前以 `(message, errors)` 接收 `list[BaseException]`，这个构造形式由
`normalize_failures()` 继续支持：原始异常与纯文本说明都会转成 `FailureRecord`（动作名留空），
不会因为改造而丢弃失败项。

分类模块位于 `application`，因为它是跨层契约而不是某一层的实现：`instrument` 作为适配器
依赖 `application` 的端口与分类（与既有的 `instrument.flow.cleanup` →
`application.ports.measurement_session` 方向一致），`infrastructure`、`presentation`、`app`
同理；`application` 自己不导入 `instrument` 的具体 flow。

领域层的值对象错误（`domain.measurement.values.MeasurementValueError` /
`MeasurementUnitError`）不属于本分类：领域层不能依赖上层模块。应用层在边界处把它们翻译
成 `MeasurementError` 或 `ConfigurationError`（见 `validate_amplifier_calibration_inputs`）。

### 1.1 失败动作记录

`FailureRecord(action, error)` 记录“哪个动作失败、原始异常是什么”。`AutoTestError` 因此
统一提供：

- `failures`：失败动作元组，顺序即动作顺序；
- `errors`：原始异常元组（文本记录时为说明字符串）；
- `actions`：失败动作名元组；
- `to_dict()`：可直接写入运行记录/现场报告的纯文档（`category`、`message`、`failures`）。

安全清理是唯一允许“继续尝试后续动作”的类别。RF、电源、连接三个动作分别记录为
`rf_output`、`power_supplies`、`resources`；供电流程记录到通道级
（`drain.output_off`、`gate.output_on` 等）。多故障一次聚合上报，不会只留下最后一条消息。

资源释放策略（与步骤 8 的现场决定一致）：

- RF 关闭失败 ⇒ 保留信号源连接，现场可以重试关闭 RF；
- 电源关闭失败 ⇒ 仍释放连接（异常状态的 VISA 会话不能再被后续安全动作依赖）；
- 借用的端口（`release_resources=False` / `close_resource=False`）既不关闭也不谎报成功，
  记录里标记为 `skipped`。

`CleanupRecord` 因此新增 `failures` 字段，`to_dict()` 同时输出 `errors`（文本）与
`failures`（动作 + 说明）。`SafetyCleanupError` 的消息与 `errors` 覆盖记录里的全部失败，
只有文本消息的旧记录也不会丢项。记录的不变式是“有 `failures` 就必须算失败”：
`__post_init__` 用失败说明补齐空 `errors`，`succeeded` 同时检查两者，避免出现
“记录了失败动作却报告成功”的记录。

## 2. 宽泛捕获的处理原则

1. **不允许通过捕获异常继续执行硬件动作**：非清理类别一旦抛出就是动作链的终点。
2. **清理聚合**：清理动作无论抛出什么异常都要执行完，最后一次性上报。
3. **边界翻译**：第三方库（pyvisa）异常在适配器内翻译成本项目异常并保留
   `from` 链：`_open_resource_manager()` / `_open_device()` 把 `ResourceManager` 创建失败与
   VISA 打开失败翻译成 `DeviceConnectionError`，`_query()` 把已连接设备的查询失败翻译成
   `ProtocolError`，型号不符与初始输出未关闭翻译成 `DeviceCapabilityError`。
4. **尽力记录**：日志、阶段状态、事件、遥测失败不得掩盖原始返回值或原始异常。

本步骤实际收窄或删除的宽泛捕获：

| 位置 | 处理 |
| --- | --- |
| `instrument/measurement_adapter.set_power` | 删除 `except Exception: raise` 空转（行为不变，去掉一处无效宽泛捕获） |
| `instrument/session.close` | 只翻译 `InstrumentSafetyError`；其他异常原样上抛 |
| `instrument/drivers/signal_generator.close` | 只翻译 `ScpiTransportError`，并继续抛出 `ScpiTransportError`（协议分类）；其他异常原样上抛 |
| `instrument/measurement_factory._create_hardware_measurement_port` | 资源释放的 `except Exception: pass` 改为记录日志；资源管理器/VISA 打开失败翻译成 `DeviceConnectionError`，身份查询失败翻译成 `ProtocolError`，型号与初始输出校验翻译成 `DeviceCapabilityError` |
| `instrument/measurement_factory._ConfiguredPowerSupply.close` | 聚合为 `CleanupError`，按电源名逐项记录 |
| `instrument/flow/cleanup.cleanup_measurement` | 聚合为 `InstrumentSafetyError` 并记录动作名；RF 未关闭时不再释放连接 |

## 3. 静态门禁规则

| 规则 | 范围 | 判定 |
| --- | --- | --- |
| 裸 `except` | 正式运行时包 + `analysis` + 根目录入口脚本 | 一处都不允许 |
| 静默宽泛捕获 | 同上 | `except Exception/BaseException` 的处理器不得只有 `pass`/`...`/`continue` |
| 宽泛捕获基线 | 同上 | 按“文件 + 作用域 + 序号”冻结站点身份，必须与代码严格相等（只减不增） |
| 生产 `print` | `app`、`application`、`domain`、`infrastructure`、`instrument`、`presentation` | 一处都不允许；入口脚本与分析报告有自己的输出契约 |
| 旧模块导入 | 正式运行时包 + 根目录入口脚本 | 不得导入步骤 1 登记的旧模块；第一方导入路径必须真实存在 |
| 动态设备路由 | 正式运行时包 | 不得按运行时名字访问设备能力、不得 `getattr(<设备>, <名字>)(...)`、不得保存后调用、不得 `setattr(<设备>, ...)` |

`DPD_auto_test/`、`hardware/`、`format_convert/` 与 `tools/` 不属于正式测量链路，
不参与本门禁；它们由各自的 smoke/工具契约约束。动态设备路由的装配级断言仍在
`tests/test_instrument_routing.py`（步骤 9），本门禁把它扩展到服务与适配器。

宽泛捕获基线共 31 个文件、102 个站点，全部属于第 2 节的四类边界之一；新增一处必须先说明它
属于哪类边界，而不是直接扩大基线。收窄或删除后必须同步收缩基线（基线严格相等）。

站点身份形如 `SafetyCleanupAdapter.cleanup#2`（模块级作用域写 `<module>`）：它不随行号移动
变化，因此整文件挪动不会让基线失效；而“删掉一处、再到别的函数里加一处”处数虽然不变，站点
身份却不同，门禁仍然失败。这一点由 `test_site_identity_tracks_the_enclosing_scope` 守住。

动态设备路由的唯一豁免是 `DYNAMIC_ROUTING_BOUNDARIES` 中登记的按名字“探测”边界：
`instrument/ports.py::require_measurement_capabilities` 需要按名字检查能力并在缺失时抛出
`InstrumentCapabilityError`（构造阶段失败，而不是硬件动作中途 `AttributeError`）。核对
名字的字面量探测（如 `getattr(instrument_control, "signal_gen", None) is not None`）仍然允许，
因为它不转发调用；集合由 `test_routing_boundaries_stay_minimal` 固定，新增条目必须在评审中
说明理由。

## 4. 验证命令

```powershell
& $env:AUTO_TEST_PYTHON -m unittest tests.test_static_quality_gate tests.test_exception_taxonomy -v
```

`tools/run_tests.py` 在编译检查与依赖核对之后执行门禁：`unit`/`simulation` 等窄范围运行会先
执行门禁；默认 `offline` 全量发现已包含这些测试，因此不重复扫描仓库，失败即终止；
发布清单的 `verification.static_quality` 也指向它（`verification_commands()` 是唯一来源）。

完整验证执行全量 unittest、`launcher.py --check`、
`launcher.py --validate-config` 和 `tools/compile_check.py`。
