# 技术债分阶段重构计划

## 目标与范围

依据项目技术债审查结果，按数据可靠性、运行契约收敛、职责解耦、代码可维护性和仓库卫生分阶段推进。用户明确不要求向后兼容，因此计划允许移除旧入口、旧数据格式转换和兼容分支；历史运行数据只在仍属于正式产品能力时保留读取支持，不为已退役的调用接口继续维护代码。

每一步应保持范围窄、可独立验证并单独提交。除文档和仓库清理步骤外，完成代码步骤后运行对应测试及仓库门禁；涉及 `application`、`domain`、`infrastructure`、`instrument`、`app`、`launcher.py` 或 `tools/` 时按 `AGENTS.md` 运行全量离线测试。纯 Qt 表现层拆分使用 `tools/run_tests.py --layer ui`；存在真实服务接线时使用 `--layer integration`。

## 分阶段执行策略与技术决定

### 阶段一：可靠写入

#### 步骤 1：固化配置写入原子性

- **执行策略：** 检查 `JsonConfigurationAdapter.save()` 及其调用路径；将配置序列化和写入改为“同目录唯一临时文件、flush/fsync、原子替换”，临时文件清理不得覆盖原始写入异常。优先复用 `infrastructure.filesystem.atomic_json`，避免再造第二种原子写入实现。同一步骤内补齐失败路径测试：序列化失败、fsync 失败、编码器失败、目标替换失败、目标目录创建失败、临时文件清理失败和非映射载荷，全部使用隔离临时目录加故障注入，不依赖真实配置文件。
- **技术决定：** 配置文件在序列化或替换失败时保留原文件；不提供“先截断再尽力恢复”的行为。沿用项目现有 JSON 缩进、UTF-8 和非 ASCII 字符策略，避免无关格式变更。共用原语 `write_json_atomic()` 的失败语义同步收紧为“原始异常优先”：清理临时文件是尽力动作，任何普通 `Exception` 只记录警告（不捕获 `BaseException`），不得顶替真正的写入/替换异常。失败测试只验证可观察契约（旧文件未损坏、没有半份新配置、异常可见、清理成功时无临时残留、清理失败时仍报原始原因），不绑定临时文件的随机命名格式或内部实现步骤。
- **验收：** 正常保存可被现有读取器读取；序列化、fsync、编码、替换或目录创建失败后原文件字节保持不变；清理成功时无遗留临时文件，清理失败时调用方拿到的仍是原始异常且日志记录临时文件路径；首次保存失败时目标文件不会被创建；现有保存调用方无需改变其用户可见行为。
- **验证：** 针对配置写入适配器的正常与失败路径测试；变更涉及基础设施，运行全量离线测试。

#### 步骤 3：明确配置适配器的唯一写入入口

- **执行策略：** 搜索配置 JSON 的所有写入点，将应用配置保存统一委托到配置仓储/原子写入函数；区分配置编辑与运行快照创建，运行快照仍由运行仓储负责。
- **技术决定：** 配置读取/校验与持久化的边界清晰分开；GUI 适配器不直接管理文件打开模式。暂不合并不同用途的 JSON 仓储。
- **验收：** 生产代码只有一个正式的用户配置写入路径；快照写入仍保持独立；相关边界测试通过。
- **验证：** 全量离线测试。

### 阶段二：收敛运行契约

#### 步骤 4：盘点无运行契约调用方

- **执行策略：** 搜索 `PreparedRun`、`run_repository is None`、`run_contract=False`、调用方直接传入配置路径及历史测试替身；建立生产调用点和仅测试调用点清单，先移除或迁移调用方，不同时修改底层所有分支。
- **技术决定：** 以“每次测量必须有运行目录、manifest 和冻结快照”为唯一生产契约。测试可以使用明确的 fake 仓储实现该契约，不以无契约对象作为捷径。
- **验收：** 清单中每个生产调用点均能提供正式运行上下文；无契约路径只剩明确待移除项。
- **验证：** 运行调用点相关单测及静态边界门禁。

#### 步骤 5：将测量装配入口收敛为 PreparedRun

- **执行策略：** 调整 `create_cable_loss_measurement()`、`create_driver_mapping_measurement()`、`create_amplifier_measurement()` 的调用边界，使测量装配只接受已创建/加载的正式 `PreparedRun`，并由其解析冻结硬件配置路径。逐类迁移 GUI worker 和应用组合根调用点。
- **技术决定：** 不再以 `config_path` 作为测量输入权威来源；运行目录快照是唯一硬件配置权威。显式注入的 measurement port 继续用于测试和受控装配，但不绕过运行契约校验。
- **验收：** 缺少或损坏运行快照时，在打开设备前失败；三个测量入口的运行标识、配置和硬件快照来自同一运行。
- **验证：** 运行测量工厂、运行服务及相关 UI/集成测试；按实际改动面执行全量测试或 integration 层。

#### 步骤 6：删除无运行契约的前置校验分支

- **执行策略：** 在步骤 5 调用方全部迁移后，删除 `run_repository is None` 的跳过逻辑、旧配置路径回退、旧输入显式性检查和仅为无契约快照保留的结构探测。保留对正式运行快照完整性、manifest 哈希和阶段输入的校验。
- **技术决定：** 运行契约缺失视为调用错误，不做降级、不猜测输入、不连接硬件。删除后不提供隐藏的兼容工厂或迁移开关。
- **验收：** 生产代码无旧兼容快照分支；无契约测量调用在任何仪器连接前失败；正式流程行为保持一致。
- **验证：** 全量离线测试、`launcher.py --check`、`launcher.py --validate-config`。

### 阶段三：解除主功放旧模型耦合

#### 步骤 7：定义主功放用例的正式输入模型

- **执行策略：** 根据当前用例真实使用字段设计一组类型明确的输入 DTO/领域输入对象，覆盖频率、功率扫描参数、压缩点、衰减器、DUT 限制、驱动模式和供电通道映射；明确构造时校验规则。
- **技术决定：** 新模型表达业务语义，不复刻旧字典键名；仪器地址和传输对象仍由 instrument 端口/运行上下文提供，不塞进测试参数 DTO。
- **验收：** 字段来源、单位、必填性和非法值处理在模型定义与文档中明确；用例不需要 `Mapping[str, Any]` 作为正式配置类型。
- **验证：** DTO/模型单测及配置领域测试；完成后运行全量离线测试。

#### 步骤 8：让主功放用例消费正式输入模型

- **执行策略：** 将正式 DTO 从应用服务边界传入 `AmplifierMeasurementUseCase`，逐段替换字典键访问；先迁移构造和预检，再迁移测量执行和结果生成。
- **技术决定：** 只有一个正式输入表示；输入验证在应用边界完成，设备相关能力校验留在 instrument 层。测量结果 DTO 不随本步骤改变。
- **验收：** 主功放测量主路径不再读取历史字典结构；合法输入结果与既有仿真基线一致，非法输入在设备动作前失败。
- **验证：** 主功放用例、运行阶段、测量循环和仿真流程测试；全量离线测试。

#### 步骤 9：删除旧字典配置转换器

- **执行策略：** 确认步骤 8 后没有生产调用点，删除 `_service_config()`、`_run_configuration_to_service_config()` 及只服务于它们的转换逻辑；清理对应旧格式测试。
- **技术决定：** 领域拆分配置不再重建旧服务配置作为中间格式；历史运行若需查看，使用已冻结配置快照的正式解析流程，不复用测量转换器。
- **验收：** 生产代码无主功放旧配置字典转换器；现有正式运行快照仍可解析。
- **验证：** 全量离线测试。

#### 步骤 10：删除旧通道名解析分支

- **执行策略：** 检查持久化的历史快照是否仍需读取裸 `CH1`/`CH2`。若历史快照查看属于支持范围，将迁移逻辑限制在明确的数据迁移工具/只读历史解析边界；否则直接删除 `_split_channel_token()` 中的裸通道回退和 `legacy_power_supply()` 依赖。
- **技术决定：** 新运行映射只接受 `supply_id/channel` 显式路由，不按单电源假设或名称猜测设备。是否保留历史数据迁移须以已存档样本和产品要求为依据，不在运行装配路径长期兼容。
- **验收：** 新运行不可能生成无供电设备标识的通道引用；格式错误的正式映射明确失败；如保留迁移，迁移工具输入输出契约单独测试。
- **验证：** 电源映射、配置 schema、仿真测量和全量离线测试。

### 阶段四：清理启动器兼容面

#### 步骤 11：简化启动器公开入口

- **执行策略：** 检索仓内、部署脚本与开发入口对 `get_gui_version()`、`launch_gui_version()` 的实际调用；将内部 GUI 启动流程改为无版本选择的单一入口，并先迁移仓内调用方。
- **技术决定：** GUI 版本检测不属于启动策略；启动器只负责环境校验、命令路由和启动唯一 GUI。保留必要的静默输出控制，但不保留无消费者的旧位置参数。
- **验收：** 仓内无旧函数签名依赖；依赖错误和 GUI 启动错误的退出码/消息契约不变。
- **验证：** 启动器单测、静态门禁、`launcher.py --check`。

#### 步骤 12：删除旧启动参数及其测试

- **执行策略：** 删除 `--gui` 等明确标记为旧兼容的参数及分支；更新 README、帮助文本、启动器测试和 IDE/脚本说明。先确认发布脚本与现场操作文档无引用。
- **技术决定：** 未知参数遵循 argparse 标准错误退出，不做忽略或静默兼容；正式命令保持 `launcher.py` 单入口。
- **验收：** `--help` 不展示退役参数；传入旧参数返回参数错误；文档只记录正式命令。
- **验证：** 启动器测试、`launcher.py --check`、`launcher.py --validate-config`。

### 阶段五：控制模块规模

#### 步骤 13：拆分配置页面的控件构建职责

- **执行策略：** 从 `presentation/qt/config_page.py` 抽取一个内聚的控件构建/布局模块，优先迁移一个稳定分区（如仪器或供电标签页）；保持 `ConfigPage` 对外入口和信号契约不变。
- **技术决定：** 新模块仍属于 presentation/qt，不承担 schema 解释或文件 I/O；不为了拆分创建通用 UI 框架。
- **验收：** 页面模块只负责组合与交互协调；抽取模块具有单一职责，配置页现有可见行为不变。
- **验证：** `tools/run_tests.py --layer ui`。

#### 步骤 14：拆分配置表单状态读写职责

- **执行策略：** 将 `config_form_state.py` 的读取、应用、校验/规范化中至少一个边界清晰的职责拆到独立模块；每次只迁移一类字段或表单区块，删除原文件中的重复实现。
- **技术决定：** 状态快照保持显式、可测试，不引入反射式控件发现；正式配置 schema 的构造仍由 `configuration_authoring` 负责。
- **验收：** 每个职责有明确输入输出；UI 测试无需依赖其他表单区块的 Qt 状态即可测试其行为。
- **验证：** `tools/run_tests.py --layer ui`。

#### 步骤 15：缩小仪器装配模块职责

- **执行策略：** 对 `instrument/measurement_factory.py` 按资源解析、设备构造、会话清理等现有职责做调用图盘点；抽出一个稳定且可独立测试的职责，维持现有公开工厂入口转调新模块，之后再逐步移除转发层。
- **技术决定：** instrument 层负责设备和会话；配置 schema 解释留在配置/应用边界。资源所有权及失败清理顺序必须保持明确，不以拆文件改变安全行为。
- **验收：** 单个模块不再同时承担多种装配职责；资源释放和错误分类测试通过。
- **验证：** 仪器工厂、路由、安全流程测试及全量离线测试。

#### 步骤 16：拆分设备发现集成测试模块

- **执行策略：** 按扫描生命周期、身份解析/注册、UI 应用绑定等测试行为拆分 `tests/integration/test_device_discovery_panel.py`；提取少量共享 fixture 到局部辅助模块，避免跨测试目录共享隐式状态。
- **技术决定：** 测试按行为与边界分组，不按生产源码一一镜像；集成测试继续验证真实后端接线，纯 widget 行为放入 `tests/ui`。
- **验收：** 单个测试文件范围聚焦、测试名仍表达行为；拆分前后测试数量及断言覆盖不回退。
- **验证：** `tools/run_tests.py --layer integration`。

### 阶段六：仓库内容与文档收尾

#### 步骤 17：盘点并清理仓库中的生成型基线数据

- **执行策略：** 列出 `baseline/collected/` 下文件的用途、来源、是否被测试/发布工具读取及是否存在可再生成来源；先从版本控制移除确认可再生成的结果和报告，再调整基线收集工具/`.gitignore`，避免新产物重新入库。
- **技术决定：** 不删除唯一现场证据或不可再生成数据；必要基线保留小型、脱敏、可追溯样本。大体积运行产物存放在受控归档而非源代码历史。
- **验收：** 仓库内保留数据有用途说明和生成/来源说明；普通运行不会污染 git 工作区。
- **验证：** `git ls-files` 检查目标目录；运行基线相关测试和全量离线测试。

#### 步骤 18：明确大体积静态资源的版本管理策略

- **执行策略：** 汇总 `assets/` 与 `DPD_auto_test/` 的大文件，标注运行时必需、开发素材、实验 Notebook 和可替代资源；对必需 UI 图片进行无损/适度压缩评估，对实验资产决定保留、拆分仓库或启用 Git LFS。
- **技术决定：** 用户界面运行必需的资源必须随发布包可获得；不为减少仓库体积而引入不稳定的运行时网络下载。Notebook 输出清理与源代码清理分开提交。
- **验收：** 每项大资源有保留理由或迁移目标；图片压缩后尺寸、透明度与 UI 显示通过检查；常规安装不依赖开发 Notebook。
- **验证：** 检查资源引用、打包/启动检查及相关 UI 测试。

#### 步骤 19：更新技术债与架构文档

- **执行策略：** 根据实际完成的重构更新 README、正式 API 清单和本计划；移除已不存在的旧兼容行为说明，记录剩余历史数据迁移边界、架构决策和验证命令。未实施的步骤保持未勾选，并注明尚未解决原因。
- **技术决定：** 文档描述当前代码事实，不以计划替代实现；不保留过期的步骤编号、兼容路径或已删除入口说明。
- **验收：** 文档命令可执行、模块路径与代码一致；仓库搜索不再出现已退役接口作为生产使用指引。
- **验证：** 文档/路径检索，`launcher.py --check`、`launcher.py --validate-config` 和全量离线测试。

## 整体完成标准

1. 配置保存失败不会破坏已有配置，失败可见且无临时文件残留。
2. 每次正式测量均绑定同一 `PreparedRun`、运行快照和 manifest；不存在无契约硬件装配回退。
3. 主功放测量用例不依赖旧配置字典或隐式单电源通道推断。
4. 已确认退役的启动参数和接口不再存在；所有正式入口及文档一致。
5. 大模块拆分后保持架构边界与安全清理行为；按改动面通过 UI/integration 或全量测试。
6. 生成型数据和大资源的版本管理规则清晰，运行产物不再无意进入源代码提交。
