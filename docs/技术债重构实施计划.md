# 技术债重构实施计划

## 1. 目标与原则

本计划针对当前项目中仍存在的运行契约分叉、迁移期兼容接口、过时文档和结果 DTO 过重问题。

本次重构**不考虑向后兼容**：

- 只保留正式的 `runs/<run_id>/` 运行契约；
- 不保留旧入口、旧别名、旧快照格式或旧参数调用方式；
- 旧数据仅作为离线历史文件保留，不再由生产代码自动发现、转换或写回；
- 每个步骤只处理一个小范围职责，并在步骤结束时执行针对性测试。

当前基线：离线全量测试已通过（1446 项通过，3 项因环境不支持符号链接而跳过）；真实 Hardware Smoke 和三类现场测量仍需单独验收，不纳入本计划的离线重构步骤。

## 2. 总体阶段

| 阶段 | 目标 | 预计工作量 | 结果 |
|---|---|---:|---|
| 阶段一 | 删除旧运行快照路径，统一运行契约 | 0.5–1 天 | 所有生产测量都携带 manifest 和冻结配置 |
| 阶段二 | 删除迁移期 API 与兼容别名 | 0.5–1 天 | 生产接口只保留正式命名 |
| 阶段三 | 收敛结果持久化边界 | 1 天 | 结果写入链路只有一套正式实现 |
| 阶段四 | 拆分高负担模块、清理文档 | 1–2 天 | 降低模块复杂度，文档与实现一致 |
| 阶段五 | 回归验证与现场交接 | 0.5 天（不含现场测试） | 形成可复核的重构证据 |

## 阶段一：统一运行契约

### 步骤 1：盘点并冻结正式运行入口

**范围**

- `app/run_context.py`
- `application/run_service.py`
- `presentation/qt/application_coordinator.py`
- 相关运行创建、加载和 worker 测试

**执行策略**

1. 搜索所有 `prepare_run()`、`has_run_contract`、`run_repository is None` 和 `config_path` 调用点。
2. 确认 GUI、三类测量和历史查看均从 `create_prepared_run()` / `load_prepared_run()` 进入。
3. 将仍依赖旧路径的正式调用迁移到正式运行入口。
4. 新增一个静态门禁：生产测量入口不得调用 `prepare_run()`。

**技术决定**

- 正式运行必须具备 `run_id`、manifest、领域配置快照和硬件配置快照。
- `config_path` 只允许作为配置编辑来源，不允许作为测量或硬件连接回退路径。
- 不再为旧调用保留运行时分支；发现旧调用直接失败并要求使用正式入口。

**完成标准**

- 三类正式测量入口均只接受正式 `PreparedRun`。
- 运行契约测试覆盖配置修改、快照缺失、manifest 篡改和重新加载。
- 生产代码不再新增或调用 `prepare_run()`。

### 步骤 2：删除旧 `prepare_run()` 及旧快照写入

**范围**

- `app/run_context.py` 中的 `prepare_run()`
- `infrastructure/persistence/json_result_repository.py` 中的 `write_run_snapshot()`
- 旧快照相关测试和文档

**执行策略**

1. 先删除调用方和测试中的旧路径依赖。
2. 删除 `prepare_run()` 及 `test_plan_snapshot.json`、`run_mapping_snapshot.json`、`run_metadata.json` 写入链路。
3. 删除仅服务旧快照的参数、字段和辅助函数。
4. 运行运行契约、测量入口和架构依赖测试。

**技术决定**

- `RunRepository.create_run()` 是唯一的运行创建实现。
- 不再支持“无 manifest 的可运行快照”。
- 旧快照文件不做自动迁移；需要使用旧数据时由人工明确复制并登记到目标运行的 `inputs/`。

**完成标准**

- 生产代码不存在旧快照文件名和旧快照写入 API。
- 不存在 `run_repository is None` 的正式测量分支。
- 旧路径调用在导入或执行时明确失败。

## 阶段二：删除迁移期兼容接口

### 步骤 3：删除仪器与安全流程兼容别名

**范围**

- `instrument/measurement_adapter.py`
- `instrument/drivers/signal_generator.py`
- `hardware/power_supply_discovery.py`
- `instrument/action/spectrum_analyzer_port_adapter.py`
- 相关接口测试

**执行策略**

1. 建立正式名称到旧名称的调用清单。
2. 将生产代码和测试全部改为正式名称。
3. 删除 `safe_shutdown()`、旧 driver 类名、旧电源发现函数和 legacy port protocol 等纯转发接口。
4. 更新 `docs/正式API目录清单.md`，并运行公共 API 和架构依赖门禁。

**技术决定**

- 不保留运行时别名，也不通过 `getattr()`、字符串属性访问或再导出来维持旧接口。
- 安全清理只保留一个正式方法和一个正式调用约定。
- 若旧接口与新接口语义不同，优先保留新接口并修改调用方，不增加兼容适配层。

**完成标准**

- 生产包只暴露正式仪器端口、driver 和清理 API。
- 公共 API 清单、实现和测试中的名称一致。
- 静态门禁能够证明旧符号没有回归。

### 步骤 4：删除残留兼容字段与兼容分支

**范围**

- `application/measurements/*.py`
- `instrument/simulation.py`
- `infrastructure/persistence/json_encoder.py`
- `launcher.py` 中的旧参数或旧调用包装

**执行策略**

1. 删除以 `legacy`、`compatibility`、旧参数签名为条件的生产分支。
2. 仿真对象只保留正式故障注入和会话接口。
3. 启动器只保留正式命令行参数；删除旧 GUI 包装参数和旧函数调用形式。
4. 修改对应测试，使其验证正式失败行为，而不是验证兼容行为。

**技术决定**

- 失败必须通过正式异常、状态或错误结果表达，不通过旧字段或旧返回形状表达。
- 测试替身必须实现正式端口，不再模拟已经删除的旧对象。
- 结果 schema 只允许正式字段；拒绝旧字段是最终行为，而不是兼容入口。

**完成标准**

- 生产代码不再出现仅为兼容保留的公开字段、方法和参数。
- 仿真路径与真实仪器路径共享同一正式端口边界。
- 静态质量门禁和异常分类测试通过。

## 阶段三：收敛结果持久化

### 步骤 5：确定唯一结果写入边界

**范围**

- `infrastructure/persistence/json_result_repository.py`
- `infrastructure/persistence/result_repository.py`
- `infrastructure/persistence/run_repository.py`
- `application/ports/result_repository.py`

**执行策略**

1. 列出 `save_json_result()`、`save_measurement_result()`、`save_measurement_model()` 和仓储写入方法的调用图。
2. 区分“通用 JSON 原子写入原语”和“正式测量结果提交服务”。
3. 将正式测量结果写入统一到一个应用端口；底层只保留一个原子写入实现。
4. 删除没有正式调用方的旧包装函数和重复的 run ID 校验逻辑。

**技术决定**

- 结果文件和 canonical model 必须由同一次正式提交产生。
- 正式结果必须通过 DTO 校验后才能落盘。
- `result_type`、`measurement_type` 和 manifest 登记类型必须在一个边界内校验。
- 不再同时维护“旧结果文件”和“正式运行结果文件”。

**完成标准**

- 每类正式结果只有一个公开写入入口。
- 失败时不会留下半套结果或隐式创建无 manifest 目录。
- 结果仓储、运行仓储和应用端口的职责边界有测试覆盖。

### 步骤 6：统一运行目录内的结果路径语义

**范围**

- `domain/run/models.py`
- `application/run_stages.py`
- `infrastructure/persistence/run_repository.py`
- 历史查看与导出模块

**执行策略**

1. 统一 `inputs/`、`results/`、stage result 和 canonical model 的命名。
2. 修正常量名、注释和 manifest 字段，使“阶段输入”和“阶段结果”不再混用。
3. 对历史查询、导出和最新结果选择逻辑执行一次端到端检查。
4. 增加路径语义测试，防止阶段结果被登记到错误类别。

**技术决定**

- 测量结果统一归入 `results/`；校准输入才归入 `inputs/`。
- 历史查询只能读取 manifest 登记的正式结果。
- “最新结果”只能在正式运行目录中按运行时间和完整性选择，不扫描根目录旧文件。

**完成标准**

- 领域常量、manifest、仓储和 UI 展示使用同一套路径定义。
- 跨运行、未登记、篡改和类型错配文件均被拒绝。
- 历史查看和导出测试通过。

## 阶段四：降低模块复杂度并同步文档

### 步骤 7：拆分结果 DTO 模块

**范围**

- `application/dto/measurement_results.py`
- `analysis/` 结果消费模块
- DTO 与序列化测试

**执行策略**

1. 先保持对外导入路径不变，在内部按职责拆分：公共状态/元数据、线损结果、驱动映射结果、功放结果、解析入口。
2. 每次只移动一个结果类型，并立即运行对应 DTO 和报告测试。
3. 最后将公共解析与校验函数收敛到明确的序列化边界模块。
4. 通过 `application/dto/__init__.py` 暴露正式 API，避免调用方依赖内部文件。

**技术决定**

- DTO 只负责正式结果数据和序列化，不负责文件系统操作、报告生成或测量计算。
- 单位换算继续留在 `domain.measurement`，展示转换留在分析/展示层。
- 不引入旧格式适配器；旧字段继续明确拒绝。

**完成标准**

- 单个 DTO 模块职责清晰，新增结果类型不会修改所有结果逻辑。
- 三类结果的 schema、读取入口和展示接口保持明确。
- DTO、分析和导出测试全部通过。

### 步骤 8：清理过时文档和重构记录

**范围**

- `README.md`
- `docs/技术债分阶段重构计划.md`
- `docs/兼容层弃用与删除发布说明.md`
- `docs/测试运行目录与配置结果解耦重构指南.md`
- `infrastructure/persistence/run_repository.py` 等模块 docstring

**执行策略**

1. 删除将旧兼容路径描述为当前可用路径的文字。
2. 将已经完成的兼容层删除记录保留为历史证据，但明确标记为历史内容。
3. 更新正式入口、运行目录、结果路径和验证命令说明。
4. 增加文档一致性检查，禁止 README 和计划文档重新描述已删除入口。

**技术决定**

- 文档以当前正式架构为准，历史迁移记录不承担运行时契约说明。
- 只保留一份“当前操作口径”；重复的验收标准改为互相引用。
- 现场 Hardware Smoke 状态单独记录，不用离线测试结果替代现场结论。

**完成标准**

- 代码注释、README、API 清单和重构计划对入口及数据流的描述一致。
- 不再出现“当前仍写兼容快照”等失效说明。
- 文档门禁和编译检查通过。

## 阶段五：验证与交接

### 步骤 9：执行离线回归和发布证据整理

**执行策略**

按指定解释器顺序执行：

1. 全量单元测试；
2. 静态质量门禁和异常分类测试；
3. 依赖锁核对；
4. `launcher.py --check`；
5. `launcher.py --validate-config`；
6. `tools/compile_check.py .`；
7. 发布清单生成和文档一致性检查。

**技术决定**

- 任一步失败都修复后重新执行，不用历史测试记录替代本次结果。
- 测试输出中的跳过项必须记录原因。
- 不在本步骤自动执行真实 RF 或电源动作。

**完成标准**

- 所有离线命令产生可归档的日期、命令、解释器和结果记录。
- 发布清单不再包含兼容/回滚文件列表。
- 工作区无由测试生成的未跟踪产物。

### 步骤 10：现场验收交接

**执行策略**

1. 由获授权人员按现有 Hardware Smoke 指南执行基础连接清理、线损、驱动映射和主功放测量。
2. 每类测量独立使用新 `run_id`，记录正常、停止、急停、异常清理和重新连接结果。
3. 维护者读取本地报告和运行目录产物，核对 manifest、结果完整性、RF/电源安全状态和资源释放。

**技术决定**

- 现场验收只能使用正式运行路径。
- 离线仿真、历史 minimal action 结果和旧结果文件不能作为现场通过证据。
- 现场证据不提交敏感设备信息；只在受控归档中保存脱敏记录。

**完成标准**

- 三类正式测量均有可核验运行产物。
- 安全清理、资源释放和重新连接均有记录。
- 验收记录、重构计划和发布清单状态一致。

## 3. 建议提交顺序

每个步骤单独提交，提交信息使用统一前缀：

1. `refactor(run): remove legacy run preparation`
2. `refactor(api): remove migration compatibility aliases`
3. `refactor(persistence): unify formal result writes`
4. `refactor(dto): split measurement result contracts`
5. `docs(debt): align current architecture documentation`
6. `test(verification): record debt refactor acceptance`

步骤之间不混入无关格式化或功能改动；每次提交完成后先运行该步骤的针对性测试，再运行全量回归。

## 4. 计划完成条件

满足以下条件后，本计划可标记完成：

- 生产代码只有正式运行契约和正式 API；
- 旧快照、旧别名、旧参数和迁移期分支已删除；
- 结果持久化只有一套正式写入边界；
- 代码、测试、README、API 清单和技术债文档一致；
- 离线验证全部通过；
- 真实 Hardware Smoke 与三类现场测量按独立验收记录完成。
