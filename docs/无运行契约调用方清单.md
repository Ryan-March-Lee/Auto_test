## 1. 唯一生产契约与判定口径

生产契约只有一条：**每次测量都必须绑定同一个 `runs/<run_id>/` 运行目录**（`config.json` +
`manifest.json` + `inputs/hardware_config.json` 冻结快照），由它提供运行标识、领域配置和硬件装配
配置。判定口径固定如下：

| 判据 | 含义 |
| --- | --- |
| `PreparedRun.run_repository` 非 `None` | 运行仓储存在（唯一判据的第一项，见 `application.run_service.has_run_contract`） |
| `PreparedRun.hardware_connection_path()` | 硬件连接与测量的配置权威：运行目录内冻结的 `inputs/hardware_config.json`，并先校验 manifest SHA-256/大小 |
| `create_prepared_run()` / `load_prepared_run()` | 唯一的“创建运行快照”与“按 `run_id` 重新打开”入口，两者都产出带契约的 `PreparedRun`；用户可见的最终动作由 P8/F1 编排，不另开创建入口 |
| `prepared_run is None` 或 `has_run_contract` 为假 | 无运行契约对象；任何以它为输入的硬件装配都是调用错误，必须明确失败 |

生产侧不得再新增无契约对象进入装配；测试需要“无契约”时只能用 `tests/contract_doubles.py`
显式构造不满足契约的替身并断言**失败**，不得反过来把流程跑通。

**契约判据单源（步骤 5 已收敛）**：判定实现只有一处 ——
`application.run_service.has_run_contract()`，它要求运行标识、运行目录、运行仓储与可调用的
`hardware_connection_path()` 四项齐备。`app/run_context.py` 的
`PreparedRun.has_run_contract` 与 GUI 边界的 `presentation/qt/run_contract.py::is_valid_prepared_run()`
都只做委托，不再自带一套检查；因此两个入口对“是否有运行契约”永远给出同一个答案，也**不得**新增
第三套判据（例如另写一个 `getattr(..., "run_repository", None) is not None`）。

### 1.1 装配入口分层：组合根、硬件模式与仿真模式

“唯一装配入口”指的是**唯一的装配模块**，不是“只有一次装配调用”：生产组合根里各有一处硬件
模式与仿真模式装配，门禁按模式分别计数，避免把仿真装配误当成无契约的生产入口，也避免新增
第二个装配模块。分层固定如下：

| 层 | 位置 | 契约要求 |
| --- | --- | --- |
| 生产组合根 | `app/gui_runtime.py` | 唯一的装配模块：生产代码只有它调用 `create_measurement_port()`；三个测量工厂与 `connect_instruments()` 都在这里 |
| 硬件模式 | `create_measurement_port(mode="hardware")` | 连接真机，必须受运行契约约束：装配输入是运行目录冻结的 `inputs/hardware_config.json`（`hardware_config_path`），由 `connect_instruments(prepared_run)` 从运行契约解析并校验后传入；工厂本身只按给定路径装配、不校验来源（D15）。连接入口与 `InstrumentWorker` 上的遗留 `config_path` 已在步骤 6 删除，配置路径不再有任何入口 |
| 仿真模式 | `create_measurement_port(mode="simulation", ...)` | 离线/仿真装配，不打开任何 VISA 资源，允许没有运行目录；只由显式离线调用方（`create_offline_measurement_port`）使用 |
| 受控例外 | `hardware/new_path_minimal_action_smoke.py` | 真机冒烟，先过 `smoke_gate.py`，直接使用本地冒烟配置装配（不经生产连接入口），见第 5 节 |

门禁同时冻结：三个测量工厂**没有位置参数**且 `prepared_run` 是**必填关键字参数**（不得有默认值），
生产调用必须显式传入，且测量 worker 必须在装配用例之前调用 `require_prepared_run()`；测量命令
`MeasurementCommand` 与测量请求 `MeasurementRequest` 都在构造期就要求**满足契约**的输入
（D1、D10、D17；非空但不带契约的对象同样被拒绝）。

### 1.2 提交、失败与撤销不变量（计划步骤 1.1 登记）

- **提交即已连接（时刻语义）**：`prepared_run` 提交的时刻端口已存在且连接确认已完成（逐台
  `open_resource`、电源身份核对、全部声明通道 `OUTP?`）。不存在“已创建未连接”的已提交运行，
  也不存在“端口已提交、运行未提交”的中间态。提交后失去端口是后续事件：运行保留，状态写
  “需重新连接”，不删除运行。
- **连接入口唯一**：`connect_instruments(prepared_run)` 只由最终化事务（F1）在运行冻结之后
  调用；页面只发意图，不调用连接工厂、不持有端口。仪表配置页的旧“连接仪器”入口随计划步骤
  5.1 删除；重连复用同一最终动作，不新增第二条连接路径。
- **端口缺失只提示**：需要测量的页面在端口缺失时只提示“请先完成配置并连接仪器”或
  “端口已释放，请在仪器配置页重新连接”，不自行打开设备。
- **释放与撤销的失败落态**：`release_instrument_for_new_run()` 失败时旧运行保留、端口进入
  未决清理清单，状态写“需人工处理”；释放成功之后发生 F6–F7 失败时，旧运行保留但没有端口，
  状态写“需重新连接”；补偿撤销失败（F8）转“需人工处理”。不得把“旧运行 + 无端口”报告成仍可
  直接测量，也不得用重试绕过未决清理。
- **撤销分两类**：现状 `create_run_snapshot` 内部失败由 `_discard_created_run → discard_run()`
  回滚（未提交运行，仓储级补偿，不属于用户可见撤销）；目标上用户可见的未开始运行只由
  `discard_unstarted_run()`（F2，计划步骤 9.1）撤销——最终化补偿与放弃/退出共用。仓储
  `discard_run()` 保持补偿语义，不提供状态判断；已开始/已完成/已失败的运行不删除。
- **未决清理阻断**：`has_unreleased_ports()` 为真时，最终化、重连与测量一律拒绝；现场确认
  清理后再重试，避免重试绕过失败的清理。
- **判据不放宽**：`has_run_contract()` 与 `PreparedRun` 的四项要求不变；最终化事务与撤销
  用例都只消费运行契约，不接受无契约对象，也不为测试或兼容新增旁路。

## 3. 仅测试调用点清单

测试可以用**明确的 fake 仓储**实现契约，但不能用“无契约对象”作为捷径。步骤 6 已把原先
依赖无契约回退的测试调用点全部迁移为契约替身或真实运行，因此本节只保留判定规则。

### 3.0 测试边界判定规则

1. **正式测量链路测试**（测量页面、测量 worker、组合根、三类测量用例、运行阶段）必须使用
   `PreparedRun` 或**契约替身**：替身提供 `run_repository`、`run_id`、`run_directory`，并复用生产
   的 `has_run_contract` / `hardware_connection_path()` 判定规则，不得自行简化判定。
   `tests/contract_doubles.py` 的 `contract_run()` 是正式链路共用的契约替身，
   `RecordingStageRecorder` 与 `MappingInputReader` 是运行阶段记录器/输入读取器的替身。
2. **instrument 层纯装配单测**（`tests/test_measurement_factory.py`、`tests/test_multi_supply_connection.py`）
   直接以配置文件测试底层适配器与装配计划，它验证的是 `create_measurement_port` 的内部职责，
   不代表生产测量入口，允许不经过运行契约；不得为了“统一入口”删除这些层内单测的能力。
3. **契约缺失的验证必须是失败断言**：需要证明“没有运行就不能连硬件”时，断言的是明确失败
   （异常/错误信号），而不是用空 `run_repository` 的替身把流程跑通。步骤 6 新增的失败断言覆盖
   “没有运行对象”“请求缺少阶段记录器”“前置阶段未完成”三类。
4. 除第 5 节的受控例外，不得在生产代码里为测试便利保留无契约分支。

## 4. 底层无契约分支冻结表

步骤 6 的删除目标。每条都带稳定的“符号 + 标记 + 出现次数”身份，删除或改写会
让 `tests/test_run_contract_inventory.py` 失败，从而强制同步本文与基线。

第 4 节的冻结身份分两类，缺一不可：

- **符号 + 标记**：每条分支的每个无契约出口都要在该符号源码里出现，只登记一个出口会掩盖另一个；
- **语义计数**：门禁按 AST 统计“无契约判据”的语义出现次数（`run_repository`/`prepared_run`/

  因此本表之外若出现新的等价判据，门禁会直接失败。

**非回退点**同样登记在语义计数里，用来区分“合法判定”和“无契约回退”：

## 8. 技术决定

本步骤不改行为，但把后续两个步骤的判定提前固定下来，避免步骤 5/6 各自发明口径：

| 编号 | 决定 | 影响 |
| --- | --- | --- |
| D1 | 正式接口**构造即满足契约**：`MeasurementCommand.prepared_run` 与 `MeasurementRequest.stage_recorder` 改为必填；用例构造时拒绝缺少运行记录器的请求。worker 里的 `require_prepared_run()` 保留为边界防御，而不再是主要契约实现方式 | 步骤 5 已把 `MeasurementCommand` 改为必填并在构造期拒绝 `None` 与非契约对象（D10）；`MeasurementRequest.stage_recorder` 已在步骤 6b 改为必填关键字字段，显式传 `None` 在构造期失败 |
| D2 | “唯一装配入口”按**组合根 + 模式**判定：生产代码只有一个装配模块 `app/gui_runtime.py`，其内硬件模式与仿真模式各一处；仿真模式允许没有运行目录，但不得被当成生产测量入口 | 门禁按模式计数；新增装配模块或把仿真装配当生产入口都会失败 |
| D3 | 测试分两类：正式测量链路测试必须用 `PreparedRun`/契约替身；`instrument` 层纯装配单测可直接用配置文件。契约缺失的验证必须是**失败断言**，不得用空替身跑通流程 | 第 3.0 节；步骤 5 不得为“省事”删除层内单测能力 |
| D4 | 步骤 6 内部拆成 **6a 先迁移测试、6b 再删除分支** 两个执行阶段，用来隔离失败原因（测试数据问题 vs 业务逻辑删除）；两者**不是两次提交**：6a 迁移完成的当下就删分支并一次验证完，本项目在同一次改动内落地（见第 6 节） | 第 6 节；单次提交内保持“清单 / 代码 / 基线”三方同步，不留下“测试已迁移、分支还在”的中间态 |
| D5 | 无契约分支的冻结身份是“文件 + 符号 + 标记 + 出现次数”，清单与门禁**双向一致**（编号集合相等、不允许重复）；只减不增 | 第 4 节与门禁 `InventoryParityTests` |
| D6 | 受控例外（真机 smoke、`launcher.py` 只读入口、`tools/` 等）不因步骤 5/6 改变；接入运行契约属于新增能力，需单独评估 | 第 5 节 |
| D7 | 门禁本身是仓库门禁：登记进 `tools/run_tests.py::GATE_MODULES`，UI/集成改动不得绕过清单检查 | 第 7 节 |
| D8 | **契约判据单源**：`PreparedRun.has_run_contract` 与 `presentation/qt/run_contract.py::is_valid_prepared_run()` 收敛为一处实现，正式判据至少要求 `run_id`、`run_directory`、运行仓储与可调用的 `hardware_connection_path()`；收敛后不得新增第三套判据 | 步骤 5 已实现：唯一实现是 `application.run_service.has_run_contract()`，两个入口只做委托；门禁冻结“一处实现 + 两个委托 + 四项要求”，并继续禁止第三套判据 |
| D9 | **门禁按语义而不是文本冻结**：无契约判据用 AST 统计（`is None`/`is not None`/`isinstance(..., Mapping)`/指定调用），清单编号按章节解析，受监测符号不得经别名或动态 `getattr` 绕过；测试调用点用 AST 探针 | 注释、docstring、字符串拼接不再误伤；短名子串（例如 `MeasurementRequest(` 命中 `AmplifierMeasurementRequest(`）不再产生假条目；新增等价分支会失败 |
| D10 | **命令级契约判据复用单源**：`MeasurementCommand` 在构造期就要求**有效运行契约**（委托 `is_valid_prepared_run()`），不接受“非空但不带契约”的对象；正式链路测试不得用 `object()` 之类的空替身，需要“不满足契约”的替身时用 `tests/contract_doubles.py::contract_run(...)` 把某一项显式置 `None` 并断言失败 | 文档说的“构造即满足契约”与代码一致；空替身无法再冒充运行契约；新增失败断言覆盖四个必需项 |
| D11 | **遗留通道补登不改语义基线**：`connect_instruments(config_path=)` 属**既有**遗留回退（不是新增回退），登记后归属步骤 6；`config_path` 不进入语义计数的受监测名字集，避免全仓同名判空被误伤 | 步骤 6 已删除该参数：`config_path` 不再是任何装配入口的输入 |
| D12 | **单点解析**：硬件配置路径只允许解析一次，且只在组合根的连接入口 `connect_instruments()` 里解析（`_hardware_config_path()` → `PreparedRun.hardware_connection_path()`）。解析结果不外传：入口没有任何配置路径参数，三个测量工厂既不解析也不转发路径，只把运行契约交给连接入口；因此不存在“两个来源不同的路径变量”，也不可能为同一份快照做两遍 manifest 校验。请求 DTO 不再携带 `config_path`，端口与测量请求之间没有第二条路径通道 | `hardware_connection_path()` 每次装配恰好调用一次、`_hardware_config_path()` 全仓只出现一处（有 AST 断言钉住）；想让硬件装配用别的配置，只能改运行快照本身 |
| D13 | **受控例外必须可执行**：清单第 5 节的每个例外至少有一条 AST 断言（真机冒烟脚本：恰好一处 `create_measurement_port(mode="hardware")`、零处 `connect_instruments`、不 import `app.gui_runtime`） | 例外只能在门禁允许的形状内存在，不会被悄悄扩大 |
| D14 | **连接时的配置漂移必须可见**：连接仪器一律使用当前运行的冻结快照；配置页存在尚未冻结为运行的修改时只写日志提示（不阻断，是否重建运行由现场决定），且不再有“保存全局配置后直接连线”的路径（`update_and_save_configuration()` 已删除） | 界面改动被忽略这件事有据可查；连接入口只剩一条需要运行契约的路径 |
| D15 | **工厂不校验来源**：`create_measurement_port()` 只负责“按给定路径装配”，不做来源校验；运行快照这条约束由生产组合根（`connect_instruments`）与门禁保证。文档不得再声称工厂会拒绝其它来源，否则与 `instrument` 层纯装配单测、受控真机冒烟直接传路径的事实矛盾 | 口径统一：谁能提供路径、谁保证来源，两件事分开写；层内单测与受控例外不再需要“绕过”一句不存在的检查 |
