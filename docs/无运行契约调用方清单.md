## 1. 唯一生产契约与判定口径

生产契约只有一条：**每次测量都必须绑定同一个 `runs/<run_id>/` 运行目录**（`config.json` +
`manifest.json` + `inputs/hardware_config.json` 冻结快照），由它提供运行标识、领域配置和硬件装配
配置。判定口径固定如下：

| 判据 | 含义 |
| --- | --- |
| `PreparedRun.run_repository` 非 `None` | 运行仓储存在（唯一判据的第一项，见 `application.run_service.has_run_contract`） |
| `PreparedRun.hardware_connection_path()` | 硬件连接与测量的配置权威：运行目录内冻结的 `inputs/hardware_config.json`，并先校验 manifest SHA-256/大小 |
| `create_prepared_run()` / `load_prepared_run()` | 唯一的“创建运行”与“按 `run_id` 重新打开”入口，两者都产出带契约的 `PreparedRun` |
| `prepared_run is None` 或 `has_run_contract` 为假 | 无运行契约对象；任何以它为输入的硬件装配都是待移除路径 |

生产侧不得再新增无契约对象进入装配；测试需要“无契约”时只能使用明确登记在第 3 节的调用点，
并随步骤 6 迁移为契约替身。

**契约判据单源（步骤 5 已收敛）**：判定实现只有一处 ——
`application.run_service.has_run_contract()`，它要求运行标识、运行目录、运行仓储与可调用的
`hardware_connection_path()` 四项齐备。`app/run_context.py` 的
`PreparedRun.has_run_contract` 与 GUI 边界的 `presentation/qt/run_contract.py::is_valid_prepared_run()`
都只做委托，不再自带一套检查；因此两个入口对“是否有运行契约”永远给出同一个答案，也**不得**新增
第三套判据（例如另写一个 `getattr(..., "run_repository", None) is not None`）。

### 1.1 装配入口分层：组合根、硬件模式与仿真模式

“唯一装配入口”指的是**唯一的装配模块**，不是“只有一次装配调用”：生产组合根里各有一处硬件
模式与仿真模式装配，门禁按模式分别计数，避免把仿真装配误当成无契约的生产入口，也避免新增
第二个装配模块。分层固定如下：

| 层 | 位置 | 契约要求 |
| --- | --- | --- |
| 生产组合根 | `app/gui_runtime.py` | 唯一的装配模块：生产代码只有它调用 `create_measurement_port()`；三个测量工厂与 `connect_instruments()` 都在这里 |
| 硬件模式 | `create_measurement_port(mode="hardware")` | 连接真机，必须受运行契约约束：装配输入是运行目录冻结的 `inputs/hardware_config.json`（`hardware_config_path`），由 `connect_instruments(prepared_run)` 从运行契约解析并校验后传入 |
| 仿真模式 | `create_measurement_port(mode="simulation", ...)` | 离线/仿真装配，不打开任何 VISA 资源，允许没有运行目录；只由显式离线调用方（`create_offline_measurement_port`）使用 |
| 受控例外 | `hardware/new_path_minimal_action_smoke.py` | 真机冒烟，先过 `smoke_gate.py`，直接使用本地冒烟配置装配（不经生产连接入口），见第 5 节 |

门禁同时冻结：三个测量工厂的 `prepared_run` 必须是**必填关键字参数**（不得有默认值），生产调用
必须显式传入，且测量 worker 必须在装配用例之前调用 `require_prepared_run()`；测量命令
`MeasurementCommand` 也必须在构造时携带 `prepared_run`（D1）。

## 3. 仅测试调用点清单

测试可以用**明确的 fake 仓储**实现契约，但不能用“无契约对象”作为捷径。下列调用点目前依赖无契约
回退分支，全部随第 4 节分支删除而迁移或删除。

### 3.0 测试边界判定规则

1. **正式测量链路测试**（测量页面、测量 worker、组合根、三类测量用例、运行阶段）必须使用
   `PreparedRun` 或**契约替身**：替身提供 `run_repository`、`run_id`、`run_directory`，并复用生产
   的 `has_run_contract` / `hardware_connection_path()` 判定规则（`tests/integration/test_gui_two_phase_flow.py::_contract_run_stub`
   是模板），不得自行简化判定。
2. **instrument 层纯装配单测**（`tests/test_measurement_factory.py`、`tests/test_multi_supply_connection.py`）
   直接以配置文件测试底层适配器与装配计划，它验证的是 `create_measurement_port` 的内部职责，
   不代表生产测量入口，允许不经过运行契约。步骤 5 只收敛**硬件模式**的配置权威来源，不得因此
   删除这些层内单测需要的能力（需要时改为经仿真模式或显式装配计划构造）。
3. **契约缺失的验证必须是失败断言**：需要证明“没有运行就不能连硬件”时，断言的是明确失败
   （异常/错误信号），而不是用空 `run_repository` 的替身把流程跑通。
4. 除第 5 节的受控例外，不得在生产代码里为测试便利保留无契约分支。

- **符号 + 标记**：每条分支的每个无契约出口都要在该符号源码里出现（B3 两个出口、B7 两段文案、

  `isinstance(..., Mapping)`、`create_measurement_port`/`connect_instruments`/`prepare_run`/
  `create_measurement` 的调用），注释、docstring 与字符串拼接不计入，新增等价分支也无处可藏。
  因此本表之外若出现新的等价判据，门禁会直接失败。

两个**非回退点**同样登记在语义计数里，用来区分“合法判定”和“无契约回退”：

| 位置 | 为什么不是无契约回退 |
| --- | --- |
| `application/run_service.py::RunSnapshot.__post_init__` | `hardware_config_path is None` 直接抛 `ValueError`，是“契约缺失必须失败”的正面示例（D3 第 3 条） |

| `hardware/new_path_minimal_action_smoke.py` | 受控真机 smoke 脚本，先过 `hardware/smoke_gate.py`（本地配置、`environment: hardware_smoke`、`HARDWARE_SMOKE_ENABLED=1`、人工确认空载），只验证装配与动作链路，不写运行目录；因此它显式使用本地冒烟配置调用 `instrument.measurement_factory.create_measurement_port()`，不经过需要运行契约的生产连接入口 |

## 6. 迁移顺序（步骤 5 已完成，步骤 6 待执行）

### 步骤 5：装配入口收敛（已完成）

1. `connect_instruments()` 只接受 `PreparedRun`，硬件配置路径由
   `hardware_connection_path()` 解析并在打开 VISA 资源前校验（B11、X2）；
   `create_measurement_port()` 的**硬件模式**只接受运行快照路径 `hardware_config_path`
   （B12、X3），仿真模式保持不连设备。
2. `InstrumentWorker` 接收 `PreparedRun` 并在连接前 `require_prepared_run()`（B13、X4）；
   `ApplicationCoordinator.connect_instruments()` 无运行即失败，不再保存全局配置后连线
   （B15、X5）；`measurement_config_path()` 的全局回退已删除，未创建运行时直接抛
   `RunNotResumable`（B14、X6）。
3. 三个测量工厂的首个位置参数 `config_path` 不再是硬件权威：契约运行一律走运行快照，
   该参数只服务旧兼容快照/替身（T1–T3 留在步骤 6 迁移后删除）。
4. 收尾：`MeasurementCommand.prepared_run` 已改为必填并在构造期拒绝 `None`（B20、X7），
   真实调用点本来就显式传入运行契约；按 D8 把契约判据收敛为
   `application.run_service.has_run_contract()` 一处实现，`PreparedRun.has_run_contract` 与
   `is_valid_prepared_run()` 只做委托，基线同步更新。
   `MeasurementRequest.stage_recorder` 的默认值（B19）**留到步骤 6b**：把它改成必填会同时
   删除 B10（`_request_kwargs` 的条件装配）并要求 T1–T8 全部迁移为契约替身，而这些正是
   步骤 6a/6b 的范围；`prepare_run`／映射探测等分支此时已无生产调用方，同样留给步骤 6。

### 步骤 6：删除无契约前置校验分支（内部两阶段）

  无运行必须失败”的失败断言。此阶段只改测试，不改生产分支，失败原因必然是测试数据问题。

## 8. 技术决定

本步骤不改行为，但把后续两个步骤的判定提前固定下来，避免步骤 5/6 各自发明口径：

| 编号 | 决定 | 影响 |
| --- | --- | --- |
| D1 | 正式接口**构造即满足契约**：`MeasurementCommand.prepared_run` 与 `MeasurementRequest.stage_recorder` 改为必填；用例构造时拒绝缺少运行记录器的请求。worker 里的 `require_prepared_run()` 保留为边界防御，而不再是主要契约实现方式 | X7、B19、B20；`MeasurementCommand` 已在步骤 5 改为必填并在构造期拒绝 `None`，`MeasurementRequest.stage_recorder` 的默认值随 B19 在步骤 6b 删除 |
| D2 | “唯一装配入口”按**组合根 + 模式**判定：生产代码只有一个装配模块 `app/gui_runtime.py`，其内硬件模式与仿真模式各一处；仿真模式允许没有运行目录，但不得被当成生产测量入口 | 门禁按模式计数；新增装配模块或把仿真装配当生产入口都会失败 |
| D3 | 测试分两类：正式测量链路测试必须用 `PreparedRun`/契约替身；`instrument` 层纯装配单测可直接用配置文件。契约缺失的验证必须是**失败断言**，不得用空替身跑通流程 | 第 3.0 节；步骤 5 不得为“省事”删除层内单测能力 |
| D4 | 步骤 6 内部拆成 **6a 先迁移测试、6b 再删除分支**；每阶段单独验证、单独提交 | 第 6 节 |
| D5 | 无契约分支的冻结身份是“文件 + 符号 + 标记 + 出现次数”，清单与门禁**双向一致**（编号集合相等、不允许重复）；只减不增 | 第 4 节与门禁 `InventoryParityTests` |
| D6 | 受控例外（真机 smoke、`launcher.py` 只读入口、`tools/` 等）不因步骤 5/6 改变；接入运行契约属于新增能力，需单独评估 | 第 5 节 |
| D7 | 门禁本身是仓库门禁：登记进 `tools/run_tests.py::GATE_MODULES`，UI/集成改动不得绕过清单检查 | 第 7 节 |
| D8 | **契约判据单源**：`PreparedRun.has_run_contract` 与 `presentation/qt/run_contract.py::is_valid_prepared_run()` 收敛为一处实现，正式判据至少要求 `run_id`、`run_directory`、运行仓储与可调用的 `hardware_connection_path()`；收敛后不得新增第三套判据 | 步骤 5 已实现：唯一实现是 `application.run_service.has_run_contract()`，两个入口只做委托；门禁冻结“一处实现 + 两个委托 + 四项要求”，并继续禁止第三套判据 |
| D9 | **门禁按语义而不是文本冻结**：无契约判据用 AST 统计（`is None`/`is not None`/`isinstance(..., Mapping)`/指定调用），清单编号按章节解析，受监测符号不得经别名或动态 `getattr` 绕过；测试调用点用 AST 探针 | 注释、docstring、字符串拼接不再误伤；短名子串（例如 `MeasurementRequest(` 命中 `AmplifierMeasurementRequest(`）不再产生假条目；新增等价分支会失败 |
