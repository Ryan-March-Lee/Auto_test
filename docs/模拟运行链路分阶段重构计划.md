# Mock 模拟运行链路分阶段重构计划

> 状态：调研完成，待实施。
>
> 本计划只描述实现顺序与技术决策，不在本阶段修改程序代码。每个步骤都保持较小的
> 变更边界，完成一个步骤后即可单独验证，再进入下一步。

## 1. 目标

在不打开真实仪器、不创建正式运行目录、不写入正式测量结果的前提下，增加一条可从
GUI 操作的 Mock 模拟链路：

```text
欢迎页
  └─ 加载配置 → 选择 Mock
                   ↓
             进入模拟模式
                   ↓
       模拟连接完成，进入测量工作区
                   ↓
   各测量页分别点击“开始测量”
                   ↓
       按 0.5 秒/数据点回放实时数据
```

三类测量分别使用已有数据：

```text
mock_data/cable_loss/scenario.json
mock_data/driver_mapping/scenario.json
mock_data/amplifier/scenario.json
```

本次模拟链路的边界：

1. 每个测量页分别启动，不自动串联线损、驱放和主功放三个阶段。
2. 线损仍保留“请连接路径 2”的确认点。
3. 每个 `data` 事件间隔 0.5 秒；消息和进度随回放顺序发送。
4. 驱动映射自动使用 Mock 线损结果；主功放自动使用 Mock 线损和驱动映射结果。
5. 回放结果只展示，不写入 `test_results`、`runs` 或正式归档目录。
6. 模拟模式不调用 VISA，不连接任何真实仪器。

## 2. 调研基线

### 2.1 当前入口和运行限制

- 欢迎页当前实际提供的是“加载配置”入口：
  `presentation/qt/welcome_page.py`。
- 配置加载通过 `ConfigurationSnapshotDialog` 选择已保存快照，当前只回填配置并进入
  工作区，不创建执行上下文：`presentation/qt/configuration_snapshot_actions.py`。
- `config.mock.json`、`config.json` 和
  `test_results/configurations/Mock_20261114_1020/Mock.json` 当前内容一致。
- Mock 配置的设备绑定带有 `source: simulated`。正式运行在
  `app/gui_runtime.py::_reject_simulated_bindings()` 处被拒绝，这是正确的真机安全门禁，
  不应通过修改门禁来实现模拟链路。
- 正式测量页面要求 `PreparedRun`、测量端口和校准输入，因此模拟链路不能伪造一个
  “已经连接真实仪器”的正式运行对象。

### 2.2 已有可复用能力

- `mock_data/README.md` 已定义场景格式、阶段、事件和正式结果契约。
- 三个正式结果文件都能由
  `application.dto.measurement_results.measurement_result_from_document()` 解析。
- 页面已经消费统一的实时事件：`data_update` → 各测量页的 `update_realtime()`。
- `MeasurementController`、`WorkerSignals` 和现有 worker 已提供线程、停止、进度、消息、
  实时数据及完成事件的通用生命周期。

### 2.3 需要避免的实现方式

- 不把 `mock_data` 复制到 `test_results` 再走正式阶段结果选择流程。
- 不让模拟配置通过 `_reject_simulated_bindings()`，也不把模拟地址当成真实地址连接。
- 不在模拟 worker 中调用 `create_measurement_port(mode="hardware")`。
- 不用假的 `PreparedRun` 绕过 `MeasurementCommand` 的正式运行契约校验。
- 不让 GUI 线程用 `time.sleep()` 播放数据。

## 3. 已确认的技术决定

1. **入口**：复用欢迎页现有“加载配置”入口；选择快照后按快照显示名称识别 `Mock`，
   名称去除首尾空格后大小写不敏感匹配。首期不新增第二个欢迎页入口。
2. **配置固定性**：Mock 模拟数据固定对应 `config.mock.json` 和当前 Mock 快照；进入模拟
   模式时校验场景 `source_config` 的关键配置摘要，配置不匹配就拒绝进入模拟模式。
3. **连接动作**：保留“连接仪器”按钮作为进入测量工作区的确认动作，但模拟模式下不创建
   `PreparedRun`、不启动 `InstrumentWorker`、不打开 VISA；由协调器建立独立的模拟会话状态。
4. **测量启动**：各页面仍使用自己的“开始测量”按钮；模拟模式跳过物理接线确认对话框，
   因为模拟模式没有真实接线动作。
5. **校准输入**：由模拟模式自动绑定 `mock_data/cable_loss`、`mock_data/driver_mapping`
   下的正式结果文件；页面显示来源，但不要求用户手动选择。
6. **回放时序**：不使用场景中的 `at_ms` 作为实际播放时间；以 `data` 事件为计时单位，
   每个数据点间隔 500 ms。非数据事件按场景顺序在对应数据点前后立即发出。
7. **线损阶段**：保留场景的 `user_confirm` 语义；路径 1 完成后进入等待状态，用户确认
   后才播放路径 2，拒绝则按普通停止处理。
8. **结果处理**：回放完成时加载对应正式结果 DTO，并通过现有结果信号交给页面展示；不
   通过正式归档服务保存，不生成 CSV/报告，不制造虚假的归档路径。
9. **模拟完成提示**：新增独立的模拟完成展示载荷或信号，不复用要求正式文件路径的
   `ArchivalOutcome`；界面明确显示“模拟数据，仅展示，未写入正式结果”。
10. **停止与重放**：停止使用可中断等待；停止后保留已经显示的数据；再次开始从场景第
    一个事件重新播放。

## 4. 分阶段步骤

## 阶段一：冻结 Mock 数据与识别契约

### 步骤 1：建立 Mock 数据路径和阶段索引

- **范围**：`infrastructure/filesystem/paths.py`，新增纯路径属性或独立的 Mock 路径
  服务；不接入 GUI，不改变正式结果路径。
- **执行策略**：统一从项目根目录派生 `mock_data/<stage>/scenario.json` 和正式结果文件，
  不在各页面拼接相对路径。
- **技术决定**：Mock 路径只读；不存在时由回放服务报告错误，不自动创建目录；正式
  `PathService` 的 `test_results` 路径保持不变。
- **验收**：临时项目根目录可以解析三类场景和三类正式结果；路径越界或缺失有明确错误。
- **工作量控制**：只增加路径和测试，不改测量流程。

### 步骤 2：定义 Mock 场景纯 Python 契约

- **范围**：新增 `application` 或 `domain` 下的场景 DTO/校验模块；不启动线程。
- **执行策略**：定义场景、阶段、事件、完成结果和 `source_config` 的最小模型；读取
  JSON 后一次性校验，再交给回放器。
- **技术决定**：只接受 `kind = measurement_mock_scenario`；只支持 README 已列出的
  `message`、`progress`、`data`、`user_confirm`、`result`、`finished` 语义；未知事件
  类型拒绝，不静默跳过。
- **验收**：三套现有场景都能加载；损坏 JSON、缺阶段、事件顺序错误、缺结果文件名、
  错误 `measurement_type` 均能在播放前失败。
- **工作量控制**：先只做结构校验和数据对象，不包含 Qt、线程和文件归档。

### 步骤 3：实现 Mock 配置匹配器

- **范围**：新增纯 Python 的 `MockConfigurationMatcher` 及单元测试。
- **执行策略**：输入配置快照名称和配置文档，先判断名称是否为 `Mock`，再按场景
  `source_config` 校验频率、衰减器、压缩点、驱放开关/估计增益、扫描计划等关键事实。
- **技术决定**：名称只是进入候选模拟模式的入口，配置摘要不匹配仍拒绝；不比较设备 IP、
  VISA 地址等模拟硬件字段；不修改配置文件。
- **验收**：当前 Mock 快照匹配成功；改名、修改频点、功率计划或驱放参数会得到可读错误；
  普通配置不会误判为模拟配置。
- **工作量控制**：匹配规则独立于窗口和协调器，便于后续扩展新的 Mock 数据包。

## 阶段二：建立独立的模拟会话

### 步骤 4：增加模拟会话状态模型

- **范围**：`presentation/qt/application_coordinator.py` 及相关纯 Python 状态测试。
- **执行策略**：在协调器中增加显式的 `SimulationSession`/模拟模式状态，记录 Mock 配置
  身份、场景索引和固定校准结果路径；不复用 `prepared_run` 字段表达模拟状态。
- **技术决定**：模拟会话与 `RunFlowState.CONNECTED` 分开表达，避免现有正式流程把它误认
  为可连接真实仪器的运行；测量页面通过统一的会话提供器获取“正式运行或模拟会话”。
- **验收**：加载 Mock 后状态可查询；普通配置状态不变；返回欢迎页或放弃会话会清除模拟
  状态；模拟状态不能调用真机连接入口。
- **工作量控制**：只增加状态和生命周期，不接入回放数据。

### 步骤 5：让“连接仪器”进入模拟会话

- **范围**：`main_window.py`、协调器最终化入口及相关 UI 测试。
- **执行策略**：`_finalize_run()` 先判断当前是否为 Mock 模式；是则执行配置匹配、场景
  文件可读性检查和模拟会话提交，然后直接进入工作区；否仍走现有正式连接事务。
- **技术决定**：模拟分支不调用 `prepare_configuration()`、不写 `runs/`、不启动
  `InstrumentWorker`；失败时留在配置页并恢复按钮状态。
- **验收**：Mock 点击“连接仪器”后进入线损页；没有 VISA 连接、没有新运行目录；普通
  配置的连接和失败补偿测试全部保持原行为。
- **工作量控制**：只接入“进入模拟会话”，不在本步修改各页面的开始按钮。

### 步骤 6：增加模拟模式显示和只读规则

- **范围**：工作台徽标、配置页编辑状态、返回欢迎页清理；不改数据回放。
- **执行策略**：沿用现有 `WorkspaceBinding`/模式徽标通道，增加“Mock 模拟模式”文案；
  模拟配置从加载到会话结束保持只读。
- **技术决定**：模拟模式禁止保存配置和重新连接真机；返回欢迎页前先结束模拟会话，不能
  保留到下一份普通配置中。
- **验收**：徽标和状态栏显示模拟状态；保存按钮不可用或明确提示；返回欢迎页后重新选择
  普通配置不会残留 Mock 状态。
- **工作量控制**：只改状态展示和按钮可用性，不引入业务判断到 Qt 控件内部。

## 阶段三：实现逐点回放 worker

### 步骤 7：实现可中断的回放时钟

- **范围**：新增纯 Python 回放时钟/调度器和测试；不连接 Qt。
- **执行策略**：用注入的 clock/sleep 函数实现 500 ms 数据点间隔；用 `Event` 或取消
  token 中断等待，测试中使用 fake clock，不依赖真实 181 秒回放。
- **技术决定**：`at_ms` 仅作为数据校验和说明，不控制首期播放速度；第一条数据在启动后
  立即或经过一个 500 ms 周期的选择要固定在契约中，建议首条立即发出、后续数据间隔
  500 ms，以便点击开始后快速看到反馈。
- **验收**：数据事件间隔符合 500 ms；停止能打断等待；进度点不倒退；重复播放从头开始。
- **工作量控制**：本步只验证时序，不读取大场景文件。

### 步骤 8：实现 MockReplayWorker 和统一信号适配

- **范围**：新增 `presentation/qt/mock_replay_worker.py`，复用 `WorkerSignals` 事件形状；
  增加 worker 单元测试。
- **执行策略**：worker 在线程中加载并校验场景，按阶段事件顺序发送 `message`、`progress`、
  `data_update`；完成时读取正式结果 DTO，发送结果引用和模拟完成载荷。
- **技术决定**：不调用 `app.gui_runtime.create_*_measurement`；worker 只依赖场景读取器、
  回放时钟和结果 DTO 解析器；大场景文件读取发生在线程内。
- **验收**：三类场景能分别回放；消息/进度/数据都能收到；场景或正式结果损坏时发 error；
  stop 后线程可退出且不发送 finished 误报。
- **工作量控制**：先用内存 callback/fake signal 测试，暂不改页面。

### 步骤 9：增加模拟 worker 工厂分支

- **范围**：`measurement_worker_factories.py`、`MeasurementCommand`/启动请求契约及工厂测试。
- **执行策略**：在命令中增加明确的执行模式和 Mock 场景标识；正式命令仍要求有效
  `PreparedRun`，模拟命令则要求有效 `SimulationSession`，二者互斥。
- **技术决定**：不构造假的 `PreparedRun`；`MeasurementController` 只按命令模式选择正式
  worker 或 Mock worker；模拟 worker 的 `measurement_port` 固定为 `None`。
- **验收**：正式命令仍拒绝缺失运行契约；模拟命令可构造并选择正确场景；模式和场景不
  匹配时在 worker 启动前失败。
- **工作量控制**：只扩展命令和工厂分派，不接入连接流程和页面。

## 阶段四：接入三个测量页面

### 步骤 10：让启动 Facade 支持模拟会话

- **范围**：`measurement_start_facade.py` 及启动 Facade 测试。
- **执行策略**：启动请求同时支持正式运行和模拟会话；模拟模式跳过正式运行契约检查及
  物理接线确认，仍保留忙碌检查和 controller 单例检查。
- **技术决定**：页面仍调用同一个 `prepare()`/`launch()` 入口，不在三个页面各自复制
  “模拟判断”；模拟模式仍生成不可变 `MeasurementCommand`。
- **验收**：模拟会话可以启动；正式会话的“必须先连接仪器”和接线确认行为不变；已有
  测量运行时两种模式都统一拒绝重复启动。
- **工作量控制**：只改启动前置条件，不改页面结果渲染。

### 步骤 11：接入线损模拟回放

- **范围**：`cable_loss_page.py`、线损页面测试和路径2暂停测试。
- **执行策略**：模拟模式选择 `cable_loss/scenario.json`；实时数据继续走现有
  `update_realtime()`；场景的 `user_confirm` 转换为现有 `step_pause` 信号。
- **技术决定**：路径2确认弹窗和取消行为保持现有页面生命周期；模拟停止不触发正式端口
  清理；完成后用正式线损 DTO 一次性完成结果状态收尾。
- **验收**：路径1数据逐点出现；等待路径2时按钮状态正确；确认后继续；拒绝后停止；
  完成结果表与已有 Mock 正式结果一致。
- **工作量控制**：只接入线损页面，不同时修改驱动映射和主功放。

### 步骤 12：接入驱动映射和主功放模拟回放

- **范围**：`driver_mapping_page.py`、`amplifier_page.py`、页面测试。
- **执行策略**：模拟会话启动时自动注入固定校准来源；页面仍使用已有实时曲线、读数条、
  频点导航和结果 DTO 展示。
- **技术决定**：模拟模式不要求用户点击“加载线损结果/加载驱动映射结果”；来源标签显示
  `mock_data` 文件名；普通模式的显式文件选择和缺失输入校验保持不变。
- **验收**：驱动映射逐点累计曲线正常；主功放逐点显示功率、电压、电流、效率；两页都能
  在 0.5 秒节奏下停止并重新开始；普通测量输入流程无回归。
- **工作量控制**：页面只消费模拟选择状态，不让页面直接读取场景 JSON。

### 步骤 13：接入模拟完成提示

- **范围**：新增模拟完成载荷/展示适配，修改 `archival_page.py` 或归档展示边界；不改
  正式 `ArchivalOutcome` 的路径约束。
- **执行策略**：Mock worker 完成时发送专用模拟完成事件；页面显示“模拟数据已加载”及
  “未写入正式结果、未生成 CSV/报告”，同时保留正式结果页面展示。
- **技术决定**：模拟完成不调用 `ResultArchivalService`，不发送带虚假路径的正式归档 DTO；
  现有正式归档文案和状态机保持原样。
- **验收**：模拟完成后不显示“结果已自动归档”或假路径；正式测量完成提示不变；模拟停止
  和异常提示仍能区分。
- **工作量控制**：只增加一个展示分支，避免改动归档领域模型。

## 阶段五：安全收尾、回归和文档

### 步骤 14：补齐模拟会话生命周期和资源门禁测试

- **范围**：协调器、主窗口和 controller 的集成测试。
- **执行策略**：覆盖加载 Mock、模拟连接、进入工作区、逐页启动、停止、返回欢迎页、再
  进入普通配置等完整状态转换；用 fake VISA/端口断言从未打开真实资源。
- **技术决定**：模拟会话结束不执行正式端口清理，不影响正式会话的端口生命周期；任何
  模拟状态都不能调用 `connect_instruments()`。
- **验收**：模拟链路可重复运行；切换普通模式后没有残留 worker、状态或输入来源；测试中
  不需要真实网络和真实仪器。
- **工作量控制**：只覆盖跨模块接线，纯逻辑测试前置步骤已分别完成。

### 步骤 15：补齐数据契约和大场景回放验证

- **范围**：新增模拟场景测试和 `mock_data` 校验脚本/测试；不修改场景数据。
- **执行策略**：验证三套场景的事件数量、数据频点覆盖、正式结果类型和 `source_config`
  一致性；时间测试使用 fake clock，另增加一个短场景做真实 Qt 线程烟测。
- **技术决定**：完整驱动映射和主功放回放不在自动化测试中等待真实 181.5/156 秒；只验证
  事件顺序、计时调用次数、取消和完成语义。
- **验收**：场景数据变化会被测试及时发现；大文件加载不阻塞 GUI；正式结果 DTO 与实时
  事件结构能同时被页面消费。
