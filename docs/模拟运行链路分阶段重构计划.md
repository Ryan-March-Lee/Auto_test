# Mock 模拟运行链路分阶段重构计划

> 状态：步骤 1～16 已完成，五个阶段全部收尾。
>
> 本计划描述实现顺序与技术决策。每个步骤都保持较小的变更边界，完成一个步骤后即可
> 单独验证，再进入下一步。

## 1. 目标

在不打开真实仪器、不创建正式运行目录、不写入正式测量结果的前提下，增加一条可从
GUI 操作的 Mock 模拟链路：

```text
欢迎页
  └─ 加载配置 → 选择 Mock
                   ↓
             进入模拟模式
                   ↓
       模拟连接完成，进入测量工作区
                   ↓
   各测量页分别点击“开始测量”
                   ↓
       按 0.5 秒/数据点回放实时数据
```

三类测量分别使用已有数据：

```text
mock_data/cable_loss/scenario.json
mock_data/driver_mapping/scenario.json
mock_data/amplifier/scenario.json
```

本次模拟链路的边界：

1. 每个测量页分别启动，不自动串联线损、驱放和主功放三个阶段。
2. 线损仍保留“请连接路径 2”的确认点。
3. 每个 `data` 事件间隔 0.5 秒；消息和进度随回放顺序发送。
4. 驱动映射自动使用 Mock 线损结果；主功放自动使用 Mock 线损和驱动映射结果。
5. 回放结果只展示，不写入 `test_results`、`runs` 或正式归档目录。
6. 模拟模式不调用 VISA，不连接任何真实仪器。

## 2. 调研基线

### 2.1 当前入口和运行限制

- 欢迎页当前实际提供的是“加载配置”入口：
  `presentation/qt/welcome_page.py`。
- 配置加载通过 `ConfigurationSnapshotDialog` 选择已保存快照，当前只回填配置并进入
  工作区，不创建执行上下文：`presentation/qt/configuration_snapshot_actions.py`。
- `config.mock.json`、`config.json` 和
  `test_results/configurations/Mock_20261114_1020/Mock.json` 当前内容一致。
- Mock 配置的设备绑定带有 `source: simulated`。正式运行在
  `app/gui_runtime.py::_reject_simulated_bindings()` 处被拒绝，这是正确的真机安全门禁，
  不应通过修改门禁来实现模拟链路。
- 正式测量页面要求 `PreparedRun`、测量端口和校准输入，因此模拟链路不能伪造一个
  “已经连接真实仪器”的正式运行对象。

### 2.2 已有可复用能力

- `mock_data/README.md` 已定义场景格式、阶段、事件和正式结果契约。
- 三个正式结果文件都能由
  `application.dto.measurement_results.measurement_result_from_document()` 解析。
- 页面已经消费统一的实时事件：`data_update` → 各测量页的 `update_realtime()`。
- `MeasurementController`、`WorkerSignals` 和现有 worker 已提供线程、停止、进度、消息、
  实时数据及完成事件的通用生命周期。

### 2.3 需要避免的实现方式

- 不把 `mock_data` 复制到 `test_results` 再走正式阶段结果选择流程。
- 不让模拟配置通过 `_reject_simulated_bindings()`，也不把模拟地址当成真实地址连接。
- 不在模拟 worker 中调用 `create_measurement_port(mode="hardware")`。
- 不用假的 `PreparedRun` 绕过 `MeasurementCommand` 的正式运行契约校验。
- 不让 GUI 线程用 `time.sleep()` 播放数据。

## 3. 已确认的技术决定

1. **入口**：复用欢迎页现有“加载配置”入口；选择快照后按快照显示名称识别 `Mock`，
   名称去除首尾空格后大小写不敏感匹配。首期不新增第二个欢迎页入口。
2. **配置固定性**：Mock 模拟数据固定对应 `config.mock.json` 和当前 Mock 快照；进入模拟
   模式时校验场景 `source_config` 的关键配置摘要，配置不匹配就拒绝进入模拟模式。
3. **连接动作**：保留“连接仪器”按钮作为进入测量工作区的确认动作，但模拟模式下不创建
   `PreparedRun`、不启动 `InstrumentWorker`、不打开 VISA；由协调器建立独立的模拟会话状态。
4. **测量启动**：各页面仍使用自己的“开始测量”按钮；模拟模式跳过物理接线确认对话框，
   因为模拟模式没有真实接线动作。
5. **校准输入**：由模拟模式自动绑定 `mock_data/cable_loss`、`mock_data/driver_mapping`
   下的正式结果文件；页面显示来源，但不要求用户手动选择。
6. **回放时序**：不使用场景中的 `at_ms` 作为实际播放时间；以 `data` 事件为计时单位，
   每个数据点间隔 500 ms。非数据事件按场景顺序在对应数据点前后立即发出。
7. **线损阶段**：保留场景的 `user_confirm` 语义；路径 1 完成后进入等待状态，用户确认
   后才播放路径 2，拒绝则按普通停止处理。
8. **结果处理**：回放完成时加载对应正式结果 DTO，并通过现有结果信号交给页面展示；不
   通过正式归档服务保存，不生成 CSV/报告，不制造虚假的归档路径。
9. **模拟完成提示**：新增独立的模拟完成展示载荷或信号，不复用要求正式文件路径的
   `ArchivalOutcome`；界面明确显示“模拟数据，仅展示，未写入正式结果”。
10. **停止与重放**：停止使用可中断等待；停止后保留已经显示的数据；再次开始从场景第
    一个事件重新播放。

## 4. 分阶段步骤

## 阶段一：冻结 Mock 数据与识别契约

### 步骤 1：建立 Mock 数据路径和阶段索引（已完成）

- **范围**：`infrastructure/filesystem/paths.py`，新增纯路径属性或独立的 Mock 路径
  服务；不接入 GUI，不改变正式结果路径。
- **执行策略**：统一从项目根目录派生 `mock_data/<stage>/scenario.json` 和正式结果文件，
  不在各页面拼接相对路径。
- **技术决定**：Mock 路径只读；不存在时由回放服务报告错误，不自动创建目录；正式
  `PathService` 的 `test_results` 路径保持不变。
- **验收**：临时项目根目录可以解析三类场景和三类正式结果；路径越界或缺失有明确错误。
- **工作量控制**：只增加路径和测试，不改测量流程。
- **实施记录**：
  - `MockDataPathService` 只派生路径，不建目录、不读内容；`require_scenario_path()` /
    `require_result_path()` 在读取前解析链接，依次确认 `mock_data` 在项目根目录内、
    阶段目录在 `mock_data` 内、目标是阶段目录的直接子文件。符号链接、Windows 目录联接、
    指向上级目录的路径和目录目标都会在播放前失败，不会把 Mock 数据解析到项目之外。
  - 场景固定为 `mock_data/<stage>/scenario.json`；结果文件名只能是纯文件名，拒绝路径
    分隔符、盘符、`.` / `..`、首尾空白、以点结尾的名字和 Windows 保留设备名。
  - `MockStage` 只表示场景目录，`MOCK_STAGE_INDEX` 记录对应的正式测量类型：
    `cable_loss`、`driver_power_mapping`、`amplifier`；校准依赖为线损 → 驱动映射 →
    主功放。索引条目的 `calibration_inputs` 在构造时规范化为不可变 `tuple`。
  - 路径模块只保存测量类型字符串，正式枚举以 `MeasurementType` 为权威；跨层一致性
    用例比较两边取值，字符串到枚举的转换留给步骤 2 的场景契约，避免路径模块依赖
    应用层业务枚举。`MockDataPathError` 归入 `ConfigurationError`（同时保留
    `ValueError`），使路径缺失/越界与场景契约错误使用同一配置类类别。
  - 覆盖：三类场景与三类正式结果的解析、临时根目录注入、链接越界、目录目标、缺失
    文件不建目录和文件名安全，见 `tests/test_mock_data_paths.py`。

### 步骤 2：定义 Mock 场景纯 Python 契约

- **范围**：新增 `application` 或 `domain` 下的场景 DTO/校验模块；不启动线程。
- **执行策略**：定义场景、阶段、事件、完成结果和 `source_config` 的最小模型；读取
  JSON 后一次性校验，再交给回放器。
- **技术决定**：只接受 `kind = measurement_mock_scenario`；阶段事件只支持 README
  已列出的 `message`、`progress`、`data`，阶段起点只支持 `auto`、`user_confirm`，
  完成事件只支持 README 已列出的 `result`、`archival`、`message`、`finished`；未知
  类型拒绝，不静默跳过。完成事件顺序固定为
  `result → archival → message → finished`。
- **验收**：三套现有场景都能加载；损坏 JSON、缺阶段、事件顺序错误、缺结果文件名、
  错误 `measurement_type` 均能在播放前失败。
- **工作量控制**：先只做结构校验和数据对象，不包含 Qt、线程和文件归档。
- **实施记录**：
  - 契约集中在 `application/dto/mock_scenario.py`：只含纯数据模型、枚举与校验，不读
    文件；`application/inputs/mock_scenario.py::load_mock_scenario()` 负责“文件 →
    UTF-8/BOM → JSON → 契约”的一次性读取。应用层不导入基础设施，路径边界仍由步骤 1
    的 `MockDataPathService` 在调用读取器之前确认。读取器按模块直接导入，不改变
    `application.inputs.__all__` 只导出正式结果读取器的既有契约。
  - 固定 `kind = measurement_mock_scenario`、`schema_version = 1.0`；根对象、阶段、
    阶段起点、事件、完成事件、`run` 和 `source_config` 都拒绝未声明字段，字段名拼写
    错误不会被静默忽略。
  - 阶段事件只有 `message` / `progress` / `data`；未知类型直接失败并列出支持项。
    `at_ms` 必须非负且阶段内非递减，每个阶段至少一个 `data` 事件作为回放计时单位，
    跨阶段的实际进度值不能倒退。
  - 阶段起点只支持 `auto` 与 `user_confirm`：第一个阶段必须 `auto`，最多一个
    `user_confirm`；确认点固定 `signal = step_pause`、`accepted = continue_stage2`、
    `rejected = stop`，与线损路径 2 的现有页面语义一致。
  - 完成事件顺序固定为 `result → archival → message → finished`：必须且只有一个
    `result`（带非空纯文件名）、只有一个 `finished` 且位于最后，最多一个 `archival`；
    `archival` 与 `message` 可以省略。`archival` 只保留场景摘要供展示，不代表会执行
    正式归档。结果文件名拒绝路径分隔、盘符、`.`/`..`、NUL 和 Windows 保留设备名；
    符号链接、目录目标和存在性仍由 `MockDataPathService` 确认。
  - `source_config` 解析出匹配器需要的显式事实：频点、衰减器、驱放开关/估计增益/
    最大输入、DUT 最大输入、功率扫描计划、目标输入网格、信号源功率范围与校准结果
    引用；压缩目标统一为 `compression_point`，兼容摘要里的 `compression_type` 与
    `compression_point` 两种键名，同时出现时必须一致。必需字段和可选字段由固定白名单
    校验，未知键直接失败。校准结果引用必须是 `mock_data/<stage>/<文件名>` 相对路径，
    只校验字符串形状和阶段前缀，读取仍由步骤 12 的 Mock 路径服务完成。完整摘要另存为
    冻结的 `document`，供步骤 3 及之后的校准来源取用。
  - 数值校验把超出浮点范围的 JSON 整数翻译为 `MockScenarioError`；阶段起点、阶段事件
    和完成事件只接受具体子类，基类实例不会绕过校验；`run.started_at` 必须是带时区的
    ISO 8601 时间。读取器会把契约错误前缀为具体场景文件路径，便于播放前定位。
  - 场景的 `measurement_type` 在契约内转换为正式 `MeasurementType`；读取时可选传入
    期望类型，阶段不匹配会在播放前失败。`data` 载荷用现有 `freeze()` 深冻结，跨线程
    传递安全；交给 Qt 信号或页面修改前须用 `thaw()` 还原。
  - 覆盖：三套仓库场景加载、事件/进度/数据点数量、阶段与正式测量类型一致性、完成
    结果文件存在性、载荷冻结，以及损坏 JSON、缺阶段、顺序错误、未知事件、缺结果
    文件名、错误测量类型、结果文件名路径穿越、校准引用越界、`source_config` 未知键、
    数值溢出、基类事件和无时区时间等拒绝路径，见
    `tests/test_mock_scenario_contract.py`。

### 步骤 3：实现 Mock 配置匹配器（已完成）

- **范围**：新增纯 Python 的 `MockConfigurationMatcher` 及单元测试。
- **执行策略**：输入配置快照名称和配置文档，先判断名称是否为 `Mock`，再按场景
  `source_config` 校验频率、衰减器、压缩点、驱放开关/估计增益、扫描计划等关键事实。
- **技术决定**：名称只是进入候选模拟模式的入口，配置摘要不匹配仍拒绝；不比较设备 IP、
  VISA 地址等模拟硬件字段；不修改配置文件。
- **验收**：仓库跟踪的 Mock 配置文档匹配成功；改名、修改频点、功率计划或驱放参数会得到
  可读错误；普通配置不会误判为模拟配置。
- **工作量控制**：匹配规则独立于窗口和协调器，便于后续扩展新的 Mock 数据包。
- **实施记录**：
  - 匹配器集中在 `application/mock_configuration_matcher.py`：只做纯数据比较，不读
    文件、不依赖 Qt、窗口或协调器，也不修改传入的配置文档；路径、场景读取仍由步骤
    1/2 的服务在调用前完成。本步没有接入 GUI 或运行事务。
  - 名称入口统一由 `is_mock_configuration_name()` 与
    `MockConfigurationMatcher.matches_name()` 判断：删除首尾空白后大小写不敏感地
    等于 `Mock` 才算候选；`Mock 副本`、`Mock_2`、空白名称和非字符串都不是候选。
    非候选名称在 `match()` 里给出可读错误，调用方应先用谓词分流，普通配置继续走正式
    连接流程。`snapshot_name` 只是去首尾空白后的快照显示名称（保留大小写），模拟态
    身份由独立标志/`MOCK_CONFIGURATION_NAME` 表达，不做字符串相等判断。
  - 配置读取复用 `domain.configuration.models.TestPlan.from_dict()` 的 `test_plan`
    段：同时理解 1.2 的 `power_scan_plans` 列表与 1.1 的单段标量形状，不另写一套
    配置格式。文档不是对象、缺少 `test_plan` 段或 `test_plan` 不是对象时在比较前
    失败；错误文案区分“缺段”和“类型错误”。匹配器要求输入是已保存或已按正式格式
    规范化的文档（`test_plan` 已由编辑段重新生成），界面在匹配前先走正式保存门禁。
  - 比较事实固定为：测试频点（有序，单位必须 GHz）、衰减器（单位 dB）、压缩点（只在
    场景声明时比较，驱动映射场景没有该事实）、驱放开关/预估增益/最大输入功率、DUT
    最大输入功率、功率扫描计划（有序的起止功率与步长，单位必须 dBm）、功率基准必须
    是 `dut_input`。设备 IP、VISA 地址、配置模板文件名和电源通道设置等不参与比较。
  - 扫描来源歧义直接拒绝：`signal_source` 同时包含 `power_scan_plans` 与
    `start_power`/`stop_power`/`step` 任意旧字段时给出“只能有一个来源”的可读错误；
    检查原始键，`power_scan_plans` 为空列表时也不会替调用方选一个来源。
  - 数值比较使用 1e-9 相对容差与 1e-12 绝对容差，只吸收浮点表述误差；频点与扫描
    计划按顺序比较，不把重排当成同一份计划。超出浮点范围的 JSON 整数按“不可比较”
    处理（如 `10**400`），不会让 `OverflowError` 逃出匹配器。比较失败时一次性列出
    每个不一致场景（标题与正式测量类型）和每个不一致字段的“配置值 / Mock 数据值”，
    不因第一个字段就停止。
  - 匹配结果 `MockConfigurationMatch` 暴露去首尾空白后的快照显示名称、全部场景、
    可用测量类型和 `scenario_for()`；后续模拟会话不需要再读场景文件。各场景的配置
    摘要通过 `scenario_for(...).source_config` 取用，阶段特有字段（压缩点、校准结果
    路径）不跨场景合并。构造器接受单个场景或场景序列，拒绝空集合、非场景元素和重复
    测量类型，避免按测量类型取场景时出现歧义。
  - 覆盖：仓库跟踪的 `config.mock.json`（内容与当前保存的 Mock 快照一致）匹配全部
    三类场景；改名、频点、扫描计划、驱放开关/增益、衰减器、压缩点、DUT 上限、
    功率基准和功率单位分别得到可读错误；扫描来源冲突、超大整数溢出、非法数值、
    缺/非对象 `test_plan`、非对象文档、浮点噪声、1.1 标量扫描形状、阶段特有事实、
    构造器校验与异常分类，见 `tests/test_mock_configuration_matcher.py`。保存快照目录
    `test_results/**` 被 `.gitignore` 排除，不作为单测夹具。异常分类登记同步
    `tests/test_exception_taxonomy.py`。
  - 验证：全量测试 3915 项通过（跳过 9 项），`launcher.py --check` 与
    `launcher.py --validate-config` 退出码为 0。

## 阶段二：建立独立的模拟会话

### 步骤 4：增加模拟会话状态模型

- **范围**：`presentation/qt/application_coordinator.py` 及相关纯 Python 状态测试。
- **执行策略**：在协调器中增加显式的 `SimulationSession`/模拟模式状态，记录 Mock 配置
  身份、场景索引和固定校准结果路径；不复用 `prepared_run` 字段表达模拟状态。
- **技术决定**：模拟会话与 `RunFlowState.CONNECTED` 分开表达，避免现有正式流程把它误认
  为可连接真实仪器的运行；测量页面通过统一的会话提供器获取“正式运行或模拟会话”。
  模拟态用独立模式标志/`MOCK_CONFIGURATION_NAME` 表达，不用 `snapshot_name` 与字面量
  相等来判断身份；场景索引按测量类型取用，各阶段摘要不合并。

### 步骤 5：让“连接仪器”进入模拟会话

- **范围**：`main_window.py`、协调器最终化入口及相关 UI 测试。
- **执行策略**：`_finalize_run()` 先判断当前是否为 Mock 模式；是则先执行配置校验与
  内存规范化，再执行配置匹配、场景文件可读性检查和模拟会话提交，然后直接进入工作区；
  否仍走现有正式连接事务。
- **技术决定**：模拟分支复用 `validate_configuration()` +
  `ConfigurationAuthoringService.author_document()` 在内存中规范化并校验编辑段，再拿
  规范化后的候选文档调用 `MockConfigurationMatcher.match()`；不写 `config.json` 或
  命名快照。不能直接匹配用户编辑中的原始文档，否则可能读到旧的 `test_plan` 摘要。
  模拟分支不调用 `prepare_configuration()`、不写 `runs/`、不启动
  `InstrumentWorker`；匹配或场景检查失败时留在配置页、恢复按钮状态并显示可读原因，
  不创建半成品模拟会话，也不改变当前配置。
- **验收**：Mock 点击“连接仪器”后进入线损页；没有 VISA 连接、没有新运行目录；普通
  配置的连接和失败补偿测试全部保持原行为。
- **工作量控制**：只接入“进入模拟会话”，不在本步修改各页面的开始按钮。
- **实施记录**：
  - `finalize_configuration()` 在完成测量中、最终化中、未决端口清理等前置检查后先
    分流：已有模拟会话时拒绝重复提交；已加载 Mock 配置时调用
    `_enter_simulation()`；否则保持原正式事务。窗口仍只调用
    `finalize_configuration()`，模拟成功后走同一条 `on_instrument_connected()` 交接

    `CONNECTED`，模拟会话要求独立的 `SIMULATING`。
  - `_enter_simulation()` 顺序固定为“页面校验 → 内存规范化当前配置 → 读取并校验

    模拟会话不会重写 `config.json`。
  - Mock 路径服务由真实 GUI 的组合根 `build_mock_data_paths()` 注入；协调器只按
    `MeasurementType` 取场景/结果路径，不 import 基础设施。场景每次连接都重新读取
    并校验，数据包被删除或损坏时在进入会话前失败。
  - 覆盖：`tests/integration/test_mock_simulation_flow.py` 用真实窗口、真实配置页和
    仓库 Mock 数据走完“加载 Mock 快照 → 连接仪器 → 线损页”，断言
    `prepare_configuration`、连接 worker、`config.json` 写入与
    `app.gui_runtime.connect_instruments` 均未被调用、临时根目录没有 `runs/`、
    三个场景与会话校准输入正确；失败与重复提交路径见
    `tests/ui/test_application_coordinator.py`。

## 阶段三：实现逐点回放 worker

### 步骤 7：实现可中断的回放时钟

- **范围**：新增纯 Python 回放时钟/调度器和测试；不连接 Qt。
- **执行策略**：用注入的 clock/sleep 函数实现 500 ms 数据点间隔；用 `Event` 或取消
  token 中断等待，测试中使用 fake clock，不依赖真实 181 秒回放。
- **技术决定**：`at_ms` 仅作为数据校验和说明，不控制首期播放速度；第一条数据在启动后
  立即或经过一个 500 ms 周期的选择要固定在契约中，建议首条立即发出、后续数据间隔
  500 ms，以便点击开始后快速看到反馈。
- **验收**：数据事件间隔符合 500 ms；停止能打断等待；进度点不倒退；重复播放从头开始。
- **工作量控制**：本步只验证时序，不读取大场景文件。
- **实施记录**：
  - `presentation/qt/mock_replay.py` 是不导入 Qt 的纯 Python 回放时钟：第一条
    `data` 事件立即放行，之后相邻数据点固定等待 500 ms。等待通过注入的
    `wait_fn(seconds)` 或 `stop_event.wait(seconds)` 完成，二者都能被停止事件打断；
    `reset()` 让再次播放仍从第一条数据点立即开始。场景的 `at_ms` 只参与契约校验，
    不进入播放节奏。
  - 同一模块定义模拟完成载荷 `MockReplayCompletion`：只含测量类型、场景标题、结果
    文件名/路径与场景记录的归档摘要，摘要被深冻结；`simulated` 固定为真，展示文案
    来自统一的 `MOCK_SIMULATION_NOTICE`（“模拟数据，仅展示，未写入正式结果”），
    不复用要求正式路径的归档 DTO。
  - `mock_replay.py` 登记为纯 Python 表现层模块，架构门禁会拒绝它导入 Qt 或页面
    注册表。
  - 覆盖：首条立即/后续 500 ms、自定义间隔、停止打断等待、已停止不发送数据、
    重置后从头计时、非法间隔/停止事件/等待函数，以及完成载荷的不可变与字段校验，
    见 `tests/ui/test_mock_replay_clock.py`。

### 步骤 8：实现 MockReplayWorker 和统一信号适配

- **范围**：新增 `presentation/qt/mock_replay_worker.py`，复用 `WorkerSignals` 事件形状；
  增加 worker 单元测试。
- **执行策略**：worker 在线程中加载并校验场景，按阶段事件顺序发送 `message`、`progress`、

- **验收**：三类场景能分别回放；消息/进度/数据都能收到；场景或正式结果损坏时发 error；
  stop 后线程可退出且不发送 finished 误报。
- **工作量控制**：先用内存 callback/fake signal 测试，暂不改页面。
- **实施记录**：
