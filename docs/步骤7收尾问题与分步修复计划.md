# 步骤 7 收尾问题与分步修复计划

## 1. 文档目的

本文记录步骤 7（GUI 两阶段运行流程）审查后发现的问题，并将修复工作拆分为较小、可独立验证的步骤。

本文的使用规则：

1. 每个步骤只处理一个主要责任边界。
2. 每个步骤完成后单独运行对应测试，再进入下一步。
3. 每个步骤都应形成独立提交，提交信息说明行为变化和兼容影响。
4. 修复过程中不扩大到测量算法、仪器驱动或全量兼容层清理。

## 3. 问题清单

### 3.1 运行创建失败会遗留半成品目录

当前 `create_run_snapshot()` 先创建运行目录、写入 `config.json` 和 `manifest.json`，再写入并登记 `inputs/hardware_config.json`。如果硬件快照写入、登记或 manifest 更新失败，函数会抛出异常，但已经创建的运行目录可能继续留在磁盘上。

影响：

- 运行根目录出现无法恢复的半成品运行。
- 用户可能在运行列表中看到一个看似有效、实际缺少硬件快照的运行。
- 失败创建可能污染后续运行检查和人工审计。

### 3.2 底层创建接口允许创建不可恢复的运行

`create_run_snapshot()` 当前允许 `hardware_config=None`。这会创建只有领域配置快照、没有硬件配置快照的运行，而当前恢复流程会拒绝加载该运行。

影响：

- 创建接口的成功结果不满足当前运行契约。
- 调用方稍有遗漏就会生成不可恢复运行。
- 测试只能覆盖 GUI 主路径，无法保证其他调用方遵守契约。

### 3.3 运行契约损坏时可能回退到全局配置

主窗口的 `_measurement_config_path()` 当前对 `hardware_connection_path()` 的异常进行捕获，并回退到全局 `config.json`。这只适合尚未创建运行的兼容流程，不适合已经存在 `PreparedRun` 但快照损坏或缺失的情况。

影响：

- 已创建运行可能连接到与该运行无关的仪器地址。
- 用户看到的是某个运行的状态，实际使用的却是当前全局配置。
- 违反“运行契约存在时不回退全局配置”的核心约束。

### 3.4 硬件配置和领域配置的校验职责混杂

`_ensure_frozen_config_matches()` 当前会把 `inputs/hardware_config.json` 再按领域运行配置加载，并与运行目录中的 `config.json` 比较。

影响：

- 硬件装配配置格式被强行绑定到领域运行配置格式。
- 将来硬件快照只保留连接所需字段时，现有校验会错误失败。
- “文件完整性校验”和“两个不同快照的语义关联校验”没有清晰边界。

### 3.5 配置页回填可能保留旧控件状态

`ConfigPage.apply_config()` 已经可以回填主要字段，但部分组合框和缺失字段不会明确清空或重置。加载运行失败或配置字段不完整时，界面可能残留上一次运行的显示。

影响：

- 页面显示与当前 `PreparedRun` 不完全一致。
- 用户可能误以为页面上的旧值属于当前运行。
- 虽然测量仍使用运行快照，但 GUI 审计和操作体验不可靠。

### 3.6 测试覆盖不足和小型质量问题

当前缺少以下回归测试：

- 硬件快照失败时整个运行目录的清理。
- 创建接口禁止生成缺少硬件快照的运行。
- 运行契约损坏时绝不使用全局配置。
- 硬件快照与领域配置格式可以独立演化。
- 配置页完整重置后再回填，不残留上一次运行的值。

此外，`presentation/qt/config_page.py` 当前存在文件末尾空白行，提交前应清理。

## 4. 分步修复计划

### 步骤 A：补齐运行仓储的整目录取消接口

目标：提供一个明确的“创建失败后撤销整个运行”能力。

工作范围：

- `application/ports/run_repository.py`
- `infrastructure/persistence/run_repository.py`
- 仓储测试

建议实现：

1. 在 `RunRepositoryPort` 增加 `discard_run(run_id)` 或语义等价的 `abort_run(run_id)`。
2. 实现必须只删除指定运行目录，不允许影响其他运行。
3. 对不存在的运行定义明确行为，优先采用幂等删除。
4. 删除前后不得修改其他运行的 manifest 或结果。

验收标准：

- 可以创建两个运行并只删除其中一个。
- 删除后被撤销运行不再出现在有效运行列表中。
- 其他运行目录、manifest 和文件保持不变。
- 路径穿越参数会被拒绝。

建议测试：

- `test_discard_run_removes_only_target_run`
- `test_discard_run_is_idempotent`
- `test_discard_run_rejects_invalid_run_id`

本步骤不修改 `create_run_snapshot()`，只先提供仓储能力。

### 步骤 B：为硬件快照写入增加补偿清理

目标：硬件快照写入或登记失败时，不留下半成品运行目录。

工作范围：

- `application/run_service.py`
- `tests/test_run_service.py`

工作内容：

1. 在创建运行之后执行硬件快照写入。
2. 任意写入、登记或 manifest 更新异常都调用步骤 A 的整目录撤销接口。
3. 保留原始异常作为主要错误，不用清理异常覆盖它。
4. 清理失败时记录清理失败上下文，但仍向调用方抛出原始创建错误。

验收标准：

- 硬件文件写入失败后，运行目录不存在。
- 文件登记失败后，运行目录不存在。
- manifest 更新失败后，运行目录不存在或明确处于不可见的失败状态。
- 原始异常类型和消息仍可被调用方捕获。

建议测试：

- `test_hardware_config_write_failure_discards_run`
- `test_hardware_config_register_failure_discards_run`
- `test_hardware_config_manifest_failure_discards_run`
- `test_original_creation_error_is_preserved`

### 步骤 C：强制运行契约必须包含硬件配置

目标：任何成功创建的运行都可以按当前恢复规则重新加载。

工作范围：

- `application/run_service.py`
- `app/run_context.py`
- 直接调用 `create_run_snapshot()` 的代码和测试

建议实现：

1. 将运行契约路径下的 `hardware_config` 设为必需参数。
2. 若必须保留底层函数的旧签名，则在函数入口明确拒绝 `None`，不要创建不完整运行。
3. 保留旧版 `prepare_run()` 作为兼容快照，但明确它不属于可恢复运行契约。
4. `RunSnapshot.hardware_config_path` 对成功的运行契约快照不再允许为空。

验收标准：

- 缺少 `hardware_config` 时创建立即失败。
- 失败调用不会创建运行目录。
- 成功创建的运行一定登记 `inputs/hardware_config.json`。
- 成功创建的运行可以被 `load_prepared_run()` 重新加载。

建议测试：

- `test_create_run_snapshot_requires_hardware_config`
- `test_successful_run_snapshot_is_resumable`
- `test_legacy_prepare_run_remains_non_contract_compatible`

### 步骤 D：禁止运行契约异常时回退全局配置

目标：已经选择运行契约后，硬件配置路径异常必须明确失败。

工作范围：

- `presentation/qt/main_window.py`
- `app/gui_runtime.py`
- GUI 和运行组合测试

工作内容：

1. 仅在 `prepared_run is None` 时允许使用全局配置路径。
2. `prepared_run` 存在但冻结硬件路径无效时直接抛出明确异常。
3. 连接按钮流程捕获该异常并提示重新创建或重新加载运行。
4. 禁止异常吞掉后继续创建 `InstrumentWorker(global_config_path)`。

验收标准：

- 运行契约路径失效时，不调用全局配置连接仪器。
- 用户可以看到“运行缺少有效硬件配置快照”的明确提示。
- 旧兼容流程在没有 `PreparedRun` 时仍能使用全局配置。

建议测试：

- `test_measurement_config_path_does_not_fallback_for_contract_run`
- `test_invalid_contract_blocks_instrument_connection`
- `test_legacy_flow_still_uses_global_config`

### 步骤 E：拆分领域配置和硬件配置的校验职责

目标：硬件配置快照不再被误当作领域运行配置解析。

工作范围：

- `app/gui_runtime.py`
- 必要时调整 `application/run_service.py` 的辅助函数
- 运行恢复和组合层测试

工作内容：

1. `config.json` 继续负责领域运行配置校验。
2. `inputs/hardware_config.json` 只执行 JSON 对象校验和 manifest SHA-256/大小校验。
3. 删除或收窄“硬件快照与领域快照结构相等”的校验路径。
4. 如果需要关联两个快照，新增明确的摘要或来源字段，不通过互相套用 schema 实现。

验收标准：

- 合法但字段集合不同的硬件配置可以被加载和连接。
- 修改硬件快照内容会因 SHA-256 不匹配被拒绝。
- 修改领域配置快照内容会因领域快照校验失败被拒绝。
- 全局配置变化不会影响已创建运行。

建议测试：

- `test_hardware_snapshot_can_use_independent_schema`
- `test_hardware_snapshot_hash_tampering_is_rejected`
- `test_domain_snapshot_tampering_is_rejected`
- `test_global_config_change_is_ignored`

### 步骤 F：完善配置页的确定性回填

目标：加载运行后，配置页显示必须完整反映当前运行，不残留旧运行状态。

工作范围：

- `presentation/qt/config_page.py`
- `presentation/qt/main_window.py`
- GUI 测试

工作内容：

1. `apply_config()` 开始时重置所有受控 widget 到明确的默认值或空值。
2. 对组合框、复选框、数值框和电源通道执行完整投影。
3. 配置缺失或类型不正确时使用一致的空值策略，不保留旧值。
4. 回填失败返回可识别结果或抛出明确异常；不要静默吞掉全部错误。

验收标准：

- 先加载配置 A，再加载配置 B，页面不存在 A 的残留值。
- 配置 B 缺少字段时，相关控件显示明确默认状态。
- 页面显示值与 `PreparedRun.hardware_config` 一致。
- 回填异常不会悄悄报告为加载成功。

建议测试：

- `test_apply_config_clears_previous_values`
- `test_apply_config_projects_all_supported_fields`
- `test_apply_config_reports_invalid_payload`

## 6. 推荐提交顺序

建议按以下顺序提交，避免一次提交包含多个责任边界：

1. `fix(run): 增加运行目录撤销能力`
2. `fix(run): 创建硬件快照失败时清理运行目录`
3. `fix(run): 强制运行契约包含硬件配置快照`
4. `fix(gui): 禁止运行契约回退到全局配置`
5. `refactor(run): 分离领域配置与硬件快照校验`
6. `fix(gui): 完整回填冻结运行配置`
7. `test(run): 补齐步骤七收尾边界测试并更新文档`

每个提交完成后都应记录：

- 修改的文件范围。
- 新增或调整的测试。
- 验证命令和结果。
- 是否改变旧兼容流程。

## 7. 暂不处理的事项

为控制每步工作量，本计划暂不处理：

- 测量算法和仪器驱动重写。
- 全局兼容配置和兼容结果文件的立即删除。
- 运行目录格式升级到数据库。
- 真实硬件 smoke 测试流程改造。
- 旧运行目录的批量迁移。

这些事项应在本计划全部完成、运行契约稳定后另行拆分。

## 8. 完成判定

当以下条件全部满足时，步骤 7 收尾问题才算处理完成：

- 创建运行失败不会遗留可见半成品目录。
- 每个成功创建的运行都包含并登记硬件配置快照。
- 运行契约损坏时不会回退到全局配置。
- 领域配置和硬件配置拥有独立、清晰的校验边界。
- 加载运行后配置页不会残留其他运行的显示状态。
- 失败路径、隔离路径和兼容路径均有自动化测试。
- 全量测试、启动器检查、编译检查和差异检查全部通过。
