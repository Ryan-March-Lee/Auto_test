# 测试模式与运行身份同源问题重构计划

- 状态：进行中（步骤 1 已完成并通过真实窗口回归；步骤 2 起待实施）
- 日期：2026-11-13
- 调研依据：[`测试模式与运行身份同源问题调研简报.md`](测试模式与运行身份同源问题调研简报.md)
- 范围：`presentation/qt` 中的会话模式、运行身份、返回欢迎页流程和测量入口；不改配置/运行持久化格式及历史数据。

## 1. 目标与已确认决定

修复“新会话页面显示模式 B、底层仍持有旧运行 A 并可能按 A 启动测量”的状态错配，并让欢迎页返回语义符合现场流程：

1. **采用方案 C**：返回欢迎页表示放弃当前窗口中的运行会话。成功返回前释放当前仪器端口，清除内存中的当前运行/后台运行关联及工作台身份；不删除运行目录、配置文件或历史数据。
2. **欢迎页返回入口只保留在仪表配置/查询设备页**，用于用户刚选错测试模式时纠正。
3. **移除测试配置页的“返回欢迎页”按钮和整条返回逻辑**。用户进入配置流程后若确认链路选错，可关闭并重新启动程序。
4. 端口清理失败时不得丢弃端口引用或进入一个看似干净的新会话；留在当前流程并明确报告失败，保留人工清理/重试路径。
5. 会话模式与冻结运行模式仍明确区分；测量入口增加状态守卫，作为防止残留运行被误用的最后边界。

## 2. 当前问题与边界

- `ApplicationCoordinator.amplifier_driver_mode()` 优先采用 `prepared_run` 的冻结模式，适用于运行身份；页面 provider 和仪器排布页却把它用于下一次会话。
- 当前 `_return_to_welcome()` 只重置工作台身份，没有释放端口或清除 `prepared_run`，旧模式和旧运行仍可进入新流程。
- `resolve_measurement_run()` 未要求 `RunFlowState.CONNECTED`，仅凭旧运行和端口引用仍可能解析出旧运行。
- “返回欢迎页”同时存在于仪表配置页和测试配置页；后者还关联脏配置确认、信号、主窗口槽和多处按钮状态管理。
- 仪表配置页扫描线程采用协作取消与代次失效；返回欢迎页时要使本次扫描结果失效，不能让迟到信号恢复旧结果。

## 3. 分阶段步骤

### 阶段一：修正模式与测量契约

#### 步骤 1：为配置 UI 提供当前会话模式

- **范围**：`presentation/qt/main_window.py` 的 `PageContext` 装配、仪器排布页入口；相关 UI 测试。
- **工作量**：小（一个查询方法和两处接线）。
- **执行策略**：增加窗口级当前模式查询。配置阶段优先读取 `WorkspaceBinding` 当前会话模式；测量正在运行时使用冻结运行模式；绑定层尚未装配或没有会话模式时回退到协调器查询。
- **技术决定**：
  - `amplifier_driver_mode()` 保持“运行优先”语义，不将其改造成多语义查询。
  - `PageContext.driver_mode_provider` 和仪器排布页使用窗口级会话查询；新会话 UI 不从旧 `prepared_run` 推导模式。
  - 加载/连接成功后的身份绑定仍直接采用刚加载或刚提交运行的冻结模式。
- **验收**：旧运行 A 后选择相反模式 B，排布页与功放页都按 B 呈现；测量运行中仍按冻结运行模式呈现。
- **验证**：`tools/run_tests.py --layer ui`，覆盖 provider 的会话态、测量态和未装配回退路径。
- **完成情况**：已完成。`tests/ui/test_main_window.py` 的 `CurrentDriverModeTests` 锁定 provider 的四条路径；真实窗口回归见 `tests/integration/test_main_window_flow.py` 的 `test_new_no_driver_mode_reaches_the_rack_and_amplifier_pages`（旧运行有驱放 → 选无驱放）与 `test_new_driver_mode_restores_the_driver_chain_and_mapping_entry`（反向），同时断言旧运行仍返回其冻结模式，证明 UI 已不再读它。

#### 步骤 2：测量运行解析要求已连接状态

- **范围**：`ApplicationCoordinator.resolve_measurement_run()` 及协调器测试。
- **工作量**：小（一个守卫和测试状态调整）。
- **执行策略**：保留未决清理、无运行、无端口等现有具体错误检查；这些检查通过后，再要求流程状态为 `CONNECTED`，否则返回 `None` 并通过错误通道说明当前不在有效连接会话。
- **技术决定**：
  - `CONNECTED` 是启动测量的必要条件，不因 `prepared_run` 与端口对象仍存在而放宽。
  - 只调整模拟有效连接的既有测试状态；不改变运行加载、重连和历史查看语义。
- **验收**：`DEVICE_SELECTION` 下即使存在旧运行和旧端口也不能解析为可测量运行；`CONNECTED` 下既有有效契约照常通过。
- **验证**：运行 `tests/ui/test_application_coordinator.py` 对应测试；随后进入阶段三时运行 `--layer integration`。

### 阶段二：移除配置流程的欢迎页返回入口

#### 步骤 3：删除测试配置页按钮与页面信号

- **范围**：`config_page_widgets.py`、`test_configuration_page.py`、测试配置页 UI 测试。
- **工作量**：小（删除一个按钮及关联控件状态维护）。
- **执行策略**：从底部操作栏移除“返回欢迎页”，保留“上一步：仪表配置”和“保存配置”；移除 `return_welcome_requested` 信号、点击连接，以及 finalizing/read-only 状态中对该按钮的特判。
- **技术决定**：
  - 测试配置页的“上一步：仪表配置”仍用于当前测试链路内重新扫描/调整设备，不属于返回欢迎页功能，不删除。
  - 配置页不承担关闭程序或模式切换职责。
- **验收**：测试配置页不再创建或暴露返回欢迎页按钮；保存、上一步、只读和最终化状态行为不回归。
- **验证**：`tools/run_tests.py --layer ui`。

#### 步骤 4：移除配置页返回槽及脏配置确认

- **范围**：`main_window.py`、`welcome_page.py`、相关 UI/集成测试。
- **工作量**：小（删除单一路由和仅供其使用的确认函数）。
- **执行策略**：删除配置页到 `_return_to_welcome()` 的信号连接；删除 `confirm_leave_configuration()` 及其导入和相关测试。欢迎页返回处理只接受仪表配置页的请求。
- **技术决定**：
  - 不在配置页增加替代确认框或“放弃配置”入口；选错链路时由用户关闭并重启。
  - 配置页的“上一步”留在当前模式链路内，不能改道至欢迎页。
- **验收**：源码和运行时均只有仪表配置页的返回欢迎页路径；配置页改动不再触发返回确认对话框。
- **验证**：`tools/run_tests.py --layer ui`；集成测试确认仪表配置页的返回信号仍连通。

### 阶段三：实现返回欢迎页时的会话清理

#### 步骤 5：为协调器增加显式放弃当前会话操作

- **范围**：`application_coordinator.py` 和协调器单元测试。
- **工作量**：中（封装释放、状态检查和引用清除；不涉及 UI 重排）。
- **执行策略**：新增明确的会话放弃入口，先拒绝测量活动、连接 worker 运行中、最终化事务或其他不允许导航的状态；释放当前仪器端口并检查未决清理；只有确认清理成功后才清除 `prepared_run`、`background_run` 等当前运行引用，并将流程状态回到设备选择初态。
- **技术决定**：
  - 复用 `release_instrument_port()`、端口清理记录和现有未决清理机制，不复制关闭端口实现。
  - 清理失败时返回失败并保留未决端口引用；不清除运行身份，不伪装成成功返回。
  - “清除运行”仅清除内存中的当前会话绑定，不调用待提交运行撤销，不删除已保存运行目录或历史记录。
  - 不允许在连接 worker 或测量仍使用资源时放弃会话；调用方必须等待/拒绝操作，而非丢弃 worker 引用。
- **验收**：无端口时可安全清除旧运行；有端口时先关闭再清除；关闭失败会保留未决引用和可诊断状态；运行目录始终保留。
- **验证**：`tests/ui/test_application_coordinator.py` 覆盖成功释放、清理失败、测量活动/worker/最终化拒绝，以及历史运行数据未被删除。

#### 步骤 6：将清理结果接入仪表配置页返回

- **范围**：`main_window.py` 的返回槽、`WorkspaceBinding` 复位和集成测试。
- **工作量**：小（一个流程编排入口）。
- **执行策略**：用户请求返回时先让设备发现面板作废当前扫描并清除本次设备结果，再调用协调器的会话放弃操作。清理成功后复位工作台身份/模式并切换欢迎页；失败时留在仪表配置页，显示明确错误，不启动新模式会话。
- **技术决定**：
  - 仪表配置页按钮保持现状与位置，不扩展到其它页面。
  - 页面清理/扫描取消与硬件端口清理职责分开；端口所有权仍由协调器管理。
  - 只有会话清理成功，才允许下一次欢迎页选择；不得先切页再异步丢弃旧运行身份。
- **验收**：返回后当前运行与模式显示清空、驱动映射阶段/标签页停用；端口清理失败时不进入欢迎页；扫描中的迟到结果不能重新写回页面。
- **验证**：`tools/run_tests.py --layer integration`，覆盖无旧运行、存在已连接旧运行、端口清理失败、扫描中返回和重选相反模式。

### 阶段四：端到端回归与收尾

#### 步骤 7：清理旧行为断言并验证完整切换链路

- **范围**：测试配置页、主窗口、协调器和真实窗口集成测试；必要时更新调研/计划状态。
- **工作量**：小到中（主要为测试迁移与缺口补齐）。
- **执行策略**：移除“从测试配置页返回欢迎页”的旧集成用例；新增端到端顺序：运行 A 连接 → 返回欢迎页清理 A → 选择相反模式 B → 排布/功放 UI 按 B → 未完成新连接前测量入口拒绝旧运行。
- **技术决定**：
  - 覆盖“返回后清空的是当前会话身份，不是磁盘历史”的产品语义。
  - 只验证离线假设备与测试端口；不运行真实硬件冒烟。
  - 不为此放宽架构边界或页面/主窗口行数门禁；若装配逻辑增长，优先抽取协调器操作而非复制流程。
- **验收**：欢迎页返回入口唯一；旧运行不会影响新模式展示或启动测量；失败清理路径可见且不会丢资源；已有历史运行仍可从历史入口重新加载。
- **验证**：`tools/run_tests.py --layer integration`；按收尾门禁执行依赖锁检查、`launcher.py --check` 与 `launcher.py --validate-config`。

## 4. 执行顺序与阶段门

按步骤 1 至 7 顺序推进。阶段一先锁定模式查询和测量入口契约；阶段二去掉配置流程的欢迎页捷径；阶段三实现“清理成功才返回”的会话生命周期；阶段四完成真实窗口回归。每步仅修改其范围内的一个局部契约，验收通过后再开始依赖步骤。

## 5. 不在本计划中的工作

- 不删除或迁移已保存配置、运行目录、结果文件或历史记录。
- 不改应用层/领域层/基础设施层的正式运行和结果格式。
- 不移除仪表配置页“返回欢迎页”链接，也不移除“上一步：仪表配置”。
- 不自动启动测量，不改变重连与历史加载功能本身；返回欢迎页后需要重连时，通过历史运行显式重新加载。
- 不运行需要现场设备和授权的硬件测试。
