# 测试结果归档与导出链路盘点

本文对应 [测试结果自动归档与导出流程重构计划](测试结果自动归档与导出流程重构计划.md) 的
**步骤 1：盘点现有结果与导出链路**。

范围约定：只记录现状与调用链，不修改任何运行时行为。文中的“缺口”与“待决策契约”是后续
步骤的输入，不是本步骤的修改项。审查后修订过 8 处事实与结论，修订记录见第 10 节。

事实来源：`runs/<run_id>/manifest.json` 及其登记文件。不以 `ExportPage` 的当前行为推断测试
流程契约，也不把兼容快照目录下的结果文件当作正式结果。

---

## 1. 结论摘要

1. **GUI 生产路径的正式结果已经自动写入运行目录**：配置页创建/加载运行后，三类测试在测量
   成功的那一刻就把结果原子写入 `runs/<run_id>/` 并登记 manifest，用户不需要额外的“保存”
   动作。这是**运行契约路径**（`stage_recorder` 已注入）的行为。
2. **兼容快照路径仍在代码里**：`app.run_context.prepare_run()` 产生的无运行契约快照会让
   `stage_recorder` 为 `None`，此时用例改用 `FileMeasurementResultRepository.save()` 写文件，
   **不登记 manifest**，因此历史查询看不到这些结果。该分支目前只被离线测试和外部调用方使用。
3. **交付产物没有任何自动生成**：CSV、HTML 报告、图表只有两条手动入口（`ExportPage` 的导出
   按钮、数据可视化页的“生成报告”按钮）。
4. **运行级完成只由主功放阶段触发**：`complete_run()` 只在
   `AmplifierMeasurementUseCase` 里调用。线损或驱动映射完成后运行仍是 `running` 是**设计使然**
   （`complete_run()` 要求所有阶段 `completed/skipped`），不应在每个阶段后调用它。
5. **现有导出用例不能当自动归档用**：`ResultExportUseCase` 面向历史 `result_id`，JSON/CSV 强制
   要求用户目标路径，报告输出位置由适配器决定；它无法表达“写回运行目录的默认位置”。
6. **报告产物落在运行目录之外**：报告与手动 CSV 都写到 `test_results/report-<唯一名>/`，与重构
   计划“产物路径必须是运行目录内的受控相对路径”冲突，必须在步骤 2 冻结契约。
7. **测试完成后的用户反馈里没有结果状态**：worker 只发“XX测量完成！”，页面只填结果表格；
   结果 DTO 里的 `result_reference["archive_path"]` 已存在但界面从未使用，页面也不应自行判断
   文件是否存在。
8. **自动归档的唯一正确编排位置是应用层测量用例的提交完成点**，不是 Qt 页面、worker、
   基础设施适配器，也不是 `RunStageRecorder` 内部；详见第 7 节。

## 2. 两条结果写入路径

同一个用例类在两种运行形态下走不同分支，盘点时必须分开，否则会得出错误的“已自动归档”结论。

| 维度 | 运行契约路径（GUI 生产） | 兼容快照路径（`prepare_run`） |
| --- | --- | --- |
| 运行创建 | `app/gui_runtime.prepare_configuration()` → `create_prepared_run()` → `RunRepository.create_run` | `app/run_context.prepare_run()` → `write_run_snapshot()` |
| 目录 | `test_results/runs/<run_id>/`（`config.json`、`manifest.json`、`inputs/`、`results/`） | `test_results/<run_id>/`（`test_plan_snapshot.json`、`run_mapping_snapshot.json`、`run_metadata.json`） |
| `PreparedRun.run_repository` | 有 | `None` |
| `stage_recorder` | `RunStageRecorder`（由 `app/gui_runtime._request_kwargs` 注入） | `None` |
| 结果写入 | `RunStageRecorder.complete()` → `write_run_json` + `register_file` + `update_manifest` | `FileMeasurementResultRepository.save()` |
| 写入文件 | `inputs/cable_loss.json`、`inputs/driver_mapping.json`、`results/amplifier_measurement*.json` | `<run_directory>/<type>_results.json` + `<type>_model.json` |
| manifest 登记 | 有，含 SHA-256 与大小 | 无（该目录没有 manifest） |
| 历史查询可见 | 是 | 否（历史只枚举 `test_results/runs/`） |
| 阶段/运行状态 | 有完整状态机 | 无 |

兼容路径的关键行为（`infrastructure/persistence/json_result_repository.save_measurement_result`）：
写入 `<result_type>_results.json` 与 `<result_type>_model.json` 两个文件，任一目标已存在时抛
`FileExistsError`（拒绝覆盖），失败回滚本次写入，且**不写 manifest**。因此“兼容快照里有结果
文件”不等于“这是一次可追溯的正式运行”。

## 3. 三类测试的调用链与完成登记

三类测试共用“页面 → controller → worker → 应用用例 → 阶段记录器”的通路，差异只在写入路径
与完成登记。

```text
<Page>.run_*()
  -> MeasurementController.start_<kind>()            presentation/qt/measurement_controller.py
  -> <Kind>Worker.run()                              presentation/qt/workers.py
  -> create_<kind>_measurement()                     app/gui_runtime.py（组装层）
  -> <Kind>UseCase.measure_all_frequencies()         application/measurements/
  -> _begin_stage()  -> RunStageRecorder.start()     application/run_stages.py
  -> _save()         -> RunStageRecorder.complete()  application/run_stages.py
  -> RunRepository.write_run_json / register_file / update_manifest
```

在运行契约路径下，`RunStageRecorder` 是**阶段结果与阶段/运行状态变更**的唯一写入者（运行创建
时的初始 manifest 由 `RunRepository.create_run` 写入，兼容快照的结果由
`FileMeasurementResultRepository` 写入）；“文件写入完成 → 校验登记 → 更新 manifest”的顺序只在
它内部实现。

### 3.1 线损 `cable_loss`

| 项目 | 现状 |
| --- | --- |
| 用户入口 | `presentation/qt/cable_loss_page.py` → `MeasurementController.start_cable_loss()` |
| 用例 | `application/measurements/cable_loss.py::CableLossUseCase` |
| 阶段开始 | `measure_all_frequencies()` → `_begin_stage()` → `RunStageRecorder.start("cable_loss")` |
| 第一段测量 | `measure_all_frequencies()` 只测路径 1，返回 `waiting_for_continue`，**不写结果文件** |
| 结果写入 | `continue_to_step2()` → `_save()` → `_save_to_run_directory()` → `_record_complete()` → `complete("cable_loss", payload)` |
| 写入文件 | `inputs/cable_loss.json`（`domain/run/models.py::STAGE_RESULT_PATHS`） |
| 阶段完成登记 | 同一次 `complete()`：`register_file()` 后 `manifest.transition_stage(completed, result=...)` |
| 运行级完成 | 不触发，运行保持 `running`（合理：后续阶段未完成） |
| 返回给上层的位置 | `result.with_saved_result(archive_path=<运行目录内绝对路径>)` |

### 3.2 驱动映射 `driver_mapping`

| 项目 | 现状 |
| --- | --- |
| 用户入口 | `presentation/qt/driver_mapping_page.py` → `MeasurementController.start_driver_mapping()` |
| 用例 | `application/measurements/driver_mapping.py::DriverPowerMappingUseCase` |
| 阶段开始 | `measure_all_frequencies()` → `_begin_stage()` → `start("driver_mapping")` |
| 输入来源 | 当前运行 `inputs/cable_loss.json`（`_read_run_cable_loss()` 经 `verified_result_path()` 校验） |
| 结果写入 | `_save()` → `_save_to_run_directory()` → `_record_complete()` → `complete("driver_mapping", payload)` |
| 写入文件 | `inputs/driver_mapping.json` |
| 阶段完成登记 | 同一次 `complete()` |
| 运行级完成 | 不触发，运行保持 `running` |
| 返回给上层的位置 | `result_reference["archive_path"]` |

### 3.3 主功放 `amplifier`

| 项目 | 现状 |
| --- | --- |
| 用户入口 | `presentation/qt/amplifier_page.py` → `MeasurementController.start_amplifier()` |
| 用例 | `application/measurements/amplifier_test.py::AmplifierMeasurementUseCase` |
| 阶段开始 | `_begin_stage()`：驱动模式关闭时先 `skip("driver_mapping")`，再 `start("amplifier")` |
| 结果写入 | `measure_all_frequencies()` → `_save()` → `_save_to_run_directory()` → `_record_complete()` |
| 写入文件 | 主结果 `results/amplifier_measurement.json`；每频率拆分文件 `results/amplifier_measurement_<freq>.json` 经 `extra_files` 一并写入并登记 |
| 阶段完成登记 | `complete("amplifier", payload, result_path=..., extra_files=...)` |
| 运行级完成 | 有：随后调用 `complete_run()`，把阶段全为 `completed/skipped` 的运行收敛为 `completed` |
| 返回给上层的位置 | `result_reference["archive_path"]`（主结果路径） |

### 3.4 差异一览

| 维度 | 线损 | 驱动映射 | 主功放 |
| --- | --- | --- | --- |
| 结果文件 | `inputs/cable_loss.json` | `inputs/driver_mapping.json` | `results/amplifier_measurement.json` + 拆分文件 |
| 需要前置阶段 | 无 | 线损 | 线损（+ 驱动映射，若启用） |
| 触发运行级完成 | 否 | 否 | 是 |
| 支持 CSV 导出 | 否（`_require_amplifier`） | 否 | 是 |
| 支持报告导出 | 否 | 否 | 是 |
| 可跳过的阶段 | — | — | `driver_mapping`（未启用驱动模式） |

## 4. 运行目录实际生成的文件

| 文件 | 生成时机 | 生成位置 |
| --- | --- | --- |
| `config.json` | 创建运行时 | `application/run_service.py::create_run_snapshot` |
| `manifest.json` | 创建运行时及每次阶段/运行状态变化 | `infrastructure/persistence/run_repository.py` |
| `inputs/hardware_config.json` | 创建运行时（硬件配置快照） | `application/run_service.py::_freeze_hardware_config` |
| `inputs/cable_loss.json` | 线损第二段完成时 | `RunStageRecorder.complete` |
| `inputs/driver_mapping.json` | 驱动映射完成时 | `RunStageRecorder.complete` |
| `results/amplifier_measurement.json` | 主功放完成时 | `RunStageRecorder.complete` |
| `results/amplifier_measurement_<freq>.json` | 主功放完成时 | `RunStageRecorder.complete` + `_split_result_files` |
| CSV / 图表 / HTML 报告 | **不在运行目录，也不自动生成** | 手动导出时写入用户选择的位置或 `test_results/report-<唯一名>/` |
| 兼容快照结果 | 仅兼容路径 | `test_results/<run_id>/<type>_results.json` + `<type>_model.json`（无 manifest 登记） |

manifest 中**没有“产物”概念**：`FileReference` 只有 `path`、`stage`、`sha256`、`size_bytes`、
`created_at`、`description` 等字段；`outputs` 目前只被主功放拆分结果文件使用。因此“CSV 已生成/
失败”这类状态今天无处登记，步骤 2 需要扩展 manifest 或新增产物记录。

路径约束（步骤 2 必须遵守）：`RunRepository.write_run_json` / `register_file` 通过
`_classify()` 只接受 `inputs/` 或 `results/` 下的路径，其它前缀直接抛 `ValueError`。新增
`artifacts/` 目录需要同时修改 `_classify`、`RunDirectoryLayout`、manifest 模型与历史列表过滤；
把产物放在 `results/` 下并以 `stage=None` 登记则不会出现在历史结果列表（`_result_entries` 只
收录属于已知 stage 的 `outputs`）。

## 5. 失败、取消与状态语义

### 5.1 阶段写入路径

| 场景 | 现状行为 |
| --- | --- |
| 结果写入/登记/manifest 更新失败 | `complete()` 回滚本次已写入文件并抛出；用例 `except` → `_record_failure()` → `fail()` 把阶段置 `failed`、运行置 `failed`，异常继续上抛到 worker |
| 测量过程中失败 | `_record_failure()` → `fail()`；`fail()` 先删除阶段标准路径上的未提交文件 |
| 用户停止/取消/紧急停止 | `_record_cancel()` → `cancel()`；阶段置 `cancelled`、运行置 `cancelled`，不保留阶段结果 |
| 阶段已终态时再次写入 | `complete()` 抛 `ValueError`（防覆盖保护，不是缺陷） |
| `fail()`/`cancel()` 自身写入失败 | 只 `logger.exception()`，不改变测量结果也不提示用户；manifest 可能仍停留在 `running` |
| 主功放 `complete_run()` 失败 | 阶段已 `completed`（`_stage_open` 已置 `False`），运行仍 `running`；异常上抛，worker 走 `_failed()` 汇报“测量失败” |

### 5.2 运行状态语义

- 运行创建后为 `created`，第一个阶段开始时转 `running`。
- 阶段级完成（`completed`）与运行级完成（`completed`）是两层语义：只有所有阶段
  `completed/skipped` 才允许 `complete_run()`。
- 因此“只做了线损/驱动映射”的运行会长期停留在 `running`，这是**部分运行**，不是状态机缺陷；
  历史列表以 `finished_stages < total_stages` 表达它。
- 真正缺的是 UI/DTO 层没有区分“本阶段已完成”“整次运行已完成”，用户只能看到“XX测量完成！”。

### 5.3 用户可见反馈

- worker 成功路径只发一条消息：`线损测量完成！` / `驱动映射测量完成！` / `主功放测量完成！`。
- 测量页面把结果 DTO 填进表格，不显示结果位置、不显示产物状态。
- 导出页/可视化页的失败提示只覆盖导出动作本身，与测试执行成功与否没有关联表达。

## 6. 导出链路现状

### 6.1 调用关系

```text
ExportPage.export(format)                       presentation/qt/export_page.py
  -> HistoryViewModel.reload()/select()         presentation/qt/history_view_model.py
  -> ResultQueryPort.list_results()             application/ports/gui_data_service.py
  -> ResultQueryAdapter                          infrastructure/gui_data_service.py
  -> FileRunHistoryRepository                    infrastructure/persistence/run_history_repository.py
     （数据源：runs/<run_id>/manifest.json 登记的阶段结果）
  -> ExportRequest(result_id, format, target)   application/dto/export_requests.py
  -> ResultExportUseCase.execute()              application/export_service.py
  -> ResultExportPort                           application/ports/gui_data_service.py
  -> ResultExportAdapter                        infrastructure/gui_data_service.py
  -> DataVisualization                          analysis/visualization.py
```

装配：`presentation/qt/composition.py::build_gui_data_service` → `application/gui_data_service.py::
GuiDataService`，导出用例作为 `GuiDataService.export_requests` 暴露；`ResultQueryAdapter` 与
`ResultExportAdapter` 共用同一个 query 实例。

### 6.2 三种导出格式

| 格式 | 目标位置 | 实际生成 | 前置判定 |
| --- | --- | --- | --- |
| JSON | 用户在 `QFileDialog` 选择 | `export_json` 逐字节复制已校验源文件 | 结果必须在历史列表中 |
| CSV | 用户在 `QFileDialog` 选择 | `export_csv` → `generate_csv_report` 在 `test_results/report-<唯一名>/` 生成 `full_sweep_data.csv`，再复制到目标 | 结果必须为主功放结果 |
| 报告 | 由导出端口决定，请求不得携带目标 | `export_report` → `create_summary_report` 在 `test_results/report-<唯一名>/` 生成 HTML + 图表 + CSV | 结果必须为主功放结果 |

约定已写进代码：JSON/CSV 的 `ExportFormat.needs_target is True`，报告为 `False`；`export_report`
返回空值或非字符串即判失败（`ResultExportUseCase._export_report`）。注意：**手动 CSV 导出也会
在 `test_results/report-*` 留下中间目录**，不会自动清理。

### 6.3 与历史查询的耦合

- `result_id` 是基础设施内部编码 `run::<run_id>::<运行内相对路径>`（`_encode_run_result_id`），
  应用层没有该函数。
- 导出前必须用 `list_results()` 核对标识，因此自动归档无法凭空构造 `result_id` 去调用
  `ResultExportUseCase`；应用层需要“按 run_id + 阶段读取”的能力（步骤 2/3 的契约决策）。
- 历史列表只排除 `RunHistoryState.INVALID` 的运行；`running` 状态的运行仍可浏览、可导出，
  所以“测试未完成”与“结果已登记”在导出侧没有区分。

### 6.4 “最新结果”的现有调用点（步骤 8 的清理范围）

| 调用点 | 用途 |
| --- | --- |
| `presentation/qt/visualization_page.py::generate_report()` | 未加载结果时用 `history.load_latest(AMPLIFIER_RESULT_TYPE)` 兜底生成报告 |
| `presentation/qt/history_view_model.py::load_latest()` | 上一项的实现，基于 `ResultQueryPort.latest_result()` |
| `presentation/qt/main_window.py::_load_cable_loss_result()` | 线损页“加载结果”按钮，直接调用 `results.latest_result("cable_loss")` |

三处都只用于**查看/报告**，没有进入测量输入；但报告来源因此不是显式选择的 `run_id`。

### 6.5 现有架构门禁

- `tests/test_architecture_dependencies.py` 强制：导出页面只能构造 `ExportRequest` 并调用
  `execute()`；`application/export_service.py` 不得导入 `infrastructure` 或 `PySide6`。
- `application/` 目前完全不导入 `analysis.`。因此自动生成 CSV/报告必须走端口，不能在应用层
  直接 `import analysis.reporting`（计划步骤 4 的“复用 `export_csv`”要落成“复用端口能力”）。

## 7. 自动归档应接入的应用层边界

**结论：接入点是应用层测量用例的“成功提交完成点”，由新增的统一归档服务承担。**

| 测试 | 接入位置 | 已有上下文 |
| --- | --- | --- |
| 线损 | `CableLossUseCase.continue_to_step2()` 中 `result = self._save(result)` 之后 | `run_id`、`run_directory`、结果 DTO、`FileReference` |
| 驱动映射 | `DriverPowerMappingUseCase.measure_all_frequencies()` 中 `result = self._save(result)` 之后 | 同上 |
| 主功放 | `AmplifierMeasurementUseCase._record_complete()` 中 `complete()` 与 `complete_run()` 都成功后 | 同上，且运行级状态已收敛 |

理由：

1. 这三个位置已经是“正式结果已写入并登记、阶段状态已确定”的唯一边界，归档服务无需重新推断
   阶段状态。
2. 归档需要 `run_id` 与结果 DTO；只有应用层同时持有两者，页面拿到的是展示引用，worker 只是
   转发者。
3. `RunStageRecorder` 应继续只做“保存 + 登记 + manifest 更新”，不注入导出端口，否则阶段记录器
   会同时承担交付产物职责，失败语义互相污染。
4. 与重构计划 2.2 一致：应用层不导入基础设施实现，产物生成经端口完成。

**复用范围的技术决定**：`ResultExportUseCase` 保留给历史手动导出（副本、格式转换），不复用为
自动归档入口；自动归档需要一个面向“正式结果 + 受控运行内目标路径”的新端口，内部再由基础设施
适配器复用 `analysis` 能力。

明确不应接入的位置：

- `presentation/qt/*`：页面无法判断文件是否存在，也不应拼接导出规则（门禁已禁止页面直接调用
  导出端口）。
- `presentation/qt/workers.py`：只负责线程与信号转发，没有 run 契约与仓储。
- `infrastructure/gui_data_service.py`：适配器无编排职责，且归档跨“写入 + 导出”两个端口。
- `RunStageRecorder.complete()` 内部：会让底层 manifest 写入依赖交付产物，违背“manifest 是
  正式结果唯一事实来源”的分层。

## 8. 待步骤 2 决策的契约问题

1. **产物路径**：报告与 CSV 落到运行目录内（推荐）还是继续留在 `test_results/report-*`；若进
   运行目录，按第 4 节的 `_classify` 约束选择 `results/` 子目录或扩展 `artifacts/`。
2. **产物登记**：扩展 manifest（新增产物集合与状态字段）还是新增运行内 `artifacts.json`；
   旧 manifest 必须保持可读。
3. **产物状态取值**：`pending` / `completed` / `failed` / `not_applicable` 与测试状态的组合规则。
4. **幂等与覆盖**：以 `run_id + result_id + kind` 判定已完成产物；正式结果永不覆盖；只有显式
   “重新生成”允许覆盖交付产物（`complete()` 现有的终态拒绝保持不变）。
5. **部分运行报告**：只有主功放完整成功才生成报告；线损、驱动映射、取消与异常运行登记
   `not_applicable`。
6. **页面展示口径**：页面只接收结构化归档 DTO（含 `run_id`、运行内相对路径、产物状态），不读
   绝对路径、不做存在性判断。

## 9. 现状缺口清单（供步骤 2～9 使用）

| 编号 | 缺口 | 影响 | 对应计划步骤 |
| --- | --- | --- | --- |
| G1 | 完成路径不生成任何交付产物（CSV/报告） | 用户必须手动导出 | 步骤 4、5 |
| G2 | `ResultExportUseCase` 只认历史 `result_id`，JSON/CSV 强制用户目标路径 | 无法表达“写回运行目录默认位置” | 步骤 2、3 |
| G3 | 报告与手动 CSV 产物写在 `test_results/report-*`，不在运行目录 | 与“运行目录内受控路径”冲突 | 步骤 2（需决策） |
| G4 | UI/DTO 不区分“阶段完成”与“运行整体完成” | 用户看到“测量完成”却不知道运行还剩阶段 | 步骤 2、6 |
| G5 | 没有归档状态 DTO；页面不显示结果位置与产物状态 | 用户无法确认是否已保存、产物是否生成 | 步骤 2、6 |
| G6 | 报告生成有两处实现，且三处“最新结果”入口 | 规则分散、来源不可追溯 | 步骤 8 |
| G7 | `result_id` 编码只在基础设施内部；应用层无“按 run_id + 阶段取结果”的能力 | 自动归档与历史重试无法复用同一入口 | 步骤 3、7 |
| G8 | 空数据时 `generate_csv_report()` 返回 `None` 并 `print`，导出侧表现为 `FileNotFoundError` | 自动流程需要显式“不适用/空数据”判定 | 步骤 2、4 |
| G9 | 没有“已归档”幂等语义（阶段终态拒绝覆盖，但产物状态无处记录） | 重复触发与重试语义不明 | 步骤 3、9 |
| G10 | `fail()`/`cancel()` 自身写入失败只写日志；`complete_run()` 失败时阶段已 completed 而运行仍 running | 归档状态可能与实际文件不一致 | 步骤 3、9 |
| G11 | 页面/worker 的完成提示不含运行 ID、结果相对路径与产物状态 | 失败时用户无法定位、无法重试 | 步骤 6 |
| G12 | `_classify()` 只允许 `inputs/`、`results/` | 直接在运行目录新增 `artifacts/` 会被仓储拒绝 | 步骤 2 |
| G13 | 兼容快照结果不登记 manifest，历史列表不可见 | “结果文件存在”不等于“正式运行结果” | 步骤 9（迁移/删除时机） |
