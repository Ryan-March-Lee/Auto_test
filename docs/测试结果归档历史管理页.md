# 测试结果归档：历史运行/结果管理页（步骤 7）

本文对应 [测试结果自动归档与导出流程重构计划](测试结果自动归档与导出流程重构计划.md) 的
**步骤 7：将 `ExportPage` 改为历史结果管理页**。它建立在
[测试结果归档契约](测试结果归档契约.md)（步骤 2）、[归档服务](测试结果归档服务.md)
（步骤 3）、[CSV 自动生成](测试结果归档CSV自动生成.md)（步骤 4）、
[报告自动生成](测试结果归档报告自动生成.md)（步骤 5）与
[主测试页面显示归档结果](测试结果归档结果展示.md)（步骤 6）之上，不重新定义归档状态。

本步骤完成四件事：

1. 正常测试已经自动归档，页面不再承担“首次保存”职责：原来的“数据导出”页收敛为
   **历史运行/结果管理**，标题、分组与按钮文案同步改写；
2. 默认视图从“文件列表”改为**运行 → 阶段 → 正式结果 → 交付产物**状态，用户能定位
   某次运行以及它缺了哪个产物；
3. JSON/CSV/报告按钮降级为“导出副本”，只有用户明确需要另一份文件时才弹出保存对话框；
4. 新增“重新生成失败的产物”：只对**已登记的运行**、只对**失败的产物**重试，产物写回
   原运行目录，不新增页面、不复制导出规则。

## 1. 入口与模块

| 模块 | 名称 | 职责 |
| --- | --- | --- |
| `application.dto.run_history` | `RunHistorySummary`、`RunStageSummary`、`RunArtifactSummary`、`RunArchiveState` | 只读视图 DTO：运行可用性三档、阶段状态与正式结果标识、产物状态与失败原因；只带运行内相对路径，不读文件、不判断文件存在、无页面文案 |
| `application.ports.gui_data_service` | `RunArchiveStatusPort` | 历史运行状态查询端口：`list_run_summaries()`，由运行目录适配器实现 |
| 同上 | `RunHistoryServicePort` | 历史管理用例入口：`list_runs()` + `regenerate_failed_artifacts(run_id)` |
| `application.run_history_service` | `RunHistoryService`、`RunHistoryRequestError` | 用例：列表转交只读端口；重新生成前核对 `run_id` 在历史列表中，再以 `retry_failed=True` 调用归档服务 |
| `infrastructure.persistence.run_history_repository` | `FileRunHistoryRepository.list_run_summaries()` | 读 manifest 得出运行/阶段/产物状态；`list_runs()` 与它共用同一份可用性判定（`_inspect`） |
| `application.gui_data_service` | `GuiDataService.run_history` | 门面新增历史管理入口，页面只依赖 `GuiDataServicePort` 暴露的窄接口 |
| `presentation.qt.composition` | `build_gui_data_service()` | 装配 `ResultArchivalService` + `ArchiveArtifactGenerator`，让历史重试复用自动归档的同一条实现 |
| `presentation.qt.history_view_model` | `HistoryViewModel.run_rows` / `reload_runs()` / `select_run()`、`RunHistoryRow` | 把运行摘要转成展示文本（运行状态、阶段进度、结果数、产物状态、阻塞原因）与 `can_regenerate` 事实；纯 Python，无 Qt、无路径 |
| `presentation.qt.export_page` | `ExportPage`、`build_history_page()` | 历史管理页：运行表格、结果表格、重新生成与导出副本；`build_history_page()` 只做装配，窗口不再逐项拼装页面内部结构 |
| `presentation.qt.pages` | `PageDefinition("export", "历史运行", ...)` | 保留路由与 key，只改用户可见标题 |
| `presentation.qt.main_window` | `create_data_export_tab()` | 调用 `build_history_page()`；主窗口仍只做页面装配 |

调用形状：

```python
# 列表：只读端口 -> 用例 -> 视图模型 -> 表格
summary = FileRunHistoryRepository(runs=RunRepository(paths)).list_run_summaries()
service = RunHistoryService(statuses=history, archival=ResultArchivalService(...))
row = HistoryViewModel(query, runs=service).reload_runs()[0]

# 重新生成：页面只给 run_id
outcome = service.regenerate_failed_artifacts(row.run_id)   # retry_failed=True
```

## 2. 页面结构与文案

运行表格固定七列，全部来自 `RunHistoryRow`：

| 列 | 内容 | 来源 |
| --- | --- | --- |
| 运行 | `run_id` | `RunHistorySummary.run_id` |
| 创建时间 | `YYYY-MM-DD HH:MM:SS` | `created_at` |
| 状态 | 运行状态；不可用时追加“（结构不完整/不可用）” | `run_status` + `RunArchiveState` |
| 阶段 | `已完成/总阶段 已完成`，无阶段时 `—` | 阶段记录 |
| 正式结果 | `N 个正式结果` | 已登记结果的阶段数 |
| 交付产物 | `CSV 已生成、报告 失败` 这类逐项状态；没有产物时“无交付产物” | manifest 产物记录 |
| 说明 | 运行级阻塞原因与每个失败产物的原因；不可用运行在这里说明为什么不能浏览 | `problem` + 失败产物 `error` |

结果表格保留“文件名/类型/来源/修改时间”，继续作为“导出副本”的数据来源；来源列仍显示
`运行 <run_id>`。

操作分组：

| 按钮 | 行为 | 可用条件 |
| --- | --- | --- |
| 重新生成失败的产物 | 调用 `RunHistoryServicePort.regenerate_failed_artifacts(run_id)`，写回原运行目录 | 选中运行 `can_regenerate`（结构完整 + 有失败且能定位阶段的产物） |
| 导出JSON/CSV/测试报告副本 | 构造 `ExportRequest`，由 `ResultExportUseCase` 执行 | 已选中历史结果，且**结果所属运行**可浏览（见第 4 节） |

页面在 `on_activated()` 与构造时刷新两份列表；测量完成后主窗口仍调用
`refresh_file_list()`，因此结果列表不会比运行列表更陈旧。

## 3. 重新生成的边界

- **只对失败产物**：状态迁移沿用 `ARTIFACT_STATUS_TRANSITIONS`——`failed → pending` 只能
  经显式 `retry_failed=True`，`completed` 与 `not_applicable` 保持终态。页面按钮在没有
  失败产物时禁用，服务端也会拒绝（“没有失败的交付产物，无需重新生成”）。
- **只接受已登记的运行**：`RunHistoryService` 自己重新列一遍运行摘要并核对 `run_id`；
  任意字符串、不存在或不可用的运行都被拒绝，页面无法凭路径触发归档。
- **阶段由应用层决定**：阶段取自已登记产物所属的阶段（`RunArtifactSummary.stage`，由
  适配器把 `source_result` 对应到 manifest 阶段），页面不传阶段。
- **写回原运行目录**：复用 `ResultArchivalService`，产物目标仍是
  `artifacts/<stage>.csv` / `artifacts/<stage>_report.html` 这类受控相对路径；需要另存文件
  时走“导出副本”，两条路径不混用。
- **失败不吞**：归档契约失败（`ArchivalRequestError`、manifest 写回失败）转成
  `RunHistoryRequestError`，页面写日志并弹窗；产物级失败仍由归档服务登记为 `failed` 并
  在刷新后的表格里可见。

## 4. 导出副本与运行可用性的拦截

- 导出仍然只针对历史查询端口返回的结果标识：`ResultExportUseCase` 会核对 `result_id`
  在历史列表中，页面只持有 `row.result_id`。
- **判定绑定结果所属的运行**：`ExportPage._export_blocker()` 用 `HistoryRow.run_id` 反查
  运行摘要（`HistoryViewModel.run_row()`），不只看运行表格的当前选中行。两张表格可以
  各选一行，只看选中行会出现“界面显示某运行不可用、实际导出另一次运行的结果”的情况。
  以下情形一律拒绝导出，且不打开保存对话框：
  1. 运行表格里选中了不可用的运行（`INVALID`）；
  2. 结果所属运行不在历史运行列表里（含未登记到运行目录的结果）；
  3. 结果所属运行与选中运行不是同一次运行（提示用户选择该运行自己的结果）。
  未选中运行行时以结果所属运行为准；未装配运行摘要来源（可视化页复用本页面）时只保留
  第 1 项基础判定，其余交给导出用例与历史查询端口。
- 无效运行（manifest 缺失/损坏、`run_id` 与目录名不一致）不会出现在结果列表里；若用户在
  运行表格里选中了这类运行，页面在调用导出前直接拒绝并提示“不能导出其结果”，连保存
  对话框都不会打开。
- 结构不完整但可浏览的运行（`INCOMPLETE`）仍允许导出副本，但页面会通过状态列与说明列
  显示“结构不完整”与原因，不把缺配置快照的运行描述成完整成功。
- 运行摘要读取失败不会让页面构造或切换标签页失败：运行表格清空、重新生成按钮禁用、
  原因写入日志，结果列表仍可用（刷新即可恢复）。

`tests/test_run_history_page.py`（30 项）覆盖：

- DTO：可用性三档；`invalid` 必须有原因且不携带阶段/产物；创建时间必须带时区；
  `can_regenerate` 只在“结构完整 + 失败产物能定位阶段”时成立；空阶段名/空产物阶段被拒绝；
- `RunHistoryService`：列表转交端口与端口失败上报；重新生成传对 `run_id`/阶段且
  `retry_failed=True`；未知运行、不可用运行、无失败产物、未装配归档服务、归档契约失败
  各自明确报错；构造期拒绝缺少端口方法的对象；
- `FileRunHistoryRepository.list_run_summaries`：阶段与产物状态来自 manifest；重新生成后
  产物变为 `completed`；损坏运行只列可用性与原因；`list_runs()` 的阶段/结果计数保持不变；
- `HistoryViewModel`：运行摘要的展示文本、不可用运行的状态与说明、选中项清理、
  未配置摘要来源时明确失败；
- `ExportPage`：运行表格显示状态与产物、按失败产物启用重新生成、重新生成把 CSV/报告写回
  运行目录并刷新、不可用运行禁止导出且不打开保存对话框、可浏览运行仍能导出副本、
  未装配运行服务时只显示结果列表；
- 组合根：`GuiDataService.run_history` 装配到位，`build_history_page()` 能直接建立页面；
- 重新生成文案：逐个产物说明“已生成/未生成/不适用”，非 DTO 返回值被拒绝。
