# 测试结果归档契约（步骤 2）

本文对应 [测试结果自动归档与导出流程重构计划](测试结果自动归档与导出流程重构计划.md) 的
**步骤 2：定义归档状态与产物契约**，并冻结后续步骤赖以实现的路径、状态和幂等规则。

本步骤只建立契约与测试：新增归档 DTO、manifest `artifacts` 记录、产物路径策略和兼容读取，
不接入任何测量完成流程，不生成 CSV/报告，也不改变现有导出页面行为。

---

## 1. 事实边界

| 类别 | 唯一事实来源 | 是否参与自动归档 | 历史查询可见 |
| --- | --- | --- | --- |
| 正式结果 | `runs/<run_id>/manifest.json` 及其登记的阶段结果 | 是，归档的前置条件 | 是 |
| 交付产物 | 同一 manifest 的 `artifacts` 集合 | 是，由自动归档生成 | 步骤 6/7 接入 |
| 兼容快照结果 | `test_results/<run_id>/`（无 manifest） | **否** | 否 |

兼容快照路径（`app.run_context.prepare_run()`）仍然存在，但它写出的结果没有 manifest
登记，不属于正式结果，也不允许进入自动归档。归档服务只接受已登记到 manifest 的正式结果。

---

## 2. 运行目录与 manifest v2

### 2.1 目录

```text
runs/<run_id>/
  manifest.json
  config.json
  inputs/                 # 阶段输入与固定阶段结果
  results/                # 主功放结果与拆分结果
  artifacts/              # 自动归档交付产物（新增，受控）
```

- `artifacts/` 由 `RunDirectoryLayout.artifacts_dir` 定义，新运行创建时自动建立。
- 旧运行可能没有该目录，读取 manifest 和浏览历史不依赖它存在。
- 产物路径必须是运行目录内的 POSIX 相对路径，并且以 `artifacts/` 开头；绝对路径、
  盘符、`..` 片段和 `results/`、`inputs/` 下的路径一律拒绝
  （`normalize_artifact_path()`）。

### 2.2 默认路径

默认路径集中在 `domain.run.models.default_artifact_path(stage, kind)`：

| 产物 | 主功放 | 线损 | 驱动映射 |
| --- | --- | --- | --- |
| CSV | `artifacts/amplifier.csv` | 不适用 | 不适用 |
| 报告 | `artifacts/amplifier_report.html` | 不适用 | 不适用 |

报告引用的图表文件与报告同目录（例如 `artifacts/*.png`），属于报告产物的一部分，
不单独登记为独立产物：否则同一来源结果会出现多条 `plot` 记录，与
`(source_result, kind)` 幂等键冲突。

报告只是**引用**同目录的兄弟文件，不假设它存在：数据链接（CSV）只在对应的 CSV 产物已登记
为 `completed` 且 `verify_artifact()` 复核通过时才写入，否则省略链接；引用一律只写文件名，
不写绝对路径。

用户手动导出仍可选择任意目标路径；自动归档不依赖用户选择，也不弹保存对话框。

### 2.3 `ArtifactRecord`

manifest v2 新增可选集合 `artifacts`，每项字段如下：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `kind` | `csv` / `report` | 交付产物类型；图表属于报告产物，不单独登记 |
| `status` | `pending` / `completed` / `failed` / `not_applicable` | 见 2.4 |
| `path` | 字符串或 null | 仅 `completed` 必填，必须是 `artifacts/` 下的相对路径 |
| `source_result` | 字符串或 null | 产生该产物的正式结果路径，必须是 `inputs/` 或 `results/` 下的相对路径；`pending`、`completed`、`failed` **必填**，只有 `not_applicable` 可省略 |
| `error` | 字符串或 null | 仅 `failed` 必填 |
| `created_at` | 字符串或 null | UTC ISO-8601 时间戳 |
| `sha256` | 字符串或 null | 仅 `completed` 必填，64 位小写十六进制 |
| `size_bytes` | 整数或 null | 仅 `completed` 必填，非负 |

幂等键是 `(source_result, kind)`：同一运行内同一来源结果的同类产物只有一条记录。
`pending`、`completed`、`failed` 必须登记 `source_result`，否则幂等键失效、产物无法追溯到
哪份正式结果；只有 `not_applicable` 允许省略来源结果（该阶段没有交付产物）。

manifest 上的入口：

| 方法 | 行为 |
| --- | --- |
| `find_artifact(kind, source_result=...)` | 按幂等键查找，缺失返回 `None` |
| `with_artifact(record, now=...)` | 首次登记追加；已有同键记录时必须满足 2.4 的状态转换，完全相同的记录重复登记是幂等 no-op |
| `retry_artifact(kind, source_result=..., now=...)` | 唯一的 `failed -> pending` 入口，其余状态一律拒绝 |

`with_artifact()` 不再是无条件覆盖：`completed -> pending`、`completed -> failed`、
`not_applicable -> *` 都会被拒绝，成功产物不会被静默改写。

### 2.4 产物状态转换

```text
pending -> completed | failed | not_applicable
failed  -> pending            # 仅 retry_artifact() 显式重试
completed, not_applicable     # 终态
```

- `completed` 不允许回到 `pending`：重新生成已完成产物属于**新的一次归档尝试**，
  不能原地把成功记录改回未完成，从而掩盖曾经的成功产物。
- `failed -> pending` 只由 `retry_artifact()` 触发，`with_artifact()` 会拒绝该转换；
  重试必须基于已登记的 `run_id` 与 `source_result`，不接受任意路径。
- 正式结果永不覆盖；阶段终态的 `RunStageRecorder.complete()` 拒绝重写规则保持不变。

### 2.5 schema 兼容

- `MANIFEST_SCHEMA_VERSION` 由 1 升为 2，`SUPPORTED_MANIFEST_SCHEMA_VERSIONS = {1, 2}`。
- 读取 v1 manifest 时缺少 `artifacts`，按空集合处理，并在内存中升级为 v2；
  再次写回即为 v2。旧运行因此仍可浏览、校验和继续使用。
- v1 manifest 只要出现 `artifacts` 字段（**包括空数组**）即视为非法：产物记录要求 v2，
  不能靠改写版本号绕过契约检查。
- 以 `schema_version=1` 序列化时不输出 `artifacts` 字段，避免写出“回读即报错”的 v1 文件。
- 未登记的未知字段仍按原有前向兼容策略忽略。

## 3. 归档结果 DTO

`application.dto.archival.ArchivalOutcome` 是应用层和页面唯一消费的归档结果：

| 字段 | 说明 |
| --- | --- |
| `run_id` | 运行标识，必须是合法目录名 |
| `stage` | 产生本次归档的阶段（`cable_loss` / `driver_mapping` / `amplifier`） |
| `test_status` | 本次测试边界的归档语义，见 3.1 |
| `formal_result_path` | 正式结果的运行内相对路径；没有结果时为 null |
| `artifacts` | CSV 与报告两条 `ArchivedArtifact`，必须显式登记；线损/驱动映射、取消、异常与部分完成填 `not_applicable`，主功放完整成功必须填真实产物状态 |
| `archived_at` | 归档时间，可选 |

`ArchivedArtifact` 只含 `kind`、`status`、`path`、`reason`：

- 不携带 `sha256` / `size_bytes`（这些属于 manifest 记录）；
- 不携带绝对路径，也不判断文件是否存在；
- 不携带页面文案；提示语由界面层按状态生成。

### 3.1 两个状态维度

`ArchivalTestStatus`（测试维度）：

| 值 | 含义 |
| --- | --- |
| `completed` | 本次边界之后运行整体完成（当前只有主功放阶段会触发） |
| `partial` | 本阶段已完成，但运行整体仍未完成（线损、驱动映射的正常结果） |
| `failed` | 阶段或运行级失败；已保存的正式结果仍可追溯 |
| `cancelled` | 阶段/运行被取消，取消路径会清理阶段结果 |

`ArchivalStatus`（归档维度）：

| 值 | 判定 |
| --- | --- |
| `pending` | 正式结果已保存，至少一个适用产物仍在生成 |
| `completed` | 正式结果已保存，全部交付产物已完成（没有适用产物的阶段要求全部 `not_applicable`） |
| `partial` | 正式结果已保存，至少一个适用产物失败 |
| `failed` | 运行异常且没有可归档的正式结果 |
| `not_applicable` | 运行取消，没有可归档的正式结果 |

两个维度刻意分开：产物失败不会把 `test_status` 改成 `failed`，测试失败也不会伪装成
“没有产物”。

## 4. 组合规则

| `test_status` | 正式结果路径 | 产物状态 | `archive_status` |
| --- | --- | --- | --- |
| `completed` | 必填，且等于阶段固定路径 | 主功放阶段只能是 `pending` / `completed` / `failed`，禁止 `not_applicable` | 按产物状态：`pending` / `partial` / `completed` |
| `partial` | 必填，且等于阶段固定路径 | 必须全部 `not_applicable` | `completed` |
| `failed` | 可选；有值时必须是阶段固定路径 | 必须全部 `not_applicable` | 有结果为 `completed`，无结果为 `failed` |
| `cancelled` | 禁止 | 必须全部 `not_applicable` | `not_applicable` |

补充规则：

1. 只有 `stage=amplifier` 且 `test_status=completed` 时，CSV/报告才允许不是
   `not_applicable`。线损、驱动映射、取消、异常与部分完成一律不生成完整报告。
2. 主功放完整成功必须交付**完整产物**：CSV 与报告都不得是 `not_applicable`，
   否则「完整成功」会退化成「报告/数据缺失也算成功」。产物可以是 `failed`——
   此时 `archive_status=partial`，测试状态仍是 `completed`。
3. `partial` 不会触发 `complete_run()`；运行保持 `running` 是设计语义，不是缺陷。
4. `cancelled` 禁止携带正式结果路径，因为取消路径会删除阶段标准结果文件。
5. `failed` 允许携带正式结果路径，用于表达“结果已保存但运行级步骤失败”的情况
   （例如主功放结果已登记、`complete_run()` 失败）；此时归档维度仍是 `completed`，
   测试维度保留 `failed`。
6. `artifacts` 必须同时包含 `csv` 与 `report`；缺失、重复或类型未知都直接拒绝，
   避免“没有记录”被误读成“已完成”。

---

## 5. 明确不属于本契约的内容

- **页面文案**：应用层不生成“归档成功”“已保存到”等提示。
- **文件存在性**：DTO 构造只校验路径形状，不访问文件系统。
- **任意路径导出**：自动归档只接受运行目录内默认位置；用户副本仍走
  `ResultExportUseCase` 与文件对话框。
- **“最新结果”作为输入**：自动归档必须显式持有 `run_id` 与阶段结果路径。
- **兼容快照结果**：没有 manifest 登记的结果不进入归档。

## 6. 后续步骤落点

| 步骤 | 使用本契约的方式 |
| --- | --- |
| 步骤 3 | `ResultArchivalService` 构造 `ArchivalOutcome`，按 `(source_result, kind)` 幂等；实现与验证见[测试结果归档服务](测试结果归档服务.md) |
| 步骤 4 | CSV 使用 `default_artifact_path(stage, csv)`，失败只把该产物标为 `failed` |
| 步骤 5 | 报告写入 `artifacts/`，经 `with_artifact()` 登记 `ArtifactRecord` 并校验 SHA-256/大小；只引用真实存在的同目录兄弟文件（CSV 未完成时省略链接）；图表若生成则与报告同目录，本步骤不生成图表（见[报告自动生成](测试结果归档报告自动生成.md)） |
| 步骤 6 | 页面只消费 `ArchivalOutcome` 并映射成文案与按钮状态，不读取绝对路径、不判断文件存在（见[主测试页面显示归档结果](测试结果归档结果展示.md)） |
| 步骤 7/9 | 历史重试读取 `ArtifactRecord.status=failed`，经 `retry_artifact()` 显式重试 |

本步骤**未**修改 `RunRepository._classify()`：自动产物的写入、登记与校验统一在步骤 5
实现，避免现在就出现“能写进 `artifacts/` 但被记进 `outputs`”的半套行为。

## 7. 本步骤验证

```powershell
& "D:\Anaconda\envs\Auto_test\python.exe" -m unittest tests.test_archival_contract -v
& "D:\Anaconda\envs\Auto_test\python.exe" -m unittest tests.test_run_manifest tests.test_run_directory tests.test_run_repository -v
& "D:\Anaconda\envs\Auto_test\python.exe" -m unittest discover -s tests -v
```

覆盖范围：

- manifest v1 无 `artifacts` 可读并升级到 v2；v1 出现 `artifacts`（含空数组）被拒绝；
  v1 序列化不输出 `artifacts`；v2 带产物往返一致；
- 产物记录路径越界、空路径、缺失校验值、失败无原因、交付态缺 `source_result`、
  重复记录均被拒绝；
- 状态转换 `pending -> completed/failed/not_applicable` 允许；`completed -> pending`、
  `completed -> failed`、`not_applicable -> completed` 拒绝；`failed -> pending`
  只能经 `retry_artifact()`；相同记录重复登记是幂等 no-op；
- 完整成功（CSV 与报告都必须生成）、部分完成、CSV 失败、报告失败、产物待生成、
  取消、异常等组合；
- DTO 不导入 Qt/基础设施/文件系统，不含 `message` 等界面文案字段。

### 7.1 审查后加固的四处契约缺口

本步骤初稿在自审中暴露了四处会让契约“看起来通过、实际可被绕过”的缺口，已在冻结前修复：

| 缺口 | 原行为 | 现行为 |
| --- | --- | --- |
| 完整成功可缺少交付产物 | 主功放 `completed` 时 CSV/报告允许 `not_applicable` | 两类产物都必须是 `pending` / `completed` / `failed` |
| manifest 可绕过产物状态机 | `with_artifact()` 无条件按幂等键覆盖，`completed` 能被改回 `pending` | 覆盖必须满足状态转换表；`failed -> pending` 只能经 `retry_artifact()` |
| v1 可携带空 `artifacts` | 只拦截非空集合，且 v1 序列化仍写出 `artifacts: []` | v1 出现该字段（含空数组）即拒绝；v1 序列化不输出该字段 |
| 幂等键来源可为空 | `pending` / `completed` / `failed` 允许 `source_result=None` | 三种状态必须登记来源结果，仅 `not_applicable` 可省略 |

对应测试见 `tests/test_archival_contract.py` 的
`test_full_success_requires_both_deliverables`、`test_completed_artifacts_cannot_be_rewritten`、
`test_not_applicable_artifacts_are_terminal`、`test_failed_artifact_only_returns_to_pending_through_retry`、
`test_repeated_identical_artifact_is_an_idempotent_no_op`、`test_artifact_order_is_stable_across_updates`、
`test_v1_manifest_rejects_an_empty_artifacts_field`、`test_v1_manifest_serialisation_omits_artifacts`、
`test_deliverable_states_require_the_source_result`。
