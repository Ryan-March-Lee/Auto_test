# 测试结果归档服务（步骤 3）

本文对应 [测试结果自动归档与导出流程重构计划](测试结果自动归档与导出流程重构计划.md) 的
**步骤 3：抽取统一的结果归档应用服务**，并按审查结论“先做骨架、再接三类测量”的拆分，只实现
**服务骨架与端口**：不接入线损/驱动映射/主功放的完成路径（步骤 4），也不生成真实 CSV/报告文件
（步骤 5）。

依赖的合同在 [测试结果归档契约](测试结果归档契约.md) 中冻结：产物路径、manifest `artifacts`
记录、状态转换和幂等键都不在本步骤重新定义。

---

## 1. 入口与模块

| 模块 | 公开名称 | 职责 |
| --- | --- | --- |
| `application.archival_service` | `ResultArchivalService`、`ArchivalRequestError` | 统一归档入口：校验正式结果已登记、初始化产物状态、调用产物生成端口、写回 manifest、返回 `ArchivalOutcome` |
| `application.ports.result_artifacts` | `ResultArtifactGeneratorPort`、`ArtifactGenerationRequest`、`GeneratedArtifact`、`ArtifactGenerationError` | 产物生成端口：只接受运行目录内的受控目标路径，返回实际路径与 SHA-256/大小 |
| `application.dto.archival` | `ArchivalRequest`（新增）、`ArchivalOutcome`、`ArchivedArtifact`、`ArchivalTestStatus`、`ArchivalStatus` | 请求只带 `run_id` 与阶段；结果只带运行内相对路径与状态 |

调用形状：

```python
service = ResultArchivalService(runs=run_repository, generator=artifact_generator)
outcome = service.archive(ArchivalRequest(run_id, stage), retry_failed=False, now=now)
```

- `generator` 可为 `None`：此时适用产物停在 `pending`，等步骤 5 的基础设施适配器补齐生成能力，
  骨架阶段也能完整验证状态编排。
- 服务只依赖 `RunRepositoryPort` 的 `load_manifest()` / `update_manifest()` /
  `verify_artifact()`，**不写正式结果**，也不接受页面传入的目标路径。三项能力缺一即在
  构造服务时 `TypeError`：没有 `verify_artifact()` 就无法复核已完成产物的文件。

## 2. 编排顺序

```text
读取 manifest
  -> 推导归档测试状态（阶段状态 + 运行状态）
  -> 确认阶段正式结果已写入并登记（含校验值）
  -> 初始化产物：pending（主功放完整成功）/ not_applicable（其它情况）
  -> 对 pending 产物调用生成端口，登记 completed 或 failed
  -> 组装 ArchivalOutcome
```

顺序与计划一致：**文件写入 -> 校验登记 -> 更新 manifest**。归档服务不重复实现写入，正式结果
由 `RunStageRecorder.complete()` 完成，所以“正式 JSON 永不覆盖”由调用链结构保证，而不是运行期
判断。

## 3. 测试状态由 manifest 推导

调用方不能传入 `test_status`，否则“部分运行”可以被自称完整成功。推导规则：

| manifest 事实 | `ArchivalTestStatus` | 交付产物 |
| --- | --- | --- |
| 阶段或运行 `cancelled` | `cancelled` | 全部 `not_applicable`，且禁止携带正式结果 |
| 阶段或运行 `failed` | `failed` | 有已登记结果则记录路径，产物全部 `not_applicable` |
| 阶段 `completed`，运行仍 `created` / `running` / `interrupted` | `partial` | 全部 `not_applicable`；主功放**不写**产物记录 |
| 阶段 `completed`，运行 `completed` 且所有阶段 `completed` / `skipped` | `completed` | 主功放必须是 `pending` / `completed` / `failed` |
| 阶段 `pending` / `running` / `skipped` | 拒绝（`ArchivalRequestError`） | — |

补充规则：

- 运行标记为 `completed` 却仍有未完成阶段时拒绝归档，避免 manifest 自相矛盾时继续生成产物。
- 主功放未达完整成功时只在本次 `ArchivalOutcome` 里表达 `not_applicable`，**不写** manifest：
  否则同一来源结果会留下 `not_applicable` 终态，挡住之后的完整成功（契约 2.4 的终态规则）。
- 反过来，主功放未完整成功但 manifest 已登记交付产物，说明运行与产物状态不一致，直接拒绝。

## 4. 产物状态与幂等

| 场景 | manifest 变化 | `ArchivalOutcome` |
| --- | --- | --- |
| 线损 / 驱动映射完成 | 追加两条 `not_applicable`（`source_result` 为该阶段固定结果） | 两条 `not_applicable`，`archive_status=completed` |
| 主功放完整成功（无生成端口） | 追加两条 `pending` | 两条 `pending`，`archive_status=pending` |
| 生成成功 | `pending -> completed`，登记 `path`、`sha256`、`size_bytes` | 两条 `completed` |
| 生成失败 | `pending -> failed`，登记错误文本，正式结果不动 | 该产物 `failed`，`archive_status=partial` |
| 生成到非请求路径 | `pending -> failed`，不登记返回的路径 | 该产物 `failed`，`archive_status=partial` |
| 重复调用 | 完全相同的记录按幂等 no-op，不新增、不改写；复用 `completed` 前先 `verify_artifact()` 复核文件 | 与首次一致 |
| 重复调用但已完成产物文件缺失/被替换 | 不做任何改写，按归档请求失败上报（`ArchivalRequestError`） | 由 `archive_completed_stage()` 降级为错误日志 |
| `retry_failed=True` 且记录为 `failed`、端口声明支持该类型 | 只经 `retry_artifact()` 回到 `pending` 后重新生成 | 重试结果 |
| `retry_failed=True` 但端口未声明该类型（含 `generator=None`） | 不改动：保持 `failed` 与原有失败原因，只写一条跳过日志 | 仍是 `failed` |
| `retry_failed=False` 且记录为 `failed` | 不改动，不自动重新生成 | 仍是 `failed` |
| 记录为 `not_applicable` 却要求生成 | 拒绝（终态不可改判） | — |

幂等键是 `(source_result, kind)`：同一运行内同一份正式结果的同类产物只有一条记录。服务不对
`completed` 记录做任何原地改写，重新生成必须是一次显式的 `retry_failed=True`。

同一运行的归档在**本进程内串行执行**：`archive()` 按 `run_id` 取互斥锁（可重入），把
“读 manifest -> 改产物记录 -> 写回”整段包在锁内，避免并发归档互相覆盖产物记录。跨进程
并发不在保证范围内——一个运行目录只由一个实例负责，同一 `run_id` 的重复触发由该锁合并。

## 5. 失败与拒绝

- 缺少 manifest、阶段未完成、阶段结果未登记或缺少校验值、请求路径不是阶段固定结果、
  运行目录外路径、请求类型错误：一律 `ArchivalRequestError`（`ValueError` 子类，与
  `ExportRequestError` 的定位一致，不属于六类运行时失败）。
- 已登记 `completed` 的产物在复用前复核失败（文件缺失、被替换、解析后越出 `artifacts/`）：
  同样 `ArchivalRequestError`，manifest 记录与正式结果都不改写——`completed` 是终态，
  损坏的产物只能交给显式的重新生成入口（步骤 7/9）处理。
- 产物生成失败（`ArtifactGenerationError` / `OSError` / `ValueError`，含生成端口返回非
  `GeneratedArtifact`、返回路径不等于请求的受控目标路径、空路径、错误摘要）：只把该产物
  标为 `failed` 并记录原因，正式结果保留。
- 重试受端口能力约束：`retry_failed=True` 只把端口**当前声明**生成得出来的 `failed` 产物
  复位成 `pending`；端口不支持的产物保持 `failed` 与原失败原因，不会被退化成“待生成”
  （见第 10 节）。
- 端口抛出的其它异常（`RuntimeError` 等未被契约覆盖的类型）**不被兜底**：异常直接上抛，
  该产物停在 `pending`，由调用方或恢复流程重新检查；端口实现必须把可预期的渲染/写入/
  空数据失败显式包成 `ArtifactGenerationError`。
- manifest 写回失败不捕获、不降级：直接抛给调用方，避免“归档失败但看着像成功”。
- 服务不使用宽泛 `except`，产物失败与运行失败不会混在一个处理器里。

- 不接入 `CableLossUseCase` / `DriverPowerMappingUseCase` / `AmplifierMeasurementUseCase`

## 8. 交付前审查加固

自审发现两处“契约写了、服务没兜住”的缺口，已在收尾前修复：

| 缺口 | 原行为 | 现行为 |
| --- | --- | --- |
| 端口可写到受控目标以外 | 只校验返回类型，随后直接登记 `generated.path`；返回另一条仍位于 `artifacts/` 的合法路径也会被接受 | 要求 `generated.path == request.target_path`，不一致即把该产物记为 `failed`，并把期望/实际路径写进失败原因 |
| 未预期异常会留下 `pending` 却无人说明 | 只捕获 `ArtifactGenerationError` / `OSError` / `ValueError`，其它异常静默上抛，文档未说明残留语义 | 保留快速失败（不加宽泛 `except`），在端口与服务文档中冻结“可预期失败必须包成 `ArtifactGenerationError`，其它异常上抛且产物停在 `pending` 由调用方复查” |

对应测试为 `test_generator_returning_a_different_artifact_path_is_a_failed_artifact` 与
`test_unexpected_generator_exception_propagates_and_leaves_the_artifact_pending`；
静态门禁仍要求 `BROAD_CATCH_BASELINE` 严格相等，因此“捕获一切再降级”不是可选修法。

## 9. 步骤 4 落地后的服务加固

CSV 自动生成接入成功路径后，审查发现三处“服务侧兜不住”的缺口，随步骤 4 一并修复：

| 缺口 | 原行为 | 现行为 |
| --- | --- | --- |
| 已完成产物再归档时不校验文件 | `completed` 记录直接复用：CSV 被删除或被改写后仍返回 `completed`，只有调用 `verify_artifact_files()` 才能发现 | 复用前调用 `RunRepositoryPort.verify_artifact()`（服务构造时强制要求该能力）；缺失/被替换/越界按 `ArchivalRequestError` 拒绝本次归档，`completed` 记录与正式结果都不改写 |
| 并发归档会互相覆盖产物记录 | manifest 的“读-改-写”没有互斥，两个线程同时归档可能丢掉一条记录或登记到别处的摘要 | `archive()` 按 `run_id` 取可重入互斥锁，把整段归档包在锁内；跨进程并发明确不在保证范围内 |
| 仓储能力要求未写进契约 | 只校验 `load_manifest()` / `update_manifest()` | 增加 `verify_artifact()` 为必需能力，缺一即在构造服务时 `TypeError` |

对应测试：`test_reused_completed_artifacts_are_verified_against_the_manifest`、
`test_damaged_completed_artifact_is_rejected_instead_of_reused`、
`test_service_requires_artifact_verification_capability`，以及生成侧的
`test_concurrent_archival_keeps_a_single_consistent_artifact`、
`test_damaged_completed_csv_blocks_reuse`、`test_tampered_completed_csv_blocks_reuse`。

## 10. 步骤 9 落地后的重试加固

重试与幂等测试（[失败重试与幂等](测试结果归档失败重试与幂等.md)）发现两处缺口：

| 缺口 | 原行为 | 现行为 |
| --- | --- | --- |
| 重试会把端口不支持的产物退化成 `pending` | `retry_failed=True` 对所有 `failed` 产物先执行 `failed → pending`，之后 `_generate_pending()` 才按 `supported_kinds` 跳过不支持的产物：记录停在 `pending`，失败原因被清空，历史页从此不再把该产物算作可重试 | 复位前先检查 `supported_kinds`（含 `generator=None`）：端口当前生成不了的失败产物保持 `failed` 与原失败原因，并写一条 `跳过产物重试` 日志 |
| 归档与产物生成日志没进应用日志文件 | 本服务与 `infrastructure.persistence.artifact_generator` 都用 `logging.getLogger(__name__)`，而 `setup_logging()` 只给 `pa_auto_test` 树装配文件处理器：生成失败（`WARNING`）只在 stderr，重试跳过（`INFO`）连 stderr 都没有，日志文件里查不到 | 本服务改用 `logging.getLogger("pa_auto_test." + __name__)`（不导入 infrastructure，与 `application.run_service` 同口径），生成适配器改用 `get_logger(__name__)`：生成失败、重试跳过与归档边界错误都写进 `logs/pa_auto_test_*.log` |

未预期端口异常仍按第 8 节的快速失败口径上抛、产物停在 `pending`，不新增宽泛捕获，也不写
服务级日志：宽泛捕获基线要求严格相等且只减不增，把缺陷降级成日志会把它伪装成可恢复的
生成失败。

对应测试：`test_retry_keeps_a_failure_the_port_cannot_generate`、
`test_retry_without_a_generator_keeps_the_failure`、
`test_retry_never_regenerates_completed_artifacts`、
`test_repeated_failed_retries_keep_one_record_and_the_latest_reason`、
`test_generation_failure_is_written_to_the_application_log_file`、
`test_retry_skip_is_written_to_the_application_log_file`、
`test_generation_adapter_logger_is_on_the_application_log_tree`（均在
`tests/test_archival_retry_idempotency.py`）。
