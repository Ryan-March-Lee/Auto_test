# 测试结果自动归档与导出流程重构计划

## 1. 背景与重构目标

当前系统把“测试结果保存”和“结果导出”拆成了两个用户动作：测试完成后，用户还需要进入独立的 `ExportPage`，选择历史结果，再手动导出 JSON、CSV 或测试报告。

该流程不符合测试工具的主要使用习惯：测试完成后，结果应自动归档，用户不应依赖记忆执行第二次保存动作。本次重构的目标是：

1. 测试流程自动持久化正式结果，并自动生成约定的交付产物。
2. 将导出失败与测试执行失败分开表达，避免状态混淆。
3. 将独立“导出页面”收敛为历史运行/结果管理能力。
4. 保留手动重新导出能力，用于补救、格式转换和历史数据管理。
5. 保持现有运行目录、`manifest.json`、结果校验和历史查询边界不被破坏。

## 2. 设计原则与范围

### 2.1 术语

- **正式结果**：测试过程产生并登记到当前运行目录 `runs/<run_id>/` 的结构化结果，通常为 JSON。
- **交付产物**：面向用户或下游流程的 CSV、HTML/PDF（如已有 PDF 生成能力）或测试报告。
- **自动归档**：测试阶段完成后，由应用流程自动写入正式结果并触发交付产物生成。
- **历史管理**：查看、定位、打开和重新生成已有运行的结果，不承担首次保存责任。

### 2.2 不在本次重构中改变的内容

- 不改变测量公式、仪器控制和安全清理逻辑。
- 不允许页面绕过运行目录和 manifest 直接访问任意文件路径。
- 不删除 `ResultExportUseCase`；它将从主流程和历史管理两个入口复用。
- 不把部分运行伪装成完整成功运行。

### 2.3 推荐的目标流程

```text
创建运行
  -> 执行测试阶段
  -> 写入并登记正式结果
  -> 自动生成 CSV/报告等交付产物
  -> 更新运行归档状态
  -> 主测试页面显示结果和产物位置

历史运行页面
  -> 查看运行和产物状态
  -> 打开结果/报告
  -> 对失败产物执行重新生成
```

## 3. 分阶段实施计划

每个步骤控制在一个小变更范围内，完成后应能单独运行测试并提交。步骤之间按顺序执行；同一阶段内只有明确标注“可并行”的步骤才建议并行处理。

## 第一阶段：确认现状并冻结契约

### 步骤 1：盘点现有结果与导出链路

**目标**：建立从测试完成到结果文件生成的实际调用链，避免在错误的页面或 worker 层重复实现逻辑。

**执行策略**：

1. 梳理三类测试的完成入口、结果写入入口和运行阶段完成入口。
2. 梳理 `ExportPage`、`VisualizationPage`、`ResultExportUseCase`、历史查询端口之间的调用关系。
3. 记录每种结果目前生成的文件、生成时机、失败行为和用户提示。
4. 只补充文档或代码注释，不在本步骤修改行为。

**技术决定**：

- 以运行目录和 manifest 作为正式结果的唯一事实来源。
- 不以 `ExportPage` 当前行为推断测试流程契约。
- 自动归档的编排位置应在应用层运行/测量完成边界，而不是 Qt 页面中。

**验收标准**：

- 能明确指出三类测试各自的“结果文件写入”和“阶段完成登记”位置。
- 能明确指出自动导出应接入的应用层边界。
- 没有新增运行时行为。

**工作量**：小，建议 0.5 天以内。

### 步骤 2：定义归档状态与产物契约

**目标**：把“测试成功”和“各类产物生成成功”表达为可区分的结构化状态。

**执行策略**：

1. 设计一个最小的归档结果 DTO，例如包含 `run_id`、正式结果路径、CSV 路径、报告路径和各产物状态。
2. 明确产物状态：`pending`、`completed`、`failed`、`not_applicable`。
3. 明确测试状态与归档状态的组合规则。
4. 先补充单元测试和契约说明，再实现生产调用。

**技术决定**：

- 正式结果保存成功后，测试结果才允许标记为可归档。
- CSV 或报告生成失败不回滚已经保存的正式结果；应记录为产物失败并允许重试。
- 取消、异常和部分完成只归档已有的阶段结果，不生成完整测试报告。
- 产物路径必须是运行目录内的受控相对路径或由导出端口返回的已校验位置。

**验收标准**：

- DTO 能表达完整成功、部分完成、产物失败和不适用四类情况。
- DTO 不携带页面文案，不依赖 Qt。
- 为状态转换和非法组合补充单元测试。

**工作量**：小，建议 0.5～1 天。

## 第二阶段：将正式结果保存纳入测试流程

### 步骤 3：抽取统一的结果归档应用服务

**目标**：提供一个由测试完成流程调用的统一归档入口。

**执行策略**：

1. 新增应用层归档服务，例如 `ResultArchivalService`，只依赖结果写入端口、运行仓储端口和导出端口。
2. 服务负责调用正式结果保存、manifest 登记和产物生成，不负责 Qt 提示。
3. 将现有三类测试完成后的重复保存逻辑逐步接入该服务。
4. 每次只迁移一种测试类型，迁移后立即运行对应测试集。

**技术决定**：

- 归档服务不直接导入基础设施实现，也不直接操作 Qt。
- “文件写入完成 -> 校验登记 -> 更新 manifest”的顺序保持不变。
- 归档服务必须支持幂等调用：同一运行和阶段重复触发时不能产生伪造的第二份正式结果。
- 产物生成使用现有 `ResultExportUseCase` 或其端口能力，避免复制导出规则。

**验收标准**：

- 三类测试均能通过统一入口登记正式结果。
- 现有运行目录结构和 manifest 校验保持兼容。
- 重复完成、异常和取消路径不会生成“看起来完整”的运行结果。

**工作量**：中小，建议 1～1.5 天；按测试类型分成三个小提交。

### 步骤 4：把 CSV 生成接入成功完成路径

**目标**：测试成功后自动生成常用的 CSV 交付数据。

**执行策略**：

1. 复用 `analysis.reporting.export_csv` 或现有导出端口，不在页面中实现 CSV 序列化。
2. 只对支持 CSV 的结果类型自动生成；不适用类型明确登记为 `not_applicable`。
3. 自动生成使用运行目录内的默认目标路径，不弹出保存对话框。
4. 增加 CSV 生成成功、空数据和写入失败测试。

**技术决定**：

- 自动归档的默认目标路径由运行目录和结果类型决定，路径规则集中定义。
- 用户手动导出时仍可选择其他目标路径；自动归档不依赖用户选择。
- CSV 失败不删除正式 JSON，也不把测量状态改成失败。

**验收标准**：

- 成功测试结束后，CSV 文件自动出现在运行目录约定位置。
- CSV 文件路径登记在归档结果中，文件缺失或写入失败能被发现。
- 历史查询仍能读取正式结果。

**工作量**：小，建议 0.5～1 天。

## 第三阶段：自动生成报告并改善状态反馈

### 步骤 5：将测试报告生成接入完整成功路径

**目标**：主功放等支持报告的完整测试结束后自动生成报告。

**执行策略**：

1. 复用现有报告生成服务和 `ResultExportPort.export_report`。
2. 仅在运行所有必要阶段完成且正式结果通过校验后生成完整报告。
3. 报告生成失败时保留正式结果和失败原因，提供后续重试入口。
4. 先为报告服务补充返回实际产物路径的契约测试，再接入测试完成流程。

**技术决定**：

- 报告生成不再要求用户先打开可视化页面或手动选择结果。
- 报告导出端口必须返回非空、可定位的实际产物位置；否则视为失败。
- 线损、驱动映射等不支持完整报告的结果不触发报告生成，并记录 `not_applicable`。

**验收标准**：

- 完整成功运行自动产生报告。
- 部分完成运行不会产生“完整测试报告”。
- 报告生成失败时，界面能显示失败状态，并且历史页面可重试。

**工作量**：小，建议 0.5～1 天。

### 步骤 6：在主测试页面显示归档结果

**目标**：让用户在测试完成后立即知道结果是否已保存、哪些产物已生成。

**执行策略**：

1. 由 controller 或应用协调器接收结构化归档结果。
2. 页面只负责把状态 DTO 转为用户文案和按钮状态。
3. 为成功、部分产物失败、测试异常和取消分别设计简短提示。
4. 提供“查看结果目录”或“查看报告”的快捷动作，但不强制用户操作。

**技术决定**：

- 页面不得自行判断文件是否存在或拼接导出业务规则；这些判断由应用层和仓储完成。
- 自动归档期间显示明确的“正在保存/生成”状态，避免用户误以为测试已完全结束。
- 产物失败提示必须包含可重试动作或可定位的运行 ID。

**验收标准**：

- 测试结束后用户无需进入其他页面即可确认结果状态。
- 各类失败状态有清晰且不误导的提示。
- 页面单元测试只验证状态展示和按钮行为，不测试文件格式细节。

**工作量**：小，建议 0.5～1 天。

## 第四阶段：收敛页面职责

### 步骤 7：将 `ExportPage` 改为历史结果管理页

**目标**：消除“导出是独立主流程”的产品语义，同时保留历史结果操作能力。

**执行策略**：

1. 先保留现有类名和路由，降低一次性改动范围。
2. 将标题、分组和按钮文案改为“历史运行/结果管理”。
3. 默认展示运行、阶段、结果状态和产物状态，而不是仅展示文件列表。
4. 将 JSON/CSV/报告按钮改为“重新生成/导出副本”等辅助操作。
5. 迁移完成后再决定是否将类重命名为 `RunHistoryPage`。

**技术决定**：

- 历史页面仍只能使用 `HistoryViewModel` 和应用服务，不能直接读取路径。
- 默认不弹出保存对话框；“重新生成正式产物”写回原运行目录，“导出副本”才选择目标路径。
- 历史页显示部分运行和不完整运行，但禁止对无效运行执行导出。

**验收标准**：

- 用户可以从历史页定位某次运行及其产物状态。
- 可以重新生成失败的 CSV 或报告。
- 无需手动导出也能完成一次正常测试流程。

**工作量**：中小，建议 1～1.5 天。

### 步骤 8：删除重复的可视化导出入口

**目标**：避免可视化页和历史管理页同时承担相同的报告生成职责。

**执行策略**：

1. 保留可视化页的加载、浏览和绘图功能。
2. 将“生成报告”动作改为调用历史管理中的统一重试/生成服务，或移至历史页面。
3. 删除页面内自行决定“最新结果”的逻辑；始终使用显式选择或当前运行结果。
4. 更新页面测试和用户文案。

**技术决定**：

- 报告生成规则只能存在于应用导出/归档服务，不在多个 Qt 页面复制。
- 可视化页可以提供“基于当前已加载结果生成报告”的快捷入口，但不再承担自动归档。
- 禁止用“最新文件”作为自动归档的隐式输入。

**验收标准**：

- 报告生成只有一个应用层实现。
- 可视化页仍可正常浏览数据。
- 当前结果、历史结果和报告来源之间可追溯到明确的 `run_id` 与结果 ID。

**工作量**：小，建议 0.5～1 天。

## 第五阶段：清理、验证与发布

### 步骤 9：补齐失败重试和幂等测试

**目标**：确保自动流程在失败、重复触发和部分完成时不会破坏已有结果。

**执行策略**：

1. 为归档服务增加正式结果已存在、CSV 失败、报告失败、重复重试和运行取消测试。
2. 为历史页面增加无效运行、部分运行和产物缺失测试。
3. 为应用层端口增加返回空路径、错误类型和路径越界测试。
4. 只修复发现的行为问题，不在本步骤扩大功能范围。

**技术决定**：

- 重试必须基于已登记的结果 ID 或运行 ID，不能接受任意用户输入路径作为结果来源。
- 已成功的产物默认不重复覆盖，除非明确执行“重新生成”。
- 所有自动生成错误都写入应用日志，并在历史状态中可见。

**验收标准**：

- 自动归档核心路径有单元测试覆盖。
- 失败重试不会删除正式结果或破坏 manifest。
- 任意路径、空报告路径和未登记结果均被拒绝。

**工作量**：中小，建议 1 天。

### 步骤 10：删除旧导出页面语义并完成门禁

**目标**：完成产品语义和代码结构收口。

**执行策略**：

1. 检查菜单、路由、窗口标题、帮助文案和日志中是否仍把导出描述为必经页面。
2. 删除不再使用的页面专属状态和重复导出适配代码。
3. 保留必要的兼容导入或路由过渡，确认无调用后再删除。
4. 执行完整离线测试、编译检查、依赖锁检查和配置校验。

**技术决定**：

- 删除页面前先完成历史管理页的全部替代能力。
- 不能仅因为 UI 页面删除就删除应用层导出服务；历史重试和外部调用仍需要它。
- 发布说明应明确：正常测试自动归档，手动导出仅用于副本、重试和历史管理。

**验收标准**：

- 正常测试流程不需要打开导出页面。
- 历史结果可查看、可定位、可重试导出。
- 运行目录、manifest、报告和 CSV 均能通过现有完整性检查。
- 按项目约定通过：

  ```powershell
  & "D:\Anaconda\envs\Auto_test\python.exe" -m unittest discover -s tests -v
  & "D:\Anaconda\envs\Auto_test\python.exe" tools/export_dependency_lock.py --check
  & "D:\Anaconda\envs\Auto_test\python.exe" launcher.py --check
  & "D:\Anaconda\envs\Auto_test\python.exe" launcher.py --validate-config
  ```

**工作量**：小，建议 0.5～1 天。

## 4. 推荐提交顺序

为降低回归风险，建议按以下顺序拆分提交：

1. 现状盘点和归档契约测试。
2. 归档 DTO 与统一归档服务骨架。
3. 线损测试接入自动正式结果归档。
4. 驱动映射测试接入自动正式结果归档。
5. 主功放测试接入自动正式结果归档。
6. CSV 自动生成。
7. 测试报告自动生成和失败状态。
8. 主测试页面显示归档结果。
9. 历史页面改造和手动重试。
10. 删除重复入口、完成全量门禁。

每个提交应保持可运行，并在提交说明中记录对应的测试命令和结果。

## 5. 最终验收口径

重构完成后，应满足以下用户场景：

1. 用户创建运行并完成测试，不进入任何导出页面，正式结果已自动保存。
2. 支持的 CSV 和测试报告已自动生成；不支持的产物明确显示为不适用。
3. 生成某个产物失败时，测试结果仍可追溯，失败原因可见并可重试。
4. 用户可以从历史运行页面查看运行、阶段、结果和产物状态。
5. 历史页面不能读取未登记结果、任意路径或无效运行。
6. 取消、异常和部分完成不会生成误导性的完整测试报告。
7. 所有正式结果仍由运行目录和 manifest 管理，既有完整性校验继续有效。
