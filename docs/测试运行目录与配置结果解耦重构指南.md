# 测试运行目录与配置结果解耦重构指南

## 1. 文档目的

本文是功放自动化测试系统下一阶段重构的实施指南。目标是把当前“配置、线损测量、驱动映射、主功放测量”统一到清晰的运行边界中：

1. 配置阶段负责填写、校验并冻结一次运行所需的配置。
2. 测量阶段只消费已冻结的运行配置和明确指定的阶段输入。
3. 每次运行拥有独立目录，配置、校准输入和结果可以整体归档、复制和复现。
4. 阶段之间不再通过“最新结果”或固定全局文件名隐式传递数据。

本文只定义重构目标和步骤，不要求一次性完成所有代码迁移。每个步骤都应保持系统可运行，并配套小范围测试。

## 2. 当前状态与重构判断

当前系统已经具备部分基础：

- GUI 可以保存配置 JSON。
- 三类测量 worker 都通过配置路径启动，并在测量前执行配置加载和校验。
- 已有 `run_id`、运行目录快照和结果仓储。
- 线损、驱动映射和主功放结果已经可以持久化。

当前仍存在以下耦合：

- 配置页和测量页仍由同一个主窗口协调。
- 每个测量开始前可能重新从 UI 更新并覆盖配置。
- 驱动映射默认读取结果目录中的最新线损结果。
- 主功放测量默认读取兼容路径中的线损结果，并在驱动模式下读取最新驱动映射结果。
- 配置文件、校准输入、阶段结果没有统一归属于一个可追溯的运行目录。
- 测量阶段无法仅凭一个明确的运行标识判断自己应使用哪些输入文件。

因此，本次重构的重点不是重新实现测量算法，而是建立稳定的运行数据契约和阶段边界。

## 3. 目标架构

建议将一次完整测试视为一个 `Run`。一个 `Run` 包含配置快照、阶段输入、阶段结果和状态清单。

```text
配置阶段
    |
    | 创建并冻结 Run
    v
运行目录
    ├── manifest.json
    ├── config.json
    ├── inputs/
    │   ├── cable_loss.json
    │   └── driver_mapping.json       # 可选
    └── results/
        ├── amplifier_measurement.json
        └── ...                       # 允许多个结果文件
```

推荐的依赖方向：

```text
配置页面 / 配置服务
        |
        v
Run 创建服务 -> config.json + manifest.json
        |
        v
测量阶段服务 -> 显式读取 Run 目录中的 inputs/ 和写入 results/
```

测量阶段可以由 GUI 启动，也可以由命令行或其他调度器启动，但必须使用同一个 `run_id` 或运行目录，不能依赖 GUI 内存中的配置对象作为唯一来源。

## 4. 运行目录契约

### 4.1 目录位置

建议在现有结果根目录下增加运行目录：

```text
runs/<run_id>/
```

`run_id` 必须稳定、唯一、适合文件名，例如：

```text
20261022T153000Z_<uuid短串>
```

不要使用用户可编辑的名称作为唯一 ID。可以在 `manifest.json` 中另存用户备注或产品名称。

### 4.2 文件职责

`config.json`：

- 本次运行实际使用的完整配置快照。
- 由配置阶段结束时生成。
- 运行创建后不得被后续 UI 编辑覆盖。
- 应包含配置 schema 版本、创建时间和必要的运行参数。

`inputs/cable_loss.json`：

- 本次运行实际消费的线损数据副本。
- 线损阶段完成后写入。
- 如果主功放或驱动映射需要线损数据，必须从该文件读取。

`inputs/driver_mapping.json`：

- 驱动模式启用且映射阶段完成时写入。
- 无驱动模式时不创建，或在 manifest 中明确标记为未启用。
- 主功放测量必须根据 manifest 判断该输入是否必需。

`results/`：

- 保存主功放最终结果及其拆分文件。
- 允许保存 JSON、CSV、图片、报告等多个文件。
- 结果文件必须带有 `run_id` 和阶段类型，避免脱离目录后无法识别来源。

`manifest.json`：

- 是运行目录的索引和状态来源。
- 记录配置快照、阶段状态、输入文件、输出文件、软件版本和错误信息。
- 不保存大体积测量数据，只保存路径、类型、时间、状态和摘要。

### 4.3 manifest 建议结构

初始版本可以采用以下结构，字段名一旦对外使用应保持向后兼容：

```json
{
  "schema_version": 1,
  "run_id": "20261022T153000Z_a1b2c3d4",
  "created_at": "2026-10-22T15:30:00Z",
  "updated_at": "2026-10-22T15:45:00Z",
  "status": "running",
  "software_version": "python-3.12.x",
  "config": {
    "path": "config.json",
    "sha256": "..."
  },
  "stages": {
    "cable_loss": {"status": "completed", "result": "inputs/cable_loss.json"},
    "driver_mapping": {"status": "skipped", "result": null},
    "amplifier": {"status": "running", "result": null}
  },
  "inputs": [],
  "outputs": [],
  "error": null
}
```

阶段状态至少支持：`pending`、`running`、`completed`、`skipped`、`failed`、`cancelled`。

## 5. 明确的阶段边界

### 5.1 配置阶段

配置阶段负责：

1. 读取 GUI 当前配置。
2. 执行完整配置校验和接线确认校验。
3. 创建唯一 `run_id` 和运行目录。
4. 写入不可变的 `config.json`。
5. 初始化 `manifest.json`，状态为 `created` 或 `pending`。
6. 返回一个只包含运行标识和目录路径的 `PreparedRun`。

配置阶段不负责：

- 打开仪器。
- 执行线损测量。
- 执行驱动映射。
- 执行主功放扫描。

配置阶段完成后，用户修改配置页面不应影响已经创建的运行。

### 5.2 线损阶段

线损阶段只读取：

- 指定运行目录中的 `config.json`。
- 运行上下文和测量端口。

线损阶段完成后：

1. 将完成的线损数据写入 `inputs/cable_loss.json`。
2. 更新 manifest 中线损阶段为 `completed`。
3. 写入结果摘要和文件校验值。

如果线损阶段失败或取消，不得生成一个看起来完整的 `cable_loss.json`，也不得把旧运行的文件复制过来冒充当前结果。

### 5.3 驱动映射阶段

驱动映射阶段只读取：

- 当前运行目录的 `config.json`。
- 当前运行目录的 `inputs/cable_loss.json`。

驱动映射完成后，将数据写入：

```text
inputs/driver_mapping.json
```

如果配置未启用驱动模式，阶段状态设为 `skipped`，主功放阶段不得要求该文件存在。

### 5.4 主功放阶段

主功放阶段只读取：

- 当前运行目录的 `config.json`。
- 当前运行目录的 `inputs/cable_loss.json`。
- 驱动模式启用时的 `inputs/driver_mapping.json`。

主功放阶段不得：

- 扫描全局结果目录寻找最新线损结果。
- 自动选择另一个运行目录的驱动映射结果。
- 使用配置页面当前内存状态替换已冻结配置。

主功放阶段的所有输出写入当前运行目录的 `results/`，完成后将 manifest 状态更新为 `completed`。

## 6. 推荐的分步实施计划

每一步都应单独提交、单独验证，避免同时改变目录、结果仓储和 GUI 控制流程。

### 步骤 1：定义运行目录和数据契约

工作内容：

- 新增运行目录、manifest、阶段状态和文件引用的数据模型。
- 定义 `run_id` 生成规则。
- 定义相对路径规则，manifest 内统一使用相对运行目录的路径。
- 暂不改变现有测量流程。

验收标准：

- 可以在临时目录创建一个空运行。
- 可以序列化和反序列化 manifest。
- 非法阶段状态和非法路径能被校验拒绝。

建议测试：manifest 模型、run_id 唯一性、路径规范化。

### 步骤 2：实现运行目录仓储

工作内容：

- 新增 `RunRepository` 或等价服务。
- 提供 `create_run()`、`load_manifest()`、`update_manifest()`、`register_file()` 等最小接口。
- 创建 `config.json`、`inputs/`、`results/` 和初始 manifest。
- 所有 JSON 写入采用临时文件加原子替换。

验收标准：

- 创建运行不会覆盖已存在的运行目录。
- 中断写入不会产生半截目标 JSON。
- manifest 能记录阶段状态和文件校验值。

### 步骤 3：把配置保存改为创建运行快照

工作内容：

- 保留现有配置文件作为兼容入口。
- 增加“创建运行”操作，生成运行目录中的 `config.json`。
- 将配置校验放在创建快照之前。
- 返回 `PreparedRun`，后续阶段使用它携带的运行目录。

验收标准：

- 无效配置不能创建可运行的快照。
- 创建运行后修改 GUI 配置，不会改变已创建的 `config.json`。
- 快照中的配置可以脱离 GUI 单独加载。

### 步骤 4：迁移线损结果

工作内容：

- 让线损用例接收 `PreparedRun` 或等价运行上下文。
- 将线损完成结果写入当前运行的 `inputs/cable_loss.json`。
- 更新 manifest 中线损阶段状态。
- 保留现有全局兼容结果文件，但标记为兼容副本，不再作为新流程输入。

验收标准：

- 线损结果必定归属于当前 `run_id`。
- 线损失败、取消和部分完成不会把旧数据标记为完成。
- 旧结果读取测试仍通过。

### 步骤 5：迁移驱动映射输入和结果

工作内容：

- 删除新流程对“最新线损结果”的默认依赖。
- 驱动映射启动前验证当前运行的 `inputs/cable_loss.json` 存在且已完成。
- 将映射结果写入当前运行的 `inputs/driver_mapping.json`。
- 更新 manifest，并保留旧路径参数作为过渡兼容层。

验收标准：

- 没有当前运行线损结果时，驱动映射在硬件动作前失败。
- 另一个运行目录的线损数据不会被自动使用。
- 映射结果可以通过当前运行目录单独加载。

### 步骤 6：迁移主功放输入和结果

工作内容：

- 主功放阶段从当前运行目录读取线损数据。
- 驱动模式启用时，从当前运行目录读取驱动映射数据。
- 驱动模式关闭时，不要求映射文件存在。
- 所有最终结果写入当前运行目录的 `results/`。

验收标准：

- 主功放不会扫描全局目录选择最新校准数据。
- 缺少必需输入时，在连接仪器或 RF 动作前失败。
- 最终结果和所有拆分文件都能从 manifest 找到。

### 步骤 7：收敛 GUI 流程为“两阶段”

工作内容：

- 配置页面提供“校验并创建运行”操作。
- 线损、驱动映射、主功放页面只接受当前 `PreparedRun`。
- 删除各测量开始前重复调用 UI 配置保存的主路径。
- 保留必要的兼容提示，但不能覆盖已冻结快照。

验收标准：

- 配置阶段结束后可以关闭并重新打开 GUI，再通过 `run_id` 继续测量。
- 三个测量页面不直接依赖配置页面控件。
- 测量页面只通过运行上下文和服务接口访问配置、输入和结果。

### 步骤 8：增加命令行/离线恢复入口

工作内容：

- 增加按 `run_id` 加载运行的入口。
- 支持查看 manifest、阶段状态和结果文件。
- 支持从 `pending` 或可恢复状态继续执行前置检查。
- 不允许对已完成运行静默覆盖配置和结果。

验收标准：

- 无 GUI 时可以读取运行配置和结果。
- 已完成运行只能以新运行复制或显式重跑方式继续。
- 失败运行可以明确展示失败阶段和错误原因。

### 步骤 9：收紧兼容层并更新文档

工作内容：

- 标记旧全局配置、旧结果路径和“最新结果发现”接口为 deprecated。
- 更新 README、启动说明和硬件验收文档。
- 增加迁移工具或一次性转换说明。
- 清理新流程中不再使用的隐式路径查找。

验收标准：

- 新流程测试不依赖全局最新结果。
- 兼容接口有明确弃用日志和删除计划。
- 文档中的目录结构、状态定义和实际代码一致。

## 7. 失败、取消和恢复规则

### 7.1 写入规则

- 所有 JSON 使用 UTF-8 和原子替换。
- 大文件先写临时文件，完成后登记到 manifest。
- 文件登记顺序应为“文件完成 -> 校验 -> 更新 manifest”。
- manifest 更新失败时不能把阶段报告为 `completed`。

### 7.2 阶段状态规则

- `pending` 只能进入 `running`、`skipped` 或 `cancelled`。
- `running` 可以进入 `completed`、`failed` 或 `cancelled`。
- `completed` 不允许被静默改回 `running`。
- 重跑已完成阶段必须创建新运行，或使用显式的“覆盖/重跑”操作并留下审计记录。

### 7.3 恢复规则

- 程序启动时发现 `running` 运行，应标记为 `interrupted` 或转换为待人工确认状态。
- 不自动把未完成的临时文件视为有效输入。
- 恢复前重新执行配置校验、输入文件校验和硬件安全检查。
- 任何恢复动作都必须保留原始错误和恢复时间。

## 8. 数据一致性与安全建议

1. 每个运行目录保存配置快照，不使用运行期间可变的全局 `config.json` 作为唯一事实来源。
2. manifest、输入和结果都记录 SHA-256，发现文件被替换时拒绝继续运行或至少给出明确警告。
3. 运行目录内使用相对路径，导出到其他机器后仍可整体搬迁。
4. 设备地址、凭据和敏感现场信息不要写入版本库；如果必须进入运行快照，应提供脱敏或加密策略。
5. 运行目录命名不能包含用户输入的任意路径片段，防止路径穿越。
6. 结果文件应记录单位、频率范围、配置版本和运行 ID，避免脱离 GUI 后失去语义。
7. 全局兼容目录只作为旧版本读取和迁移来源，不作为新运行的输入源。

## 9. 测试策略

按风险从低到高逐步增加测试：

1. **模型测试**：manifest、运行状态、路径和 schema 校验。
2. **仓储测试**：创建运行、原子写入、文件登记、校验值和并发/重复 ID。
3. **阶段用例测试**：每个阶段只读取当前运行目录，并正确更新 manifest。
4. **隔离测试**：创建两个运行，验证运行 A 不会读取运行 B 的输入或结果。
5. **失败路径测试**：配置失败、线损取消、映射缺失、功放异常和进程中断。
6. **GUI 测试**：配置阶段创建运行，重新打开后按运行 ID 启动测量。
7. **兼容测试**：旧 `config.json` 和旧结果文件仍能被迁移或明确报错。
8. **硬件验收**：按照现有硬件 smoke 文档，在新运行目录下验证正常、停止、紧急停止、异常清理和重新连接。

隔离测试是本次重构的关键验收：必须证明“最新结果”即使存在，也不会被新流程使用。

## 10. 暂不做的事项

为控制每步工作量，以下事项不作为第一阶段目标：

- 重写测量算法和仪器驱动。
- 更换 JSON 为数据库或对象存储。
- 一次性删除所有历史兼容文件。
- 在运行目录中保存全部原始仪器通信日志，除非已有容量和脱敏方案。
- 引入复杂的分布式任务调度。

先完成本地运行目录和显式输入契约，再根据运行数量、归档需求和现场部署方式决定是否引入数据库或集中式结果服务。

## 11. 最终完成标准

当以下条件全部满足时，本次运行数据重构才算完成：

- 每次测量都有唯一运行目录。
- 运行目录包含不可变配置快照、manifest、阶段输入和结果目录。
- 线损、驱动映射和主功放只消费当前运行明确指定的输入。
- 驱动模式关闭时不要求驱动映射文件。
- 失败、取消、中断和恢复状态可识别，且不会生成伪完成数据。
- 运行可以脱离 GUI 读取、审计和复现。
- 新流程不再依赖全局“最新结果”。
- 现有硬件安全清理和现场验收要求仍然通过。

建议每完成一个步骤，就在对应提交信息和测试记录中写明：运行目录结构、输入来源、状态变化和兼容行为。这样后续重构可以按本文逐步推进，而不需要再次依赖当前 GUI 的隐含流程。
