# 电源设备身份与动态配置重构计划

## 1. 文档目的

当前系统把 `PS1`、`PS2`、`PS3`、`PS4` 同时当作电源名称、设备角色、配置键和分配引用。设备实际流转时，这些编号不能帮助操作者核对实物，也限制了同时使用多台电源。

本计划将系统逐步改为：

- 设备身份按“厂商 + 完整序列号”识别；
- 现场标签使用序列号派生的短标签，例如 `DP8B1519`；
- `role` 只表示设备类别 `power_supply`，不表示第几台；
- 电源集合、绑定和分配按实际设备动态生成；
- 正式运行快照冻结全部实际使用的电源；
- 旧的 `PS1..PS4` 配置可读取和迁移，新配置不再生成固定编号。

## 2. 当前基线与约束

调研确认：

1. `domain.instruments.models` 已使用 `厂商:序列号` 作为设备唯一身份，IP 只属于地址端点，这部分设计保留。
2. `instruments.json` 的 `role` 当前只允许 `signal_generator`、`spectrum_analyzer` 和 `PS1..PS4`。
3. `config_form_state.py`、`config_page.py`、`config_projection.py` 固定使用 `PS1..PS4`（步骤 6 已把前两者的电源键与绑定改成 `supply_id`；`config_projection` 的固定默认值已在步骤 8 删除）。
4. `configuration_authoring.py` 生成的正式 `run_mapping` 目前只有单数 `power_supply`。
5. `instrument.measurement_factory` 已支持 `supply/channel` 形式的多电源路由，例如 `DP8B1519/CH1`，因此底层路由可以复用。
6. 当前工作区已有测试文件重命名和未跟踪测试包目录变更。本计划实施时不得覆盖、回退或批量重排这些现有改动。

## 3. 目标模型与技术决定

### 3.1 四个概念必须分离

| 概念 | 用途 | 是否可变 |
|---|---|---|
| `device_key` | 系统匹配和去重，值为 `vendor:serial` | 不可变 |
| `serial` | 设备原始身份 | 不可变 |
| `label` / `supply_id` | 人和配置使用的短标签，如 `DP8B1519` | 首次生成后不可变 |
| `role` | 功能类别，如 `power_supply` | 可登记，但不是编号 |

技术决定：内部逻辑以 `device_key` 做身份校验，以 `supply_id` 做电源配置引用；不能仅凭短标签识别设备。

### 3.2 短标签规则

默认规则为“序列号前缀 + 序列号末四位”。例如：

```text
DP8B214901519 -> DP8B1519
DP8B174700950 -> DP8B0950
DP8B174400885 -> DP8B0885
```

技术决定：

- 序列号先去空格、去引号并转大写；
- 前缀取序列号开头的产品/系列字母数字段；
- 默认取末四位，保留前导零；
- 发生冲突时依次扩展到末五位、末六位，最后使用完整归一化序列号；
- 标签生成后写入设备注册表，不因 IP、型号序号或重新扫描而重算；
- 退役设备的标签不回收。

### 3.3 配置格式决定

新格式的电源配置使用动态键：

```json
{
  "instruments": {
    "power_supplies": {
      "DP8B1519": {
        "label": "DP8B1519",
        "device_key": "rigol technologies:dp8b214901519",
        "serial": "DP8B214901519",
        "model": "DP832A",
        "address": "TCPIP0::192.168.1.102::inst0::INSTR",
        "enabled": true,
        "channels": {}
      }
    }
  }
}
```

分配引用使用 `supply_id`；过渡期可同时写 `name`，但新代码内部统一读取 `supply_id`。

正式运行映射增加 `instruments.power_supplies` 集合，保留旧的单数 `power_supply` 读取兼容。通道连接使用 `supply_id/CHx`。

## 4. 分阶段实施计划

每个步骤应单独提交、单独测试。步骤之间以数据契约为边界，避免一次修改同时触及注册表、Qt 页面和运行模型。

## 阶段一：建立标签基础能力

### 步骤 1：编写数据契约和迁移样例

**工作内容**

- 新建一份 schema 示例，列出旧配置和新配置的对应关系。
- 固定字段名称：`label`、`supply_id`、`device_key`、`role`。
- 明确旧字段 `PS1..PS4` 只作为兼容输入。

**执行策略**

- 只新增文档和 fixture，不修改业务逻辑。
- 用当前 `instruments.json` 的三台 DP832A 编写真实迁移样例。
- 同时记录“只有地址、没有序列号”的无法自动迁移场景。

**技术决定**

- 不把 `device_key` 替换成可读标签；二者同时保留。
- 不使用 IP、MAC、型号序号生成标签。

**验收标准**

- 文档中的字段能够表达 1 台、2 台和多台电源。
- 旧配置缺少序列号时有明确的人工重新扫描路径。

**交付物**

- `docs/电源设备身份与配置数据契约.md`：字段契约、旧新对照、迁移判定与人工重扫路径。
- `tests/fixtures/power_supply_identity/`：以当前 `instruments.json` 三台 DP832A 与 `config.json` 编写的迁移样例，含无法自动迁移条目的迁移摘要。
- `tests/test_power_supply_identity_contract.py`：校验样例自洽（标签、设备键、分配引用、规模、快照范围、迁移摘要）。

### 步骤 2：实现短标签生成器

**工作内容**

- 新增 `domain/instruments/labels.py`。
- 实现序列号归一化、前缀提取、末四位生成和冲突扩展。

**执行策略**

- 纯 Python 实现，不依赖 Qt、文件系统或网络。
- 输入已有标签集合，输出稳定候选标签。
- 标签生成器不负责写注册表，由调用方决定持久化。

**技术决定**

- 第一次生成的标签必须显式保存。
- 冲突不能覆盖旧标签。
- 无法生成合法标签时抛出可识别的领域异常。
- 归一化只在 `domain.instruments.models.normalize_serial` 里定义，并循环到稳定值；标签生成器
  复用该值，不另写一套循环，保证 `serial`、`device_key` 与标签同源。
- 标签同时是 `supply_id`，会拼成 `supply_id/CHx`，因此标签不含 `/`；扩展越过分隔符即停止，
  没有可用候选时抛领域异常，交回操作员处理。

**验收标准**

- 覆盖当前三台设备的预期结果。
- 覆盖前导零、大小写、空格、碰撞和纯数字序列号。
- 覆盖归一化稳定值在三处一致（`serial`、`device_key`、标签），以及含 `/` 的序列号被拒绝。
- 独立单元测试通过。

### 步骤 3：扩展仪器领域模型

**工作内容**

- 给 `Instrument` 增加 `label` 或等价稳定字段。
- 增加 `POWER_SUPPLY_ROLE = "power_supply"`。
- 保留旧 `PS1..PS4` 常量，仅用于迁移识别，不再作为新角色集合。

**执行策略**

- 先扩展 dataclass 和序列化，不改变设备扫描流程。
- `normalize_role` 同时接受旧角色和新角色，旧角色进入兼容分支。

**技术决定**

- `device_key` 继续动态计算，不复制多份来源。
- `name` 继续保留为软件资产名；现场显示优先使用 `label`。

**验收标准**

- 新模型可表达多个 `power_supply`。
- 旧注册表记录仍可读取。

## 阶段二：升级设备注册表和发现流程

### 步骤 4：迁移注册表字段

**工作内容**

- 修改 `instrument_registry.py` 的读写和校验。
- 为旧的 `PSn` 电源根据完整序列号补生成 `label`。
- 将可识别的旧角色转换为 `power_supply`。

**执行策略**

- 读取时兼容旧 schema。
- 保存时统一写新字段和新 schema 版本。
- 迁移前保留原文件备份或通过原子写入避免半文件。

**技术决定**

- 同一序列号只允许一个注册记录。
- 标签冲突必须阻止保存并报告冲突设备。
- 未登记角色不自动猜测为电源。
- 迁移、校验、`schema_version` 与 `updated_at` 的更新都在内存副本上完成，写盘成功后才提交回
  对象；失败时内存文档与原文件都不变。已有标签原样冻结（不裁剪空白、不改大小写），标签必须
  能当 `supply_id` 用（不含空白与 `/`），否则报错交回操作员。

**验收标准**

- 现场注册表迁移后，两台已登记（`PS3` / `PS4`）的电源各得到一个明确短标签；第三台
  `role: null` 迁移后保持 `role: null`、`label: null`，操作员显式登记为 `power_supply` 后
  保存即得到第三条标签（`DP8B0950`，见契约 §5.2 的两份样例）。「三台都有标签」以显式登记
  为前提，与“未登记角色不自动猜成电源”一致。
- 重新加载后标签、序列号和设备键保持一致。
- 保存失败（标签冲突、标签不能当 `supply_id`、序列号派不出标签、磁盘写入失败）时，内存文档
  与原文件都保持迁移前的样子。

### 步骤 5：改造设备发现结果

**工作内容**

- 修改发现结果中的电源角色、显示名称和绑定数据。
- 将显示从“资产名（电源 PS3）”改为“短标签（型号，电源）”。

**执行策略**

- 扫描匹配仍只使用 `device_key`。
- 发现结果增加 `label`、`supply_id`、`serial` 和 `device_key`。
- 先支持新字段，同时保留旧测试数据的转换适配。

**技术决定**

- 设备发现不负责分配标签；标签只来自注册表或注册动作。
- 多台电源使用列表/集合传递，不再以角色键覆盖彼此。
- 身份与类别分开传递：发现结果里 `known_role` 保留设备表登记的原字面量（旧设备表是
  `PS1..PS4`），`role` 是折叠后的类别（`power_supply`）；`label` / `supply_id` / `serial` /
  `device_key` 随每条记录一起交给配置页，匹配与预选始终只按 `device_key`，短标签只用于显示
  和“同一个 ``supply_id``”的比对。`to_dict()` 同时输出 `role` 与 `registry_role`。
- 标签只读注册表：旧设备表还没有 `label` 时 `label` / `supply_id` 都是 `None`，显示退回
  资产名；跑一次注册表保存就按步骤 4 的迁移补上。
- 地址落点由配置页按 `supply_id` 决定（步骤 6 起）：发现结果**不再提供** `config_slot`。
  步骤 5 落地时配置集合仍按 `PSn` 存放，所以当时额外用过渡字段 `config_slot`（设备表登记的
  旧槽位）限制“一批只接受一台电源”；该字段与这条限制随步骤 6 的绑定集合一起删除。
- “有没有角色”只有一个判据：`DiscoveredDevice.has_role` 也用折叠后的类别判断，与
  `device_applicable`、配置页接受的角色集合同源。登记成未知字面量（手改出 `PS9`）的设备
  在状态列是“未分配角色”且不可勾选，不会出现“状态说已登记、勾选框却是灰的”。
- 电源绑定记录在步骤 6 收敛为“键 = `supply_id`、记录内只留身份字段”：不再重复写
  `role` / `label` / `supply_id`。面板“当前配置”按集合键显示短标签，应用结果的消息写成
  `电源 DP8B1519`，不再出现槽位编号。

实现见 `infrastructure/discovery/instrument_discovery.py`（结果字段与类别折叠）、
`presentation/qt/device_discovery_panel.py`（显示“短标签（型号，电源）”、多台电源独立传递、
按身份预选）与 `presentation/qt/config_page.py`（写入边界的校验与按 `supply_id` 落地址）。

**验收标准**

- 同时发现两台以上电源时，每台都能独立显示，并在一次勾选中各自独立交付（不再按角色键互相
  覆盖）。
- IP 变化后仍能匹配原设备和原标签。

**本步的已知边界（不是缺陷，留给步骤 6；步骤 6 已全部关闭）**

- “应用”仍是整批替换，且配置里的电源集合还按旧槽位存放，所以一批里只接受一台带旧槽位的
  电源：勾选两台会被明确拒绝并说明原因，不会静默应用最后一台。因此“每台都能独立**应用**”
  要等步骤 6 的 `device_bindings.power_supplies[<supply_id>]` 与配置动态化落地，那时的验收
  标准是「绑定 2 台电源后一次应用即得到两条独立绑定」。
- 迁移后的设备表（`power_supply`、没有旧槽位）在配置页无法写入地址，需要同一批步骤 6 的改动。

### 步骤 6：改造设备绑定结构

**工作内容**

- 将电源绑定从 `device_bindings["PS3"]` 迁移到 `device_bindings.power_supplies["DP8B1519"]` 或等价集合结构。
- 更新整批替换、清除绑定和绑定校验。

**执行策略**

- 信号源和频谱仪暂时保留单设备绑定结构。
- 仅电源分支改为动态集合，降低一次改动范围。
- 旧绑定按序列号迁移；只有地址的旧绑定要求重新扫描。

**技术决定**

- 电源绑定的主键为 `supply_id`，记录内必须带 `device_key`。
- 同一 `device_key` 不能出现在多个电源绑定中。
- 引用格式（无空白、无 `/`）与身份一致性在读入和写入边界用同一套判定校验；不合格的
  记录不进入可用集合，并必须被明确报告，不能静默丢弃。

**验收标准**

- 清除绑定后所有对应电源地址和启用状态同时失效。
- 重新应用一批电源时不会残留未勾选的旧电源。

**实现见** `presentation/qt/config_form_state.py`（`power_supply_bindings` /
`bound_power_supplies` / `power_supply_binding_problems` / `supply_id_problem` /
`read_instrument_config` 的地址与身份回写）、
`presentation/qt/config_page.py`（整批替换、同一 `device_key` 去重、引用格式校验、
按 `supply_id` 建电源标签页、读入/保存校验报告坏绑定）、
`presentation/qt/device_discovery_panel.py`（交付短标签，不再交付
`config_slot`）与 `domain/configuration/rules.py`（模拟扫描门禁覆盖 `power_supplies` 集合）。

**本步的完成度与边界**

- 绑定结构、配置地址回写、配置页写入校验与电源标签页已全部按 `supply_id` 工作，步骤 5
  的两条已知边界（多台电源整批拒绝、迁移后的设备表无法写地址）随之关闭。
- 绑定读取与 UI 写入共用同一套判定：`supply_id` 必须能当引用（无空白与 `/`），记录必须
  带自洽的 `device_key`。不合格的记录不会变成可分配电源，也不会被静默丢弃——配置页在
  读入时提示，并在保存/运行校验时明确失败。
- 身份字段以绑定记录为唯一来源：绑定里没有的 `device_key` / `serial` / `model` 不再从
  旧配置沿用，避免地址与身份错配。
- 旧的 `instruments.power_supplies.<PSn>` 条目在本步之后**只保留参数、不再连接**；把它们
  改挂到 `supply_id` 上属于步骤 13 的配置迁移器。
- 电源分配下拉框仍以文本显示 `supply_id`，`itemData` 保存值与视觉优化属于步骤 9；正式
  `run_mapping` 仍是单数 `power_supply`（步骤 10～12），因此一次运行仍只能登记一台本机
  供电电源。

## 阶段三：改造配置编写和 Qt 页面

### 步骤 7：将电源配置读取改为动态集合

**工作内容**

- 修改 `config_form_state.py`。
- 删除业务逻辑对 `POWER_SUPPLY_NAMES` 的依赖。
- 让 `bound_power_supplies()` 返回当前绑定的动态电源 ID。

**执行策略**

- 先保留旧函数名，内部改为动态实现，减少调用点变更。
- 读取旧配置时执行一次旧键到新 ID 的适配。
- 未绑定的配置引用保持空选择并交给校验报告。

**技术决定**

- 可用电源来源统一为设备绑定，不再看静态“启用”标志。
- 配置中未绑定的电源不能临时塞进下拉框。

**验收标准**

- 绑定 1、2、5 台电源时，返回集合准确。
- 电源替换后旧 ID 不会自动指向新设备。

**实现见** `presentation/qt/config_form_state.py`（`assignment_supply_id` /
`bound_power_supplies` / `_assignment_entry` / `read_power_assignment` 与分配校验）、
`presentation/qt/config_page.py`（`_power_choice_combo`：只回填真实绑定过的引用）。

**本步的完成度与边界**

- 固定常量已清空：`POWER_SUPPLY_NAMES` 随步骤 6 一起删除，本步确认生产代码里不再有
  槽位常量参与配置读取。电源集合的键与分配引用都只来自 `supply_id`，
  `bound_power_supplies()` 返回的就是本次绑定里所有有地址的电源——1 台、2 台、5 台
  只是同一份集合的不同长度，不需要改代码或加常量。
- 供电分配的引用主字段改为 `supply_id`：读入时 `assignment_supply_id()` 以 `supply_id`
  为准（`null` 表示“引用未绑定”），只有完全没有该字段的旧记录才回落读一次旧字段
  `name`；写出时同时写同名 `name`，过渡期尚未迁移到集合的读取方（正式运行映射、硬件
  装配）不必同步改动。两者取值相同，不存在第二套编号。
- 可用电源只看设备绑定，不看 `instruments.*.enabled`：未绑定的引用在下拉框里保持空
  选择并交给校验报告。载入配置与整批应用两条路径共用同一判定，避免 `QComboBox` 找不到
  文本时停在第一项、把“这台电源已经不在”显示成“换成了另一台电源”。
- “配置里没有这条分配”和“声明了但未绑定”是两种状态，回填时必须分开
  （`assignment_declared()`）：前者按缺省规则选第一台可用电源，后者（`supply_id: null`、

  `assignment_supply_id()` 判定，`supply_id` 与旧别名 `name` 冲突时以 `supply_id`
  为准。投影模块的固定槽位默认值已在步骤 8 删除，回填顺序也改为“已有引用优先，否则
  第一个可用设备，否则空选择”（见步骤 8）。
- 仍按 `name` 读取的调用方：`domain.configuration.rules`、`configuration_authoring`、

**技术决定**

- 电源数量由实际分配和绑定共同决定，不由旧的 `model` 单字段推断。
- 多电源的地址重复、通道重复和角色冲突必须在连接前报错。

**实现见** `presentation/qt/configuration_authoring.py`（`_author_dut_channel_mappings` /
`_author_driver_channel_mappings` 不再静默去重、`_author_power_supply_entries` 按实际引用的
`supply_id` 逐台写条目）、`domain/configuration/rules.py`（`assignment_supply_id` 成为引用
判据的唯一实现、`_validate_assignment` 改用 `supply_id`、新增
`_validate_supply_addresses` / `_validate_cross_group_channels` / `_require_reference_alias`
与只取连接冲突的 `validate_hardware_connections`）、`domain/configuration/models.py`
（`_validate_role_uniqueness`）、`presentation/qt/config_form_state.py`
（`validation_errors` 增加正式运行校验与 `validate_hardware_connections`；关闭驱放时不再写回
遗留的驱动分配）与 `app/run_context.py`（`create_prepared_run` 在写任何运行目录之前拒绝连接冲突）。

**本步的完成度与边界**

- 配置作者不再有任何“只能一个电源”的分支（步骤 10 已删除），本步补齐的是**冲突检测**：
  通道映射不再按 token 去重——同一条 `supply_id/CHx` 被排两次时原样写进映射，由正式校验报
  `通道重复分配`，而不是悄悄只留一条、让页面上的第二个角色凭空消失。
- 两个层次的冲突各报一次、都能在连接前失败：
  - 正式映射（`validate_run_mapping`）：同一物理通道重复、DUT 供电角色重复（两台电源都
    声称 `gate`，通道不同也算）、地址/`device_key` 重复、通道前缀指向不存在的电源。
  - 硬件装配段（`validate_config` 与 `validate_hardware_connections`）：启用的电源之间、
    电源与信号源/频谱仪之间地址重复（忽略大小写与首尾空白）、分配引用了不存在的电源或
    未绑定的 `supply_id`、过渡别名 `name` 与 `supply_id` 不同值、同一物理通道同时供 DUT
    与驱动功放。只比对**启用**的条目：未启用的电源不会被连接，它的历史地址不是冲突。
- 引用判据只有一处实现：`domain.configuration.rules.assignment_supply_id`（`supply_id`
  为准，只有完全没有该字段的旧记录回落读一次 `name`）。`config_form_state` 与
  `configuration_authoring` 都调用它，不再各写一遍；文件级校验因此也能读懂 `supply_id`
  引用（此前只认 `name`，新配置会在文件校验收不到的地方“看起来合法”）。
- 失败落在三个入口，且都不产生副作用：配置页 `validation_errors`（创建运行前的那一条
  提示里就能看到具体原因）、`launcher --validate-config`（文件级）、
  `create_prepared_run`（写运行目录之前）。运行创建用的是 `validate_hardware_connections`
  而不是完整 `validate_config`：它只拦“会连错设备”的冲突，不把通道保护值缺失之类的字段
  完整性问题带进运行创建（那两处入口负责）。
- `validate_hardware_connections` 与 `validate_config` 共用同一份解析
  （`_collect_assignment_channels`：每台电源引用了哪些物理通道），但**共用实现不等于共用
  报告**：连接校验只收引用层错误（引用缺失、电源不存在、电源未启用、过渡别名不一致、
  通道不在该电源上）与地址/跨组通道冲突；通道未声明 `role`、gate/drain 不齐、
  `power_supply_count` 不符、`channel` 为空或不是列表都是字段完整性问题，只由
  `validate_config` 报。否则一份结构缺失的配置会在写运行目录前被拒成“供电连接存在冲突”，
  把排查方向引到接线。测试覆盖两面：这些都是连接校验的“无冲突”，同时又必须是完整校验
  的错误。
- 配置页的正式校验只把 `ConfigurationError`（配置作者对当前读数的判断）转成页面错误；
  其它异常照常抛给上层，不伪装成“配置有问题”。
- 关闭驱放测试模式后，页面不再写回上一次保存的驱动分配；`build_config` 在页面不提交驱动
  分配且驱放关闭时清空 `power_supply_assignment.driver_amplifier`，避免协调器持有的旧副
  本让“页面已做对的配置”在校验阶段被拒。
- 仍属于后续步骤：连接与安全关闭仍按旧硬件装配路径读取 `instruments.power_supplies`
  与分配的 `name`（步骤 12）；`config.json` 仍是旧单数结构（步骤 13 的迁移器）。

**验收证据**

- `tests/test_config_validation.py`：两台启用电源同地址、电源与信号源同地址、
  未启用电源不参与冲突、同一物理通道跨组重复、`supply_id` 引用合法、`name` 与
  `supply_id` 不同值报错、`supply_id: null` 报“必须填写已绑定的电源引用”；以及
  `validate_hardware_connections` 只取连接冲突（缺保护值、通道未声明角色、gate/drain
  不齐、`channel` 为空或不是列表都不算，而完整校验必须报）、未绑定引用、跨组通道、
  通道不在该电源上仍算冲突。
- `tests/test_run_mapping_multi_supply.py`：同一物理通道分配两次、DUT 供电角色重复、
  一台电源供两个角色仍合法、驱动功放与 DUT 同通道被拒 / 不同通道合法。
- `tests/ui/test_configuration_authoring.py`：通道被排两次时原样写出并由正式校验报错、
  两台电源都声称 `gate` 被拒。
- `tests/ui/test_config_form_state.py`：页面校验报出“同一物理通道”与“共用同一 VISA 地址”，
  地址不同时没有连接类错误；引用判据与领域实现是同一个函数；`ConfigurationError` 变成
  页面错误，其它异常不被吞掉。
- `tests/test_run_service.py`：`create_prepared_run` 在连接冲突时不创建运行目录；通道未声明
  `role`（字段完整性问题）不阻止创建运行。
- `tests/integration/test_main_window_flow.py`：关闭驱放后页面仍能创建运行。

## 阶段五：迁移、清理和发布

### 步骤 13：实现旧配置迁移器

**工作内容**

- 新增独立迁移函数或迁移模块。
- 支持 `PS1..PS4` 到短标签的字段级迁移。

**执行策略**

- 迁移输入和输出都保留在内存对象中，最终由现有原子保存机制写盘。
- 迁移前输出摘要：旧键、新键、设备序列号和无法迁移项。
- 任何无法确认身份的旧电源都不自动猜测。

**技术决定**

- 有 `device_bindings.serial` 时自动迁移。
- 只有旧地址时必须重新扫描。
- 迁移失败不覆盖原配置。

**验收标准**

- 当前 `config.json` 可生成等价的新配置。
- 旧配置中的电压、电流、通道角色和分配关系不丢失。
- 迁移失败时原文件仍可继续使用。

### 步骤 14：更新运行记录、日志和显示

**工作内容**

- 将历史页面、运行日志、连接图和错误信息中的电源名称改为短标签。
- 保留序列号用于详情和审计。

**执行策略**

- 新日志使用 `label/channel`。
- 旧运行记录按旧字段显示，不强行推导不存在的标签。
- 详情页同时展示短标签、型号和完整序列号。

**技术决定**

- 标签用于快速识别，完整序列号用于最终追溯。
- 不在日志中使用位置编号替代设备身份。

**验收标准**

- 操作者可以从日志直接对应到实物标签。
- 历史运行仍可读取。

### 步骤 15：删除固定槽位依赖

**工作内容**

- 清理 `PS1..PS4` 在生产逻辑中的固定引用。
- 更新文档、示例配置、初始化脚本和测试名称。

**执行策略**

- 先用搜索确认生产代码不再依赖固定槽位。
- 再删除仅用于兼容的旧常量或将其移动到迁移模块。
- 不删除旧配置读取测试。

**技术决定**

- 旧字段只允许存在于迁移和兼容边界。
- 新增电源不需要修改 Python 常量或重新发布程序。

**验收标准**

- 支持 1、2、5 台电源无需增加新常量。
- 新配置、运行快照和日志均使用短标签。
