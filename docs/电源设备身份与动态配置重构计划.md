# 电源设备身份与动态配置重构计划

## 1. 文档目的

当前系统把 `PS1`、`PS2`、`PS3`、`PS4` 同时当作电源名称、设备角色、配置键和分配引用。设备实际流转时，这些编号不能帮助操作者核对实物，也限制了同时使用多台电源。

本计划将系统逐步改为：

- 设备身份按“厂商 + 完整序列号”识别；
- 现场标签使用序列号派生的短标签，例如 `DP8B1519`；
- `role` 只表示设备类别 `power_supply`，不表示第几台；
- 电源集合、绑定和分配按实际设备动态生成；
- 正式运行快照冻结全部实际使用的电源；
- 旧的 `PS1..PS4` 配置可读取和迁移，新配置不再生成固定编号。

## 2. 当前基线与约束

调研确认：

1. `domain.instruments.models` 已使用 `厂商:序列号` 作为设备唯一身份，IP 只属于地址端点，这部分设计保留。
2. `instruments.json` 的 `role` 当前只允许 `signal_generator`、`spectrum_analyzer` 和 `PS1..PS4`。
3. `config_form_state.py`、`config_page.py`、`config_projection.py` 固定使用 `PS1..PS4`。
4. `configuration_authoring.py` 生成的正式 `run_mapping` 目前只有单数 `power_supply`。
5. `instrument.measurement_factory` 已支持 `supply/channel` 形式的多电源路由，例如 `DP8B1519/CH1`，因此底层路由可以复用。
6. 当前工作区已有测试文件重命名和未跟踪测试包目录变更。本计划实施时不得覆盖、回退或批量重排这些现有改动。

## 3. 目标模型与技术决定

### 3.1 四个概念必须分离

| 概念 | 用途 | 是否可变 |
|---|---|---|
| `device_key` | 系统匹配和去重，值为 `vendor:serial` | 不可变 |
| `serial` | 设备原始身份 | 不可变 |
| `label` / `supply_id` | 人和配置使用的短标签，如 `DP8B1519` | 首次生成后不可变 |
| `role` | 功能类别，如 `power_supply` | 可登记，但不是编号 |

技术决定：内部逻辑以 `device_key` 做身份校验，以 `supply_id` 做电源配置引用；不能仅凭短标签识别设备。

### 3.2 短标签规则

默认规则为“序列号前缀 + 序列号末四位”。例如：

```text
DP8B214901519 -> DP8B1519
DP8B174700950 -> DP8B0950
DP8B174400885 -> DP8B0885
```

技术决定：

- 序列号先去空格、去引号并转大写；
- 前缀取序列号开头的产品/系列字母数字段；
- 默认取末四位，保留前导零；
- 发生冲突时依次扩展到末五位、末六位，最后使用完整归一化序列号；
- 标签生成后写入设备注册表，不因 IP、型号序号或重新扫描而重算；
- 退役设备的标签不回收。

### 3.3 配置格式决定

新格式的电源配置使用动态键：

```json
{
  "instruments": {
    "power_supplies": {
      "DP8B1519": {
        "label": "DP8B1519",
        "device_key": "rigol technologies:dp8b214901519",
        "serial": "DP8B214901519",
        "model": "DP832A",
        "address": "TCPIP0::192.168.1.102::inst0::INSTR",
        "enabled": true,
        "channels": {}
      }
    }
  }
}
```

分配引用使用 `supply_id`；过渡期可同时写 `name`，但新代码内部统一读取 `supply_id`。

正式运行映射增加 `instruments.power_supplies` 集合，保留旧的单数 `power_supply` 读取兼容。通道连接使用 `supply_id/CHx`。

## 4. 分阶段实施计划

每个步骤应单独提交、单独测试。步骤之间以数据契约为边界，避免一次修改同时触及注册表、Qt 页面和运行模型。

## 阶段一：建立标签基础能力

### 步骤 1：编写数据契约和迁移样例

**工作内容**

- 新建一份 schema 示例，列出旧配置和新配置的对应关系。
- 固定字段名称：`label`、`supply_id`、`device_key`、`role`。
- 明确旧字段 `PS1..PS4` 只作为兼容输入。

**执行策略**

- 只新增文档和 fixture，不修改业务逻辑。
- 用当前 `instruments.json` 的三台 DP832A 编写真实迁移样例。
- 同时记录“只有地址、没有序列号”的无法自动迁移场景。

**技术决定**

- 不把 `device_key` 替换成可读标签；二者同时保留。
- 不使用 IP、MAC、型号序号生成标签。

**验收标准**

- 文档中的字段能够表达 1 台、2 台和多台电源。
- 旧配置缺少序列号时有明确的人工重新扫描路径。

### 步骤 2：实现短标签生成器

**工作内容**

- 新增 `domain/instruments/labels.py`。
- 实现序列号归一化、前缀提取、末四位生成和冲突扩展。

**执行策略**

- 纯 Python 实现，不依赖 Qt、文件系统或网络。
- 输入已有标签集合，输出稳定候选标签。
- 标签生成器不负责写注册表，由调用方决定持久化。

**技术决定**

- 第一次生成的标签必须显式保存。
- 冲突不能覆盖旧标签。
- 无法生成合法标签时抛出可识别的领域异常。

**验收标准**

- 覆盖当前三台设备的预期结果。
- 覆盖前导零、大小写、空格、碰撞和纯数字序列号。
- 独立单元测试通过。

### 步骤 3：扩展仪器领域模型

**工作内容**

- 给 `Instrument` 增加 `label` 或等价稳定字段。
- 增加 `POWER_SUPPLY_ROLE = "power_supply"`。
- 保留旧 `PS1..PS4` 常量，仅用于迁移识别，不再作为新角色集合。

**执行策略**

- 先扩展 dataclass 和序列化，不改变设备扫描流程。
- `normalize_role` 同时接受旧角色和新角色，旧角色进入兼容分支。

**技术决定**

- `device_key` 继续动态计算，不复制多份来源。
- `name` 继续保留为软件资产名；现场显示优先使用 `label`。

**验收标准**

- 新模型可表达多个 `power_supply`。
- 旧注册表记录仍可读取。

## 阶段二：升级设备注册表和发现流程

### 步骤 4：迁移注册表字段

**工作内容**

- 修改 `instrument_registry.py` 的读写和校验。
- 为旧的 `PSn` 电源根据完整序列号补生成 `label`。
- 将可识别的旧角色转换为 `power_supply`。

**执行策略**

- 读取时兼容旧 schema。
- 保存时统一写新字段和新 schema 版本。
- 迁移前保留原文件备份或通过原子写入避免半文件。

**技术决定**

- 同一序列号只允许一个注册记录。
- 标签冲突必须阻止保存并报告冲突设备。
- 未登记角色不自动猜测为电源。

**验收标准**

- 当前注册表迁移后有三个明确短标签。
- 重新加载后标签、序列号和设备键保持一致。

### 步骤 5：改造设备发现结果

**工作内容**

- 修改发现结果中的电源角色、显示名称和绑定数据。
- 将显示从“资产名（电源 PS3）”改为“短标签（型号，电源）”。

**执行策略**

- 扫描匹配仍只使用 `device_key`。
- 发现结果增加 `label`、`supply_id`、`serial` 和 `device_key`。
- 先支持新字段，同时保留旧测试数据的转换适配。

**技术决定**

- 设备发现不负责分配标签；标签只来自注册表或注册动作。
- 多台电源使用列表/集合传递，不再以角色键覆盖彼此。

**验收标准**

- 同时发现两台以上电源时，每台都能独立显示和应用。
- IP 变化后仍能匹配原设备和原标签。

### 步骤 6：改造设备绑定结构

**工作内容**

- 将电源绑定从 `device_bindings["PS3"]` 迁移到 `device_bindings.power_supplies["DP8B1519"]` 或等价集合结构。
- 更新整批替换、清除绑定和绑定校验。

**执行策略**

- 信号源和频谱仪暂时保留单设备绑定结构。
- 仅电源分支改为动态集合，降低一次改动范围。
- 旧绑定按序列号迁移；只有地址的旧绑定要求重新扫描。

**技术决定**

- 电源绑定的主键为 `supply_id`，记录内必须带 `device_key`。
- 同一 `device_key` 不能出现在多个电源绑定中。

**验收标准**

- 清除绑定后所有对应电源地址和启用状态同时失效。
- 重新应用一批电源时不会残留未勾选的旧电源。

## 阶段三：改造配置编写和 Qt 页面

### 步骤 7：将电源配置读取改为动态集合

**工作内容**

- 修改 `config_form_state.py`。
- 删除业务逻辑对 `POWER_SUPPLY_NAMES` 的依赖。
- 让 `bound_power_supplies()` 返回当前绑定的动态电源 ID。

**执行策略**

- 先保留旧函数名，内部改为动态实现，减少调用点变更。
- 读取旧配置时执行一次旧键到新 ID 的适配。
- 未绑定的配置引用保持空选择并交给校验报告。

**技术决定**

- 可用电源来源统一为设备绑定，不再看静态“启用”标志。
- 配置中未绑定的电源不能临时塞进下拉框。

**验收标准**

- 绑定 1、2、5 台电源时，返回集合准确。
- 电源替换后旧 ID 不会自动指向新设备。

### 步骤 8：将配置投影改为动态电源

**工作内容**

- 修改 `config_projection.py`。
- 删除 `DEFAULT_POWER_ASSIGNMENT` 中的固定 PS 默认值。
- 对缺失电源采用“已有引用优先，否则第一个可用设备，否则空选择”的规则。

**执行策略**

- 先改纯 Python 投影逻辑，再改 Qt 控件创建。
- 明确区分“配置缺失”和“配置引用未绑定”。

**技术决定**

- 不根据设备排序把新设备静默填入已有角色。
- 所有默认选择都必须能在当前绑定集合中找到。

**验收标准**

- 旧配置可以投影。
- 新配置可以只包含一台或多台电源。
- 未绑定引用会保持空选择并触发验证错误。

### 步骤 9：将 Qt 电源页面改为动态创建

**工作内容**

- 修改 `config_page.py` 的电源 Tab、分配下拉框和页面刷新逻辑。
- 下拉显示短标签，可通过 `itemData` 保存 `supply_id`。

**执行策略**

- 电源详细配置页面按当前配置和绑定集合动态创建。
- 刷新时保存已有控件值，再按 ID 重建或更新，不能按位置对应设备。
- 小范围先支持动态数量，再处理界面视觉优化。

**技术决定**

- 业务值不从显示字符串反解析。
- 显示文本可为 `DP8B1519（DP832A）`，实际值必须是 `DP8B1519`。
- PA 单元数量和电源数量保持两个独立概念。

**验收标准**

- 电源数量变化时页面不崩溃、不丢通道参数。
- 下拉框只显示当前绑定电源。
- 旧配置中的 PS 引用经过迁移后能正确回填。

## 阶段四：升级正式运行模型和硬件装配

### 步骤 10：扩展正式运行映射

**工作内容**

- 修改 `RunResourceMapping`，增加多电源集合。
- 保留旧 `instruments.power_supply` 的读取兼容。

**执行策略**

- 新字段建议为：

  ```json
  "instruments": {
    "power_supplies": {
      "DP8B1519": {
        "label": "DP8B1519",
        "model": "DP832A",
        "serial": "DP8B214901519",
        "visa_address": "..."
      }
    }
  }
  ```

- 新配置只写多电源结构。
- 旧运行目录仍可按单数结构读取。

**技术决定**

- 运行快照必须记录标签、序列号、型号和地址，而不是只记录名称。
- 运行创建后不重新从设备注册表推导设备。

**验收标准**

- 两台电源都能进入运行快照。
- 快照可独立用于历史查看和重现。

### 步骤 11：修改配置作者和运行校验

**工作内容**

- 修改 `configuration_authoring.py`，移除“正式映射只能有一个电源”的限制。
- 修改 `domain.configuration.models` 和 `rules.py` 的运行映射校验。

**执行策略**

- 从分配中的所有 `supply_id` 收集实际使用电源。
- 为每个实际使用的电源生成正式映射。
- 通道连接统一写为 `supply_id/CHx`。

**技术决定**

- 电源数量由实际分配和绑定共同决定，不由旧的 `model` 单字段推断。
- 多电源的地址重复、通道重复和角色冲突必须在连接前报错。

**验收标准**

- gate 和 drain 可以来自不同电源。
- 同一物理通道重复使用时校验失败。
- 不再出现“多个电源无法生成正式 run_mapping”的错误。

### 步骤 12：连接和安全关闭使用动态电源集合

**工作内容**

- 修改运行配置到服务配置的转换。
- 检查 `measurement_factory`、`PortMeasurementAdapter` 和安全关闭路径对动态 ID 的支持。

**执行策略**

- 优先复用现有 `_ConfiguredPowerSupply` 的 `supply_id/channel` 路由。
- 只在边界适配旧字段，不修改 SCPI 电源驱动协议。
- 增加多电源连接、初始化、上电、测量和关闭测试。

**技术决定**

- 物理电源路由必须始终使用显式 `supply_id/CHx`。
- 紧急关闭只关闭实际声明和使用过的通道。

**验收标准**

- 多电源均能连接并完成初始输出检查。
- 任意异常路径都能关闭所有已打开电源。
- 日志包含短标签和通道，例如 `DP8B1519/CH1`。

## 阶段五：迁移、清理和发布

### 步骤 13：实现旧配置迁移器

**工作内容**

- 新增独立迁移函数或迁移模块。
- 支持 `PS1..PS4` 到短标签的字段级迁移。

**执行策略**

- 迁移输入和输出都保留在内存对象中，最终由现有原子保存机制写盘。
- 迁移前输出摘要：旧键、新键、设备序列号和无法迁移项。
- 任何无法确认身份的旧电源都不自动猜测。

**技术决定**

- 有 `device_bindings.serial` 时自动迁移。
- 只有旧地址时必须重新扫描。
- 迁移失败不覆盖原配置。

**验收标准**

- 当前 `config.json` 可生成等价的新配置。
- 旧配置中的电压、电流、通道角色和分配关系不丢失。
- 迁移失败时原文件仍可继续使用。

### 步骤 14：更新运行记录、日志和显示

**工作内容**

- 将历史页面、运行日志、连接图和错误信息中的电源名称改为短标签。
- 保留序列号用于详情和审计。

**执行策略**

- 新日志使用 `label/channel`。
- 旧运行记录按旧字段显示，不强行推导不存在的标签。
- 详情页同时展示短标签、型号和完整序列号。

**技术决定**

- 标签用于快速识别，完整序列号用于最终追溯。
- 不在日志中使用位置编号替代设备身份。

**验收标准**

- 操作者可以从日志直接对应到实物标签。
- 历史运行仍可读取。

### 步骤 15：删除固定槽位依赖

**工作内容**

- 清理 `PS1..PS4` 在生产逻辑中的固定引用。
- 更新文档、示例配置、初始化脚本和测试名称。

**执行策略**

- 先用搜索确认生产代码不再依赖固定槽位。
- 再删除仅用于兼容的旧常量或将其移动到迁移模块。
- 不删除旧配置读取测试。

**技术决定**

- 旧字段只允许存在于迁移和兼容边界。
- 新增电源不需要修改 Python 常量或重新发布程序。

**验收标准**

- 支持 1、2、5 台电源无需增加新常量。
- 新配置、运行快照和日志均使用短标签。

## 6. 发布顺序和回滚策略

建议按以下顺序发布：

1. 发布标签生成和注册表兼容读取；
2. 发布设备发现的新显示和新绑定数据；
3. 发布配置页面动态电源；
4. 发布多电源正式运行映射；
5. 最后将新配置设为默认写出格式。

每一步都应保证：

- 原始配置在迁移失败时不被覆盖；
- 旧运行目录仍可读取；
- 旧的 `PS1..PS4` 只在兼容边界有效；
- 新设备可以使用短标签，不需要修改固定常量；
- 任一阶段未完成时，不提前删除旧字段。

## 7. 建议的首个实施切片

第一轮只做以下三个小步骤：

1. 步骤 1：数据契约和迁移样例；
2. 步骤 2：短标签生成器；
3. 步骤 3：领域模型增加 `label` 和 `power_supply`。

这三个步骤不改变 Qt 页面、不改变运行流程，风险最小，但能先锁定后续所有模块共同使用的数据规则。
