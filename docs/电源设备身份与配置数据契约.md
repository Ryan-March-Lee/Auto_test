# 电源设备身份与配置数据契约

本文件是[电源设备身份与动态配置重构计划](电源设备身份与动态配置重构计划.md)“步骤 1：编写数据契约和迁移样例”
的交付物。它固定后续所有步骤共用的字段名、旧新对照和迁移判定，并把当前现场数据写成可复核的样例。

**本步骤只新增文档和 fixture，不改变任何运行时行为**：没有新增/修改业务代码，旧配置在现有版本里
仍然按 `PS1..PS4` 读取。字段落地顺序见计划的步骤 2（标签生成器）、步骤 3（领域模型）、步骤 4（注册表迁移）、
步骤 6（绑定结构）、步骤 10（运行映射）、步骤 13（配置迁移器）。

样例数据在 `tests/fixtures/power_supply_identity/`，清单见本文第 10 节与
[fixture README](../tests/fixtures/power_supply_identity/README.md)。

## 1. 适用范围

| 对象 | 位置 | 本契约覆盖 |
| --- | --- | --- |
| 设备注册表 | `instruments.json` | 字段、角色取值、标签生成与冻结 |
| 配置 | `config.json` 的 `instruments.power_supplies` / `power_supply_assignment` / `device_bindings` | 电源集合键、分配引用、绑定结构 |
| 运行资源映射 | `config.json` 的 `run_mapping` 与运行目录里的 `run_mapping.json` | 多电源集合、`supply_id/CHx` 路由、快照冻结 |

不覆盖：信号源与频谱仪的单设备绑定（保持现状）、PA 单元数量（与电源数量是两个独立概念）、
SCPI 电源驱动协议、`instrument.measurement_factory` 已有的 `supply/channel` 路由实现（直接复用）。

## 2. 四个概念必须分离

| 概念 | 用途 | 取值 | 可变性 |
| --- | --- | --- | --- |
| `device_key` | 系统匹配、去重、绑定校验 | `厂商:序列号`，`make_device_key` 生成的小写形式 | 不可变 |
| `serial` | 设备原始身份 | `*IDN?` 第三段，去空白/引号后的大写序列号 | 不可变 |
| `label` / `supply_id` | 人和配置使用的短标签 | 序列号派生的短标签，如 `DP8B1519` | 首次生成后不可变 |
| `role` | 功能类别 | `signal_generator` / `spectrum_analyzer` / `power_supply` | 可登记，但**不是编号** |

规则：

- 身份校验只用 `device_key`。`label` 只用于显示和配置引用，**不能**单独用来识别设备。
- `label` 与 `supply_id` 是同一个字符串：注册表里叫 `label`，配置/运行映射里用它做键，称为 `supply_id`。
  不存在第二套编号，也不允许两者不一致。
- `role` 只表示“这是哪一类设备”，没有第几台。`PS1..PS4` 不再是角色取值，只在迁移读取时被识别。
- 退役设备的 `label` 不回收；新设备生成新标签。

## 3. 短标签规则

### 3.1 生成算法

1. **归一化**：只调用 `domain.instruments.models.normalize_serial`，不在标签生成器里另写一套。
   该函数折叠首尾与连续空白、去掉成对引号、转大写，但**保留单个内部空白**——内部空白是设备身份的一部分，
   标签生成器不得私自去掉它。引号与空白同时出现时（如 `*IDN?` 分段带引号且带空格）一轮剥不完，
   因此 `normalize_serial` 自身**反复应用单轮归一化直到结果不再变化**（实测两轮收敛）：
   这是唯一的稳定值来源，`serial`、`device_key` 与短标签都用它，标签生成器不再重复这套循环。
2. **取前缀**：从序列号开头读取，字母一律保留；数字只有在“后面紧跟字母”时才保留（`DP8B` 里的 `8`）；
   遇到连续两位及以上的数字段即停止；遇到第一个既不是字母也不是数字的字符（空格、点、斜杠、连字符）
   也立即停止。前缀可以为空。
3. **取尾部四位**：`serial[-4:]`，保留前导零；序列号不足四位时取全部。第 1 步已排除内部空白，
   因此这里不会截到空格。
4. **候选标签** = 前缀 + 尾部四位；前缀为空时候选标签就是尾部四位。归一化序列号长度不超过四位时，
   候选标签直接取归一化序列号本身，避免 `A12` 拼成 `AA12` 这类重复拼接；前缀占满整个序列号
   （如 `ABCDE`）时同理只保留完整序列号，不会拼成 `ABCDEABCDE`。
5. **冲突扩展**：候选标签与已有标签（含退役设备）冲突时，依次改用末五位、末六位，最后用完整归一化序列号；
   扩展同样保留前缀，且**不会越过通道分隔符 `/`**：标签要当 `supply_id` 用（会拼成 `supply_id/CHx`），
   尾段一旦出现 `/` 就停止加宽，含 `/` 的完整序列号不作为候选。一个可用候选都没有时抛领域异常。
   冲突绝不覆盖已有标签。

### 3.3 边界情形

| 情形 | 输入 | 标签 | 说明 |
| --- | --- | --- | --- |
| 前导零 | `DP8B174700950` | `DP8B0950` | 末四位补零，不裁掉 |
| 大小写与空白 | `" dp8b214901519 "` | `DP8B1519` | 先归一化（引号与空白并存需两轮）再生成 |
| 纯数字序列号 | `105462` | `5462` | 前缀为空，只用末四位 |
| 序列号过短 | `A12` | `A12` | 不足四位时用完整序列号 |
| 碰撞（末四位相同） | 已有 `DP8B1519`（来自 `DP8B214901519`）；新设备 `DP8B151519` | `DP8B51519` | 扩展为末五位 |
| 碰撞（末五位也相同） | 已有 `DP8B1519`、`DP8B51519`；新设备 `DP8B126951519` | `DP8B951519` | 扩展为末六位 |
| 碰撞（末六位也相同） | 已有 `DP8B1519`、`DP8B51519`、`DP8B951519`；新设备 `DP8B1951519` | `DP8B1951519` | 最后用完整归一化序列号 |
| 前缀后紧跟非字母数字 | `1412.0000K02/105462` | `5462` | 点与斜杠终止前缀，前缀为空 |
| 前缀占满整个序列号 | `ABCDE` | `ABCDE` | 没有可加宽的尾部，候选只有完整序列号，不拼成 `ABCDEABCDE` |
| 尾段跨过通道分隔符 | `1412.0000K02/105462`（`5462`、`05462`、`105462` 都已被占用） | 抛出领域异常 | 标签要当 `supply_id` 用，含 `/` 会打断 `supply_id/CHx` 路由，不做候选 |
| 完整序列号含 `/` | `AB/CD1` | 抛出领域异常 | 每个候选都含 `/`，交回操作员修正序列号 |
| 归一化后仍有内部空白 | `"DP8B 2149 01519"` | 抛出领域异常 | 内部空白属于解析异常，静默去掉会让标签与身份不同源，交回操作员修正序列号 |
| 归一化后为空 | `""` / `"''"` | 抛出领域异常 | 步骤 2 实现为可识别的领域异常 |

### 3.4 冻结与不回收

- 标签在第一次生成时写入注册表，之后**不因 IP 变化、型号序号变化、重新扫描或重新匹配而重算**。
- 退役设备的标签保留在注册表里，不被新设备复用；同型号序号同样只增不减。
- 标签生成器不写注册表，由调用方决定持久化（步骤 2）。实现见 `domain/instruments/labels.py`：
  纯计算，输入原始序列号与已有标签集合，输出不与既有标签冲突的稳定候选标签；归一化直接调用
  `domain.instruments.models.normalize_serial`（该函数自己循环到稳定），生成器只补领域校验。
- 实际调用方是设备注册表的保存路径（步骤 4）：`instrument_registry.py` 的 `_canonical_document`
  在写盘前为登记为 `power_supply` 却缺标签的设备生成标签并立刻写进文件，之后冻结。

## 4. 字段契约

### 4.1 身份与标签字段

| 字段 | 出现位置 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- | --- |
| `device_key` | 注册表条目、`device_bindings`、配置电源条目、运行映射电源条目 | string | 是 | `厂商:序列号`（小写），唯一身份 |
| `serial` | 同上 | string | 是 | `normalize_serial` 归一化后的稳定值（大写、无引号、无首尾空白） |
| `label` | 注册表条目、配置电源条目、运行映射电源条目 | string | 登记为 `power_supply` 的设备必填；未登记角色可为 `null` | 现场短标签；不含空白与 `/`，可直接当 `supply_id` |
| `supply_id` | 配置 `power_supplies` 的键、分配引用、运行映射的键、`supply_id/CHx` 前缀 | string | 引用未绑定时可为 `null` | 电源引用 ID，取值等于该设备的 `label` |
| `role` | 注册表条目 | string | 可空 | 设备类别；`null` 表示未登记，不能绑定 |
| `vendor` / `model` | 注册表条目、绑定、运行映射电源条目 | string | 是 | 身份来源与现场显示 |
| `name` | 注册表条目 | string | 是 | 软件资产名 `型号-序号`（如 `DP832A-1`），**不是引用** |

电源条目**不在条目内部重复写 `supply_id`**：集合的键就是 `supply_id`，只有一处来源。

### 4.2 `role` 的取值

| 取值 | 含义 | 状态 |
| --- | --- | --- |
| `signal_generator` | 信号源 | 现行 |
| `spectrum_analyzer` | 频谱仪 | 现行 |
| `power_supply` | 本机直流电源（可有多台） | 本计划新增 |
| `PS1`..`PS4` | 旧槽位编号 | **仅兼容输入**：只在读取旧注册表时被识别，写回时折叠成 `power_supply`（折叠已在步骤 4 接入注册表保存路径） |
| `null` | 未登记角色 | 不能绑定，不自动猜成电源 |

实现见 `domain/instruments/models.py`：

- `POWER_SUPPLY_ROLE = "power_supply"`，`DEVICE_ROLES` 是可写回的新类别集合；
- `POWER_SUPPLY_SLOTS` 保留为**只读兼容**常量（迁移识别用），不在 `DEVICE_ROLES` 里。它是
  固定槽位字面量的**唯一**登记处：生产代码（含 `tools/` 脚本与配置页）不得再写槽位名，也
  不得按序号拼电源键（步骤 15 由 `tests/test_power_supply_identity_contract.py` 静态守住）；
- `normalize_role` 同时接受新类别与旧槽位：旧值走兼容分支原样返回，读取方仍能按旧角色找到设备；
- `canonical_role` 提供写回时用的规范取值，把旧槽位折叠成 `power_supply`，未知值与空值返回
  `None`，不猜成电源；
- `is_legacy_power_supply_slot` 回答“这段文本是旧槽位名吗”这一步唯一的问题，供读取边界
  （例如判断旧条目的 `model` 里填的其实是 `PS1` 而不是型号）使用；任何地方都不得用它去
  **生成**电源键——新键来自短标签 `supply_id`；
- `Instrument.label` 是可空短标签（即 `supply_id`），`Instrument.display_name` 优先返回它，
  没有标签时退回资产名 `name`；`device_key` 仍由 `厂商 + 序列号` 动态计算，不因标签变化。

**当前边界（步骤 4 结束时的状态）**：

- 注册表的**保存路径已经接上迁移**：写盘前把 `PS1..PS4` 经 `canonical_role` 折叠成
  `power_supply`、为登记为电源却缺标签的设备按第 3 节补生成 `label`、`schema_version` 升到 3，
  迁移结果与 §5.2 的 `registry_migrated_v3.json` 逐字段一致。迁移、校验、`schema_version` 与
  `updated_at` 的更新都在内存副本上完成，**写盘成功后才提交回对象**；标签冲突、标签不能当
  `supply_id`、序列号派不出可用标签、结构不合法或磁盘写入失败都会抛错并指出设备，此时内存
  文档与原文件都保持迁移前的样子（写入本身仍是原子替换）。
- **已有标签原样冻结**：迁移只填空缺，不裁剪空白、不改大小写、不回收。标签必须能当
  `supply_id` 用（非空字符串、不含空白与 `/`），否则读取或保存直接报错让操作员改正——迁移
  不许把写错的标签悄悄“洗干净”。`null`、空串与纯空白都表示“还没有标签”，保存时统一写
  `null`；非字符串值同样报错。
- **读取侧行为不变**：旧记录里的 `PS1..PS4` 读出来还是原字面量、没有 `label` 就是 `None`。
  折叠发生在**发现结果的边界**（步骤 5）：`DiscoveredDevice.role` 把旧槽位折成
  `power_supply`，`known_role` 仍保留原字面量。注册表读取侧不折叠。配置绑定结构已在
  步骤 6 动态化（见下面“绑定结构”一段），但**旧配置里的电源键仍是 `PSn`**，它们要等
  步骤 13 的迁移器改挂到 `supply_id` 上；在那之前这些旧条目只保留参数，不再被当作可
  连接设备。
- **现场 `instruments.json` 还没有迁移**：它仍是 `schema_version: 2`。步骤 5、6 已落地，
  现在跑一次注册表保存即可完成迁移；迁移后两台已登记电源得到短标签，**配置里的
  `PS1..PS4` 旧条目仍不会被自动改挂**——它们要经过重新扫描应用（§8.3）或步骤 13 的
  迁移器，旧地址本身不构成身份。
- **未登记角色的设备不生成标签**：`DP832A-2`（`role: null`）迁移后仍是 `role: null`、
  `label: null`，不会被猜成电源；操作员显式登记为 `power_supply` 后保存时才得到 `DP8B0950`，
  对应 `registry_migrated_v3_all_registered.json`。
- `Instrument.label` 是**追加在既有字段之后**的可空字段：`Instrument` 是公开领域模型，位置参数
  顺序不能变，否则外部按位置传入的 `role` / `endpoints` 会被静默改写成别的字段。

**发现结果的边界（步骤 5 结束时的状态）**：

- `infrastructure.discovery.instrument_discovery.DiscoveredDevice` 现在带
  `label`（= `known_label`，注册表里冻结的短标签）、`supply_id`（等于标签，仅电源有值）、
  `serial`、`device_key`，以及两个“类别”视图：`role` 是折叠后的规范类别（旧槽位 `PS3` 也是
  `power_supply`），`known_role` 仍保留设备表里的原字面量。`to_dict()` 同时输出 `role` 与
  `registry_role`，便于排查旧数据。
- **标签只来自注册表**：发现过程绝不生成标签，所以旧设备表（`label: null`）的电源
  `label` / `supply_id` 都是 `None`，显示退回资产名；跑一次注册表保存（步骤 4 已接上迁移）
  之后才有短标签。
- **匹配只看 `device_key`**：预选与去重都用 `厂商:序列号`，短标签只用于显示、以及绑定键
  就是短标签时“是否同一台设备”的比对，绝不单独用来识别设备。
- **显示**：电源是“短标签（型号，电源）”（如 `DP8B1519（DP832A，电源）`），信号源与频谱仪
  仍是“资产名（角色）”。多台电源在结果里各自独立，勾选几台就传递几台，不再按角色键
  互相覆盖；只有信号源与频谱仪保持“一个角色一台设备”的唯一性。
- **没有短标签的电源不能应用**：短标签同时是配置引用 ID。设备表的电源还没有 `label` 时，
  面板与配置页都明确拒绝应用并说明“请先保存一次设备表补齐标签”，不会把地址写进一个
  猜出来的引用。
- **`to_dict()` 只是诊断序列化**：当前没有运行时消费方（界面的每一行、配置页的交接都用
  属性与 `selected_assignments()` 的记录），字段固定为 `role`（折叠后的类别）+
  `registry_role`（注册表里的原字面量，便于排查旧数据），不再输出与两者冲突的第三套含义。
- **“有没有角色”只有一个判据**：`has_role` 按折叠后的类别判断，与 `device_applicable`
  和配置页接受的角色集合同源。登记成未知字面量（手改出 `PS9`）的设备在状态列是“未分配
  角色”、勾选框禁用，不会被算成“已登记但角色未知”。
- **没有短标签要说清原因**：旧设备表（`label: null`）的电源在结果里显示资产名，状态列悬浮
  提示说明“还没有短标签，保存一次设备表后自动补上”。旧槽位的过渡提示随步骤 6 一起删除：
  发现结果不再提供 `config_slot`，地址是否落地只由配置页按 `supply_id` 决定。

### 4.3 绑定结构（步骤 6 结束时的状态）

`device_bindings` 从“所有设备都按角色键存放”改成“单设备角色 + 电源集合”：

```json
{
  "device_bindings": {
    "signal_generator": { "...": "保持单设备结构" },
    "spectrum_analyzer": { "...": "保持单设备结构" },
    "power_supplies": {
      "DP8B1519": { "...": "见 §6.3" }
    }
  }
}
```

实现见 `presentation/qt/config_form_state.py`：

- `power_supply_bindings()` 给出 `supply_id -> 记录` 的集合，兼容步骤 5 的过渡结构
  （按 `PS1..PS4` 落键、记录内带 `label`/`supply_id`）。**只有地址的旧绑定不迁移**：
  地址不是身份，必须重新扫描；步骤 5 的过渡记录只有在身份（`厂商:序列号`）与短标签都
  存在时才折叠成 `power_supplies[<supply_id>]`。
- **每条绑定记录（新结构与旧结构一致）都要通过同一套校验**，校验不在 UI 写入路径单独
  实现：引用必须能当 `supply_id` 用（非空、不含空白与 `/`），身份必须完整自洽
  （`device_key` 存在，且与记录里的厂商/序列号一致）。不合格的记录**不进入**
  `power_supply_bindings()`，因此不会出现在分配下拉框、不会被写地址。
- **不合格记录不静默丢弃**：`power_supply_binding_problems()` 给出面向操作员的原因
  （含集合键），配置页在读入时提示、在保存/运行校验时明确失败。同一台设备出现在两条
  电源绑定里也只保留第一条，其余同样计入问题列表。
- `bound_power_supplies()` 返回已绑定且有地址的 `supply_id`，配置页的分配下拉框与保存
  校验都只认它；集合大小完全由绑定决定（1 / 2 / 5 台不需要改代码）。
  `bound_power_supply_entries()` 给出同序的 `supply_id -> 记录`，页面用它把真实型号写进
  下拉框的**显示文本**（`DP8B1519（DP832A）`）；显示文本不参与任何比较，业务值始终是
  `itemData` 里的 `supply_id`（步骤 9）。保存时该控件没有 `itemData` 即按“未选择电源”
  处理，不回落到可见文本。
- 供电分配的引用由同一模块读写（步骤 7）：读入用 `assignment_supply_id()`——有
  `supply_id` 就以它为准，只有完全没有该字段的旧记录才读一次旧字段 `name`；写出由
  `read_power_assignment()` 完成，写 `supply_id` 并同写同名 `name` 供过渡期读取方使用。
- `read_instrument_config()` 按绑定写出地址：每台已绑定的电源写进
  `instruments.power_supplies.<supply_id>`（集合键同时写成同名 `label`，身份字段
  `device_key` / `serial` / `model` **只取绑定记录**，记录没有的字段会从配置里删除，
  不沿用旧值）；没有绑定的条目——包括旧槽位键——清空 `address` 并写成
  `enabled: false`，通道参数与未知字段原样保留。这条读路径是“清除绑定后旧地址不会继续
  连接”的保证。
- 配置页写入（`ConfigPage.apply_discovered_devices`）是整批替换：电源按 `supply_id`
  落键、每条记录必须带 `device_key`，`supply_id` 必须能当配置引用（含空白或 `/` 的
  短标签整批拒绝并指出要修的标签），同一 `device_key` 不能出现在两条电源绑定里；一次
  应用两台电源得到两条独立绑定与两条独立地址。
- 配置页的电源标签页随“配置里的电源键 + 已绑定电源”动态创建，标签页标题用短标签；
  应用/清除/加载配置后重建，不再有固定的四个槽位页。

### 5.3 字段级变化

| 旧 | 新 | 规则 |
| --- | --- | --- |
| `role: "PS3"` / `"PS4"` | `role: "power_supply"` | 按旧角色识别为该设备是电源，写回新类别；旧字面量不再写回 |
| 无 | `label` | 按第 3 节生成并冻结 |
| `role: null` | `role: null`、`label: null` | 未登记角色不猜成电源；要使用它必须显式登记 |
| `name` / `model_index` | 不变 | 资产名保留，但不作为引用 |
| `current_ip` / `known_ips` | 不变 | 地址仍是端点，不参与身份 |
| `schema_version: 2` | `schema_version: 3` | 步骤 4 已落地：保存时自动升级；读旧版本继续可用，读出来仍是旧字面量，写回才迁移 |

约束：

- 同一 `device_key` 只允许一条记录；`label` 冲突必须阻止保存并报出冲突设备。
- 标签冲突不覆盖旧标签，也不静默改名，由操作员处理后重试。
- 标签必须能当 `supply_id` 用：不含空白与 `/`，否则读取即报错（拼接 `supply_id/CHx` 会被截断）。
  校验按原字面值进行，不做裁剪或大小写统一；已有标签在迁移中原样保留。
- `null`、空串与纯空白的 `label` 都表示“还没有标签”，保存时写 `null`；其他非字符串值报错。
- 实现：`infrastructure/persistence/instrument_registry.py` 的 `_canonical_document` 只改
  `role` 与 `label` 两个字段，其余字段（含人工补充的如 `calibration_due`）逐字节保留；
  `schema_version` 高于本程序支持的文件直接报错，不降级覆盖。
- 实现：`save()` 的顺序是“副本迁移 → 副本校验（`_validate_document`）→ 补版本与时间戳 →
  原子写入 → 提交回对象”，失败时实例状态与文件都不变。

### 6.1 电源集合：键从槽位改为 `supply_id`


新：

```json
{
  "instruments": {
    "power_supplies": {
      "DP8B1519": {
        "label": "DP8B1519",
        "device_key": "rigol technologies:dp8b214901519",
        "serial": "DP8B214901519",
        "model": "DP832A",
        "address": "TCPIP0::192.168.1.102::inst0::INSTR",

          "CH1": {"role": "gate", "voltage": {"value": 2.8}, "current": {"value": 0.1}},

      }
    }
  }
}
```

| 字段 | 旧 | 新 | 说明 |
| --- | --- | --- | --- |
| 集合键 | `PS1..PS4` | `supply_id`（= `label`） | 旧键只在读取时识别 |
| `label` / `device_key` / `serial` / `model` | 无 | 必填 | 身份来源，不再从键名推断 |
| `address` | 有 | 保留 | 由设备绑定写入；未绑定的电源不写地址 |
| `enabled` | 有 | 保留 | 兼容字段；**可用电源的来源改为设备绑定**（步骤 7 已落地：分配下拉框与校验都只认绑定） |
| `channels` | 有 | 保留 | 通道名仍是现场的 `CH1`/`CH2`，通道角色仍是 `gate`/`drain` |

### 6.2 分配引用：`name` → `supply_id`

旧：

```json
{ "dut_amplifier": { "supplies": { "carrier": { "name": "PS1", "channel": ["CH1", "CH2"] } } } }
```

新（已绑定）：

```json
{ "dut_amplifier": { "supplies": { "carrier": {
    "supply_id": "DP8B1519", "name": "DP8B1519", "channel": ["CH1", "CH2"]
} } } }
```

新（未绑定，等待人工补全）：

```json
{ "dut_amplifier": { "supplies": { "carrier": {
    "supply_id": null, "channel": ["CH1", "CH2"]
} } } }
```

- 新代码只读 `supply_id`；过渡期同时写 `name`，值必须与 `supply_id` 相同，仅为旧读取与回滚。
  读入边界由 `domain.configuration.rules.assignment_supply_id()` 统一判定
  （`presentation/qt/config_form_state.py` 再导出给配置页与投影）：
  记录里出现 `supply_id` 就以它为准（`null` / 空白是“引用未绑定”），只有完全没有该字段的
  旧记录才回落读一次 `name`；写出由同一模块的 `read_power_assignment()` 完成，两个字段同值。
  配置页初次建页与整份配置回填共用这套判定，`supply_id` 与 `name` 冲突时以 `supply_id` 为准，
  并且两者被写成不同值时文件级校验报错（`…supplies.<role>.name`）。
- “配置里没有这条分配”与“声明了但未绑定”是两种状态，由 `assignment_declared()` 区分：
  没有这条分配时回填按缺省规则选第一台可用电源；记录存在但引用为空（`supply_id: null`、
  空白引用，或记录里没有引用字段）时保持空选择并交给校验报告，不得按缺省规则补一台。
- `supply_id: null` 表示“引用未绑定”，不是“临时选一个可用电源”。它保持空选择并交给校验报告，
  配置页不得把未绑定的电源补进下拉框。
- 可用电源只来自设备绑定；`enabled` 不再是可用性来源。

### 6.3 设备绑定：电源分支改为动态集合

旧：

```json
{ "device_bindings": { "PS1": { "serial": null, "device_key": null,
  "visa_address": "TCPIP0::192.168.1.101::inst0::INSTR", "source": "legacy_config" } } }
```

新（步骤 6 落地）：

```json
{ "device_bindings": {
    "signal_generator": { "...": "保持单设备结构" },
    "spectrum_analyzer": { "...": "保持单设备结构" },
    "power_supplies": {
      "DP8B1519": {
        "name": "DP832A-1",
        "vendor": "RIGOL TECHNOLOGIES",
        "model": "DP832A",
        "serial": "DP8B214901519",
        "device_key": "rigol technologies:dp8b214901519",
        "visa_address": "TCPIP0::192.168.1.102::inst0::INSTR",
        "last_ip": "192.168.1.102",
        "last_port": 5555,
        "known": true,
        "source": "scan"
      }
    }
} }
```

- 电源绑定的主键是 `supply_id`，记录内必须带 `device_key`；同一 `device_key` 不能出现在
  两条电源绑定里。集合的键就是引用 ID，记录内部不再重复写 `role` / `label` / `supply_id`。
- 键与身份都要能用：`supply_id` 不得含空白与 `/`（会打断 `supply_id/CHx` 路由），
  `device_key` 必须与记录里的厂商/序列号一致。任何一条不满足就**不是**可用绑定——
  它不会成为分配下拉框的选项，也不会被写地址；配置页同时把原因显示在读入提示与保存/
  运行校验里，不能表现为“电源莫名消失”。
- 只有地址的旧绑定（`source: legacy_config`、`serial: null`）**不迁移**为电源绑定，必须
  重新扫描：地址不是身份，无法回答“这是哪一台电源”。
- 步骤 5 的过渡记录（按 `PS1..PS4` 落键、记录内带 `label`/`supply_id` 与身份）在读取时
  折叠成 `power_supplies[<supply_id>]`，旧键不再写回。
- 写入是整批替换：本次勾选结果就是完整的绑定集合，未勾选的旧电源被移除；没有绑定的电源
  条目（含旧槽位键）在保存时清空 `address` 并写 `enabled: false`，通道参数保留。
- 配置里的电源身份字段（`device_key` / `serial` / `model`）**只来自绑定记录**：记录没有
  的字段在保存时从条目里删除，不沿用旧值，避免“地址换成了这台、身份还是上一台”。
- 配置页一次应用多台电源即得到多条独立绑定与多条独立地址（不再按角色键互相覆盖，也不再
  拒绝“多台电源”）；没有短标签的电源不能应用，因为短标签就是配置引用 ID。
- 实现：`presentation/qt/config_form_state.py`（`power_supply_bindings` /
  `bound_power_supplies` / `read_instrument_config`）、
  `presentation/qt/config_page.py`（`apply_discovered_devices` 的整批校验与写入）、
  `presentation/qt/device_discovery_panel.py`（交付 `label`/`supply_id`，不再交付
  `config_slot`；预选按 `device_key`）。

### 6.4 旧字段的兼容边界

旧字段只允许出现在“读入边界”，新配置一律不写：

| 旧字段 | 只允许出现的位置 | 读取方 | 新配置写回 |
| --- | --- | --- | --- |
| `instruments.power_supplies` 的键 `PS1..PS4` | 旧配置、旧运行快照 | 配置读取、迁移器 | 写 `supply_id` |
| 注册表 `role: "PS1".."PS4"` | 旧 `instruments.json` | 注册表迁移 | 写 `role: "power_supply"` |
| `power_supply_assignment.*.supplies.*.name`（槽位值） | 旧配置 | 配置读取、迁移器 | 写 `supply_id`（过渡期同写同名 `name`） |
| `device_bindings.PS1` | 旧配置 | 配置读取、迁移器 | 写 `device_bindings.power_supplies.<supply_id>` |
| `run_mapping.instruments.power_supply`（单数） | 旧配置、旧运行快照 | 运行映射读取 | 写 `instruments.power_supplies` |
| 运行映射 `dut_power_channels[].channel = "CH1"` | 旧运行快照 | 历史查看 | 写 `supply_id/CHx` |

“位置”是**清单式**的：`PS1..PS4` 的字面量只登记在 `domain.instruments.models`，读取边界通过
`normalize_role` / `canonical_role` / `is_legacy_power_supply_slot` 使用它；迁移器
（`infrastructure/config/legacy_power_supply_migration.py`）可以按旧槽位名判定输入。其它
production code 里出现槽位字面量、`POWER_SUPPLY_SLOTS` / `LEGACY_ROLES` 引用，或按序号拼
`PS<n>` 的写法，都会被 `tests/test_power_supply_identity_contract.py` 的门禁判为回退。

### 6.5 1 台 / 2 台 / 多台

三种规模都只是同一个集合的不同大小，不需要新增常量或改代码：

| 规模 | fixture | 表达的内容 |
| --- | --- | --- |
| 1 台 | `config_one_supply.json` | 一台电源的 `CH1` 供 gate、`CH2` 供 drain；DUT 分配一条 `supply_id` |
| 2 台 | `config_two_supplies.json` | `DP8B1519/CH1` 供 gate，`DP8B0885/CH2` 供 drain，两台各有独立地址与通道 |
| 5 台 | `config_five_supplies.json` | 集合里 5 台（3 台现场 + 2 台样例），本次只分配 2 台，其余保持已绑定未使用 |

`power_supply_count` 等计数由集合推导，不再作为“第几台电源”的表达手段。

步骤 10 的实现边界（校验器 `domain.configuration.models.validate_run_mapping`）：

- 新结构（带 `instruments.power_supplies`）里通道值必须带 `supply_id/` 前缀且前缀指向
  快照里的电源；只有**没有电源集合**的旧快照才放行裸通道名（`CH1`），保证历史运行仍可读取。
- “写的是哪种结构”看集合**键**在不在，不看集合是否非空：`power_supplies: {}` 与旧单数
  条目同时出现同样按混写拒绝，电源只有一个来源。
- 单数条目仍在时，它的 `model` / `visa_address` 按原规则校验，缺字段报在旧键上。
- 写回（`RunResourceMapping.to_dict()`）保持来源形状：旧快照读入再写出仍是旧单数结构，
  不会被补一个空集合；新结构写回时丢掉旧单数条目，只留 `instruments.power_supplies`。
- 配置作者（`presentation.qt.configuration_authoring`）按分配实际引用的 `supply_id`
  逐台写条目，未绑定的引用（`supply_id: null`）不成为条目。

步骤 11 的冲突检测（两层各报一次，都在连接前失败）：

| 冲突 | 位置 | 报告路径 |
| --- | --- | --- |
| 同一物理通道 `supply_id/CHx` 在 DUT 里排两次 | `validate_run_mapping` | `dut_power_channels[i].channel` |
| 同一物理通道同时供 DUT 与驱动功放 | 两层 + `validate_config` | `…supplies.<role>.channel` |
| 两台电源（或电源与信号源/频谱仪）启用后共用同一 VISA 地址 | 两层 + `validate_config` | `instruments.power_supplies.<id>.address` |
| DUT 供电角色重复（两台电源都声称 `gate`） | `validate_run_mapping` | `dut_power_channels[i].role` |
| 分配引用了不存在的电源 / `supply_id: null` | `validate_config` | `…supplies.<role>.supply_id` |
| 过渡别名 `name` 与 `supply_id` 不同值 | `validate_config` | `…supplies.<role>.name` |

引用判据只有一处实现：`domain.configuration.rules.assignment_supply_id`（`supply_id` 为准，
只有完全没有该字段的旧记录才回落读一次 `name`）。配置页、正式运行映射的编写与文件级校验
都调用它。解析“一条分配引用了哪些物理通道”也只有一处实现
（`rules._collect_assignment_channels`）；完整校验与连接校验共用它，但报告不同：

- `validate_config`：上表全部冲突，**加上**字段完整性问题（通道未声明 `role`、gate/drain
  不齐、`power_supply_count` 不符、`channel` 为空或不是列表）。
- `validate_hardware_connections`：只收引用层错误（引用缺失、电源不存在、电源未启用、
  `name` 与 `supply_id` 不同值、通道不在该电源上）与地址重复、跨组通道重复。
  运行创建在写任何运行目录之前用它，因此结构缺失的配置不会被拒成“连接冲突”。

## 8. 迁移判定：什么能自动迁移，什么不能

### 8.1 判定表

| 情形 | 判定依据 | 处理 | 结果 |
| --- | --- | --- | --- |
| 旧条目带 `device_key`/`serial`，注册表命中 | 身份可确认 | 新键 = 该设备 `label` | `migrated` |
| 旧键是 `PSn`，注册表正好有一条 `role == PSn` | 注册表角色可确认 | 新键 = 该设备 `label` | `migrated` |
| 旧键是 `PSn`，注册表该角色对应多台或已被替换 | 冲突 | 不自动迁移，报出两方身份 | `conflict` |
| 旧条目只有 `address` | 地址不是身份 | 不自动迁移；即使地址命中注册表 `known_ips` 也只提示“可能是某台” | `needs_rescan` |
| 旧条目无 `address` 也无 `serial` | 无法识别 | 不自动迁移 | `unidentifiable` |
| 多个旧键落在同一 `device_key` | 重复身份 | 阻止整次迁移 | `conflict` |

“不自动迁移”不等于“删掉数据”：原配置不被覆盖，旧条目的通道参数与仍引用它的分配写进迁移摘要。

### 8.2 当前现场的实际结论

输入：`instruments.json`（三台 DP832A）+ `config.json`（`PS1..PS4` 四槽位，只有 `PS1` 有地址且启用）。

| 旧键 | 旧地址 | 注册表能否识别 | 结果 | 迁移后的键 |
| --- | --- | --- | --- | --- |
| `PS1` | `TCPIP0::192.168.1.101::inst0::INSTR` | 否：无序列号；三台现场地址是 `.102` / `.106` / `.108`，`.101` 不在册 | `needs_rescan` | 无（DUT 的 `carrier` 引用置空） |
| `PS2` | 无 | 否：无地址也无序列号；`DP832A-2` 未登记角色 | `unidentifiable` | 无 |
| `PS3` | 无 | 是：`DP832A-1` 的 `role` 为 `PS3`，序列号 `DP8B214901519` | `migrated` | `DP8B1519`（未启用、未绑定） |
| `PS4` | 无 | 是：`DP832A-3` 的 `role` 为 `PS4`，序列号 `DP8B174400885` | `migrated` | `DP8B0885`（未启用、未绑定） |

这组样例正好说明“旧编号不能当身份”：注册表把 `DP8B214901519` 登记成 `PS3`，而现场真正承担 DUT 供电的是
配置里的 `PS1`。两者是不是同一台设备，只有重扫出的序列号能回答，编号本身回答不了。

迁移结果见 `config_slots_migrated_partial.json`：两台能识别的电源成形但未绑定，DUT 分配是
`supply_id: null`，运行映射的电源段为空——此时配置校验会报“引用了未绑定/不存在的电源”，不创建运行。

四个旧槽位的逐项判定、旧通道参数和仍引用它的分配记录见 `migration_summary_legacy.json`。`PS1`、`PS2`
的通道参数在迁移后**只存放在摘要里**；目标配置不会为无法识别的旧条目凭空造出电源条目，也不会把
`PS1` 的参数挂到按旧角色命中的 `DP8B1519` 上。

步骤 13 的迁移器（`infrastructure.config.legacy_power_supply_migration`）对同一组输入复现上表与这两份
样例，判定与参数逐字段一致：`PS3` / `PS4` 自动成形（未启用、未绑定、无地址），`PS1` / `PS2` 只存在于
摘要里，DUT 的 `carrier` 写成 `supply_id: null`，运行映射的电源段为空。旧条目的地址**不沿用**：
只有该电源的绑定记录本身带身份时才把地址（连同 `enabled: true`）写回配置，否则留空等重扫（§8.3）。

**这组结果不允许写盘**：`PS1` / `PS2` 认不出身份，它们的通道参数只在摘要里，写进 `config.json`
等于删掉它们、并让原配置也失去“还能继续用”。迁移器的写盘门槛因此是“每条旧条目都 `migrated` 且
没有仍为空的分配引用”；未决时用 `save_migration_summary` 把摘要写成独立文件（默认同目录
`config.json.migration-summary.json`），按 §8.3 重扫补全后再迁移一次。

### 8.3 人工重新扫描路径（缺少序列号时）

1. 配置页 → 仪器连接配置 → 真实网络扫描（无设备网络时用模拟扫描演示流程）。
2. 勾选目标电源（现在按 `power_supply` 登记的设备），点“应用所选设备到配置”。整批替换会写入
   `device_bindings.power_supplies.<supply_id>`，并给该电源写入地址与启用状态。
3. 分配下拉框此时才出现该 `supply_id`；在 DUT/驱动分配里重新选择，并按迁移摘要给出的旧值重填通道参数
   （原 `PS1`：`CH1` gate 2.8 V / 0.1 A，`CH2` drain 28 V / 2.0 A）。
4. 保存后配置校验通过，才能创建运行。完成后形态等价于 `config_one_supply.json`。

若扫描出的设备不是原来那台：把新设备显式登记为 `power_supply`（生成属于它的新标签），旧标签不被复用，
参数按摘要重新填写。

## 9. 迁移摘要（步骤 13 输出）必须包含的内容

迁移不写盘之前先给出摘要；摘要同时是操作员补全依据：

| 字段 | 内容 |
| --- | --- |
| `old_key` | 旧槽位键（`PSn`）；旧条目直接以地址为键时写该地址 |
| `legacy_address` | 旧条目地址；**只作为重扫线索**，不参与身份判定 |
| `legacy_enabled` | 旧条目 `enabled` 原值，供操作员对照 |
| `address_hint` | 旧地址命中注册表某台设备 `known_ips` 时给出的 `device_key` 提示；不命中写 `null`。它只是提示，不能替代重扫确认 |
| `new_key` | 新 `supply_id`，无法迁移时为 `null` |
| `device_key` / `serial` / `label` | 已识别设备的身份；未识别时为空 |
| `status` | `migrated` / `needs_rescan` / `unidentifiable` / `conflict` |
| `reason` | 面向操作员的原因，例如“只有地址，没有序列号，需重新扫描确认” |
| `assignments` | 仍引用它的分配：组（`dut_amplifier` / `driver_amplifier`）、角色键、通道列表 |
| `channels` | 旧通道参数快照：`role` / 电压 / 电流 / 保护值与保护开关 |

约束：

- 每个旧条目（含 `migrated` 的）都必须有一条摘要，不能只登记失败项。
- `channels` 与 `assignments` 必须原样取自旧配置，不得因“未绑定”而丢参数；`migrated` 条目的 `channels`
  还必须与新配置里对应电源条目的 `channels` 逐字段相等。
- 无法迁移的条目在目标配置里**没有**电源条目：这类参数只存在于摘要，操作员重扫后按摘要重填。
- 摘要样例：`migration_summary_legacy.json`（本步骤 fixture）。
- 实现（步骤 13 已落地）：`infrastructure.config.legacy_power_supply_migration` 的
  `migrate_legacy_power_supplies()` 返回目标配置与逐条判定，`LegacyMigrationResult.summary()` 给出
  上面这张表的结构、`summary_text()` 给出给人读的纯文本形式；写盘前先出摘要，未决项存在或文件级
  校验失败时不写盘。现场样例 `config_slots_legacy.json` + `registry_legacy_v2.json` 的迁移结果与
  §8.2、本节的样例逐字段一致（`tests/test_power_supply_config_migration.py`）。
- 摘要必须能离开进程：认不出的条目不写进配置，它们的 `channels` 只在本摘要里，因此实现提供
  `save_migration_summary()`（原子写入独立文件，默认 `default_summary_path()` =
  与配置同目录的 `<配置名>.migration-summary.json`）。摘要文件不是正式配置，不参与运行。
- 身份字段必须互相印证：旧条目同时写 `device_key` 与 `serial` 而两者指向不同设备、注册表中同一
  `device_key` 或同一序列号对应多条记录、或声明的 `device_key` 不在册，都按“无法确认是哪一台”
  报 `conflict`，不以“哪个字段更可信”为由挑一台迁移。

与运行映射（步骤 10）各自另有实现与验收门禁。

## 12. 兼容与回滚边界

- 旧 `PS1..PS4`、旧单数 `power_supply`、旧 `CH1` 式通道只在读入边界有效；新配置只写新字段。
- 任一阶段未完成时不删除旧字段读取；迁移失败不覆盖原配置。
- 运行快照冻结：历史运行按当时写下的字段显示，不因注册表变化而改写。
- 标签退役不回收，保证“曾经出现在日志里的短标签”永远指向同一台设备。

## 13. 显示、日志与审计（步骤 14）

标签、型号与序列号各有分工：**标签用于快速识别，完整序列号用于最终追溯**，位置编号在任何
地方都不再代表设备身份。

| 场景 | 文本 | 实现 |
| --- | --- | --- |
| 电源标签页标题、分配下拉框 | `DP8B1519（DP832A）` | `domain.instruments.labels.supply_display_label` |
| 详情、悬浮提示、身份核对日志 | `DP8B1519（DP832A） · 序列号 DP8B214901519 · 设备键 rigol technologies:dp8b214901519` | `domain.instruments.labels.supply_identity_text` |
| 通道动作、失败记录、急停 | `DP8B1519/CH1`（短标签 + 通道；短标签缺失时才退回 `supply_id/CHx`） | `domain.instruments.labels.supply_channel_text`，由装配计划算出 `channel_labels` 后交给 `instrument.power_control` / `instrument.measurement_adapter` |
| 身份核对结论 | `一致` / `不一致（配置 DP8B214901519，设备序列号 DP8B174400885）` / `无法比较（…）` | `domain.instruments.labels.supply_identity_verdict` |

规则：

- **显示文本只有一份实现**：标签页标题、分配下拉框与日志都来自 `domain.instruments.labels`，
  不在各页面各写一套格式；显示文本只给人读，业务值始终是 `supply_id`，不从显示字符串反解析。
- **型号缺失、型号与标签相同**时只显示标签：旧配置把槽位名填进 `model` 时不会出现 `PS1（PS1）`。
- **不推导标签**：旧槽位条目（`PS1`）与没有标签的记录按旧字段原样显示，绝不用型号或序列号
  造一个看起来像 `supply_id` 的字符串——那是第二套编号。
- **审计只列已知字段**：`supply_identity_text` 不查注册表、不补字段，旧条目没有序列号时就不
  出现“序列号”一段。
- **路由与日志分离**：发到设备上的始终是路由 token `supply_id/CHx`；日志与失败记录写的是
  `短标签/CHx`。显示文本由装配计划在拼 token 的同一处算出（`channel_labels`），**不从 token
  反解析**——反解析等于让显示文本承担身份，改一次标签就会读错设备。没有登记显示文本时日志
  退回 token 本身，宁可粗糙也不猜一个标签。
- **连接时一行身份核对，并给出结论**：每台电源连接前打印配置里的完整身份、设备自己应答的
  `*IDN?` 原文，以及核对结论。只有两边都解析出序列号才会判 `不一致`（并按 `warning` 记录）；
  配置没有序列号或 `*IDN?` 读不出身份时判 `无法比较`，不把“读不出来”说成“接错了设备”。
  结论只用于审计，不改写地址、配置或路由。
- **历史运行按当时写下的字段显示**：旧运行快照里的旧槽位键与旧列名不重写，也不为它们补标签；
  结果里的电压/电流列名是**逻辑角色键**（`carrier` / `peaking` / `main`），不是电源身份，
  电源身份在运行快照的 `instruments.power_supplies` 里（带 `label` / `model` / `serial` /
  `visa_address`）。
