# 电源配置盘点与目标字段映射

> 依据：`docs/电源配置独立化与通道上电计划重构.md` 步骤 1「盘点现有 schema、样例与实际效率输入」。
> 阅读顺序：**§1–§5 是只读盘点**（每条都对着当前代码核对过）；**§6 是冻结的 v1.1 契约**（原步骤 2 的产出，本文即唯一权威）；**§7 是上一轮审查发现问题的处置记录**；§8 是后续步骤的落点。
> 边界：本文不含生产代码改动。契约中仍标「后续步骤」的条目只涉及实现位置与交互细节，不影响字段名、字段归属和校验归属。

## 1. 结论速览

1. **效率现状不是「只读漏极」**：`AmplifierMeasurementService.perform_power_sweep` 遍历 `dut_supplies()` 的全部 DUT 通道，把每个通道的 `V × I` 累加成 `dc_power`，再算 `efficiency = P_out / P_dc`（`application/measurements/services.py:482-530`，累加在 `:520`）。没有任何 drain 过滤，也没有「gate 电流不参与效率」的既有规则。
2. **上电/关断是硬编码角色顺序**：上电 `gate → drain`、关断 `drain → gate`（`instrument/power_control.py:60-93`），组间 `driver → dut` 出现在阶段结算与急停表（`instrument/measurement_adapter.py:70-77, 136-164`）。用户既不能选通道，也不能定顺序或间隔。
3. **通道身份已有一半**：正式快照的 DUT 通道已经是 `supply_id/CHx`（`domain/configuration/models.py:788-821`），但 `test_plan`、装配、会话三层仍以 `gate`/`drain` 为键（`models.py:104, 163`、`instrument/power_routing.py:115-198`、`instrument/session.py:56-64`）。
4. **仍有 CH1/CH2 推断**：编辑约定 `DUT_CHANNEL_ROLES = {"CH1": "gate", "CH2": "drain"}`（`application/configuration_authoring.py:83`）被 UI 默认值复用（`presentation/qt/config_power_section.py:327-331`），UI 通道数固定为 `("CH1", "CH2")`（同文件 `:46`）。
5. **「保存」不校验，「能否运行」在创建运行前才校验**：`ApplicationCoordinator.save_configuration` 只调用 `author_document` 再写盘（`presentation/qt/application_coordinator.py:323-341`）；正式校验发生在 `config_form_state._formal_run_errors()`（`presentation/qt/config_form_state.py:186-217`）与运行创建路径（`application/run_service.py:259, 417`、`infrastructure/config/json_config_repository.py:75-103`）。因此「未确认的上电计划可以被保存、但不能开始测量」是现有架构本来就支持的行为，不需要新增「已确认」持久标记。
6. **保护参数目前只保存、不下发**：适配器上电前只写工作值（`instrument/measurement_adapter.py:228-234` 只读 `voltage_v`/`current_a`），`set_voltage_protection*` / `set_current_protection*` 在端口与驱动里存在（`instrument/ports.py:105-127`、`instrument/drivers/power_supply.py:40-80`）但生产代码没有调用点。本轮契约不改变这一点（见 §6.13）。
7. **样例分两代**：根 `config.json` 仍是 `PS1..PS4` + `name: PS1` + 裸 `CH1/CH2` + 单数 `instruments.power_supply`；`tests/fixtures/power_supply_identity/*` 已是 `DP8B…` + `supply_id` + 集合快照。步骤 6/14 必须以目标形态 fixture 为准，不能拿根配置当 schema 基准。

## 2. 数据流与各层职责

```text
配置页控件 ──读/写──▶ 配置编辑段（扁平段 + instruments + power_supply_assignment + device_bindings）
                          │  ConfigurationDraft.from_document / to_document
                          ▼
                      ConfigurationDraft（内存草稿，值对象）
                          │  ConfigurationAuthoringService.author_document（整段覆盖，不合并）
                          ▼
         config.json：编辑段（用户所有） + test_plan/run_mapping（派生，唯一生成入口）
                          │  JsonConfigurationRepository / validate_run_configuration
                          ▼
                  RunConfiguration（TestPlan + RunResourceMapping）
                          │  创建运行：runs/<run_id>/config.json + inputs/hardware_config.json（冻结 + SHA-256）
                          ▼
      PreparedRun ──▶ AssemblyPlan / ChannelRouting（有序路由、settings、急停表）
                          │  create_measurement_port
                          ▼
      PortMeasurementAdapter ──▶ InstrumentSession ──▶ PowerSupplyPort（只会 set_output_enabled(物理 token)）
                          ▲
   AmplifierMeasurementService（读 V/I、算 dc_power/efficiency）──▶ 结果 DTO ──▶ 归档 CSV/报告/实时图
```

| 层 | 模块 | 角色（gate/drain）当前承担什么 | 重构后定位 |
| --- | --- | --- | --- |
| 配置编辑 | `presentation/qt/config_power_section.py`、`config_form_state.py` | 每个通道必选 gate/drain；决定校验 | 删除；改为「分配通道 + 组内上电顺序 + 组间隔 + 漏极」 |
| 草稿 | `application/configuration_draft.py` | `PowerChannelDraft.role` | 删除 role；新增每组 `power_plan` 与 `drain_channel` |
| 编写 | `application/configuration_authoring.py` | 按 CH1/CH2 约定生成 `power_roles` | 原样搬运用户计划与漏极，不推断；整段重写正式段 |
| 领域 | `domain/configuration/models.py`、`rules.py` | 角色词表、成对完整性、角色唯一性 | 只保留路由引用、序列集合一致性、漏极与间隔校验 |
| 装配 | `instrument/power_routing.py`、`assembly_plan.py` | role→token 映射、急停顺序 | 有序物理路由 + 每路由 settings + 逆序急停 |
| 会话/硬件 | `instrument/session.py`、`power_control.py`、`measurement_adapter.py` | 按 role 选通道并硬编码顺序 | 按用户顺序逐通道开关，记录实际成功项 |
| 测量 | `application/measurements/services.py`、`application/dto/amplifier_inputs.py` | 全 DUT 通道求和 | 只读 `drain_channel` 的 V/I 算 `dc_power`；其余通道照常采样入库 |
| 结果 | `application/dto/measurement_results.py`、`analysis/*` | 无 role 列，键是 `supply_id_channel` | 列形状不变；`dc_power` 语义收窄为漏极功率 |

## 4. 实际行为事实（重构必须改变的点）

### 4.1 上电、关断与失败

- 上电固定 `gate → drain`；gate 步骤后 sleep（会话默认 1.5 s），drain 后不等待（`power_control.py:60-67`）。
- 主功放阶段在 DUT 输出开启后再固定 sleep 2 s（`services.py:565`）。
- 失败即 `session.close()` 全量清理并上抛（`session.py:119-127`），没有「只回滚本次已成功通道」的概念。
- 关断 `drain → gate`，drain 后 sleep（2.0 s），单项失败不阻止其余项，聚合为 `PowerControlError`（`power_control.py:69-93`）。
- 急停/结算按角色与组生成，与本次实际开启集合无关（`measurement_adapter.py:70-77, 136-164`）。
- 驱动组「先于 DUT」只体现在阶段/结算遍历，不体现在主功放阶段的实际输出开启。

### 4.2 效率输入

- 全 DUT 通道 `Σ(V×I)`；含 gate（若 gate 也在分配里）。
- 读数按 `dut_supplies()` 分组，经适配器拼成 `supply_id/channel` 再下发（`measurement_adapter.py:193-213`、`amplifier_inputs.py:294-303`）。
- 测试覆盖缺口：现有用例几乎都是单通道（`PS1/CH2` 或 `PS1/CH1`）；唯一双通道用例只断言 `dut_supplies()` 分组顺序，不断言 `dc_power`/效率数值（`tests/test_amplifier_inputs.py:330-362`）。

### 4.3 角色词表的三处不一致

1. 配置通道 `role`：只允许 `gate`/`drain`（`domain/configuration/rules.py:26, 252-308`、`instrument/power_routing.py:27-28, 298-303`）。
2. 编辑约定：`CH1→gate`、`CH2→drain`（`application/configuration_authoring.py:83`），被 UI 当默认值（`presentation/qt/config_power_section.py:327-331`）。
3. 驱动通道：authoring 在 `run_mapping.driver_mode.power_channels` 写 `role: "driver"`（`configuration_authoring.py:404-417`），但装配按通道声明的 `gate/drain` 解析并要求成对（`power_routing.py:196-197`），适配器也只接受 `gate/drain`（`measurement_adapter.py:79-90`）。即驱动组实际必须声明 gate+drain，而 `test_plan.driver_mode.power_roles` 又用 `driver` 作键。

### 4.4 保存与校验的时点

- 保存：`author_document` 生成正式段后直接 `save`，**不做 `validate_document`**（`application_coordinator.py:323-341`）。正式配置允许暂时不完整。
- 创建运行前的界面校验：`config_form_state._formal_run_errors()` → `ConfigurationAuthoringService.validate_document`（`config_form_state.py:186-217`），错误消息即用户看到的「开始」失败原因。
- 装载既有配置：`load_combined_configuration` 返回 `ConfigurationLoadResult`，校验结果是数据而不是异常（`json_config_repository.py:75-103`），因此旧配置仍能打开。
- 保存入口不检查输入版本：一份 1.0 编辑文档也会被 `author_document` 按当前扁平字段重写并写回，编辑段里的旧电源字段（`role`、`name` 引用、`PS1` 槽位键）原样留下。因此现在的「打开→保存」**不是迁移**；§6.11.3 把它改成显式拒绝。

结论：**「未确认的上电计划」不需要新的持久状态位**——它天然表现为「序列为空/与分配不一致」，保存照常，运行创建时按 §6.12 报错。

### 4.5 保护参数

`test_plan` 保存 `voltage_protection` / `current_protection`，但适配器只下发工作值（`measurement_adapter.py:228-234`）；保护开关与保护上限的端口方法存在（`instrument/ports.py:105-127`）却没有生产调用点。这是既有缺口，本契约不改变（§6.13）。

## 6. v1.1 契约（冻结）

### 6.1 命名与所有权

**核心规则：同一语义只在一个层可写；下层只做复制，且每次保存都由 authoring 整段覆盖。**

| 语义 | 配置编辑段（`config.json`，用户所有） | `test_plan`（派生） | `run_mapping`（派生，创建运行时冻结） |
| --- | --- | --- | --- |
| 组内上电顺序 + 间隔 | `power_supply_assignment.<group>.power_plan` | 无 | `run_mapping.dut_power_plan` / `run_mapping.driver_mode.power_plan` |
| 每通道工作值/保护值 | `instruments.power_supplies.<id>.channels.<CHx>.{voltage,current}` | `<dut｜driver_mode>.channel_settings` | 无 |
| 漏极测量路由 | `dut_config.drain_channel` | `dut.drain_channel` | 无（测试方案语义，非接线） |
| 通道属于哪个 PA 单元 | `power_supply_assignment.<group>.supplies.<slot>.channel` | 无 | 无（序列已给出全集） |

名字只有四个新增概念：`power_plan`（含 `power_sequence`、`inter_channel_delay_s`）、`drain_channel`、`channel_settings`。**通道 `role`、`power_roles`、`power_channels`、`connection` 在 1.1 中一律不写**（1.0 只读兼容）。

规范化对象：

- 路由（route）= `{"supply_id": <str>, "channel": <str>}`，两段都非空且都不含 `/`；不写 `"supply/CHx"` 拼接串，也不写裸 `CHx`。
- 组计划（`power_plan`）= `{"power_sequence": [route, ...], "inter_channel_delay_s": <number>}`。两个键永远同时存在；空计划写成 `{"power_sequence": [], "inter_channel_delay_s": 0.0}`。
- `channel_settings` 是**无序集合**：顺序无语义，比较与校验一律按路由集合；上电顺序只由 `power_sequence` 决定。元素形状是「路由两段平铺 + 参数」——`{"supply_id", "channel", "voltage", "current", "voltage_protection", "current_protection", "unit_voltage", "unit_current"}`（§6.3），不嵌套 `{"route": ...}` 子对象。它只出现在 `test_plan`，编辑段与 `run_mapping` 都没有第二份，所以同一路由的工作值全仓只有一处。
- `run_mapping` 的键名**有意不对称**：DUT 用顶层 `dut_power_plan`，驱放用 `driver_mode.power_plan`（`driver_mode` 已承载 `enabled`/`power_source`）。不得为了“对称”再引入 `driver_power_plan`，否则同一个驱放计划出现两处。

#### 6.1.1 编辑段与派生段的一致性

`config.json` 同时含编辑段和 `test_plan`/`run_mapping`，因此必须有防漂移规则，否则手改文件后「页面上的顺序」和「实际运行的顺序」会分叉：

- **保存**：authoring 用编辑段**整段重写** `test_plan` 与 `run_mapping`，从不合并、从不保留输入里的旧正式段。
- **读取（仅 1.1 文档）**：编辑段存在且可编写时，正式段必须等于「用编辑段重新编写的结果」（比较时忽略 `run_id`/`run_datetime`/`operator` 这类运行元数据）；不相等说明文件被手改或写入中断，报 `configuration.stale_formal_sections`（路径 `test_plan` / `run_mapping`），**不使用文件里的旧派生段**去创建运行。1.0 文档不参与该比对，按 §6.11 只读并通过 §6.14 迁移。
- **仅无编辑段的历史文件**（`runs/**`、拆分的 `test_plan.json`/`run_mapping.json`）才直接消费正式段；这类文件按自身 `schema_version` 处理，通常是 1.0，只读。
- **运行快照**（`runs/<run_id>/config.json`）是那次运行的事实，创建后不再与当前编辑段比对；重新运行必须从当前配置创建新运行（`application/run_service.py:373-424` 的既有约束）。

#### 6.1.2 round-trip 预期

「往返」分四种文件，行为必须不同；实现和测试都以这张表为准：

| 输入 | 读取 | 再保存 | 断言 |
| --- | --- | --- | --- |
| 1.1 编辑文档 | 接受；编辑段与正式段按 §6.1.1 比对 | 原值往返 | `power_sequence` 顺序、`inter_channel_delay_s`、`drain_channel`、通道工作值/保护值与地址逐项不变；变化只允许是 (a) 键序与缩进（唯一写入器 `JsonConfigurationRepository.save_document`：`indent=4`、`ensure_ascii=False`） (b) 组计划值对象把 `inter_channel_delay_s` 规范为 float（JSON `2` 写回 `2.0`），通道工作值/保护值保留读取到的同一数值（`5` 仍写 `5`），`null` 与 `0.0` 不互换 (c) 派生段按编辑段重写。 |
| 1.0 编辑文档 | 接受读取（只读）；`role` 忽略（步骤 3 的读入规则） | **没有保存入口**：authoring 拒绝非当前版本输入（§6.11.3、§6.12 规则 20），唯一升级路径是迁移器 | 迁移成功即写出 **1.1**：编辑段不再有 `role`/`name` 槽位引用，每组的 `power_plan` 是空计划（§6.14 规则 4 从不生成顺序），`drain_channel` 仅按 §6.14 规则 3 写入，正式段由 authoring 重写；之后按 1.1 行往返。迁移有未决项时不写盘（§6.14 规则 7），原文件保持 1.0。 |
| 1.0 拆分 `test_plan.json` / `run_mapping.json` | 只读 | **没有保存入口** | 只用于查看/导出；不会产生 1.1 文件，也不会被 authoring 自动回写。 |
| `runs/<run_id>/config.json` | 只读（包装版本见 §6.11.1） | **永不改写** | 迁移器与 authoring 都不触碰 `runs/`；重新运行 = 从当前编辑段创建新运行。 |

**「打开→保存」不是迁移。** authoring 只按扁平编辑字段重写正式段与版本，不做身份、参数或漏极转换；把 1.0 文档直接交给它，只会得到一份「版本写着 1.1、语义仍是 1.0」的文件（`PS1` 槽位键、`name` 引用和空计划一起被写进 1.1）。因此 authoring 按输入版本拒绝（§6.11.3、§6.12 规则 20），配置页必须先把 1.0 文档交给迁移器（步骤 13/14）；迁移器成功写盘后得到的就是本表第一行的 1.1 文档，再打开时按 1.1 规则比对。

1.1 输出必须通过的双份信息断言（golden 测试直接断言字符串/键不存在）：

- 任何 1.1 文档中不出现 `role`（电源通道内）、`power_roles`、`power_channels`、`connection`、`dut_power_channels`、`driver_power_plan`；
- `test_plan` 不出现 `power_sequence` / `inter_channel_delay_s`（顺序只在编辑段可写、只在 `run_mapping` 冻结）；
- 同一 `(supply_id, channel)` 在 `channel_settings` 至多出现一次，且 `power_sequence` 内不重复。

### 6.6 驱放自带电源 / 未确认 / 历史快照

- **驱放 `external_ac`**：`driver_mode.power_source = "external_ac"`、`driver_amplifier.supplies = {}`、`driver_plan.power_sequence = []`；`run_mapping.driver_mode.power_plan` 同样为空计划。这是合法状态，不报错。
- **DUT 组没有任何分配通道**（`power_supply_count = 0` 且 `supplies = {}`）：1.1 编辑段可保存，`power_plan` 为空计划；线损照常可运行，主功放按规则 8 阻断。它与“尚未排序”同属 §6.7 的 `unconfigured`，不回写任何确认标记。
- **未确认的上电计划**（迁移产物或用户尚未排序）：`power_plan.power_sequence = []` 而分配里已有通道，或序列与分配集合不一致。1.1 编辑段可以保存（§4.4），但创建功放运行会按 §6.12 在 `run_mapping.dut_power_plan.power_sequence` 报错。

  {"channel": "PS1/CH1", "role": "gate", "connection": "PS1/CH1 -> DUT 栅极"},

### 6.7 状态模型（派生，不落库）

每个组的计划状态由数据本身推导，**不新增 `confirmed` / `needs_confirmation` 字段**（这类标记会过期，且与数据不一致时无法判断谁对）：

| 状态 | 判据 |
| --- | --- |
| 待确认（`unconfigured`） | 序列为空，或序列集合 ≠ 该组分配通道集合，或含非法/重复/不存在的路由 |
| 就绪（`ready`） | 序列非空、无重复、集合与分配通道集合完全相等 |

DUT 额外两个漏极状态：`缺漏极`（`drain_channel` 为 `null`）、`漏极无效`（不在序列/`channel_settings` 中，或电源未登记/未绑定启用）。

可运行性按测量类型判定（不是按配置整体否决）：

| 测量类型 | 电源计划要求 |
| --- | --- |
| 线损 | 无 |
| 驱动映射 | 仅当 `driver_mode.enabled && power_source == "dc_supply"` 时要求驱放计划就绪 |
| 主功放 | DUT 计划就绪 + 漏极有效；驱放直流时另要求驱放计划就绪 |

迁移来源（旧 role 是否自动迁成漏极）只写进迁移摘要（`migration_summary_*.json`），不进配置 schema。

### 6.8 组间隔

- 字段：`inter_channel_delay_s`，单位秒，JSON 数字（整数允许，按 float 读取）。
- 范围：有限数值且 `0 ≤ value ≤ 60`；超界按配置错误报告，**不裁剪**（`2000` 这类毫秒误填必须显式失败）。常量 `MAX_INTER_CHANNEL_DELAY_S = 60.0` 与组计划值对象放在同一模块，全仓只此一份；值对象落在 domain 还是 application 由步骤 4 按依赖方向决定（路由类型也不得出现第二份实现）。
- 生效位置：同组相邻两次成功开启之间；最后一个通道开启后不再等待；单通道计划忽略该值（不要求必须为 0，也不报错）。
- 关闭过程不使用该间隔。
- 空序列与单通道序列：没有“相邻两次开启”，该值**不生效**；只要在 `0–60` 内就不报错、不裁剪。authoring 写空计划时固定写 `0.0` 作为规范形态；读取不强制该值，所以手写的「空计划 + 非 0 间隔」不因格式失败。
- 比对语义：§6.1.1 的 stale 比对是**解析后数据的语义比较**，不是字节或字符串比较：键序与缩进不参与，`2` 与 `2.0` 视为相同，`null` 与 `0.0` 视为不同。序列长度 < 2 时额外忽略 `inter_channel_delay_s`（没有「相邻两次开启」可作用），其余字段照常比较；长度 ≥ 2 时按数值相等比较，不做浮点容差。
- 回滚计时：失败清理与逆序关断不做间隔等待，立即逐通道关闭（设计决定 5/6）。
- 与既有固定等待的关系：旧 `PowerController` 的 gate/drain settle 参数随角色顺序一起删除；新实现只有「用户间隔 + 服务层 2 s 稳定等待」两种等待，后者保留在 `services.py:565` 的位置与含义（§6.11 明确不合并）。

### 6.9 漏极

- `drain_channel` 是**效率测量输入**，不是上电角色：不参与排序、间隔、启停或安全关断；它不会向序列里增加或删除任何通道。
- 需要效率的测量（当前仅主功放）必须恰有一个有效漏极；线损、驱动映射不要求。
- 有效漏极的判定链（顺序即报错顺序）：路由形状合法 → 属于 DUT 组分配通道（不能是驱放通道） → 在 `power_plan.power_sequence` 中 → 在 `test_plan.dut.channel_settings` 中（即电源上有该通道声明且工作值可读） → 电源已在 `run_mapping.instruments.power_supplies` 登记，且编辑段 `instruments.power_supplies.<id>.enabled == true`、地址非空（后两项由规则 6 在编辑文档层面判定）。
- 效率计算：`dc_power = V(drain) × I(drain)`；其余已启用通道仍逐通道采样并写入 `V_*`/`I_*` 列，但不计入 `dc_power`。
- 结果字段不改名（`efficiency` / `efficiency_percent`），`dc_power` 语义在文档与文案中收窄为「漏极直流功率」；单通道且该通道即漏极的既有结果数值不变。

### 6.10 顺序、失败与关断

- 逐通道 `set_output_enabled(token, True)`；每成功开启一个通道，若不是该组最后一个，等待 `inter_channel_delay_s`。
- 任一步失败：停止后续通道；对**本次实际成功开启**的通道按逆序 best-effort 关闭；同时保留启动失败与清理失败两类信息。
- 关断：按实际成功开启顺序逆序逐项尝试；单项失败不阻止其余项，聚合报告全部失败。
- 等待与取消检查放在每个通道动作前后；延迟经可注入 sleep 执行（沿用现有注入方式）。
- 急停表由**本次实际成功开启的通道**生成：按开启顺序逆序，不再由 role 推导。某组从未开启时，该组通道不出现在急停表里（当前实现会把未开启的驱放通道也列入，属过度关闭，不是安全缺口）。
- 组间仍沿用「先 driver、后 DUT」的阶段语义（设计决定 3）；主功放阶段是否开启驱放输出是步骤 8 的独立决定，本契约不改变现状。

### 6.11 版本策略

#### 6.11.1 版本轴：只有一个是本契约的

同名 `schema_version` 在仓库里有多个互不相关的轴，不能互相推导、也不随本重构一起升版：

| 轴 | 载体 | 当前值 | 本重构是否变化 |
| --- | --- | --- | --- |
| **配置文档（本契约）** | 根 `config.json`、`test_plan`、`run_mapping` | `"1.0"` → `"1.1"` | **是**：写 1.1，读 1.0/1.1 |
| 运行快照包装 | `runs/<run_id>/config.json` 顶层，`RUN_CONFIG_SNAPSHOT_SCHEMA_VERSION`（整数） | `1` | 否：仍写 `1`，内层两段各自是 `"1.1"` |
| 运行 manifest | `RunManifest.schema_version`（整数） | `2` | 否 |
| 设备表 | `instruments.json`（整数） | `4` | 否 |
| 迁移摘要 | `migration_summary_*.json`，`SUMMARY_SCHEMA_VERSION`（整数） | `2` | 否：不跟配置版本走；只有摘要自身新增字段时才由步骤 14 单独升 3 |
| 测量结果文件 | 结果 `schema_version`（字符串集合） | `{"1.0"}` | 否 |
| 基线清单 | `baseline/` 清单（字符串，`collect_baseline.py:173`） | `"1.0"` | 否 |
| 阶段 1 内存模型 | `domain/models.py:21 SCHEMA_VERSION`（`TestPlan`/`MeasurementSession` 的字段） | `"1.0"` | 否；不是配置文档版本来源，见 §6.11.2 |

推论：给旧运行补 1.1 的计划字段不需要升快照包装版本，因为包装只回答「运行目录格式是否可读」；内层 `test_plan`/`run_mapping` 的版本由各自字段决定。

#### 6.11.2 常量与唯一定义处

| 常量 | 值 | 唯一定义处 | 用途 |
| --- | --- | --- | --- |
| `SUPPORTED_SCHEMA_VERSION` | `"1.1"` | `domain/configuration/models.py`（现 `:20`） | 新写入的唯一版本；保留现名，减少全仓改名 |
| `READABLE_SCHEMA_VERSIONS` | `("1.0", "1.1")` | 同上 | 读取/结构校验接受的集合（按旧→新排列） |

- **生产代码只允许一处配置版本文面量**：`"1.0"`/`"1.1"` 只在 `domain/configuration/models.py` 定义一次；`domain`/`application`/`infrastructure`/`instrument`/`app`/`presentation`/`launcher.py` 只引用常量，不写字面量。`application/configuration_authoring.py:81 OFFICIAL_SCHEMA_VERSION = "1.0"` 改为 `OFFICIAL_SCHEMA_VERSION = SUPPORTED_SCHEMA_VERSION`（保留导出名，减少改名）。
- 测试 fixture、golden 与文档示例里的版本值是**数据**，不受上一条限制；扫描只针对生产代码，并且只针对「配置文档」这一轴，不覆盖设备表/manifest/结果文件各自的版本（§6.11.1）。
- `domain/models.py:21 SCHEMA_VERSION = "1.0"` 属于阶段 1 内存模型（`domain.models.TestPlan`/`MeasurementSession`），**不是配置文档版本的来源**：authoring、读取、校验都不得引用它。若后续证明它参与了文档生成，才改为引用同一常量；否则保留原值并加注释说明用途不同。
- 版本常量属于 **domain**，application 与 infrastructure 只引用不定义；`infrastructure/config/json_config_repository.py:77` 的根判定也改用 `READABLE_SCHEMA_VERSIONS`，并要求与两段同值（规则 18）。
- 迁移器写出的编辑段版本取同一常量，不自行拼接。
- 门禁：静态检查只扫描生产代码里的配置版本文面量（步骤 15 的常量扫描思路），测试与样例数据不参与。

#### 6.11.4 版本值判定与 1.0 的校验分派

- 写入只写 `"1.1"`；读取只在 `READABLE_SCHEMA_VERSIONS` 内。`"1.2"`/`"2.0"` 等更高版本：报「配置由更新版本写入，请升级程序」，**不降级读取、不忽略未知字段**。
- 低于 1.0、非字符串、缺失：`schema_version` 错误；缺失不再补默认值写盘。
- 版本一致性只对**组合配置**成立：根文档与 `test_plan`、`run_mapping` 三处必须同值（规则 18）；只有根为 1.0 的文档允许内层 1.0（现场文件形态）。拆分文件和运行快照没有根可比，各自按自身版本判定（运行快照还要先过整数包装版本）。
- 1.0 文档**只做结构与类型校验**，不跑 1.0 视角的供电角色判据：`role` 按「忽略」处理（步骤 3 的读入规则）。`validate_run_configuration` 因此必须按版本分派，1.0 时跳过 §6.12 规则 8–13，并附一条 `warning`「旧版电源计划：可查看，不能创建新运行」；warning 不得升级为 error（否则历史配置打不开、`launcher --validate-config` 也会误红）。

三类载体的 1.0 行为分别固定，不能互相顶替：

| 载体 | 1.0 时允许 | 校验范围 | 1.0 时拒绝 |
| --- | --- | --- | --- |
| 组合 `config.json` | 打开、查看、导出；启动器文件级校验（warning） | 结构/类型；跳过规则 8–13 | 保存（authoring 拒绝，规则 20）、创建运行（规则 16） |
| 拆分 `test_plan.json` / `run_mapping.json` | 打开、查看、导出 | 各文件结构/类型；跳过规则 8–13 | 保存（无入口）、创建运行 |
| `runs/<run_id>/config.json` | 打开、查看、导出、浏览已保存结果 | `load_run_configuration` 的结构校验（跳过 8–13） | 继续运行 / 连接仪器（`RunNotResumable`） |

- 1.0 运行快照的「浏览已保存结果」只读取 `results/` 下已冻结的结果文件（结果文件按自己的版本集合读取），**不重新执行测量、不重新校验上电计划**。若不拒绝继续运行，要么按 1.1 判据对旧快照误报语义错误，要么得保留一套已删除的角色规则——两者都违反「旧角色只在读取兼容层处理」。
- 版本号只描述文档形状，不表达「顺序/漏极是否已确认」（§6.7）；状态不落库、不进入版本号。

### 6.13 不在本契约内的事项

- **保护参数下发**：`channel_settings` 保留 `voltage_protection` / `current_protection` 两个数值（不新增 `*_enabled`），因为当前硬件路径只下发工作值；编辑段仍保留页面的 `protection_enabled`，authoring 与现状一样只搬运数值。启用保护是单独的行为变更。
- **界面交互细节**：排序控件的操作方式、间隔输入控件、漏极下拉的过滤与提示文案属于步骤 11/12；本契约只规定它们的读写字段。
- **`drain_channel` 在「仅测量不供电」场景的生命周期**：设计决定 7 明确留待后续需求。
- **跨组交错上电**（全局编排器）：设计决定 3 明确不在第一版。

### 6.14 迁移规则

1. **电源身份**：沿用既有 `legacy_power_supply_migration` 的 `PS1..PS4` → `supply_id` 迁移，不改判据。
2. **通道参数**：旧 `test_plan.dut.power_roles`（role→参数）+ 旧 `run_mapping.dut_power_channels`（role→`supply/CHx`）**按 role 值连接**：
   - 两侧 role 集合必须完全一致且各自唯一；
   - token 必须能解析为 `(supply_id, channel)` 且 `supply_id` 在 `run_mapping.instruments.power_supplies` 中；
   - 全部满足才生成 `dut.channel_settings`；否则不生成，报 `configuration.power_settings_unmapped` 并保持为空（运行被规则 9/10 拦住）。
   - 驱放的旧 `power_roles` 只有一个 `"driver"` 键：仅当驱放路由恰好一条时可套用；多条时无法区分，按未映射处理。
3. **漏极**：仅当 DUT 分配通道中恰好一条旧 `role == "drain"` 且能映射到路由时写入 `drain_channel`；0 条或多条一律写 `null` 并记入迁移摘要的待确认项，不按 `CH2` 推断。
4. **上电顺序**：**从不自动生成**。迁移把每组的 `power_plan` 写成空计划（空序列 + 0 间隔），在摘要里列出候选路由集合，由用户在电源页确认。authoring 读到**缺少** `power_plan` 的 **1.1** 编辑段时按空计划处理（不推断）；这不构成 1.0→1.1 的隐式升级——1.0 编辑段不能进 authoring 保存（规则 7、§6.11.3）。
5. **写回方式**：迁移器只改编辑段，然后必须走 `authoring` 生成正式段（不手写 `test_plan`/`run_mapping`）；迁移输出 `schema_version = "1.1"`，不保留通道 `role`/`power_roles`/`power_channels`。
6. **运行快照**：`runs/` 下的历史快照不迁移、不改写；仍可查看，但不能直接创建新运行。
7. **写盘门槛**：与 `save_migrated_configuration` 现有语义一致，缺一不可——(a) 每条旧条目都是 `migrated`（`result.writable`）；(b) 迁移后没有 `supply_id: null` 的分配引用；(c) 文件级校验通过。任一不满足就**不写回**：原文件逐字节不变、仍按 1.0 只读打开，迁移摘要另存（`save_migration_summary`）作为人工补全依据。因此「无法自动迁移」的结果不是一份半新半旧的 1.1 文件，而是「原文件 + 摘要」。

#### 6.14.2 无法自动迁移示例（可定位的状态与错误）

`config_slots_migrated_partial.json` 是「迁移能算出什么」的**期望值**，不是可以写回现场的文件：`PS1`/`PS2` 认不出身份，`PS3`/`PS4` 自动成型但未绑定。它的 DUT 分配段长这样：

```json
"power_supply_assignment": {
  "dut_amplifier": {"power_supply_count": 0,
    "supplies": {"carrier": {"supply_id": null, "channel": ["CH1", "CH2"]}},
    "power_plan": {"power_sequence": [], "inter_channel_delay_s": 0.0}}}
```

`power_supply_count = 0` 表示「该组仍能落地的引用数」为 0，不是声明了几个槽位；`supplies` 里保留旧通道列表，供操作员在电源页重新选择电源。这是**内存中的迁移结果**，不会落盘。

可定位性要求：

| 层 | 表现 |
| --- | --- |
| 迁移摘要 | `PS1`/`PS2` 为 `needs_rescan`/`unidentifiable`（身份自相矛盾或重名则 `conflict`）；通道参数只留在摘要里；`result.writable` 为假 |
| 写盘 | 拒绝（§6.14 规则 7）：`config.json` 逐字节不变，**仍是 1.0**；摘要可另存为人工补全依据 |
| 打开 | 能打开、查看；按 1.0 规则只给 warning，配置页的保存被规则 20 拒绝（必须先迁移） |
| 创建运行 | 规则 16 先拦（`schema_version`）；不存在「半迁移的 1.1 文件」可以拿去运行 |
| 线损 | 1.0 原文件不能创建任何运行；补全身份并迁移成 1.1 之后，线损不要求电源计划（§6.7），可照常运行 |

若用户在新页面把某个 1.1 文档的引用清空后保存（authoring 不校验，§4.4），错误落在这些位置，且顺序稳定：

- `supply_id: null` 的分配 → 规则 6 在 `power_supply_assignment` 报「DUT(carrier) 未选择电源：请先在“仪表配置”页应用电源设备」（`validate_power_supply_assignment_references`），先于规则 8/11。
- 旧 `power_roles` 与旧快照 role→token 不能唯一配对 → 不生成 `channel_settings`，报 `configuration.power_settings_unmapped`，运行被规则 9/10 拦在 `test_plan.dut.channel_settings`。
- 旧 `drain` 为 0 条或多条 → `drain_channel = null` 并记摘要待确认；主功放任创建运行为规则 11 明确失败（路径 `test_plan.dut.drain_channel`），不按通道名猜。
